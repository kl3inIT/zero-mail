Current LLM, Chat, and Provider Routing Architecture

This note documents the architecture as it exists during the Phase 08.1 / quick-task refactor, explains why core.chat and core.llm are separate modules, and identifies the naming and execution boundaries that should be cleaned up before the unified provider runtime is considered complete.

Project: Zero Mail Date: 2026-05-24 Spring AI: 2.0.0-M7 Scope: Architecture explanation, no Java code changes

Executive Summary

Keep

Separate chat product logic from generic LLM execution

core.chat owns assistant conversations, persisted chat messages, tool UX, confirmation leases, and privacy sanitization for chat tool outputs. core.llm owns model calls, provider adapters, routing, usage recording, credit charging, BYOK credentials, and prompt/tool-call execution.

Rename / reshape

*ByokModelClient names are now misleading

After introducing LlmProviderCredential(source=PLATFORM|BYOK), provider execution is no longer BYOK-specific. The old BYOK clients are becoming credential adapters/wrappers, not the real execution layer.

Fix

Chat streaming still bypasses admin runtime routing

Non-streaming LLM calls are moving toward route credentials from admin master keys. Chat assistant streaming still uses SpringAiChatModelFactory directly and currently builds OpenAI-compatible models on a separate path.

Why Chat and LLM Are Separate Domains

core.chat is a product workflow domain

It should own everything that makes the assistant a user-facing workflow:

  • chat threads, messages, parts, memory, and persistence;
  • tool catalogs and tool-call state emitted to the UI;
  • confirmation cards and pending user actions;
  • send/reply/forward preview flow;
  • chat-specific privacy rules such as stripping Gmail-read body output.

core.llm is a platform capability domain

It should own model execution regardless of who consumes it:

  • provider credentials and credential-source policy;
  • model routing, fallback, and task-to-feature mapping;
  • Spring AI provider adapters;
  • tool schema conversion and result parsing primitives;
  • credit ledger integration, usage recording, and safety gates.
Decision

The split itself is valid. The problem is not that chat and LLM are separate. The problem is that chat currently owns a Spring AI model factory that duplicates provider execution decisions. Chat should keep conversation orchestration, but provider model construction should move behind the same LLM runtime used by rule, triage, draft, and semantic calls.

Current Mismatches

Area What is happening now Why it is a problem Clean target
Provider execution naming Classes named *ByokModelClient are still part of the call path even after introducing LlmProviderCredential. The name suggests the execution layer is BYOK-only, but the same executor should serve platform/admin keys too. Rename or replace them with tenant credential adapters/resolvers. Keep provider execution in one ProviderChatExecutor.
Platform fallback client SpringAiLlmModelClient.call(request) still uses fixed platformChatClient when no route credential is supplied. This is acceptable as a legacy fallback, but it must not be used when admin routing selected a concrete provider/key/model. Route-selected calls must require route credentials and fail over to the next route if credential resolution fails.
Chat assistant routing SpringAiChatModelFactory infers platform provider from config/base URL and builds OpenAI-compatible streaming models itself. Admin can configure routes for CHAT_ASSISTANT, but streaming chat does not consistently consume the same route resolver/executor policy. Chat should ask the LLM runtime for a streaming execution plan for LlmRuntimeTask.CHAT_ASSISTANT.
OpenRouter / 9router modeling They are represented like built-in providers in parts of the platform model. They are custom OpenAI-compatible endpoints, not official provider SDK families. Treating them as first-class SDK providers makes routing and UI harder to reason about. Store provider/gateway entries by execution protocol such as OPENAI_FORMAT or ANTHROPIC_FORMAT, with custom base URL.
Structured semantic output Semantic evaluation has a separate route-aware path and currently needs closer alignment with the shared provider executor. If structured-output calls do not share credential and protocol selection, future model routing bugs can reappear in a different call site. Add a shared structured-output executor or make semantic evaluation consume the same provider credential abstraction explicitly.

Recommended Target Shape

Keep domain ownership stable

  • core.chat keeps chat state, tools, UI protocol, and confirmation flow.
  • core.llm keeps LLM runtime contracts and Spring AI adapters.
  • core.admin owns admin catalog/master-key storage and implements LLM routing interfaces exposed by core.llm.routing.

Unify provider execution

  • Use one credential object for both PLATFORM and BYOK.
  • Use protocol/key format to select Spring AI adapter, not hard-coded gateway brand names.
  • Let billing/credits depend on credential source, not on the provider implementation class.
Proposed responsibility Candidate package/class shape
Common credential value core.llm.usecases.LlmProviderCredential
Platform credential resolution contract core.llm.routing.PlatformLlmRouteCredentialResolver
Admin implementation of platform credential resolution core.admin.mkey.usecases.ProviderMasterKeyRouteCredentialResolver
Tenant BYOK credential resolution Replace provider-specific BYOK clients with a tenant credential resolver or adapter that returns LlmProviderCredential(source=BYOK).
Non-streaming provider execution core.llm.gateway.springai.SpringAiProviderChatExecutor
Streaming provider execution Add a streaming sibling that uses the same credential/protocol decision and is consumed by core.chat.

Refactor Order That Minimizes Risk

  1. Finish the non-streaming shared executor and make platform route credentials mandatory when admin routing returns a key ID.
  2. Replace the *ByokModelClient naming with tenant credential adapters or a tenant credential resolver. Keep behavior unchanged first.
  3. Move chat streaming provider construction behind the same credential/protocol runtime and route it via LlmRuntimeTask.CHAT_ASSISTANT.
  4. Align semantic evaluation with the same credential abstraction, either through a shared structured-output executor or explicit route-aware provider execution.
  5. Only after runtime paths are stable, simplify the admin provider model so custom gateways like OpenRouter and 9router are OpenAI-compatible endpoint entries rather than hard-coded official providers.

Functional Impact

Expected impact

Most of this is architectural plumbing. If done in the order above, user-facing behavior should stay the same: rule compilation, triage, draft generation, semantic checks, and chat should still produce the same kinds of outputs.

Risk areas

The sensitive parts are streaming chat tool calls, provider-specific tool-choice support, cache invalidation when admin keys change, credential zeroing, and Google / Anthropic feature differences in Spring AI 2.0.0-M7.
