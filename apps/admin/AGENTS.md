# Admin app — agent rules

Vite 8 + React 19 + TanStack Router (file-based) + TanStack Query v5 + TanStack Form + Zod 4 Standard Schema + base-ui primitives via shadcn copy. **No Next.js, no next-intl, no SSR** — admin is a fully client-rendered SPA at `admin.zeromail.vn`.

Routes live at `src/routes/**`; `routeTree.gen.ts` is auto-generated by `@tanstack/router-plugin/vite` — do not hand-edit. Mutations and queries use `useMutation` / `useQuery` from `@tanstack/react-query` with the `api` client from `@/lib/api/admin-client`.

## `admin-schema.d.ts` is generated — NEVER hand-edit (MANDATORY)

`apps/admin/src/lib/api/admin-schema.d.ts` and `apps/admin/openapi/admin-spec.json` are emitted by `pnpm --filter @zeromail/admin run generate-api` (`apps/admin/scripts/generate-api.ts`). The script fetches `http://localhost:8080/v3/api-docs/admin` and pipes it through `openapi-typescript`.

When a backend DTO changes (add/remove/rename field, validation, enum value): **boot the backend → run `pnpm --filter @zeromail/admin run generate-api` → commit the regenerated files**. Hand-edits to `admin-schema.d.ts` or `admin-spec.json` are forbidden — the next regen silently overwrites them and the FE/BE schemas drift until someone notices a runtime error.

Same rule applies to web: `apps/web/lib/api/schema.d.ts` is generated by `pnpm --filter web run generate:api` (`apps/web/scripts/generate-api.ts`).

## shadcn primitives are base-ui under the hood

`components/ui/**` is generated shadcn source (new-york style) backed by `@base-ui/react` primitives — not Radix. **Notable difference:** `Button` does NOT support `asChild`. If you need a Link styled as a button, do `<Link to="..." className={buttonVariants({ variant: 'outline' })}>...</Link>` (import `buttonVariants` from `@/components/ui/button`). Never reach for `asChild` on admin Button.

`components/ui/**` is excluded from ESLint per `eslint.config.mjs`. Don't hand-roll a primitive shadcn already ships.

## Error handling, toasts, retries — TanStack Query v5 patterns

All TanStack Query callbacks are wired centrally in `apps/admin/src/main.tsx`. Follow these rules instead of re-implementing locally:

- **Toasts come from `MutationCache.onSuccess`/`onError`, opt-in via `meta`.** When writing a new `useMutation`, set `meta: { successMessage: 'Đã ...', errorMessage: 'Không thể ...' }` rather than calling `toast.success/error` from a local `onError`. The global handler reads meta and toasts via Sonner.
- **Use `meta.silent: true`** when a query or mutation should never produce a toast (e.g. background `/api/admin/me` poll).
- **Query background refetch failures auto-toast** (TkDodo's pattern — initial fetch failures are caught by the `errorComponent` at the route level). Don't add `onError` to a query just to toast.
- **Module augmentation declares the meta shape** in `main.tsx` (`declare module '@tanstack/react-query'`). Use the typed fields only — if you need a new meta key, extend the `interface Register` block there.
- **Retry policy is global:** `retry: 1` for queries, `retry: false` for mutations. Don't override.
- **401 redirect is at the fetch layer** via `onResponse` middleware in `apps/admin/src/lib/api/admin-client.ts`. Public auth surfaces (`/login`, `/enroll`) are excluded. Don't write per-callsite 401 checks.
- **XSRF is also at the fetch layer.** `onRequest` middleware in the same file reads the `XSRF-TOKEN` cookie (set by Spring `csrf().spa()`) and adds the `X-XSRF-TOKEN` header to mutating methods. Don't add the header manually — it's automatic.
- **Error code localization** lives in `apps/admin/src/lib/api/admin-errors.ts` as a static Vietnamese dictionary (no i18n framework). When the backend introduces a new `ErrorCode`, add the corresponding key to `ERROR_MESSAGES_VI` in that file.

## TanStack Router file-based routing

- Every file in `src/routes/**` exports a `Route = createFileRoute(...)` (or `createRootRouteWithContext()` for `__root.tsx`).
- ESLint disables `react-refresh/only-export-components` for `src/routes/**` (see `eslint.config.mjs`). Route files are structurally incompatible with the rule because they MUST co-locate `Route` + component. The rule is still active everywhere else (`components/`, `features/`) — don't replicate the route co-location pattern outside `routes/`.
- Root-level fallbacks (`errorComponent`, `notFoundComponent`, `pendingComponent`) live in `apps/admin/src/components/RootShell.tsx` and are wired in `routes/__root.tsx`. Add per-route variants by setting the same props on individual `createFileRoute(...)` calls.
- Protected routes nest under `_authenticated.tsx` which `beforeLoad`-ensures the session via `ensureQueryData(['admin-me'], getCurrentAdmin)` and redirects to `/login` on failure.

### Loader prefetch vs in-component `useQuery`

Default to **in-component `useQuery`** for admin routes — it keeps fetching co-located with the consumer, integrates with the global `MutationCache` toasts/error handling, and tolerates partial failures gracefully. Reach for the **loader / `beforeLoad` + `queryClient.ensureQueryData`** pattern (see `_authenticated.tsx`) only when:

1. The route guard depends on the data (e.g. the admin session in `_authenticated.tsx` — must be present before child routes render).
2. The data is render-blocking AND large enough that the in-component waterfall hurts perceived latency (a multi-second fetch that would otherwise show a skeleton).
3. You want a typed parameter (route param → loader fetch → component reads `Route.useLoaderData()`).

For everything else — list pages, secondary panels, anything that can render its own skeleton — `useQuery` inside the component is simpler and equally correct.

## No hardcoded color hex

Consume design tokens — `bg-card`, `bg-background`, `bg-secondary`, `bg-accent`, `bg-primary/10`, `text-foreground`, `text-muted-foreground`, `text-accent-foreground`, `text-ink`, `text-ink-2`, `border`, `border-border`, `ring-border`, `bg-violet-soft`, `bg-amber-soft`, etc. Never write `bg-[#xxxxxx]` or `text-[#xxxxxx]`. Tokens are declared in `src/styles/globals.css` — palette pivots stay there. Tactical data-viz colors (e.g. `bg-emerald-500` for a status bar) are OK; brand colors are not.

## Sessions are server-side, stateful

Admin auth is WebAuthn passkey → Spring Security 7 session cookie (`JSESSIONID`) backed by Spring Session Redis. The cookie is `HttpOnly`, `SameSite=Lax`, `Secure`. Logout endpoint is `POST /api/admin/logout` (configured in `backend/api/src/main/java/com/zeromail/api/security/SecurityConfig.java`, returns 200 OK via `HttpStatusReturningLogoutSuccessHandler`). The FE helper is `logoutAdmin()` in `apps/admin/src/lib/admin-session.ts` — use it from a mutation (see `AdminLayout` for the canonical wiring).
