**Edit 1 — `backend/api/build.gradle.kts`:**
Inside the existing `dependencies { ... }` block, add ONE new line. Place it after the last `implementation(...)` line and before the `testImplementation(...)` lines, so the configurations stay grouped:

```kotlin
developmentOnly("org.springframework.boot:spring-boot-docker-compose")
```

Rationale recorded in CLAUDE.md "Required starters" table — `spring-boot-docker-compose (dev only)`. NO version string: Spring Boot 4.0.6 BOM (imported by `zeromail.spring-boot-conventions` via dependency-management) manages it. Do NOT add an entry to `gradle/libs.versions.toml`: catalog entries are reserved for libraries whose versions we pin ourselves; BOM-managed artifacts are referenced by coordinate only (matches the existing pattern for `spring-boot-starter-*` lines in this same file).

The `developmentOnly` configuration is contributed by the `org.springframework.boot` Gradle plugin, which is already applied at the top of this file (`id("org.springframework.boot")` line 5). No plugin changes needed. The Spring Boot plugin guarantees `developmentOnly` artifacts are excluded from `bootJar` / `bootRun -PspringBootRunArgs` production-shaped tasks but ARE included in `bootRun` and IDE Run classpaths.

Do NOT add this dependency to `backend/worker/build.gradle.kts` or to the `zeromail.spring-boot-conventions` convention plugin — it must remain api-only for v1 (worker shell exists but does not run yet; per scope).

**Edit 2 — `backend/api/src/main/resources/application.yml`:**
Add a new top-level YAML block (do NOT nest it inside an existing `spring:` mapping rewrite; add it as additional keys under the existing `spring:` block at the appropriate indentation level). Specifically, locate the existing `spring:` root key (currently the very first line) and insert a new child `docker:` mapping. The cleanest placement is immediately after the `spring.threads.virtual` block (around line 6) and before `spring.datasource`. Result snippet:

```yaml
spring:
  application:
    name: zeromail-api
  threads:
    virtual:
      enabled: true
  docker:
    compose:
      lifecycle-management: start_only
  datasource:
    url: ${DB_URL:jdbc:postgresql://localhost:5432/zeromail}
    # ...rest unchanged...
```

Rationale: `start_only` keeps Postgres + Redis containers running across IDE restarts, which is the fast dev-loop choice. Default would be `start_and_stop`, which tears containers down on every app shutdown — undesirable for short edit-restart cycles. The opt-out path (developer prefers to manage `docker compose` manually) is `SPRING_DOCKER_COMPOSE_ENABLED=false` env var; document this in the SUMMARY but do NOT add it to application.yml (we want the default ON for new contributors).

Use a YAML scalar value `start_only` (underscore form). Spring Boot 4 accepts both `start-only` and `start_only`; pick `start_only` to match the canonical enum name in `DockerComposeProperties.LifecycleManagement`. Do NOT quote it.

Do NOT touch any other key in application.yml. Do NOT introduce a separate `application-local.yml` profile file — the goal is zero-config dev for new contributors, which means the dev-only behavior must live in the default profile and be naturally inert in production (it is, because the starter is `developmentOnly` — without the starter on classpath, the `spring.docker.compose.*` keys are simply ignored).

<task type="checkpoint:human-verify" gate="blocking">
  <name>Task 2: Human verifies dev auto-launch works end-to-end</name>
  <what-built>
Spring Boot Docker Compose support is now declared as a `developmentOnly` dependency on `backend/api`, with `lifecycle-management: start_only` so the compose stack persists across restarts. Spring Boot will detect the repo-root `docker-compose.yml` and auto-launch the `postgres` and `redis` services on `bootRun`, then auto-wire `spring.datasource.*` and `spring.data.redis.*` to those containers — overriding the localhost defaults in `application.yml`.
  </what-built>
  <how-to-verify>
Perform the following on a developer workstation with Docker Desktop installed and the Docker daemon running:

1. **Tear down any pre-existing dev stack** so we are testing the auto-launch from a clean slate:
   ```bash
   docker compose -f docker-compose.yml down -v
   docker ps   # confirm no zeromail-* containers running
   ```

2. **Start the api with no manual compose step:**
   ```bash
   ./gradlew :backend:api:bootRun
   ```
   Watch the logs. Expected sequence:
   - A line near startup mentioning `Using Docker Compose file` referencing the repo-root `docker-compose.yml`.
   - Lines for both services starting (e.g., `Container <project>-postgres-1 Started`, `Container <project>-redis-1 Started`).
   - Liquibase runs successfully against the auto-launched Postgres (look for `Liquibase: Update has been successful`).
   - The app reaches `Started ZeromailApiApplication` without datasource or Redis connection errors.

3. **Confirm containers are actually up:**
   ```bash
   docker ps | grep -E "postgres|redis"
   ```
   Both containers should be listed with status `Up`.

4. **Hit a smoke endpoint:**
   ```bash
   curl -s http://localhost:8080/actuator/health
   ```
   Expect `{"status":"UP"}` (or at least no DB / Redis component reporting `DOWN`).

5. **Stop the app (Ctrl+C in the bootRun terminal). Confirm `start_only` semantics:**
   ```bash
   docker ps | grep -E "postgres|redis"
   ```
   Containers must STILL be running (this is the fast-dev-loop guarantee). If they were torn down, `lifecycle-management` is misconfigured.

6. **Restart bootRun and confirm it reattaches without restarting containers:**
   ```bash
   ./gradlew :backend:api:bootRun
   ```
   Logs should NOT show `Container ... Started` again (it should reuse the running containers). Startup should be noticeably faster than step 2.

7. **Confirm production jar isolation:**
   ```bash
   ./gradlew :backend:api:bootJar
   unzip -l backend/api/build/libs/*.jar | grep -i docker-compose
   ```
   Expect NO matches. The starter must not be packaged into the production fat jar.

8. **Confirm opt-out works (smoke test):**
   ```bash
   docker compose -f docker-compose.yml down -v
   SPRING_DOCKER_COMPOSE_ENABLED=false ./gradlew :backend:api:bootRun
   ```
   The app should attempt to connect to localhost:5432 and FAIL (since we tore down the stack). This proves the env-var opt-out actually disables the auto-launch. Stop the app after observing the connection failure.

If all eight steps pass, approve. If any step fails, paste the failing log lines / `docker ps` output for diagnosis.
