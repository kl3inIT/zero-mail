## Frontend i18n approach

### Q1: Which i18n library/strategy for apps/web?

| Option | Description | Selected |
|--------|-------------|----------|
| next-intl | RSC-native, App Router-first; ICU MessageFormat; TS-typed keys; standard 2025-2026 choice for Next.js 16. | ✓ |
| Lightweight custom loader | ~50-100 LOC; JSON dictionaries + hooks; no external dep; simple `{var}` interpolation. | |
| react-i18next + i18next | Mature but client-centric; rough App Router story; close to the rejected `react-jhipster` pattern. | |

**User's choice:** next-intl (Recommended)
**Notes:** Library locked. Pin current stable version via Context7 at install time, not from memory.

### Q2: Dictionary file layout under apps/web/messages/?

| Option | Description | Selected |
|--------|-------------|----------|
| One file per locale, namespaced | `messages/vi.json` + `messages/en.json` with grouped top-level keys (`auth`, `onboarding`, `settings`, `common`, `errors`). | ✓ |
| Split files per namespace per locale | `messages/vi/auth.json`, `messages/vi/errors.json`, etc. Smaller bundles, more files. | |
| Flat keys, dotted | One file per locale with flat `"settings.connection.disconnect.confirm"` keys. | |

**User's choice:** One file per locale, namespaced
**Notes:** `errors` namespace mirrors backend dotted error code hierarchy 1:1.

### Q3: Parameter/plural format inside translated strings?

| Option | Description | Selected |
|--------|-------------|----------|
| ICU MessageFormat | Native to next-intl; handles plurals, named placeholders, dates. | ✓ |
| Simple `{var}` interpolation | Tiny replace helper; fine for v1 but no plurals. | |
| You decide | Tied to library choice. | |

**User's choice:** ICU MessageFormat
**Notes:** Future-proof for Phase 5 analytics copy; backend `params` map values pass straight into ICU placeholders.

## Locale routing & persistence

### Q1: How should locale appear in URLs?

| Option | Description | Selected |
|--------|-------------|----------|
| No URL prefix — cookie-driven | URLs stay `/login`/`/onboarding`/`/settings`; locale via `NEXT_LOCALE` cookie + `/me` `preferred_language`. | ✓ |
| URL prefix `/vi/...`, `/en/...` | next-intl middleware standard mode; shareable links carry language; heavier change. | |
| Hybrid: prefix only when explicit | Default vi at `/login`, English at `/en/login`; edge cases. | |

**User's choice:** No URL prefix — cookie-driven
**Notes:** Matches SPEC ("explicit user selection, no Accept-Language negotiation"); minimal Phase 1 churn.

### Q2: Where does the language preference live for authenticated users?

| Option | Description | Selected |
|--------|-------------|----------|
| `users.preferred_language` column + cookie mirror | New column + `/me` extension + `PATCH /me/language` + `NEXT_LOCALE` cookie for SSR. | ✓ |
| Cookie only (no DB column) | Fails SPEC's "persisted per user" / "survives new sessions" requirement. | |
| DB column only (no cookie) | Strictly correct but every page render does an `/me` round-trip — SSR flash. | |

**User's choice:** users.preferred_language column + cookie mirror
**Notes:** Server is the source of truth on conflict; first authenticated render overwrites cookie if `/me` differs.

### Q3: What does the unauth experience do for locale?

| Option | Description | Selected |
|--------|-------------|----------|
| Default `vi`, remember `NEXT_LOCALE` cookie | Pre-auth users see Vietnamese; switch persists in cookie; auth wins on login. | ✓ |
| Always Vietnamese until authenticated | Simpler; worse for English-speaking founders. | |
| Show switcher on /login but don't persist | Page-local state only; lost on reload. | |

**User's choice:** Default `vi`, remember `NEXT_LOCALE` cookie

### Q4: How is the locale propagated to the first server render?

| Option | Description | Selected |
|--------|-------------|----------|
| next-intl middleware reads cookie + sets request locale | Middleware composed with Phase 1 auth redirect; async `layout.tsx` uses `getLocale()`. | ✓ |
| Read cookie inline in layout.tsx | No middleware; manual locale threading through server components. | |
| You decide | — | |

**User's choice:** next-intl middleware reads cookie + sets request locale
**Notes:** No flicker, no hydration mismatch; replaces hard-coded `<html lang="en">`.

## Backend error contract shape

### Q1: How should the stable error contract be shaped on the wire?

| Option | Description | Selected |
|--------|-------------|----------|
| Extend ProblemDetail with `code`/`params`/`fieldErrors` | Stay on RFC 7807; add three extension members; keep `title`/`detail` as generic diagnostics. | ✓ |
| Custom `ApiError` envelope | Non-RFC-7807 POJO; abandons ProblemDetail; full handler rewrite. | |
| Both — ProblemDetail wrapping nested `error` | Extra nesting; over-engineered for v1. | |

**User's choice:** Extend ProblemDetail with `code`/`params`/`fieldErrors` extensions
**Notes:** Existing `message` key kept as transitional alias for `code`, dropped in a later phase.

### Q2: Field-error shape for validation failures?

| Option | Description | Selected |
|--------|-------------|----------|
| `{ field, code, params }[]` | Dotted field paths; dictionary code lookups; allow-listed scalar params. | ✓ |
| `{ field, message }[]` with localized text | SPEC explicitly forbids server-side localized prose. | |
| Keyed map: `{ "email": { code, params } }` | Loses ordering; breaks for repeat-field scenarios. | |

**User's choice:** `{ field, code, params }[]`

### Q3: Code naming convention for `code` values?

| Option | Description | Selected |
|--------|-------------|----------|
| Hierarchical dotted keys | `error.auth.unauthorized`, `error.validation.field.email.invalid`. Mirrors dictionary namespaces. | ✓ |
| SCREAMING_SNAKE constants | `AUTH_UNAUTHORIZED`; extra translation step for every lookup. | |
| JHipster-style `error.http.401` | Status-keyed defaults lose semantic meaning. | |

**User's choice:** Hierarchical dotted keys

### Q4: How to document the error schema in OpenAPI for FE codegen?

| Option | Description | Selected |
|--------|-------------|----------|
| One reusable `ApiError` schema, springdoc global config | `OpenApiCustomiser` / `@OpenAPIDefinition` registers default error response globally. | ✓ |
| Per-controller `@ApiResponse` annotations | Verbose, drifts as surface grows. | |
| Hand-write schema in static yaml shim | Defeats springdoc auto-generation. | |

**User's choice:** One reusable `ApiError` schema, springdoc global config

## Coverage gate & safety tests

### Q1: Where does the translation key parity check live?

| Option | Description | Selected |
|--------|-------------|----------|
| Custom Node script in apps/web/scripts/ | `check-i18n.ts` mirroring `generate-api.ts` pattern; `pnpm i18n:check` in CI. | ✓ |
| Vitest test in apps/web | Adds test runner not currently configured. | |
| next-intl built-in tooling | Catches typed misuse but not unused-key drift. | |
| next-intl typecheck + Node parity script (composite) | Belt + suspenders. | |

**User's choice:** Custom Node script in apps/web/scripts/
**Notes:** next-intl's typed message accessor is also enabled (D-D2) but the Node script is the gate.

### Q2: Where does the sensitive-sentinel error-payload safety test live?

| Option | Description | Selected |
|--------|-------------|----------|
| Backend Spring integration test | `GlobalExceptionHandlerSafetyTest` triggers each error path with sentinels; asserts payload + Logback clean. | |
| Frontend mock test | Asserts FE never displays raw `title`/`detail`; doesn't prove server-side payload safety. | |
| Both — backend payload + frontend display (composite) | Two thin tests, two distinct invariants. | ✓ |

**User's choice:** Both — backend payload + frontend display
**Notes:** Backend reuses Phase 1's Logback test-appender pattern; FE test mocks each known code.

### Q3: Where is `<html lang>` actually set?

| Option | Description | Selected |
|--------|-------------|----------|
| Async `app/layout.tsx` reads locale from next-intl request context | `getLocale()` server-side; no flicker; `generateMetadata` localized. | ✓ |
| Client-side useEffect updates document.documentElement.lang | SSR/CSR mismatch; SEO/AT semantics suffer. | |
| You decide | — | |

**User's choice:** Async `app/layout.tsx` reads locale from next-intl request context

### Q4: Should the implementation also bind a hard-coded English literal scanner in CI?

| Option | Description | Selected |
|--------|-------------|----------|
| Yes — small AST/regex check on Phase 1 component files | Same `check-i18n.ts` script flags prose-shaped string literals. | ✓ |
| No — rely on key parity + manual review | Risk: new copy ships without a key. | |
| Defer to a later phase | — | |

**User's choice:** Yes — small AST/regex check on Phase 1 component files
**Notes:** Catches the most common drift mode — new component shipped without its key.
