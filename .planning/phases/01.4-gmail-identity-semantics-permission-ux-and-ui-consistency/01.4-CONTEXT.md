# Phase 1.4: Gmail Identity Semantics, Permission UX, and UI Consistency - Context

**Gathered:** 2026-04-27
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 1.4 closes two independent but adjacent gaps left from Phase 1, plus runs a single bounded UI consistency sweep. The backend gap is identity semantics for the second OAuth leg: the Google account a user signs in with MUST equal the first managed Gmail account they grant `gmail.modify` to, enforced at callback time, with the existing `OAuth2AuthorizedClient` for the `google-gmail` registration converted into a real `GmailConnectionEntity` row (refresh-token encrypted via the existing AES-GCM envelope, scopes captured, status advanced) — work the Phase 1 plan-set scaffolded but never finished. The frontend gap is two-fold: (1) the surfaces shipped in Phase 1.1–1.3 are functional but inconsistent (ad-hoc Tailwind classes, no design-tokens layer, no shared page/section/state primitives), and (2) Next.js error fallbacks (`error.tsx`, `global-error.tsx`, `not-found.tsx`) were never added — a thrown exception currently nukes the route group with an unstyled default. Phase 1.4 ships a tokens layer + 5 reusable primitives, applies them across all current surfaces, and adds the Next.js error-boundary baseline backed by those primitives — without locking final brand identity (typography, palette, illustrations) which remains Phase 5's call.

**In scope:**

*Backend — Gmail identity semantics and permission UX:*
- New `GmailOAuthSuccessHandler` bound to OAuth2 client registration `google-gmail` (mirrors `GoogleOAuthSuccessHandler`'s pattern). Does, in one transactional service call: (a) validate `oidcUser.subject` of leg 2 equals the stored `users.google_subject` of the currently-logged-in user; (b) on match, encrypt the leg-2 refresh token via existing `RefreshTokenCipher` (envelope `[key_version|nonce|ciphertext]`); (c) idempotently upsert `GmailConnectionEntity(tenantId, googleEmail, status=CONNECTED, scopesGranted, refreshTokenEncrypted, connectedAt=now)` — re-grant updates token+scopes on the existing row, preserving the 1-row-per-tenant invariant; (d) advance `users.onboarding_step` from `SIGNED_IN` to `GMAIL_CONNECTED`.
- `GmailScopeRequestResolver.customize()` extension: in addition to the current `prompt=consent`, `access_type=offline`, `include_granted_scopes=true`, also adds `login_hint=<currentUser.email>` read from `SecurityContextHolder` so Google's account chooser defaults to the same account. Falls through silently if no current user (subject check still enforces correctness).
- New `GmailOAuthFailureHandler` bound to registration `google-gmail`. Distinguishes two cases via the OAuth2Error code or thrown exception subtype: (i) **identity mismatch** (subject check fail thrown by the success handler before persistence) → POST Google's revoke endpoint to drop the just-granted token, then redirect `/onboarding?error=gmail_identity_mismatch`; (ii) **consent denied** (Google returns `error=access_denied` on callback) → redirect `/onboarding?error=gmail_consent_denied`. Both map to `ErrorCodes` constants (`gmail.identity.mismatch`, `gmail.consent.denied`) and to vi/en i18n bundles.
- Wire both handlers into `SecurityConfig` alongside the existing `GoogleOAuthSuccessHandler` so the chain selects per-registration. The existing handler keeps owning the `google` registration only (sign-in / first-login provisioning).
- Extend `GmailConnectionService` with an idempotent `upsert(...)` method (single-domain, tenant-scoped). Existing `currentStatus`, `disconnect`, `deleteForCurrentTenant` methods preserved verbatim.
- Privacy: never log Google subject, email, or token contents — only structured event names + error code. Existing `@Sensitive` contract applies to refresh-token byte arrays.

*Frontend — UI consistency sweep:*
- New design-tokens layer in `apps/web/app/globals.css` using Tailwind 4's `@theme inline` directive: brand color scales (background, foreground, muted, accent, destructive, border, ring), spacing scale, radius scale, typography scale, shadow scale. Tokens defined for both `light` and `dark` modes via `[data-theme="dark"]` selectors but only `light` is shipped (dark-ready, dark-not-on). Tokens are deliberately retunable — final brand identity (logo, palette finalize, font families) remains Phase 5's call.
- Five new reusable primitives at `apps/web/components/ui/`: `PageShell` (max-w + responsive padding wrapper), `SectionCard` (Card + heading slot + body slot, replaces ad-hoc `<Card><h2>...` patterns), `StatusAlert` (variant=info|success|warn|error, accepts i18n key + optional CTA, replaces inline `<div>` alerts), `EmptyState` (icon slot + heading + body + CTA, used by 404 + future empty list views), `LoadingState` (Skeleton wrapper for typical page layout, used by `loading.tsx` files). All five compose existing shadcn primitives — no new shadcn components installed.
- Refactor all current frontend surfaces to consume tokens + primitives: login page, onboarding page (all 4 step states), settings page (account/language/Gmail/privacy/danger sections), public landing, public docs index, public docs detail, plus shared components (LanguageSwitcher, ConnectionHealthBadge, ReconnectPrompt, DeleteAccountDialog, TemplateCard). Replace hard-coded Tailwind class strings (`text-stone-700`, `max-w-3xl`, `p-6`, etc.) with token-aware utilities (`text-foreground`, `text-muted-foreground`, `bg-background`).
- New mismatch error rendering on `/onboarding`: read `?error=gmail_identity_mismatch` (or `gmail_consent_denied`) from `useSearchParams()`, render a `<StatusAlert variant=error>` at the top of the step UI with localized title/body/CTA. CTA "Try again" re-triggers `/tenant/connect-gmail`.
- New `/settings` Gmail card footer note (i18n key `settings.gmailConnection.singleAccountNote`): "Zero Mail v1 supports one Gmail account, the email you logged in with. Multi-account support is on the roadmap." Vi/en bundles.
- `frontend-design` skill MUST be invoked by every executor agent before authoring or refactoring any JSX. This is locked by the user's persistent feedback memory and Phase 1.3 D-Discretion line — applies to skeleton structure as well as polish.

*Frontend — Next.js error-boundary baseline:*
- `apps/web/app/global-error.tsx` (root-level fallback that replaces `<html>`/`<body>` if root layout itself throws). Renders a self-contained PageShell + StatusAlert("error") with a Reset button calling Next's `reset()`. Inline minimal styling because the global root has no access to the regular layout's providers.
- `apps/web/app/(public)/error.tsx`, `app/(auth)/error.tsx`, `app/(protected)/error.tsx` — segment-level error boundaries, finer-grained recovery so a crash inside `/onboarding` falls back inside the protected shell rather than nuking the whole app. Each renders SectionCard + StatusAlert + Reset button using the new tokens.
- `apps/web/app/not-found.tsx` — root 404 fallback. Renders PageShell + EmptyState with localized "Page not found" copy and a "Back home" Link.
- All boundaries: copy via `next-intl` keys (`errors.boundary.{title,body,reset}`, `errors.notFound.{title,body,backHome}`); error message + stack are NEVER rendered to the user (privacy contract — exceptions could carry body/prompt/completion fragments); `console.error(error)` only when `process.env.NODE_ENV !== 'production'`. NO error reporting SDK (Sentry/Datadog/OTel) — that's a separate observability phase.
- Existing `loading.tsx` from Phase 1.3 P06 (`(public)/docs/[slug]/loading.tsx`) preserved; if any new `loading.tsx` files emerge during the sweep, they reuse `LoadingState`.

**Out of scope (enforced):**
- Multi-account / workspace concept implementation — list endpoint `GET /gmail/connections`, additional `gmail_connections` rows per tenant, `workspace_id` column, `tenant → workspace` rename. All deferred to a future workspace phase post-v1.
- Gmail API calls beyond the OAuth scope grant itself — `users.watch`, history fetch, message reads stay Phase 2A.
- Final brand identity decisions — logo, mascot, final font pairing, finalized color palette, marketing illustrations, hero imagery. Phase 5 owns these.
- Dark-mode toggle UI, dark-mode persistence (cookie/localStorage). Tokens are dark-ready but the toggle and switching logic ship later.
- New shadcn primitives that have no v1 use case — Toast, Sheet, Tabs, DropdownMenu, Popover. Install when an actual use case appears.
- Error reporting infrastructure — Sentry, Datadog, OpenTelemetry browser instrumentation, log-shipping from frontend. Belongs to the dedicated observability phase.
- CSS-in-JS, styled-components, vanilla-extract, or any styling layer beyond Tailwind 4 + tokens.
- Visual regression tests, Storybook, Chromatic. Tokens-and-primitives discipline is tested via lint + manual `pnpm dev` review.
- Backend rename of `tenant` → `workspace`, `TenantContext` → `WorkspaceContext`. Touches Phase 1, 1.2, 1.2.1 invariants — its own dedicated future phase if/when v2 multi-account ships.
- Adding/removing OAuth2 client registrations. `google` and `google-gmail` shape stays exactly as configured today.
- Storing or surfacing the email body, OAuth secrets, refresh-token plaintext, or stack traces anywhere a user can see them.

## Implementation Decisions

### A. Same-account guard + Gmail callback persistence

- **D-A1:** New `GmailOAuthSuccessHandler` (mirroring `GoogleOAuthSuccessHandler`) is bound to client registration `google-gmail`. Within a single transactional path, it: (1) reads the authenticated `OidcUser` of leg 2 and the currently-bound user from `SecurityContext` / session principal; (2) compares `oidcUser.getSubject()` against `currentUser.googleSubject` — fails fast with a typed exception (`GmailIdentityMismatchException`) if they differ, no persistence happens; (3) on match, fetches the `OAuth2AuthorizedClient` for `google-gmail`, encrypts its refresh token via existing `RefreshTokenCipher`, calls `GmailConnectionService.upsert(...)`, advances `users.onboarding_step` from `SIGNED_IN` to `GMAIL_CONNECTED`. Rationale: invariant in one place, transactional, race-free, mirrors Phase 1 D-A1 service-pattern. Rejected: `@EventListener` (race with redirect; can't reject inline 401), custom `OncePerRequestFilter` (filter ordering with Spring Security 7's OAuth2 callback flow is brittle).

- **D-A2:** `GmailScopeRequestResolver.customize()` is extended to add `login_hint=<currentUser.email>` to the leg-2 authorization request, alongside the existing `prompt=consent`, `access_type=offline`, `include_granted_scopes=true`. The current user email is read from `SecurityContextHolder` (the authenticated principal of the active session). When no principal is available (anonymous edge cases), the hint is omitted and the flow proceeds — D-A1's subject check is the authoritative guard. Rationale: keeps all OAuth-request customization in one resolver, no controller-level URL surgery, no second customization point.

- **D-A3:** New `GmailOAuthFailureHandler` is bound to client registration `google-gmail`. It distinguishes two failure modes via OAuth2Error code or exception subtype: (i) **identity mismatch** (`GmailIdentityMismatchException` thrown by D-A1's success handler before persistence) → POST Google's token-revoke endpoint (`https://oauth2.googleapis.com/revoke`) with the leg-2 token to drop the just-granted but unwanted authorization, then redirect to `${web-base-url}/onboarding?error=gmail_identity_mismatch`; (ii) **consent denied** (Google returns `error=access_denied` on the callback URL) → redirect to `${web-base-url}/onboarding?error=gmail_consent_denied`. Both error codes are added to `ErrorCodes` (`gmail.identity.mismatch`, `gmail.consent.denied`) and to vi+en i18n bundles. Rationale: matches Phase 1.1 ApiError contract (machine-readable codes, frontend localizes), avoids dangling stale grants on Google's side.

- **D-A4:** Persistence is invoked from the same `GmailOAuthSuccessHandler` (D-A1) via a new method `GmailConnectionService.upsert(googleEmail, scopesGranted, refreshTokenEncrypted)` — idempotent: if a `GmailConnectionEntity` already exists for the current tenant, it updates `googleEmail` (defensive — should always equal stored value post-A1 check), `scopesGranted`, `refreshTokenEncrypted`, `status=CONNECTED`, and `connectedAt=now`; otherwise inserts a new row. Scopes are read from `OAuth2AuthorizedClient.getAccessToken().getScopes()` (a `Set<String>`) and joined with a single space (matches Google's space-delimited scope-string convention; round-trips cleanly via `String.split(" ")`). Existing `GmailConnectionService.{currentStatus, disconnect, deleteForCurrentTenant}` methods are preserved verbatim. Rationale: centralizes invariant ("at most one Gmail connection per tenant in v1"); D-G2 envelope schema preserved (no plaintext token ever stored); leaves `JdbcOAuth2AuthorizedClientService` (if used at all) as a transient holder, never the source of truth.

### B. Future workspace/multi-account seam

- **D-B1:** API shape stays singular for v1. The current `GET /gmail/connection/status` endpoint is preserved as-is. A list endpoint `GET /gmail/connections` (returning an array) is **not** introduced now and is explicitly deferred to a future workspace phase. When that phase lands, it adds the list endpoint additively (existing singular endpoint can stay or be deprecated via OpenAPI version bump). Rationale: pre-launch prosumer SaaS has no legacy clients to break; the OpenAPI version-bump cost is cheap (Phase 1 D-F1 sets the precedent); zero churn now beats speculative future-proofing.

- **D-B2:** No `workspace_id` column is added to `gmail_connections` (or any other tenant-owned table). The existing `tenant_id` column continues to play the dual role of "tenant key" and "workspace key" — the v1 invariant is `1 tenant = 1 workspace = 1 Gmail account`. When v2 multi-account work begins, the dedicated phase decides whether to introduce a `workspace_id` column, rename `tenant_id`, or pursue another model. Rationale: avoids orphan columns (YAGNI); preserves Hibernate `@TenantId` discriminator pattern from Phase 1 D-B2 without ambiguity (two columns sharing the same role would confuse the resolver).

- **D-B3:** The terminology "tenant" is preserved in code, schema, ArchUnit rules, Modulith package names, and integration-test names. The v1 user-facing UI uses **"Gmail account"** (singular, English) / **"tài khoản Gmail"** (singular, Vietnamese) wherever the concept needs a label — never "tenant", never "workspace". When v2 ships multi-account, that phase introduces a UI-level "Workspace" alias at the copy layer; backend stays untouched. Rationale: avoids a ScopedValue/Hibernate/ArchUnit/Modulith refactor that would be massive scope creep; keeps the door open for v2 without committing now.

- **D-B4:** No "add another Gmail account" affordance ships in `/settings` or anywhere else in the v1 UI — no disabled stub button, no "coming soon" badge, no list-pretending UI. The Gmail card on `/settings` shows the single connected account with `<ConnectionHealthBadge>` + email + reconnect/disconnect actions. The single-account expectation is set explicitly via the footer note from D-D5. Rationale: simplest UI, no false promise to users, no premature i18n keys, no commitment to a v2 timeline.

### C. UI consistency sweep depth

- **D-C1:** Sweep ships a **design-tokens layer + 5 reusable primitives**, applied across every existing surface — but does **not** finalize brand identity. Concrete: a new tokens block in `apps/web/app/globals.css` using Tailwind 4's `@theme inline` directive defines CSS custom properties for color (background, foreground, muted, muted-foreground, accent, accent-foreground, destructive, destructive-foreground, border, input, ring), spacing (xs/sm/md/lg/xl multiples), radius (sm/md/lg/full), typography (font sizes from xs to 3xl, line heights, weights), and shadow (none/sm/md/lg). Token values are placeholders (sane defaults; e.g., `--color-background: oklch(99% 0 0)`) and explicitly retunable — Phase 5 swaps values without touching JSX. Rationale: design-tokens layer is the cheapest unification possible while the codebase is small; baseline-only would force a second sweep in Phase 5; full design-system bootstrap would lock decisions ROADMAP defers.

- **D-C2:** Theme strategy: ship light only, dark-ready tokens. Tokens are defined for both modes via `:root` (light defaults) and `[data-theme="dark"]` selectors in `globals.css`, but no toggle UI ships, no dark-mode default, no persistence cookie. Tailwind utility usage in JSX **must** use token-aware classes (`text-foreground`, `bg-background`, `text-muted-foreground`, `border-border`) — never raw color names like `text-stone-700`, `bg-white`, `text-gray-500`. ArchUnit-style ESLint rule (or simple `pnpm` script) optionally added in Discretion if executor sees value. Rationale: zero JSX refactor cost when Phase 5 adds a dark-mode toggle; preserves token-driven discipline from day 1.

- **D-C3:** All current surfaces are in scope: `app/(auth)/login/page.tsx`, `app/(protected)/onboarding/page.tsx`, `app/(protected)/settings/page.tsx`, `app/(public)/page.tsx`, `app/(public)/docs/page.tsx`, `app/(public)/docs/[slug]/page.tsx`, plus the shared components `features/i18n/components/LanguageSwitcher`, `features/gmail/components/{ConnectionHealthBadge, ReconnectPrompt}`, `features/account/components/DeleteAccountDialog`, `features/onboarding/components/TemplateCard` — and the per-route-group layouts (`(public|auth|protected)/layout.tsx`). New mismatch error UI on `/onboarding` (D-D2) plus the new error-boundary fallbacks (D-D3) are also in scope. Rationale: codebase still small; one consolidated sweep is cheaper than incremental drift; landing/docs deserve consistency even though final design lands in Phase 5.

- **D-C4:** Five new reusable primitives ship at `apps/web/components/ui/`: `PageShell` (responsive max-width + padding wrapper, replaces ad-hoc `<main className="mx-auto max-w-3xl p-6">`), `SectionCard` (Card + optional heading + optional description + body slot, replaces inline `<Card><h2>...` patterns), `StatusAlert` (variants info/success/warn/error, props: titleKey/bodyKey/cta?, accepts i18n keys not strings), `EmptyState` (icon slot + heading + body + optional CTA, used by `not-found.tsx` and any future empty-list view), `LoadingState` (Skeleton-based wrapper matching the typical page layout, default fallback in `loading.tsx`). All five compose existing shadcn primitives in `components/ui/` (Card, Skeleton, Alert via reuse). NO new shadcn primitives installed in Phase 1.4. Rationale: 5 primitives cover every observed v1 layout pattern and the error-boundary baseline; Toast/Sheet/Tabs/Dropdown deferred to Phase 5 install when use cases appear.

### D. Connect-Gmail UX, mismatch states, and error-boundary baseline

- **D-D1:** Mismatch and consent-denied errors render as an inline `<StatusAlert variant="error">` at the top of `/onboarding`. The page reads `?error=gmail_identity_mismatch | gmail_consent_denied` via `useSearchParams()` (client component), maps the value to an i18n key set (`gmail.identity.mismatch.{title,body,cta}`, `gmail.consent.denied.{title,body,cta}`), renders the alert with a CTA that re-triggers `/tenant/connect-gmail`. The query param is cleared after dismissal via `router.replace('/onboarding')`. Step-machine rendering (SIGNED_IN/GMAIL_CONNECTED/...) continues to render below the alert. Rationale: composes with existing step UI; no new routes; reuses C-Q4 primitive; pattern reusable for any future query-param-driven UX flag.

- **D-D2:** Next.js error-boundary baseline ships the **full set**: `app/global-error.tsx`, `app/(public)/error.tsx`, `app/(auth)/error.tsx`, `app/(protected)/error.tsx`, and `app/not-found.tsx`. Five small files. `global-error.tsx` includes its own `<html>`/`<body>` because it replaces the root layout when the root itself throws — uses minimal inline styling fallback (no NextIntlClientProvider available there; uses English-only "Something went wrong" + "Reload" text as last-resort). The three per-group `error.tsx` files are client components that wrap the segment in `SectionCard + StatusAlert("error") + reset button`. `not-found.tsx` renders `PageShell + EmptyState` with "Page not found" copy and a "Back home" Link. Existing `(public)/docs/[slug]/loading.tsx` from Phase 1.3 P06 is preserved verbatim; new `loading.tsx` files are added only if a route's measured render time warrants one (Discretion).

- **D-D3:** Error-boundary discipline is locked: (a) all user-visible copy goes through `next-intl` keys (`errors.boundary.{title,body,reset}`, `errors.notFound.{title,body,backHome}`) — no inline English/Vietnamese strings except in `global-error.tsx`'s last-resort fallback (which can't load next-intl); (b) `error.message` and `error.stack` are NEVER rendered to users — the privacy contract from Phase 1 D-E1 forbids leaking body/prompt/completion fragments through exception messages, and a server-thrown ApiError code might carry tenant info; (c) every `error.tsx` exposes a Reset button calling Next's `reset()` prop; (d) `console.error(error)` only when `process.env.NODE_ENV !== 'production'`; (e) NO error reporting SDK (Sentry/Datadog/OTel browser) — observability is a dedicated future phase, vendor still open per STATE.md blockers.

- **D-D4:** Deny-consent path uses the same `GmailOAuthFailureHandler` (D-A3) with a different OAuth2Error code branch. Spring's OAuth2 callback raises `OAuth2AuthenticationException` with `error=access_denied` when Google's consent screen returns the user-denied path; the failure handler distinguishes that from `GmailIdentityMismatchException` and redirects to `/onboarding?error=gmail_consent_denied`. The frontend D-D1 alert mapping treats it as a separate variant with friendlier copy ("You declined Gmail access. To use auto-triage, please grant access to your inbox.") and the same retry CTA.

- **D-D5:** `/settings` Gmail card adds a footer note (`<p className="text-sm text-muted-foreground">`) below the connection status: i18n key `settings.gmailConnection.singleAccountNote`, vi: "Zero Mail v1 hỗ trợ một tài khoản Gmail — chính là email bạn đã đăng nhập. Hỗ trợ nhiều tài khoản đang nằm trong roadmap." en: "Zero Mail v1 supports one Gmail account, the email you logged in with. Multi-account support is on the roadmap." Sets v1 expectation explicitly so users don't open support tickets about "where do I add another?".

- **D-D6:** Reconnect-after-disconnect uses the same `/tenant/connect-gmail` flow as first-time connect — no new endpoint, no new UI, no special-case logic. The same login_hint (D-A2) defaults the Google account chooser to the stored email; the same subject check (D-A1) enforces correctness; the same failure handler (D-A3) handles mismatch/deny. If the user's Google grant was revoked externally and they re-grant with the same Google subject, success is automatic. If they accidentally pick a different Google account at the chooser, the mismatch path triggers cleanly. ReconnectPrompt component (Phase 1.3) keeps pointing at `/tenant/connect-gmail`.

### Claude's Discretion

The planner / executor have flexibility within CLAUDE.md and the decisions above on:

- Exact package placement of `GmailOAuthSuccessHandler` and `GmailOAuthFailureHandler` (probably alongside existing `GoogleOAuthSuccessHandler` in `backend/api/src/main/java/com/zeromail/api/security/`).
- Choice of HTTP client for the Google revoke endpoint POST (RestClient is preferred per Phase 1.x convention; WebClient acceptable but adds reactive surface; `HttpClient` from JDK works fine).
- Whether `GmailIdentityMismatchException` extends `OAuth2AuthenticationException` or is a domain-typed RuntimeException with mapping in the failure handler — both work; pick whichever simplifies wiring.
- Exact token names and color values in `globals.css` — sensible defaults are fine; the *structure* (token taxonomy) matters more than the values.
- Whether to introduce an ESLint rule enforcing token-aware classnames (e.g., banning `text-stone-*`, `bg-white`, etc.) or rely on review discipline. Either acceptable; user discretion.
- Whether `EmptyState` accepts a children slot for custom icons or has an icon prop — UI ergonomics call.
- Whether to add new `loading.tsx` files for `/onboarding`, `/settings`, `/login` during the sweep, or only when a measurable need appears. Default = add to `/onboarding` and `/settings` since they currently flash empty content while `useCurrentUser` resolves.
- Test strategy for the new handlers — `PostgresContainerTest`-based integration tests are preferred (per Phase 1.2.1 P03 pattern); MockMvc fragments insufficient because `TenantContext` ScopedValue must be bound and the success handler must run inside a real Spring Security flow. Reference `MultiTenantLeakIntegrationTest` for the harness.
- Whether the mismatch-error alert dismisses itself on a successful re-grant or persists in URL — recommend `router.replace('/onboarding')` after the user dismisses or after `useTenantStatus` reports CONNECTED.
- Whether to localize the `global-error.tsx` last-resort fallback at all (currently locked to English-only fallback because next-intl provider is unavailable there) — leave English as last-resort, acceptable.
- Whether the StatusAlert primitive uses Radix's `<Alert>` (existing in `components/ui/alert.tsx`) as its base or shadcn's primitive — reuse existing.
- Whether `ConnectionHealthBadge` updates its variants to use the new `StatusAlert` color tokens or stays Badge-shaped — stay Badge-shaped, just retoken colors.
- Final i18n key tree depth — `errors.boundary.title` vs `errors.boundary.heading` etc.; `gmail.identity.mismatch` vs `gmailIdentity.mismatch`. Keep dot-namespace deep enough to avoid collisions; flat enough to read.
- Whether to emit a metric/log line on identity-mismatch reject. Recommend: emit a structured log `event=gmail_identity_mismatch outcome=rejected` with `tenant_id` field but never the email/subject contents — Phase 1 D-E1 contract.

## Specific Ideas

- **One handler, one transaction, one invariant.** The user explicitly chose Option 1 across all of A.Q1–Q4: a single `GmailOAuthSuccessHandler` that owns subject check + encrypt + persist + onboarding-step advance. Do not split into multiple beans / event listeners "for separation of concerns" — that breaks the transactional contract and re-introduces the race the success-handler-pattern eliminates.
- **`include_granted_scopes=true` is preserved.** The current resolver emits `include_granted_scopes`, which means leg 2 returns a token authorized for ALL previously-granted scopes (openid+profile+email from leg 1, plus gmail.modify from leg 2). The handler must read scopes from the leg-2 access token, NOT assume "scopes_granted = gmail.modify".
- **Scopes column stores leg-2 scopes only.** When persisting to `gmail_connections.scopes_granted`, store only the gmail-related scopes (filter to those starting with `https://www.googleapis.com/auth/gmail.`). The openid+profile+email portion is leg-1 surface and not relevant to the Gmail connection's audit trail.
- **Revoke endpoint is best-effort.** Google's revoke endpoint may 500, the network may be slow, the user may close the tab — none of those should block the redirect. POST + ignore response (with a structured WARN log on non-2xx) is fine. The mismatch UX still works because no `GmailConnectionEntity` row was written.
- **`login_hint` is graceful-degrade.** When SecurityContextHolder has no authenticated principal (rare; a session-mid-OAuth race), omit the hint and let Google's default chooser show. The subject check is still the authoritative guard. Don't throw, don't redirect.
- **Tokens are dark-ready but light-only ships.** The `[data-theme="dark"]` selector is added to `globals.css` with reasonable defaults so Phase 5 can flip it on with one toggle component. Do not add a toggle, do not persist preference, do not add `useTheme()` hook — that's Phase 5.
- **Five primitives, no more.** `PageShell + SectionCard + StatusAlert + EmptyState + LoadingState`. If during the sweep the executor finds a sixth pattern repeating (e.g., a "DangerZone" card variant on /settings), prefer extending an existing primitive (SectionCard variant) over adding a sixth primitive. Six is fine if genuinely needed; ten is mission creep.
- **`frontend-design` skill is mandatory before EVERY JSX file touched.** Per the user's persistent feedback memory, executor agents that touch frontend code MUST invoke the skill first — including for the boundary fallbacks and the sweep refactors. This is not just polish; the skill's discipline applies to skeleton structure too.
- **No `error.tsx` rendering of `error.message` or stack.** Even in dev, only `console.error` to the browser console. The user-visible UI never shows raw exception fields — Phase 1 D-E1 privacy contract applies on the client too.
- **`global-error.tsx` is English-only last-resort.** It can't load the next-intl provider (it replaces the root layout). Hard-code minimal English copy ("Something went wrong. Please reload."). All other boundaries go through `useTranslations()`.
- **Reconnect needs no special-case code.** The user picked Option 1 in D.Q4: the existing `/tenant/connect-gmail` flow + login_hint + subject check naturally handle reconnect. Do not add a "reconnect path" or `disconnect_clears_subject` toggle — same flow, same guards.
- **Single-account note copy is set expectation, not apology.** The Vietnamese / English copy is: "Zero Mail v1 hỗ trợ một tài khoản Gmail — chính là email bạn đã đăng nhập. Hỗ trợ nhiều tài khoản đang nằm trong roadmap." / "Zero Mail v1 supports one Gmail account, the email you logged in with. Multi-account support is on the roadmap." Confident, forward-looking, no "sorry for the limitation".
- **No new shadcn primitives.** Toast, Sheet, Tabs, Dropdown, Popover, Command-Palette — all deferred to Phase 5 or whenever a real use case arrives. Five primitives + 8 existing shadcn = covers v1.
