## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — Blocking] I18nArchUnitTest module location**

- **Found during:** Task 1 setup, after re-reading Plan 01 SUMMARY which placed the Wave-0 stub at `backend/core/src/test/java/com/zeromail/core/architecture/`.
- **Issue:** Three of the four Plan 08 ArchUnit rules target classes in `com.zeromail.api..` (controllers, GlobalExceptionHandler, FieldErrorDto). ArchUnit's `@AnalyzeClasses(packages = "com.zeromail")` scans only what is on the test classpath. `backend/core/src/test`'s classpath does NOT include `:backend:api` artifacts (the dependency direction is api→core, not the reverse), so every `..api..` predicate would resolve vacuously: `noClasses().that().resideInAPackage("..api..").should().…` is trivially satisfied because there are zero classes in that package on the classpath. The rule passes — but it never enforces anything. Fake green.
- **Fix:** Deleted the Wave-0 stub at `backend/core/src/test/java/com/zeromail/core/architecture/I18nArchUnitTest.java` and authored the production rules at `backend/api/src/test/java/com/zeromail/api/arch/I18nArchUnitTest.java`, alongside the existing `ControllerBoundaryArchTests` (the precedent for api-side ArchUnit rules). The module's `zeromail.archunit-conventions` Gradle plugin already wires ArchUnit into api's test sourceset.
- **Files affected:** deleted `backend/core/src/test/java/com/zeromail/core/architecture/I18nArchUnitTest.java`; created `backend/api/src/test/java/com/zeromail/api/arch/I18nArchUnitTest.java`.
- **Commit:** `0a82f4e`
- **Note:** Plan 08's verify command `./gradlew :backend:core:test --tests "*I18nArchUnitTest*"` is now stale — the runnable form is `./gradlew :backend:api:test --tests "*I18nArchUnitTest*"`. The plan body's frontmatter `files_modified` reference (`backend/core/src/test/architecture/I18nArchUnitTest.java`) is also stale.

**2. [Rule 2 — Auto-add missing critical functionality] OptimisticLockingFailureException as a 7th error path**

- **Found during:** Task 2 design.
- **Issue:** The plan body's behavior section listed 6 error paths (AccessDenied, Authentication, CurrentUserNotFound, MethodArgumentNotValid, DataIntegrity, Conflict, IllegalArgument — that's actually 7, but they were collapsed under "6"). Plan 02 SUMMARY explicitly added an `OptimisticLockingFailureException` handler ("Rule 2 — Auto-add missing critical functionality") emitting `ErrorCodes.CONFLICT` / 409. Treating it as a separate path (instead of subsuming it under IllegalStateException) is the only way the safety sweep proves that handler doesn't leak its own message field. Skipping it would leave a real-but-untested handler.
- **Fix:** Added a dedicated `[conflict]` parameterized test method targeting `OptimisticLockingFailureException` thrown from a fixture endpoint. 6 additional sentinel cases (one per category).
- **Files affected:** `GlobalExceptionHandlerSafetyTest.java`
- **Commit:** `b78514f`
- **Sentinel-sweep total:** 6 sentinels × 7 paths + 1 SQL-state = 43 parameterized cases (the plan body's "6×6 = 36" was a floor; this is the floor + 7).

**3. [Rule 2 — Auto-add missing critical functionality] U+200B zero-width-space dedicated test**

- **Found during:** Task 3 acceptance check.
- **Issue:** Plan 08 acceptance criterion `grep -n "u200b" PromptInjectionSentinelTest.java` requires a literal `u200b` substring. Using the literal U+200B character in `@ValueSource` makes the special-character intent invisible to grep — a future reviewer cannot tell which entry carries the zero-width-space attack vector without a hex dump. Using the Java unicode escape `"​"` inside `@ValueSource(strings = {…})` would compile to the same string, so the source still wouldn't carry the literal substring `u200b`.
- **Fix:** Added a dedicated `@Test` method `zeroWidthSpaceSentinel_isFilteredFromParams` that constructs the payload from a literal `​` Java escape at runtime, with `@DisplayName("zero-width space (\\u200b) sentinel…")` and assertion descriptions referencing `\\u200b` so the source code self-documents. The original 6-corpus parameterized test still runs the literal-char form, so coverage is wider, not narrower.
- **Files affected:** `PromptInjectionSentinelTest.java`
- **Commit:** `efe7343`
- **Result:** PromptInjectionSentinelTest is now 7 tests instead of 6.

## Privacy Invariants Preserved

- No real PII / email body / LLM prompt / completion / refresh-token plaintext appears in any test fixture, log line, or response payload.
- The 6 sentinel categories are obvious-marker conventions: clearly synthetic, never plausibly real production traffic, and chosen because they are the exact shapes that would exfiltrate sensitive content if naively echoed.
- The U+200B zero-width-space corpus entry is an attack-vector marker; the test's job is to prove the filter rejects it. Its presence in test source code is documented and grep-visible.
- `@TestConfiguration`-based fixture controllers throw exceptions carrying sentinels but do NOT introduce sentinel-bearing strings into production code paths — fixture controllers only exist on the test classpath and are never registered in production beans.
- All title/detail prose remains generic English diagnostics ("Validation failed", "Authentication required", "Conflict", "Bad request", "Access denied") authored at Plan 02; this plan asserts the absence of any leak, not the addition of any new prose.
- The CONTEXT.md §E verification subsection cites JHipster line numbers and class names but copies no JHipster source code into the file (license cleanliness + no accidental localized-prose copy).
