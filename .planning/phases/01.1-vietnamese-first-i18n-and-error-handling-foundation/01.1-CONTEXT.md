# Phase 1.1: Vietnamese-first i18n and error-handling foundation - Context

**Gathered:** 2026-04-26
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 1.1 layers a Vietnamese-default, English-secondary i18n architecture and a stable, frontend-localizable API error contract onto the Phase 1 surface. It updates `apps/web` (login, onboarding, settings, reconnect, delete-account, template card, loading, privacy/safety copy) to render from locale dictionaries; adds a persistent in-product language switcher; persists the per-user language preference in the database; upgrades `GlobalExceptionHandler` from a single `message` key to a formal `code` + `params` + `fieldErrors` contract; documents the error schema in OpenAPI so the generated `openapi-fetch` client is typed; and wires CI gates that fail on translation drift, hard-coded English copy, or sentinel sensitive values appearing in error payloads.

**In scope:** next-intl integration in `apps/web`; `messages/vi.json` + `messages/en.json` covering Phase 1 surfaces; `NEXT_LOCALE` cookie + `users.preferred_language` column + `PATCH /me/language` + `/me` extension; next-intl middleware composed with the Phase 1 auth middleware; async root layout setting `<html lang>`; ProblemDetail extension members (`code`, `params`, `fieldErrors`); springdoc global `ApiError` schema component; FE error-localization helper used by route components; CI parity check + hard-coded EN scanner; backend integration safety test + FE display test; Liquibase YAML changelog for the new column; JHipster keep/adapt/reject record.

**Out of scope (enforced):** Translating Phase 2+ screens that don't exist yet; locales beyond `vi`/`en`; Accept-Language auto-negotiation; `react-jhipster` / Redux locale reducers / Bootstrap menus / any JHipster runtime dependency; server-side construction of localized user-facing prose; redesign of any Phase 1 business flow; localized email/digest content; storage of raw bodies/prompts/completions/embeddings/refresh tokens/SQL internals/stack traces in error payloads or logs.

<decisions>
## Implementation Decisions

### A. Frontend i18n approach
- **D-A1:** Use **next-intl** as the i18n library for `apps/web`. Reasons: RSC-native, App Router-first middleware for locale negotiation, ICU MessageFormat support for `params` (matches the SPEC error contract's `params` requirement cleanly), TS-typed message keys, server + client component support, ~12-15kb bundle. Pin a current stable version at install time via Context7 lookup, not from memory.
- **D-A2:** Dictionary layout: **one file per locale, namespaced**. Files live at `apps/web/messages/vi.json` and `apps/web/messages/en.json`. Top-level keys group by surface: `auth`, `onboarding`, `settings`, `common`, `errors`. The `errors` namespace mirrors the backend dotted error code hierarchy (D-C3 below) one-to-one.
- **D-A3:** Parameter/plural format: **ICU MessageFormat** (next-intl's native idiom). Vietnamese has no plural inflection, but ICU also handles named placeholders, gendered messages, and number/date formatting — future-proof for Phase 5 analytics copy. All `params` map values from backend errors are passed straight into ICU placeholders by the FE error helper.

### B. Locale routing & persistence
- **D-B1:** **No URL prefix.** Routes stay `/login`, `/onboarding`, `/settings`. Locale is read from the `NEXT_LOCALE` cookie (set by switcher) and overlaid with the authenticated user's `preferred_language` from `/me`. Matches the SPEC ("product default Vietnamese, explicit user selection, no Accept-Language negotiation"); minimizes churn against the Phase 1 routing/middleware shape.
- **D-B2:** Persistence layer: **`users.preferred_language` column + `NEXT_LOCALE` cookie mirror**. New column `preferred_language varchar(2) not null default 'vi'` with a `check (preferred_language in ('vi','en'))` constraint, added via a new Liquibase YAML changelog included from the master changelog. `/me` returns the value. New endpoint `PATCH /me/language` accepts `{ "language": "vi" | "en" }`, validates against the allow-list, persists, returns the updated value. Switcher writes `NEXT_LOCALE` cookie immediately (so the next SSR pass renders correct locale without an `/me` round-trip), then fires the PATCH. Server is the source of truth on conflict (cross-device drift): on first authenticated render, if `/me`'s `preferred_language` differs from the cookie, the server overwrites the cookie.
- **D-B3:** Unauth UX: **default `vi`, remember `NEXT_LOCALE` cookie**. Pre-auth users see Vietnamese by default. The `/login` page exposes the switcher; selection sets the cookie only. After authentication, the server's `preferred_language` wins and overwrites the cookie (so a user whose DB pref is `en` lands in English even if a previous device left a `vi` cookie).
- **D-B4:** SSR propagation: **next-intl middleware composed with the Phase 1 auth middleware**. `apps/web/middleware.ts` chains next-intl's middleware in front of the existing auth-redirect logic. next-intl reads `NEXT_LOCALE` and sets the request locale before the App Router renders. The async root `app/layout.tsx` calls `getLocale()` and renders `<html lang={locale}>` — no flicker, no hydration mismatch. The current hard-coded `<html lang="en">` in `apps/web/app/layout.tsx` is replaced.

### C. Backend error contract shape
- **D-C1:** **Extend `ProblemDetail` with `code`, `params`, and `fieldErrors` extension members.** Stay on RFC 7807 (no new envelope). `title` and `detail` remain populated as generic, English diagnostics for RFC compliance and operator logs only — they are explicitly NOT the user-facing message source. The frontend ignores `title`/`detail` for display and switches on `code` + locale dictionary. The existing `message` key is kept for one transitional release as an alias of `code`, then dropped.
- **D-C2:** **Field-error shape:** `fieldErrors` is an array of `{ field: string, code: string, params: Map<string, scalar>? }`. `field` is a dotted path (e.g., `email`, `templates[0].key`). `code` is a dotted hierarchical key inside the `errors.field.*` dictionary namespace. `params` values are allow-listed scalars only (numbers, booleans, enum strings, translation keys, resource identifiers) — never raw user content, never Gmail body fragments, never SQL constraint names, never exception class names. Mapped from Spring's `MethodArgumentNotValidException` and `ConstraintViolationException` by an extension to `GlobalExceptionHandler`.
- **D-C3:** **Code naming convention: hierarchical dotted keys.** Examples: `error.auth.unauthorized`, `error.auth.forbidden`, `error.auth.currentUserNotFound`, `error.validation.field.email.invalid`, `error.validation.field.preferredLanguage.invalid`, `error.gmail.disconnected`, `error.dataIntegrity`, `error.conflict`, `error.badRequest`. One-to-one mapping with the dictionary's `errors.*` namespace. Existing handler entries (`error.unauthorized`, `error.forbidden`, `error.currentUserNotFound`, `error.dataIntegrity`, `error.conflict`, `error.badRequest`) are renamed under this hierarchy in the same change.
- **D-C4:** **OpenAPI documentation:** define a single reusable `ApiError` schema as an OpenAPI component (extends `ProblemDetail` with the new extension members). Register it once via a springdoc `OpenApiCustomiser` (or `@OpenAPIDefinition`) so every Phase 1 endpoint declares it as the default error response shape via a `responses` template — no per-controller `@ApiResponse` annotations. `openapi-typescript` regeneration produces a single typed `ApiError` interface the FE can switch on.

### D. Coverage gate & safety tests
- **D-D1:** **Translation parity check is a custom Node script.** `apps/web/scripts/check-i18n.ts` deep-walks `messages/vi.json` and `messages/en.json`, asserts identical key sets (every leaf key present in both, no extras), exits non-zero on drift. Wired as `pnpm i18n:check` and runs in CI before `next build`. Mirrors the existing `apps/web/scripts/generate-api.ts` pattern; no test runner introduced.
- **D-D2:** **next-intl typed message accessor is enabled** as a complement to D-D1. TypeScript-typed message keys catch unused/misspelled keys at compile time; the Node parity script catches dictionary drift (key removed in one locale, key present only in one locale). Belt + suspenders, no extra runtime cost.
- **D-D3:** **Hard-coded English literal scanner runs in the same Node script.** `check-i18n.ts` does a small AST/regex pass over Phase 1 in-scope files (`app/login/**`, `app/onboarding/**`, `app/settings/**`, `components/ConnectionHealthBadge.tsx`, `components/DeleteAccountDialog.tsx`, `components/ReconnectPrompt.tsx`, `components/TemplateCard.tsx`) flagging string literals that look like prose (length ≥ 4, contains a space, not inside a `className`/`aria-*`/`href`/`src`/import attribute, not in an allow-list). Catches the common drift mode where a developer ships new English copy without adding a translation key.
- **D-D4:** **Backend integration safety test** lives at the API/exception-handler layer: `GlobalExceptionHandlerSafetyTest` triggers each Phase 1 error path with sentinel sensitive values seeded into request bodies, headers, validation messages, and DB constraints (refresh-token-shaped strings, SQL-state-shaped names, prompt-injection-shaped content). Asserts: (1) response body contains no sentinel; (2) response body contains a stable `code` and only allow-listed `params` scalars; (3) `title`/`detail` contain no sentinel and no SQL/exception class names; (4) captured Logback output via a test appender contains no sentinel. This is the right layer — the contract is server-defined.
- **D-D5:** **Frontend display test** is a small vitest-or-equivalent test (added under `apps/web/__tests__/` if not already present, otherwise inline alongside the route components) that mocks API failures with each known `code` and asserts the localized Vietnamese string is rendered by default, the English string after locale switch, and a localized generic fallback for an unknown code. Asserts raw `title`, `detail`, exception names, SQL constraint names, and stack traces are never displayed. Two thin tests, two distinct invariants, neither doing the other's job.
- **D-D6:** **`<html lang>` is set in async `app/layout.tsx` via `getLocale()` from next-intl's request context.** First paint is correct; no client-side correction, no SSR/CSR mismatch. `generateMetadata` localizes `<title>` and `<meta name=description>` for the few Phase 1 routes.

### E. JHipster reference patterns — kept / adapted / rejected
Required by SPEC requirement #7. Documented here so a reviewer can audit at a glance.

**Kept (used as-is in spirit):**
- Key-based dual-language dictionaries (separate `vi` / `en` JSON dictionaries with identical key sets).
- ProblemDetail-style errors carrying a stable code key and parameters that the frontend localizes.
- Field-level validation errors carried as a structured array.
- A CI gate that fails when translation dictionaries drift.

**Adapted:**
- JHipster's per-namespace directory tree → flattened to one file per locale with namespaced top-level keys (`messages/vi.json`, `messages/en.json`).
- JHipster's i18next + `react-jhipster` runtime → replaced with next-intl idioms suitable for Next.js 16 App Router + RSC.
- JHipster's Bootstrap-based language menu → replaced with a shadcn/ui-based switcher placed in the existing layout (header on authenticated routes, inline on `/login`).
- JHipster's `error.http.{status}` default codes → replaced with semantic dotted hierarchical codes (D-C3).
- JHipster's locale-by-Accept-Language negotiation → replaced with explicit `vi` default + cookie/DB user selection (matches SPEC constraint).
- JHipster's Liquibase + Spring Boot patterns for adding the user-preference column → adapted to our existing `db/changelog` layout and Liquibase YAML idiom.

**Rejected:**
- `react-jhipster` and any JHipster frontend runtime dependency.
- Redux locale reducers / Redux store altogether (we use TanStack Query + next-intl, not Redux).
- Bootstrap CSS / Bootstrap-based menu primitives (we use Tailwind 4 + shadcn).
- Server-side construction of localized user-facing prose (Accept-Language → server returns Vietnamese strings) — this violates SPEC constraint that frontend owns user-visible localization from stable codes.
- Browser-language auto-detection / Accept-Language negotiation — product default is Vietnamese, with explicit user selection.
- JHipster's bundled login/account/settings React components (we already have Phase 1 implementations and only swap copy for keys).

### Claude's Discretion
Areas the planner/executor have flexibility on within CLAUDE.md and the decisions above:
- Exact next-intl package version (verify current stable via Context7 at install time).
- shadcn switcher component composition (DropdownMenu vs ToggleGroup vs custom small select) — pick the one that matches existing layout chrome and ships in the fewest files.

- Where to keep the deny-list of allow-listed `params` value types (a single utility class on the backend, used by the handler and asserted by the safety test).
- Test framework choice on the FE if vitest is not already configured — pick the lightest option that integrates with Next.js 16 + the existing `pnpm` setup.

<specifics>
## Specific Ideas

- **Locale allow-list is exactly `['vi', 'en']`** in both backend (`PATCH /me/language` validation, DB `check` constraint) and frontend (next-intl config, switcher options). Adding a third locale in a later phase requires updating both lists + dictionaries + tests.
- **Server is the source of truth on conflict.** When `/me`'s `preferred_language` differs from the cookie on first authenticated render, the server overwrites the cookie. This avoids "user changed language on device A, comes back to device B with stale cookie."
- **`title` / `detail` stay populated as English diagnostics** for RFC 7807 compliance and operator/log readability — the frontend simply ignores them for user display. The safety test (D-D4) asserts they contain no sentinel, but does NOT assert they're empty.
- **The `message` extension field stays for one transitional release as an alias of `code`.** Do not remove it inside Phase 1.1 — that risks breaking any half-migrated FE callsite during execution.
- **`error.validation.field.preferredLanguage.invalid`** is the canonical code for the "user submitted a locale outside the allow-list" case. Worked example for the planner.
- **Both switcher placements ship together.** A compact `<LanguageSwitcher>` lives in the authenticated layout chrome; an explicit form row also appears on `/settings`. Pre-auth `/login` shows the same compact component inline.
- **JHipster reference inspection is mandatory at planning time, not execution time.** The keep/adapt/reject record (§E) is already locked, but the planner should verify it against the live `D:/study-materials-summer-2026/jhipster` files and surface any factual drift in research output before plans are finalized.
