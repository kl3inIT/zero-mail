## Critical Issues

### CR-01: Data-integrity handler logs raw exception stack traces

**File:** `backend/api/src/main/java/com/zeromail/api/config/GlobalExceptionHandler.java:100`

**Issue:** `onDataIntegrity` calls `log.warn("Data integrity violation translated to 409", ex)`, which sends the full exception and stack trace to Logback. Data-integrity exceptions commonly include SQL constraint names, SQL states, and sometimes rejected row values. This violates Phase 1.1's "no SQL internals / PII / sensitive leakage in logs" goal. The safety test does not catch this because it only checks `ILoggingEvent.getFormattedMessage()` and MDC, not the throwable proxy or encoded stack trace.

**Fix:**

```java
@ExceptionHandler(DataIntegrityViolationException.class)
public ResponseEntity<ProblemDetail> onDataIntegrity(DataIntegrityViolationException ex) {
    log.warn("Data integrity violation translated to 409: {}", ex.getClass().getSimpleName());
    return problem(HttpStatus.CONFLICT,
            "Conflict",
            "The request could not be persisted because a data integrity rule was violated.",
            ErrorCodes.DATA_INTEGRITY);
}
```

Also extend `GlobalExceptionHandlerSafetyTest` to fail if translated exception log events carry a throwable proxy, or assert against the JSON-encoded log output rather than only formatted messages.

## Warnings

### WR-01: Top-level validation errors do not localize to `errors.validation.generic`

**File:** `apps/web/lib/api/errors.ts:63`

**Issue:** The backend emits top-level validation failures as `code: "error.validation"` (`ErrorCodes.VALIDATION`). The CI checker knows this must map to `errors.validation.generic`, but `useLocalizedApiError` only strips `error.` and then looks for a string leaf at `errors.validation`. Since `errors.validation` is an object, the hook returns `[MISSING:validation]` in development and `errors.unknown` in production. The current tests miss the real backend shape because they test auth codes and field-level validation codes, not top-level `error.validation`.

**Fix:**

```ts
function bundleKeyForCode(code: string): string {
  const normalized = normalizeCode(code);
  return normalized === "validation" ? "validation.generic" : normalized;
}

// In useLocalizedApiError:
const code = bundleKeyForCode(err.code);
```

Add a Vitest case in `apps/web/__tests__/i18n/error-render.test.tsx` asserting `{ code: "error.validation" }` renders `messages.errors.validation.generic` in both `vi` and `en`.

### WR-02: Authenticated locale cookie reconciliation is attempted from a root layout

**File:** `apps/web/app/layout.tsx:75`

**Issue:** `reassertServerLocale` tries to call `cookieStore.set("NEXT_LOCALE", ...)` from the root server component layout. Response cookies are not reliably mutable from a Server Component render path; when the server preference differs from the incoming cookie, this branch can be rejected or silently swallowed by the surrounding `catch`, leaving the stale cookie in place. That breaks the documented "server preference wins across devices" behavior for authenticated users.

**Fix:** Move the response-cookie mutation into a response-capable boundary such as `proxy.ts`, a route handler, or a server action. If the layout still fetches `/me`, keep it read-only and return the preferred locale for the current render without attempting `cookies().set`.

```ts
if (preferred === "vi" || preferred === "en") {
  return preferred;
}
return currentLocale;
```

Persist `NEXT_LOCALE` from middleware/route-handler code that can write `response.cookies.set(...)`, and add an authenticated test that starts with `NEXT_LOCALE=vi` plus `/me.preferredLanguage=en` and asserts both first render and the response cookie are `en`.

### WR-03: Network failures during authenticated language switching skip rollback

**File:** `apps/web/components/LanguageSwitcher.tsx:178`

**Issue:** The authenticated switch path handles `res.error`, but it does not wrap `api.PATCH("/me/language", ...)` in `try/catch`. If `fetch` rejects because the API is down, the request is blocked, or JSON parsing fails, the optimistic `NEXT_LOCALE` cookie remains changed even though the server preference was not persisted. That creates a client/server language split and can mask the failure from the user.

**Fix:**

```ts
startTransition(async () => {
  try {
    const res = await api.PATCH("/me/language", {
      body: { language: selected },
      headers: { "Content-Type": "application/json", ...xsrfHeader() },
    });
    if (res.error) {
      writeLocaleCookie(currentLocale);
      setErrorMessage(localizedError(res.error as ApiError));
      return;
    }
    router.refresh();
  } catch {
    writeLocaleCookie(currentLocale);
    setErrorMessage(localizedError(undefined));
  } finally {
    onSettled?.();
  }
});
```

Add a `LanguageSwitcher` test where `patchSpy` rejects and assert cookie rollback plus a localized fallback error.

### WR-04: OpenAPI declares `params` values as objects instead of allowed scalars

**File:** `backend/api/src/main/java/com/zeromail/api/config/OpenApiConfig.java:122`

**Issue:** Both `ApiError.params` and `FieldErrorDto.params` are registered with `new MapSchema().additionalProperties(new ObjectSchema())`. The generated TypeScript therefore exposes `params?: { [key: string]: Record<string, never> }` (`apps/web/lib/api/schema.d.ts:180`), but the backend contract and `AllowedParamScalars` emit `number | boolean | string` values. This makes the documented API contract diverge from the wire shape and undermines generated-client safety for future ICU parameter use.

**Fix:** Define a scalar union schema for map values and reuse it for both params maps.

```java
Schema<?> safeParamScalar = new Schema<>()
        .oneOf(List.of(new StringSchema(), new IntegerSchema(), new NumberSchema(), new BooleanSchema()))
        .description("Allowed scalar value: string, number, or boolean.");

new MapSchema().additionalProperties(safeParamScalar)
```

Regenerate `apps/web/lib/api/schema.d.ts` and assert the generated params type is a scalar union or `unknown` constrained by runtime filtering, not `Record<string, never>`.
