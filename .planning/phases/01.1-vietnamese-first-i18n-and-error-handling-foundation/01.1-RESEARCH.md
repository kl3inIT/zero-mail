# Phase 1.1: Vietnamese-first i18n and error-handling foundation - Research

**Researched:** 2026-04-26
**Domain:** Spring Boot 4 RFC 9457 ProblemDetail + Next.js 16 App Router i18n (Vietnamese default, English secondary), with frontend-owned localization of API errors
**Confidence:** HIGH (stack + patterns), MEDIUM (springdoc global response wiring exact API surface)

## Summary

Phase 1.1 is largely de-risked. CONTEXT.md already locks decisions D-A1..D-D6 with strong reasoning. Independent verification against current docs (2026-04-26) confirms every locked decision is correct and current:

1. **next-intl 4.9.1** is the correct frontend i18n library — it explicitly supports Next.js 16 App Router, has native cookie-driven locale (`localePrefix: 'never'`), exposes `getLocale()` for async `app/layout.tsx`, supports ICU MessageFormat, and offers compile-time typed message keys via `declare module 'next-intl' { interface AppConfig { Messages: ... } }`.
2. **Spring 7's `ProblemDetail.setProperty()`** flattens extension members as top-level JSON keys (because Spring Boot 4 ships with Jackson 3.1.x — the `ProblemDetailJacksonMixin` is on the classpath). No envelope wrapping required; RFC 9457 compliance preserved.
3. **springdoc-openapi `GlobalOpenApiCustomizer`** is the correct mechanism for registering one reusable `ApiError` schema globally and defaulting it as the error response for every operation — no per-controller `@ApiResponse` boilerplate.
4. **JHipster patterns confirmed and correctly classified.** Inspected `D:\jhipster\src\main\java\com\vn\core\web\rest\errors\ExceptionTranslator.java`, `ErrorConstants.java`, `FieldErrorVM.java`, `frontend/public/i18n/{vi,en}.json`, `frontend/src/app/config/language.constants.ts`, `frontend/src/app/shared/language/`. CONTEXT.md §E keep/adapt/reject record matches the live reference. One refinement: JHipster's `FieldErrorVM` carries a `message` string (defaulted to validation default-message or constraint code) — we explicitly reject this in favor of `{ field, code, params? }` per D-C2.
5. **Two non-obvious pitfalls** that CONTEXT.md does not yet flag and that the planner MUST surface in plan tasks: (a) `spring.mvc.problemdetails.enabled=true` silently ignores custom `@ExceptionHandler` methods unless the handler extends `ResponseEntityExceptionHandler` *or* is annotated `@Order(Ordered.HIGHEST_PRECEDENCE)`; (b) Vietnamese form input arriving in NFD (decomposed) form vs. NFC (precomposed) creates equality/length bugs — must NFC-normalize at API ingress for any text we compare or hash.

**Primary recommendation:** Execute CONTEXT.md decisions verbatim. Add three task-level guards: (1) `spring.mvc.problemdetails.enabled=true` + handler `@Order(Ordered.HIGHEST_PRECEDENCE)` OR extend `ResponseEntityExceptionHandler`; (2) NFC-normalize Vietnamese text at any input boundary that compares strings (out-of-scope-for-display, but worth flagging now); (3) ensure the springdoc customizer is `GlobalOpenApiCustomizer` (not `OpenApiCustomizer`) since Phase 1 may use `GroupedOpenApi`.

## User Constraints (from CONTEXT.md)

### Locked Decisions (verbatim — see CONTEXT.md §A–§E)

- **D-A1** Use **next-intl** for `apps/web` i18n (RSC-native, App Router-first, ICU MessageFormat, TS-typed keys). Pin current stable at install time.
- **D-A2** Dictionary layout: one file per locale, namespaced — `apps/web/messages/vi.json` and `apps/web/messages/en.json`. Top-level keys: `auth`, `onboarding`, `settings`, `common`, `errors`. The `errors` namespace mirrors the backend dotted error code hierarchy 1:1.
- **D-A3** Parameter/plural format: ICU MessageFormat (next-intl native).
- **D-B1** No URL prefix. Cookie-driven locale via `NEXT_LOCALE` overlaid with `/me.preferred_language`.
- **D-B2** Persist language as `users.preferred_language varchar(2) not null default 'vi'` with `check (preferred_language in ('vi','en'))` via Liquibase YAML changelog. `/me` returns it; `PATCH /me/language` updates it. Switcher writes the cookie immediately, then PATCHes. Server is source of truth on conflict.
- **D-B3** Unauth UX: default `vi`, remember `NEXT_LOCALE` cookie. Auth wins on login.
- **D-B4** SSR propagation via next-intl middleware composed in front of Phase 1 auth middleware. Async `app/layout.tsx` calls `getLocale()` and renders `<html lang={locale}>`.
- **D-C1** Extend `ProblemDetail` with `code`, `params`, `fieldErrors` extension members. Stay on RFC 9457. `title`/`detail` remain English diagnostics, NOT user-facing source. `message` extension stays as a transitional alias for one release.
- **D-C2** `fieldErrors: { field: string, code: string, params?: Map<string, scalar> }[]`. `field` is dotted path; `code` is dotted hierarchical key inside `errors.field.*`; `params` allow-listed scalars only — never raw user content, Gmail body fragments, SQL constraint names, or exception class names.
- **D-C3** Code naming convention: hierarchical dotted keys (`error.auth.unauthorized`, `error.validation.field.email.invalid`, etc.).
- **D-C4** OpenAPI: one reusable `ApiError` schema component, registered globally via springdoc customizer, applied as default error response across Phase 1 endpoints.
- **D-D1** Translation parity check: custom Node script `apps/web/scripts/check-i18n.ts`, `pnpm i18n:check`, runs in CI before `next build`.
- **D-D2** next-intl typed message accessor enabled (compile-time complement to D-D1).
- **D-D3** Hard-coded English literal scanner in the same `check-i18n.ts` script.
- **D-D4** Backend integration safety test `GlobalExceptionHandlerSafetyTest` — sentinels seeded into request bodies/headers/validation/DB constraints; assert payload + Logback clean.
- **D-D5** Frontend display test mocking each known `code`; assert localized vi default, en after switch, generic fallback for unknown.
- **D-D6** `<html lang>` set via async `app/layout.tsx` + `getLocale()`. `generateMetadata` localizes `<title>` / `<meta name=description>`.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| User-visible string rendering | Browser / Frontend Server (RSC) | — | Frontend owns localization; backend never returns localized prose |
| Locale negotiation (cookie read, redirect) | Frontend Server (Next middleware) | — | next-intl middleware runs at the edge before App Router |
| Active-locale source of truth (authenticated) | API / Backend (Postgres `users.preferred_language`) | Browser (`NEXT_LOCALE` cookie mirror) | Server wins on conflict; cookie is a perf optimization for SSR |
| Active-locale source of truth (unauthenticated) | Browser (`NEXT_LOCALE` cookie) | — | No DB row exists pre-auth |
| Error contract shape & code emission | API / Backend (`GlobalExceptionHandler` + ProblemDetail) | — | Server defines the stable code; client looks it up |
| Error message rendering | Browser / Frontend Server | — | `code` → `errors.{code}` translation in active locale |
| OpenAPI schema for `ApiError` | API / Backend (springdoc) | — | Drives `openapi-typescript` codegen of `apps/web/lib/api/schema.d.ts` |
| Translation parity gate | CI / Build | — | `pnpm i18n:check` runs before `next build` |
| Sensitive-sentinel safety check | API / Backend (integration test) + Browser (display test) | — | Two thin tests, two distinct invariants |

### Pattern 1: ProblemDetail with extension members (backend)

```java
// In GlobalExceptionHandler.java — extends ResponseEntityExceptionHandler
// CRITICAL: must extend ResponseEntityExceptionHandler OR be annotated @Order(Ordered.HIGHEST_PRECEDENCE)
// when spring.mvc.problemdetails.enabled=true, otherwise Spring's built-in handler silently wins.
// Source: https://github.com/spring-projects/spring-framework/issues/35982 [VERIFIED]

@RestControllerAdvice
public class GlobalExceptionHandler extends ResponseEntityExceptionHandler {

    @ExceptionHandler(AccessDeniedException.class)
    public ProblemDetail handleAccessDenied(AccessDeniedException ex) {
        ProblemDetail pd = ProblemDetail.forStatus(HttpStatus.FORBIDDEN);
        pd.setTitle("Forbidden");                                  // generic English diagnostic — NOT user-facing
        pd.setDetail("Access denied for this resource.");          // generic English diagnostic — NOT user-facing
        pd.setProperty("code", ErrorCodes.AUTH_FORBIDDEN);         // "error.auth.forbidden"
        pd.setProperty("params", Map.of());                        // allow-listed scalars only; never raw user content
        pd.setProperty("message", ErrorCodes.AUTH_FORBIDDEN);      // transitional alias for code (keep one release)
        return pd;
    }

    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex, HttpHeaders headers,
            HttpStatusCode status, WebRequest request) {
        ProblemDetail pd = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
        pd.setTitle("Validation failed");
        pd.setDetail("One or more fields failed validation.");
        pd.setProperty("code", ErrorCodes.VALIDATION);
        pd.setProperty("fieldErrors",
            ex.getBindingResult().getFieldErrors().stream()
                .map(fe -> new FieldErrorDto(
                    fe.getField(),                                          // dotted path
                    "error.validation.field." + fe.getField() + "." + fe.getCode(),  // dictionary key
                    AllowedParamScalars.filter(fe.getArguments())))         // allow-list filter
                .toList());
        pd.setProperty("message", ErrorCodes.VALIDATION);
        return handleExceptionInternal(ex, pd, headers, status, request);
    }
}
```

JSON shape on the wire (Jackson 3 flattens extension members):

```json
{

  "message": "error.validation",
  "fieldErrors": [
    { "field": "language", "code": "error.validation.field.preferredLanguage.invalid", "params": { "allowed": "vi,en" } }
  ]
```

### Pattern 2: springdoc global ApiError schema

```java
// OpenApiConfig.java
// Use GlobalOpenApiCustomizer (NOT OpenApiCustomizer) so the customization applies even
// when GroupedOpenApi is configured. [VERIFIED: springdoc-openapi GitHub issue #114, #1627]

@Bean
public GlobalOpenApiCustomizer apiErrorCustomizer() {
    return openApi -> {
        // 1. Register the ApiError schema as a reusable component
        openApi.getComponents().addSchemas("ApiError", new Schema<>()
            .type("object")
            .description("RFC 9457 ProblemDetail extended with code/params/fieldErrors")
            .addProperty("type",       new StringSchema().format("uri"))
            .addProperty("title",      new StringSchema())
            .addProperty("status",     new IntegerSchema())
            .addProperty("detail",     new StringSchema())
            .addProperty("instance",   new StringSchema().format("uri"))
            .addProperty("code",       new StringSchema().description("Machine-readable, dotted hierarchical code"))
            .addProperty("params",     new MapSchema().additionalProperties(true))
            .addProperty("fieldErrors", new ArraySchema().items(new Schema<>().$ref("#/components/schemas/FieldError")))
            .required(List.of("status", "code")));

        openApi.getComponents().addSchemas("FieldError", new Schema<>()
            .type("object")
            .addProperty("field", new StringSchema())
            .addProperty("code",  new StringSchema())
            .addProperty("params", new MapSchema().additionalProperties(true))
            .required(List.of("field", "code")));

        // 2. Default 4xx/5xx responses on every operation to ApiError
        openApi.getPaths().values().forEach(pathItem ->
            pathItem.readOperations().forEach(op -> {
                ApiResponses responses = op.getResponses();
                List.of("400","401","403","404","409","422","500").forEach(status -> {
                    if (!responses.containsKey(status)) {
                        responses.addApiResponse(status, new ApiResponse()
                            .description(HttpStatus.valueOf(Integer.parseInt(status)).getReasonPhrase())
                            .content(new Content().addMediaType("application/problem+json",
                                new MediaType().schema(new Schema<>().$ref("#/components/schemas/ApiError")))));
                    }
                });
            }));
    };
}
```

The result in `apps/web/lib/api/schema.d.ts` (after `pnpm generate-api`) gives the FE a typed `ApiError` interface to switch on.

```typescript
// apps/web/i18n/request.ts
import { getRequestConfig } from 'next-intl/server';
import { hasLocale } from 'next-intl';
import { routing } from './routing';

export default getRequestConfig(async ({ requestLocale }) => {
  const requested = await requestLocale;
  const locale = hasLocale(routing.locales, requested) ? requested : routing.defaultLocale;
  return {
    locale,
    messages: (await import(`../messages/${locale}.json`)).default
  };
});
```

### Pattern 4: Frontend error-localization helper

```typescript
// apps/web/lib/api/client.ts (additive — keep existing openapi-fetch wrapper)
import type { components } from './schema';
import { useTranslations } from 'next-intl';

type ApiError = components['schemas']['ApiError'];

export function useLocalizedApiError() {
  const t = useTranslations('errors');
  return (err: ApiError | undefined): string => {
    if (!err?.code) return t('unknown');
    try {
      // ICU substitutes params; missing key falls through to t() default behavior
      return t(err.code as never, (err.params ?? {}) as never);
    } catch {
      return t('unknown');
    }
  };
}
```

### Anti-Patterns to Avoid

- **Hand-rolling MessageFormat / placeholder substitution.** Use ICU via next-intl. Vietnamese has no plurals (CLDR `vi` → only `other` category) so simple `{var}` would work today, but the moment Phase 5 adds `{count, plural, ...}` to a different locale you'd be rewriting.
- **Storing locale strings in two places without a single allow-list constant.** Define `['vi','en'] as const` once in `i18n/routing.ts` and once in `ErrorCodes.java` / `AllowedParamScalars`; assert parity in tests.
- **Returning localized prose from the server.** SPEC explicitly forbids it. The handler emits `code` + `params`, frontend translates.
- **Using `OpenApiCustomizer` instead of `GlobalOpenApiCustomizer`** when groups are configured — silently misses grouped paths. [VERIFIED: springdoc faq]
- **Custom `@ExceptionHandler` for `MethodArgumentNotValidException` not on a `ResponseEntityExceptionHandler` subclass and without `@Order(Ordered.HIGHEST_PRECEDENCE)`** when `spring.mvc.problemdetails.enabled=true` — silently ignored. [VERIFIED: spring-framework #35982]
- **Setting `<html lang>` from a client `useEffect`.** Causes SSR/CSR mismatch and breaks SEO/AT semantics for the first paint.
- **Storing the cookie as session-only when CONTEXT.md requires "remember in browser-local selection".** next-intl 4.x defaults the locale cookie to session-based + only-when-switched. Configure `localeCookie: { name: 'NEXT_LOCALE', maxAge: 31536000 }` to keep it for 1 year. [VERIFIED: next-intl 4.0 blog]

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Locale negotiation + cookie persistence + SSR threading | Custom middleware reading `cookies()` and threading `locale` prop through every layout | `next-intl` middleware + `getLocale()` + `getRequestConfig()` | RSC-safe; no hydration mismatch; one source of truth |
| Plural / param formatting | Regex `replace(/{(\w+)}/g, ...)` helper | ICU MessageFormat (next-intl native) | Vietnamese is plural-trivial today, but ICU also covers select/date/number which Phase 5 will need |
| RFC 9457 envelope | `class ApiError { String code; ... }` POJO returned from handlers | `org.springframework.http.ProblemDetail` + `setProperty()` | Spring already implements RFC 9457; Jackson mixin flattens extensions to top-level JSON automatically |
| `code` constant duplication backend ↔ frontend | Inline string literals at every throw / catch site | `ErrorCodes` class on backend; matching `errors.*` namespace in `messages/{locale}.json`; CI gate proves parity | Two-sided typo trap |
| Translation parity check | Eyeballing PRs | `apps/web/scripts/check-i18n.ts` (D-D1) + next-intl typed accessor (D-D2) | Drift is invisible without a gate |
| Locale allow-list validation on `PATCH /me/language` | `if (!lang.equals("vi") && !lang.equals("en"))` ad-hoc | `@Pattern(regexp = "vi|en")` Bean Validation annotation OR a typed enum DTO | Hibernate Validator + `MethodArgumentNotValidException` already plug into the new field-error contract |
| Bean Validation message → user-facing string | Letting `f.getDefaultMessage()` flow to the response (JHipster's pattern in `FieldErrorVM`) | Map `fe.getCode()` (e.g., `Pattern`, `NotNull`) to a dictionary key (`error.validation.field.preferredLanguage.invalid`) | Default messages are English prose — violates frontend-owns-localization SPEC |
| Hard-coded English literal detection | Manual review | AST/regex pass in `check-i18n.ts` (D-D3) | Single most common drift mode is "shipped a string without a key" |
| Liquibase changelog inline `addColumn + check` | Two changesets | Single `addColumn` with nested `<constraints checkConstraint="preferred_language IN ('vi','en')"/>` (Liquibase 5.0.2 supports this in YAML) | Atomic migration |

**Key insight:** Custom solutions in this domain accumulate two-sided invariants (server emits code X ↔ client has key X) that drift silently. Every "Don't Hand-Roll" entry replaces a manual-coordination tax with a typed/checked one.

## Common Pitfalls

### Pitfall 1: `spring.mvc.problemdetails.enabled=true` silently swallows custom validation handlers
**What goes wrong:** A `@ControllerAdvice` with `@ExceptionHandler(MethodArgumentNotValidException.class)` returns the default Spring 7 ProblemDetail (without our `code`/`fieldErrors` extensions), and the dev sees no warning. Tests pass against the wrong shape.
**Why it happens:** When ProblemDetail is enabled globally, Spring's built-in resolver in `ResponseEntityExceptionHandler` is registered first; ambiguous handlers lose without an explicit precedence.
**How to avoid:** Either (a) `class GlobalExceptionHandler extends ResponseEntityExceptionHandler` and `@Override protected handleMethodArgumentNotValid(...)`, or (b) annotate the advice with `@Order(Ordered.HIGHEST_PRECEDENCE)`. Decision: use option (a) — matches Spring's documented extension point.
**Warning signs:** Validation responses missing `code` / `fieldErrors`; `400` payloads look "default-shaped" despite a custom handler being present.
**Source:** [VERIFIED: github.com/spring-projects/spring-framework/issues/35982]

### Pitfall 2: Vietnamese input arrives in NFD (decomposed); equality / length / hash computations break
**What goes wrong:** Some macOS keyboards and some browsers emit decomposed Vietnamese (`ế` = `e + ◌̂ + ◌́`, three code points) while DB-stored values are usually NFC (single code point). String equality, `.length`, and any subsequent hashing diverge between client and server.
**Why it happens:** Unicode allows multiple representations; HFS+ historically forced NFD. A user typing on macOS Safari may submit decomposed text.
**How to avoid:** NFC-normalize at API ingress for any text we compare or hash. For Phase 1.1 specifically: locale strings are ASCII (`vi`/`en`) so no impact today, but flag it for any Phase 2+ task that compares Vietnamese rule names, label names, or template names. Java: `Normalizer.normalize(s, Normalizer.Form.NFC)`. JS: `s.normalize('NFC')`.
**Warning signs:** "Two values that look identical compare unequal"; intermittent unique-constraint violations on user-supplied text.
**Source:** [VERIFIED: w3.org/International/questions/qa-html-css-normalization, MDN String.prototype.normalize, int3ractive.com Vietnamese normalize blog]

### Pitfall 3: SSR hydration mismatch on `<html lang>`
**What goes wrong:** Server renders `<html lang="vi">` (from cookie) but the client hydrates with no provider context for the user's most-recent server preference, causing React hydration warning + a Vietnamese flash before English re-render (or vice versa).
**Why it happens:** Cookie read happens server-side but a non-async `app/layout.tsx` defaults to a constant.
**How to avoid:** Async `app/layout.tsx` calls `await getLocale()`; wrap children in `<NextIntlClientProvider messages={messages}>`. D-D6 already locks this — verify in code review.
**Warning signs:** Console warning "Hydration failed because the initial UI does not match…"; `<html lang>` flips on first paint.

### Pitfall 4: next-intl 4.x cookie defaults to session-only
**What goes wrong:** A user picks English on Monday, closes the browser, reopens Tuesday → back to Vietnamese (cookie expired with the session). SPEC requirement: pre-auth selection persists across reloads/new sessions.
**Why it happens:** next-intl 4.0 changed the default to "session-based + only set when user switches". [VERIFIED: next-intl.dev/blog/next-intl-4-0]
**How to avoid:** In `i18n/routing.ts`, `localeCookie: { name: 'NEXT_LOCALE', maxAge: 60 * 60 * 24 * 365 }` (1 year). Also explicitly set the cookie from the `LanguageSwitcher` (Pattern 5 above) to bypass the "only when switched" gate on first selection.
**Warning signs:** Pre-auth selection lost after browser restart.

### Pitfall 5: Allow-listed `params` accidentally include raw user content
**What goes wrong:** Validation message argument is the rejected value itself (e.g., the user typed `<script>alert(1)</script>` for their preferred language; Bean Validation passes that string into `f.getArguments()`; we put it in `params`; FE renders it via ICU placeholder; XSS.)
**Why it happens:** `MethodArgumentNotValidException` exposes the rejected value via `FieldError.getRejectedValue()` and `getArguments()`. JHipster's `FieldErrorVM` happily passes server `defaultMessage` through.
**How to avoid:** `AllowedParamScalars.filter(...)` accepts only: numbers, booleans, allow-listed enum strings, dotted dictionary keys, dotted resource identifiers. Reject anything else (null it out, log a warning). The D-D4 safety test must seed sentinels (HTML, prompt-injection, refresh-token shapes) into request bodies and assert they never reach `params`.
**Warning signs:** Sentinel sensitive value appears in API response; XSS in error toast.

### Pitfall 6: `openapi-typescript` generates `unknown` for properties added via `setProperty`
**What goes wrong:** springdoc auto-generates an `ApiError` schema by reflecting on the `ProblemDetail` Java class — but `setProperty` extension members are dynamic and don't appear in reflection. Generated `ApiError` lacks `code` / `params` / `fieldErrors`. Frontend can't switch on `code`.
**Why it happens:** Reflection-based schema generation only sees static Java fields.
**How to avoid:** D-C4's `GlobalOpenApiCustomizer` registers the `ApiError` schema **explicitly** (Pattern 2 above) — does not rely on reflection. Verify after `pnpm generate-api` that `schema.d.ts` contains `ApiError` with all four extension fields.
**Warning signs:** `apps/web/lib/api/schema.d.ts` contains `ApiError` with only `type`, `title`, `status`, `detail`, `instance`.

### Pitfall 7: `users.preferred_language` column not respecting tenant boundary
**What goes wrong:** Multi-tenant Hibernate filter (`@TenantId`) is correctly on `users`, but the new column's check constraint or default is set in a way that bypasses the filter on update — e.g., raw SQL `UPDATE users SET preferred_language='en' WHERE id=?` without `tenant_id` predicate.
**Why it happens:** New endpoints often bypass JPA managed entities and use direct JDBC.
**How to avoid:** `PATCH /me/language` reads the current authenticated user via the existing tenant-scoped `UserRepository.findById(tenantContext.userId())` and writes through JPA — never raw JDBC. ArchUnit rule should still pass.
**Warning signs:** Cross-tenant test ("user A in tenant X cannot mutate user B in tenant Y") fails.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes (transitive) | Spring Security session cookie unchanged; `PATCH /me/language` requires authenticated principal |
| V3 Session Management | yes | `NEXT_LOCALE` is a non-sensitive cookie; `Secure` + `SameSite=Lax`. Not session-bound. |
| V4 Access Control | yes | `PATCH /me/language` mutates only the calling user's row (tenant-scoped repository) |
| V5 Input Validation | **yes (primary focus)** | Bean Validation `@Pattern(regexp="vi|en")` or enum DTO; reject anything else with `error.validation.field.preferredLanguage.invalid` |
| V6 Cryptography | no | Locale is plaintext non-sensitive |
| V7 Errors and Logging | **yes (primary focus)** | `AllowedParamScalars` filter on every `params` map; D-D4 safety test seeds sentinels into bodies/headers/validation/DB constraints; assert no leak to payload OR Logback |
| V12 API and Web Service | yes | OpenAPI `ApiError` schema documents the contract; `application/problem+json` content-type |
| V14 Configuration | yes | `spring.mvc.problemdetails.enabled=true` plus handler `@Order` precedence — see Pitfall #1 |

### Known Threat Patterns for {Spring Boot 4 + Next.js 16}

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| XSS via `params` echoed into ICU placeholder | Tampering / Information Disclosure | `AllowedParamScalars` filter — only numbers, booleans, allow-listed enum strings, dotted dictionary keys, dotted resource identifiers |
| Stack-trace leak in `detail` | Information Disclosure | Production handlers set generic `detail`; D-D4 asserts no `Exception` / package-name / SQLSTATE substring |
| Cross-tenant locale mutation | Tampering / Elevation of Privilege | JPA tenant-scoped repository on `users`; ArchUnit rule still passes |
| CSRF on `PATCH /me/language` | Tampering | Spring Security 7 cookie-based CSRF token + `X-XSRF-TOKEN` header (Phase 1 pattern) |
| Unsupported locale value DoS / injection | Tampering | DB `CHECK` constraint + Bean Validation `@Pattern` — defense in depth |
| Cookie tampering to force locale | Tampering | Locale is non-sensitive; cookie tampering at worst flips display language. Authenticated `/me` overwrite reasserts server truth on first SSR. |
| Hydration-time string interpolation injection | Tampering | next-intl's ICU MessageFormat treats `{var}` as literal substitution (no HTML by default); `<RichText>` is opt-in only |
