<objective>
Split the single bundled-Google OAuth flow into three intents (first-login provision / add-mailbox / reconnect-mailbox) using server-side attributes + a session shim (D-01/02/03, B+D+E). Stamp `intent`+`targetMailboxId`+`initiatingTenantId` as `OAuth2AuthorizationRequest.attributes(...)` in the resolver; copy them into the `HttpSession` on `removeAuthorizationRequest` via the `IntentCarryingAuthorizationRequestRepository` decorator (with the Redis-dirty fresh-`setAttribute` fix) so they survive the callback the framework consumes them on; branch in the success handler (one-shot read). Keep the single bundled Google registration and framework-owned `state` for CSRF.

Purpose: GMA-07/01/04 — connecting another Gmail must never replace the current row. Intent is authenticated against the live session, never a tamperable URL param (the rejected `?intent=` IDOR vector).
Output: 2 new security classes + resolver/handler/SecurityConfig edits.

NOTE: This plan does NOT add the connect/reconnect trigger endpoints (those are Plan 06's `ConnectMailboxController`). It wires the resolver/repository/handler/SecurityConfig so that when an authenticated mailbox-management redirect arrives carrying intent, the flow routes correctly. PENDING-vs-CONNECTED add decision (RESEARCH Open Q2): INSERT a CONNECTED row in the success handler (single write, no orphan PENDING row if the user abandons consent).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → OAuth init | The mailbox-management redirect can carry attacker-controllable params; intent must be authenticated against the session |
| Google callback → success handler | The framework consumes the authorization request before the handler runs; the intent must survive via the session, not the token |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-05-01 | Tampering / EoP | OAuth intent tampering, IDOR on targetMailboxId | mitigate | Intent + initiatingTenantId authenticated against the live session (never a URL param, the rejected `?intent=` IDOR); reconnect runs `resolveOwnedConnectionOrThrow` so a forged targetMailboxId fails closed 404 |
| T-10-05-02 | Spoofing | add flow re-provisioning / replacing the existing row | mitigate | Add branches BEFORE `OAuthProvisioningService` and INSERTs a new row; first-login path is the only one calling provisioning (D-03) |
| T-10-05-03 | Information Disclosure | intent shim losing signal across callback | mitigate | `IntentCarryingAuthorizationRequestRepository` copies the snapshot into the Redis-dirtied session (#7327 fix); `IntentCarryingRepositoryTest` proves survival |
| T-10-05-04 | Information Disclosure | raw email/token in OAuth logs | mitigate | Branch logs are `event=<name> tenantId={} gmailConnectionId={}` only; refresh token never logged; encryption stays in core cipher |
| T-10-05-05 | Tampering | CSRF on OAuth | mitigate | Framework keeps owning `state`; single bundled registration unchanged; no custom signed-state HMAC (CLAUDE.md lock) |
