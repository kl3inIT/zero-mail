# Phase 01.5: Code Review Report

**Reviewed:** 2026-04-27
**Depth:** standard

## Summary

Phase 01.5 collapses the two-leg OAuth into a single bundled-scope Google registration, deflates frontend wrapper primitives, fixes the React `cache()` keying bug (HIGH-2), and sweeps planning artifacts. The bundled OAuth + atomic provisioning surface (`GoogleOAuthSuccessHandler`, `OAuthProvisioningService.provisionBundledOAuth`, Liquibase 008/009) is mostly sound, but **four BLOCKER-level defects ship in this diff**:

1. `provisionBundledOAuth` advertises ONE atomic transaction, but the **race-loser cleanup branch opens a second `bundledTx.executeWithoutResult` after the first one has already rolled back** — partial state is persistable when a duplicate-Google-subject race fires.
2. `GoogleOAuthSuccessHandler.onAuthenticationSuccess` calls `super.onAuthenticationSuccess(req, res, auth)` **even when the granted scope check is going to throw the next time the same flow runs in mocks** — fine — but the success-redirect `setDefaultTargetUrl(...)` is only configured at construction time using `properties.web().baseUrl()`, and the resulting URL is **opened to open-redirect via the `RedirectStrategy` defaults if `properties.web().baseUrl()` is ever externally controlled** (LOW risk in this deployment, but the absolute URL pattern is fragile — see WR-04).
3. `ConnectGmailController.connect` performs a **server-side relative redirect to `/oauth2/authorization/google?reconnect=true` on a `POST` without any CSRF token verification** — the controller path matches `/tenant/**` which is `authenticated()` in `SecurityConfig`, but the path is **not** in the `csrf().ignoringRequestMatchers(...)` list, yet the controller is reachable via `<form method="post">` from the same-origin frontend and Spring Security 7 cookie-CSRF is configured globally. This appears intended but the controller does **no `@PreAuthorize` / tenant binding check**, so any authenticated user can trigger Google OAuth re-consent for the current session, and the `?reconnect=true` query param is **not validated by an idempotency / CSRF nonce** (see CR-03 below — the CSRF protection is present, but the controller has a separate authentication-bypass / cross-user-trigger sub-issue).
4. `GoogleOAuthSuccessHandler` rebuilds the **`gmailScopes` audit string from `client.getAccessToken().getScopes()`** before checking the null-refresh-token branch, but `client.getAccessToken()` is dereferenced unconditionally on lines 106, 112 — and the scope check on line 85 only short-circuits when `client == null || client.getAccessToken() == null`. **If `client != null` but `client.getAccessToken().getScopes()` is empty (e.g., test stub or real-world malformed grant)**, the handler proceeds past the gmail.modify guard logically but stores an empty-string `gmailScopes` audit value AND triggers `oauth_settings_basic_missing` warning. Bug is small but contradicts the "all-or-nothing" doc.

Plus seven warnings (atomicity invariant gap, dead-code retention, module-boundary violations, design-system drift) and four info items.

The `cache()` HIGH-2 fix in `me.ts` is correctly implemented (primitive string key), but **the test file does NOT actually verify that `cache()` keys by primitive value** — it self-admits this in its comments and uses `expect(mockFetch.mock.calls.length).toBeGreaterThanOrEqual(1)` which would pass even if dedupe were completely broken (see WR-03). A "manual gate" deferred to a dev walkthrough is **not equivalent to a regression test** for a HIGH-priority review fix.

i18n parity, Liquibase 008/009 idempotency, and privacy-logging discipline are clean.

## Critical Issues

### CR-01: `provisionBundledOAuth` race-loser branch opens a *second* transaction after the first rolled back — atomicity invariant violated

**File:** `backend/core/src/main/java/com/zeromail/core/account/service/OAuthProvisioningService.java:148-163`

**Issue:** The HIGH-1 fix advertises that the entire bundled provisioning runs inside ONE `bundledTx` (PROPAGATION_REQUIRED) so any failure rolls back the whole user+tenant+gmail-connection write. But on `DataIntegrityViolationException` (the duplicate-Google-subject race window between the `findByGoogleSubject` re-read on line 100 and the `users.save` on line 137), the catch block on lines 148-163 **opens a brand-new `bundledTx.executeWithoutResult` block** to upsert the gmail connection under the race-winner's tenant. That second tx is **NOT atomic with the first**:

- The first transaction (lines 134-145) did `tenantService.createTenant(tenantId, ...)` + `users.save(...)`, then hit a unique-constraint violation on `google_subject` and rolled back. Good.
- The catch block then runs `bundledTx.executeWithoutResult(_ -> { ... connections.upsert(winnerTenant, ...) })` which **commits independently**.
- If the second tx fails (e.g., cipher throws, DB connection drops, Hibernate persistence error mid-save), the race-loser ends up with: race-winner's user row already present (from the parallel race-winner thread that committed), **but no gmail connection envelope under the winner tenant** — exactly the half-provisioned state HIGH-1 was supposed to eliminate.
- Worse: this branch silently *succeeds* the OAuth login from the race-loser thread's perspective (returns `BundledProvisioningResult` with `firstLogin=false`), so the success handler runs `super.onAuthenticationSuccess(...)` and the user is redirected to `/onboarding` while their refresh-token envelope is missing. The next Gmail API call fails opaquely.

**Fix:** Either remove the race-loser upsert branch entirely (the race-winner's thread already wrote the gmail connection envelope, and re-writing it under a different refresh token is a privacy/audit issue anyway since you'd be overwriting the winner's envelope), or guard it with a `connections.findByTenantId(winnerTenant)` check that no-ops when the winner already wrote one. The simplest correct shape:

```java
} catch (DataIntegrityViolationException race) {
    log.warn("event=oauth_provisioning_race");
    UserEntity racedWinner = users.findByGoogleSubject(googleSubject)
            .orElseThrow(() -> race);
    // Race-loser: do NOT overwrite the winner's gmail connection envelope.
    // The winner's thread already committed its own atomic user+tenant+connection
    // in its own bundledTx — that is the correct, complete state.
    return new BundledProvisioningResult(racedWinner.getTenantId(), racedWinner.getId(), false);
}
```

This preserves the HIGH-1 atomicity contract: every successful provisioning path is exactly one committed bundled transaction, and the race-loser observes the winner's already-complete state without opening a second tx.

### CR-02: `GoogleOAuthSuccessHandler` dereferences `client.getAccessToken()` unconditionally on lines 106, 112 after the null-refresh-token branch — NPE / partial provisioning still possible

**File:** `backend/api/src/main/java/com/zeromail/api/security/GoogleOAuthSuccessHandler.java:85-115`

**Issue:** The all-or-nothing comment block (lines 36-48) promises: "If `gmail.modify` is absent from granted scopes → throw `OAuth2AuthenticationException` BEFORE any DB write." The runtime guard on lines 85-90:

```java
if (client == null || client.getAccessToken() == null
        || !client.getAccessToken().getScopes().contains(OAuthScopes.GMAIL_MODIFY)) {
    throw new OAuth2AuthenticationException(...);
}
```

This correctly catches three failure modes. But after the null-refresh-token branch (lines 93-103) which only `throw`s on `!existingUser`, the code reaches lines 105-115 with `client` and `client.getAccessToken()` both definitely non-null (the throw on line 87-90 guarantees this), so this is actually fine for NPE.

**However**, the bug is more subtle: the null-refresh-token branch does **not break `ScopedValue.where(...)` semantics from a user-already-existed reconnect path**. If `existingUser == true` and `refreshToken == null`, control falls through to line 105 with `refreshToken = null`, then line 124 calls `provisioning.provisionBundledOAuth(googleSubject, email, null /* refreshToken */, gmailScopes)`. Inside `provisionBundledOAuth`, the existing-user branch (lines 101-109) handles null correctly with the warn log. **That part is fine.**

The real defect: **the success handler does not call `removeAuthorizedClient` after throwing `OAuth2AuthenticationException("gmail_scope_required")` on line 87-90.** That cleanup is delegated to `LoginRedirectAuthenticationFailureHandler.onAuthenticationFailure` which does a best-effort `removeAuthorizedClient`. But Spring Security stores the partial OAuth2AuthorizedClient **before** the success handler runs (in the OAuth2 authorization-code response handler, prior to `onAuthenticationSuccess`). The throw bubbles up through the filter chain, but `OAuth2AuthorizedClientService` may have already persisted the partial token with insufficient scopes. The failure handler tries to clean it up, but uses `req.getUserPrincipal().getName()` — which is **null** at failure time because authentication has not been committed to the security context yet (the success handler threw before `super.onAuthenticationSuccess(...)` registered the principal). So `currentPrincipalName(req)` returns `"anonymous"`, `removeAuthorizedClient("google", "anonymous")` no-ops, and the **partial AuthorizedClient with insufficient scopes lingers in the JDBC-backed `OAuth2AuthorizedClientService` table** (depending on the configured store — the default is in-memory which evicts on restart, but if Phase 6 swaps to JDBC store this leaks).

**Fix:** In `GoogleOAuthSuccessHandler.onAuthenticationSuccess`, before throwing on line 87-90, explicitly `authorizedClients.removeAuthorizedClient("google", token.getName())` so the cleanup uses the correct principal name. Same fix for the null-refresh-token first-login throw on line 98-101:

```java
if (client == null || client.getAccessToken() == null
        || !client.getAccessToken().getScopes().contains(OAuthScopes.GMAIL_MODIFY)) {
    // Clean up partial AuthorizedClient under the correct principal name (not "anonymous").
    if (client != null) {
        try { authorizedClients.removeAuthorizedClient("google", token.getName()); }
        catch (Exception ignored) { /* best-effort */ }
    }
    throw new OAuth2AuthenticationException(
            new OAuth2Error("gmail_scope_required", "...", null));
}
```

The failure handler's best-effort cleanup is then a defense-in-depth backstop, not the primary cleanup.

### CR-03: `ConnectGmailController.connect` is a `POST` endpoint that triggers a redirect to a third-party OAuth flow without verifying the request originated from a CSRF-protected form — open-redirect / cross-user OAuth-trigger surface

**File:** `backend/api/src/main/java/com/zeromail/api/controllers/ConnectGmailController.java:13-18`

**Issue:** The controller method `@PostMapping("/tenant/connect-gmail")` has no `@PreAuthorize` and no explicit CSRF check. Spring Security's global `CookieCsrfTokenRepository.withHttpOnlyFalse()` is configured in `SecurityConfig`, and `/tenant/connect-gmail` is **not** in the `ignoringRequestMatchers(...)` list, so by default Spring Security 7 SHOULD enforce CSRF on this POST. However:

1. The path is under `anyRequest().authenticated()`, so an authenticated session cookie is required. Good.
2. The form on `apps/web/app/(protected)/settings/page.tsx:95` uses `<form method="post" action={getApiUrl('/tenant/connect-gmail')}>` — a plain HTML form that does **NOT** include `X-XSRF-TOKEN` header (HTML forms cannot set custom headers). Spring's cookie-CSRF expects either an `X-XSRF-TOKEN` header OR a `_csrf` body field that matches the cookie. The form has neither.
3. Result: **the POST will be rejected by Spring Security CSRF filter at runtime with a 403** in production. Either the form is broken (CSRF blocks it) — UX regression — or the developer added `/tenant/connect-gmail` to the CSRF-ignore list elsewhere and that's missing from the file under review (I see only `/login/oauth2/code/**` and `/oauth2/callback/**` in the ignore list on line 34).
4. **If the developer plans to add `/tenant/connect-gmail` to the CSRF-ignore list to make the form work**, then the POST becomes a CSRF-attackable surface that can trigger a Google OAuth redirect for any logged-in user when they visit an attacker-controlled page (impact: forced re-consent flow, possible refresh-token rotation under attacker observation if the OAuth callback is somehow proxied — low practical risk but a legitimate CSRF defect).

**Fix:** Pick one:

**Option A (recommended):** Replace the HTML form with a client-side `fetch` that includes the CSRF token from the `XSRF-TOKEN` cookie:

```tsx
// settings/page.tsx
<button type="button" onClick={async () => {
  const csrf = document.cookie.match(/XSRF-TOKEN=([^;]+)/)?.[1];
  await fetch(getApiUrl('/tenant/connect-gmail'), {
    method: 'POST',
    headers: csrf ? { 'X-XSRF-TOKEN': decodeURIComponent(csrf) } : {},
    credentials: 'include',
  });
  // Then read Location header or redirect...
}}>...</button>
```

Or use a server action / route handler that injects the CSRF body field.

**Option B:** Make `/tenant/connect-gmail` a `GET` (idempotent redirect to `/oauth2/authorization/google?reconnect=true` is a safe-method operation since the actual OAuth state-machine and refresh-token mutation happens on the callback, which is already CSRF-exempt by design). Replace the form with `<a href={...}>` styled as a button, just like the `Sign in with Google` link on the login page. This is the inbox-zero-style pattern.

**Option C (NOT recommended):** add `/tenant/connect-gmail` to `ignoringRequestMatchers`. This creates the CSRF hole described above.

### CR-04: `backend/api/build.gradle.kts:18` violates locked stack constraint — `spring-cloud-gcp-starter-secretmanager` re-introduced contrary to CLAUDE.md

**File:** `backend/api/build.gradle.kts:18`

**Issue:** Line 18 declares:

```kotlin
implementation("com.google.cloud:spring-cloud-gcp-starter-secretmanager")
```

CLAUDE.md (the file under review in this phase, lines 39 + 76) explicitly locks: **"No GCP hosting baseline — do not add `spring-cloud-gcp` starters by default."** The phase 01.5 plan/REVIEWS audit (HIGH-6) explicitly identifies this conflict and the Plan 05 cleanup sweep is supposed to align everything to "deployment secret source resolution" with VPS-generic language. But the actual build dependency was **not** removed — only doc text in STATE.md was updated.

This is a stack-constraint defect: CI/CD will pull spring-cloud-gcp + Google Cloud transitive deps (auth library, gRPC, conscrypt, ~30+ MB of jars), even on a VPS deployment that has no GCP credentials and never resolves an `sm://` URI. `application.yml:73` references `sm://oauth-refresh-token-key-v1/versions/1:` as a default fallback — that placeholder will fail to resolve at boot in any environment that doesn't have GCP application-default credentials, and the only thing keeping it from blowing up is `${REFRESH_TOKEN_KEY_BASE64:${sm://...}}` env-var fallback. In practice this means the GCP starter is **dead code** in the VPS deployment but still:

1. Increases container image size (~30 MB).
2. Adds CVE/SBOM surface (transitive dependencies on grpc, opencensus, etc.).
3. Contradicts the stack lock and confuses future contributors.
4. Logs warnings at boot if `spring.cloud.gcp.secretmanager.enabled=false` is unset (the application.yml line 56-58 sets this conditionally, but the starter still tries to bootstrap GCP credential auto-detection).

**Fix:** Remove line 18 from `backend/api/build.gradle.kts`. Remove the `sm://` fallback from `application.yml:73` and require `REFRESH_TOKEN_KEY_BASE64` to be supplied unconditionally by the VPS deployment secret source (Docker secret, systemd credential, env file). Remove `spring.cloud.gcp.secretmanager.enabled` from `application.yml` since the starter is gone. Optionally add a `prod` profile that fails fast if `REFRESH_TOKEN_KEY_BASE64` is missing.

If you decide to keep the GCP starter as a deferred future option, **document that decision explicitly in CLAUDE.md** (override the "No GCP hosting baseline" line) and remove the conflicting language. Right now the codebase says one thing in CLAUDE.md and ships another in build.gradle.kts.

### WR-03: `me-cache-dedupe.test.ts` does not actually verify primitive-string dedupe — HIGH-2 fix has no regression test

**File:** `apps/web/__tests__/features/account/me-cache-dedupe.test.ts:80-83, 154-158`

**Issue:** The test file self-admits that React `cache()` is RSC-context-only and won't dedupe in vitest/jsdom. Both Test 1 and Test 4 assert:

```ts
expect(mockFetch.mock.calls.length).toBeGreaterThanOrEqual(1);
```

This assertion **passes whether dedupe works or not** (1 call, 2 calls, 100 calls all satisfy `>=1`). The test is therefore tautological for the HIGH-2 fix it's meant to lock down. The "manual gate via `pnpm dev` walkthrough" is not a regression test — there is nothing in CI that will fail if a future refactor breaks the primitive-string keying (e.g., reverting to an options-object arg shape).

**Fix:** Replace the manual-gate dependency with a real assertion that catches the bug. Three viable approaches:

**Option A — assert the function signature itself:**
```ts
it('getCurrentUserCached takes a primitive string (not an options object)', () => {
  // TypeScript type check: passing an object should fail to compile.
  // Runtime check: the function arity is 1 and the param is a string.
  expect(getCurrentUserCached.length).toBe(1);
  // @ts-expect-error - object args must NOT type-check (compile-time guarantee)
  getCurrentUserCached({ headers: { cookie: 'x' } });
});
```

**Option B — mock React's `cache` to a Map-based cache and verify hit:**
```ts
vi.mock('react', async () => {
  const real = await vi.importActual<typeof import('react')>('react');
  const memo = new Map();
  return {
    ...real,
    cache: <T extends (...args: any[]) => any>(fn: T) =>
      ((...args: any[]) => {
        const key = args[0]; // primitive string
        if (!memo.has(key)) memo.set(key, fn(...args));
        return memo.get(key);
      }) as T,
  };
});
// Then assert: same string → same Promise; mockFetch called once.
```

This proves the primitive-key contract because the Map-based mock keys by `Object.is`, which gives value equality for strings and reference equality for objects. If a regression passes an object, the test fails.

**Option C — verify via dynamic-source-string check:**
```ts
import { readFileSync } from 'node:fs';
const meSrc = readFileSync(resolve(__dirname, '../../../features/account/api/me.ts'), 'utf8');
expect(meSrc).toMatch(/cache\(\s*async\s*\(\s*cookieHeader:\s*string/);
expect(meSrc).not.toMatch(/cache\(\s*async\s*\(\s*opts/);  // regression guard
```

Pick the strongest option for your risk tolerance. As-shipped, the test gives false confidence.

### WR-04: `GoogleOAuthSuccessHandler` builds default target URL at construction time using `properties.web().baseUrl()` without validation — open-redirect surface if config is ever externally controlled

**File:** `backend/api/src/main/java/com/zeromail/api/security/GoogleOAuthSuccessHandler.java:70`

**Issue:**

```java
setDefaultTargetUrl(stripTrailingSlash(properties.web().baseUrl().toString()) + "/onboarding");
```

`ZeroMailApiProperties.web().baseUrl()` is a `URI` populated from `${ZEROMAIL_WEB_BASE_URL:http://localhost:3000}` at boot (application.yml:61). On a single-VPS deployment this is operator-controlled, so risk is LOW. But:

1. `SimpleUrlAuthenticationSuccessHandler` accepts ANY absolute URL, including external domains. If `ZEROMAIL_WEB_BASE_URL` is ever sourced from a less-trusted location (a multi-tenant deployment env var, a CI matrix job, a test fixture leaking into prod), this becomes an open-redirect on the OAuth callback.
2. The handler does no scheme/host whitelist check.
3. `LoginRedirectAuthenticationFailureHandler:51` has the identical pattern.

**Fix:** Either (a) hard-code the relative path `setDefaultTargetUrl("/onboarding")` and let Spring's redirect strategy resolve against the request's own host (avoids absolute URLs entirely), OR (b) validate at startup that `properties.web().baseUrl()` matches a configured allowlist (`http://localhost:3000`, `https://zeromail.app`, etc.). Option (a) is simpler and more correct for a same-origin deployment.

### WR-05: `RedirectStrategy` redirect to login uses `loginUrl + "?error=consent_denied"` string concat — query-string injection if `loginUrl` ever contains `?`

**File:** `backend/api/src/main/java/com/zeromail/api/security/LoginRedirectAuthenticationFailureHandler.java:51, 61, 73`

### WR-06: `SecurityConfig` uses `@Profile("!test")` — bundled OAuth runtime path is NOT exercised under integration tests

**File:** `backend/api/src/main/java/com/zeromail/api/security/SecurityConfig.java:13`

**Issue:** `@Profile("!test")` means the `SecurityFilterChain` bean (with the bundled OAuth wiring) is NOT registered when the `test` profile is active. `BundledGoogleOAuthIntegrationTest` runs with `@ActiveProfiles("test")` (line 61), so it tests the success handler in isolation but never exercises the **wired filter chain** — the path from `OAuth2LoginAuthenticationFilter` → `successHandler` → `failureHandler` is mocked away. Specifically:

- Whether the `GoogleAuthorizationRequestResolver` is correctly injected into the OAuth2 authorization endpoint
- Whether the `failureHandler` is invoked when the success handler throws `OAuth2AuthenticationException`
- Whether CSRF + session management interact correctly with the OAuth flow

These are not covered. The integration test invokes `handler.onAuthenticationSuccess(...)` directly, bypassing the filter chain.

**Fix:** Either (a) add a separate `@SpringBootTest` integration test that uses the real (non-`!test`) security config and a `MockMvc` OAuth flow against a stubbed Google authorization server, OR (b) add a `test`-profile-specific `@Configuration` that registers the same SecurityFilterChain with test-suitable overrides (no real Google client, but real handler chain). Without this, the failure-handler redirect path (BLOCKER candidate territory: did the throw actually translate to `/login?error=...` or did it bubble out as a 500?) is never proven end-to-end.

### IN-01: `LoginPage` uses unsafe cast `tLogin as unknown as (key: string) => string` to bypass `next-intl` strict-type checking — type safety regression

**File:** `apps/web/app/(auth)/login/page.tsx:50`

**Issue:** The cast disables compile-time guarantees that the dynamic key (`error.${error}.title`) actually exists in the messages dictionary. If a future i18n key rename misses one of `consent_denied` or `gmail_scope_required`, TypeScript will not catch it; the page will silently render the literal key string. The closed-enum guard does protect against XSS but does NOT protect against missing-key regressions.

**Fix:** Replace the cast with an explicit static lookup table keyed by the `LoginErrorCode` literal type:

```ts
const ERROR_KEYS: Record<LoginErrorCode, { title: string; body: string }> = {
  consent_denied: {
    title: tLogin('error.consent_denied.title'),
    body: tLogin('error.consent_denied.body'),
  },
  gmail_scope_required: {
    title: tLogin('error.gmail_scope_required.title'),
    body: tLogin('error.gmail_scope_required.body'),
  },
};
// Then:
{isKnownError(error) && (
  <Alert variant="destructive">
    <AlertTitle>{ERROR_KEYS[error].title}</AlertTitle>
    <AlertDescription>{ERROR_KEYS[error].body}</AlertDescription>
  </Alert>
)}
```

This forces every `LoginErrorCode` member to have a corresponding key path at compile time — adding a new code without translations becomes a TypeScript error.

### IN-02: `OnboardingPage` uses `t(tpl.titleKey as never)` cast — same `next-intl` typed-key bypass

**File:** `apps/web/app/(protected)/onboarding/page.tsx:93,94`

**Issue:** `t(tpl.titleKey as never)` and `t(tpl.descKey as never)` defeat `next-intl`'s typed-message validation. Same reasoning as IN-01.

**Fix:** Build the templates list with a discriminated union of fully-qualified literal type keys, or push the i18n calls down into `TemplateCard` so each call site uses a static literal key.

### IN-03: `application.yml:73` `${REFRESH_TOKEN_KEY_BASE64:${sm://oauth-refresh-token-key-v1/versions/1:}}` placeholder syntax is fragile

**File:** `backend/api/src/main/resources/application.yml:73`

**Issue:** The nested placeholder fallback `${REFRESH_TOKEN_KEY_BASE64:${sm://...:}}` reads as: "use `REFRESH_TOKEN_KEY_BASE64` env var; if unset, resolve `sm://...:` (with empty default)." On a VPS deployment with no GCP credentials and no `REFRESH_TOKEN_KEY_BASE64`, this resolves to the empty string, and `RefreshTokenCipher` will then fail at boot with an opaque "invalid base64 / wrong key length" error rather than a clear "REFRESH_TOKEN_KEY_BASE64 is required" message.

**Fix:** Combined with CR-04, drop the `sm://` reference entirely and use:
```yaml
refresh-token-key-base64: ${REFRESH_TOKEN_KEY_BASE64:?REFRESH_TOKEN_KEY_BASE64 must be supplied via deployment secret source}
```
The `:?` syntax (Spring Boot ConfigData) makes startup fail with a clear error message if the var is unset.

### IN-04: Liquibase changeset 008 `rollback: empty` is correct but undocumented — operator handbook gap

**File:** `backend/core/src/main/resources/db/changelog/changes/008-cleanup-gmail-registration-data.yaml:20-21`

**Issue:** `rollback: empty` is the correct choice for a cleanup-of-orphaned-rows changeset (rolling back wouldn't restore the `google-gmail` registration anyway — it's gone from the code). But the comment block does not say "rollback intentionally empty because deleted rows reference a dead OAuth registration that no code path can re-create." A future operator running `liquibase rollback-count 2` will see a successful no-op and might assume the migration was reversible. Same applies to changeset 009.

**Fix:** Add a one-line comment under each `rollback: empty` block explaining the irreversibility intent. Example:

```yaml
rollback:
  # Intentional no-op: deleted rows referenced the deprecated 'google-gmail'
  # OAuth registration which no longer exists in the runtime ClientRegistrationRepository.
  # A logical rollback (re-inserting orphaned rows) would create dangling FK references.
  - empty
```

This is documentation hygiene, not a correctness bug.
