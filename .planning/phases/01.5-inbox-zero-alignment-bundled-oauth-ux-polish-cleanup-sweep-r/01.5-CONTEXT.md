## Phase Boundary

Phase 01.5 is the architectural pivot that absorbs three concerns left over from Phase 01.4 (closed without ship): (1) collapse the two-leg `google` + `google-gmail` OAuth architecture into a single bundled-scope `google` registration aligned with Inbox Zero's pattern, persisting the Gmail connection during user provisioning in the same transaction; (2) deflate the five wrapper primitives Phase 01.4 introduced (`PageShell`, `SectionCard`, `StatusAlert`, `EmptyState`, `LoadingState`) back to raw shadcn composition with token-aware `className` discipline; (3) close the surviving REVIEW.md cleanup items (TanStack-already-shipped via quick task `8qe`; remaining: `/me` fetch dedupe, `TemplateCard` ring color, `ReconnectPrompt` Alert variant, CLAUDE.md conventions promotion, deferred verification ceremonies documentation). Plus a polish pass: invoke the `frontend-design` skill across landing, login, onboarding, settings, and `ReconnectPrompt` to lift visual quality above the current Claude-default look without committing to final brand identity (Phase 5 owns that).

**In scope:**

*Backend — bundled OAuth collapse:*
- Single `google` OAuth2 client registration in `application.yml` requesting `openid profile email https://www.googleapis.com/auth/gmail.modify https://www.googleapis.com/auth/gmail.settings.basic` upfront. Remove the `google-gmail` registration entry and its provider/redirect-uri config.
- `GoogleOAuthSuccessHandler` extended to atomically (in same transaction as user provisioning) (a) read the granted scopes from the OAuth2AuthorizedClient access token, (b) verify all required Gmail scopes are present (all-or-nothing — see deny policy below), (c) encrypt the refresh token via existing `RefreshTokenCipher`, (d) call `GmailConnectionService.upsert(...)` to create/update the tenant's `GmailConnectionEntity`, (e) advance `users.onboarding_step` directly to `GMAIL_CONNECTED` (new entry state — see state machine simplification below).

Redirect to `/login?error=consent_denied` (full deny) or `/login?error=gmail_scope_required` (partial). No half-provisioned state ever lands in the DB.

Researcher to verify Spring Security 7's idiomatic dynamic-resolver pattern. `access_type=offline` and `include_granted_scopes=true` always set.

## Implementation Decisions

### A. Bundled OAuth collapse (Inbox Zero alignment)

- **D-A1:** Single `google` OAuth2 client registration with bundled scope list `openid profile email https://www.googleapis.com/auth/gmail.modify https://www.googleapis.com/auth/gmail.settings.basic`. Match Inbox Zero's bundle exactly — covers v1 (label/archive/save-draft via `gmail.modify`) plus future Phase 3 rules-engine label/filter management (via `gmail.settings.basic`). NO `gmail.send`, `gmail.compose`, `gmail.contacts.*`, calendar scopes — auto-send is forbidden by CLAUDE.md, contacts/calendar have no v1 use case. CASA review surface = 2 restricted scopes (Inbox Zero ships production with this exact set, so the verification-cost argument that justified the original 2-leg split is overweighted).

- **D-A2:** **All-or-nothing deny policy.** If the consent screen returns without `gmail.modify` granted (full `error=access_denied` OR partial un-check), the success handler MUST NOT persist any user/tenant/Gmail row. Redirect to `/login?error=consent_denied` (full deny) or `/login?error=gmail_scope_required` (partial). No half-provisioned state. Reasoning: Zero Mail is a Gmail-centric product — there is no "try without Gmail" valuable use case (CLAUDE.md core value). Inbox-zero parity. Avoids the race + DISCONNECTED-banner-on-fresh-account UX awkwardness.

- **D-A3:** **Full deletion of 2-leg flow code, no transitional aliases, no `@Deprecated`.** Pre-release, no clients depend on the public Java surface. DELETE: `GmailOAuthSuccessHandler`, `GmailOAuthFailureHandler`, `GmailIdentityMismatchException`, `GoogleTokenRevocationClient`, `OAuth2LoginDispatchingSuccessHandler`, `OAuth2LoginDispatchingFailureHandler`, related test fixtures (`MockGoogleRevocationServer`), error codes (`gmail.identity.mismatch`, `gmail.consent.denied`), and frontend i18n keys/UI mismatch-error rendering on `/onboarding`. Add new login-side error codes: `auth.consent_denied`, `auth.gmail_scope_required` plus matching i18n keys. Aligns with the user's persistent feedback memory: "avoid backwards-compatibility hacks ... if you are certain that something is unused, you can delete it completely".

- **D-A4:** **Liquibase 008 cleanup changelog** issues `DELETE FROM oauth2_authorized_client WHERE client_registration_id='google-gmail'` to remove stale dev-DB rows. Idempotent (no-op on clean DB), safe on populated DB. Pre-launch DB state is dev-only — no preservation concern. The `oauth2_authorized_client` schema itself stays (Spring Security still uses it for the single `google` registration).

- **D-A5:** **Reconnect entry stays at `/tenant/connect-gmail`** (URL preserved for `ReconnectPrompt` and future user-initiated reconnect actions), but the endpoint's behavior changes: it 302-redirects to `/oauth2/authorization/google` with a `prompt=consent` signal that `GmailScopeRequestResolver` (now generalized) reads dynamically. **First-time login** from `/login` → direct `/oauth2/authorization/google` link, NO `prompt=consent` (smooth UX). **Reconnect** → through `/tenant/connect-gmail` → with `prompt=consent`. Researcher must verify the Spring Security 7 idiomatic pattern for runtime resolver branching (session attribute, query param, or distinct authorization URL); planner picks one. `access_type=offline` and `include_granted_scopes=true` stay always-on.

### B. Onboarding state machine simplification

- **D-B1:** **`OnboardingStep.SIGNED_IN` is dropped.** New enum: `GMAIL_CONNECTED(10) → TEMPLATE_SELECTED(20) → COMPLETE(30)`. After collapse, login + Gmail connection happen atomically — `SIGNED_IN` would only ever exist as a transient state never persisted, which makes the enum harder to reason about. Liquibase changeset `009-drop-signed-in-onboarding-step.yaml` updates any existing `onboarding_step='SIGNED_IN'` rows to `'GMAIL_CONNECTED'` (pre-launch, dev-only data, no preservation concern). Enum name `GMAIL_CONNECTED` retained (still semantically accurate as entry state — user has both signed in and Gmail granted).

- **D-B2:** **GMAIL_CONNECTED is the post-provisioning entry state.** `GoogleOAuthSuccessHandler` advances `users.onboarding_step` directly to `GMAIL_CONNECTED` after persisting the user + tenant + GmailConnectionEntity. The `/onboarding` page renders the template-selection UI (existing `step === 'GMAIL_CONNECTED'` block) immediately. The Phase 01.4 `step === 'SIGNED_IN'` block (rendering "Connect Gmail" button + form) is DELETED. The mismatch-error `<StatusAlert>` block is also DELETED (the mismatch flow no longer exists post-collapse).

- **D-B3:** **`/login` error rendering uses RSC `searchParams` prop + raw shadcn `<Alert>`.** Login page stays an `async` RSC; reads `searchParams: Promise<{error?: string}>` per Next.js 16 RSC convention. When `error === 'consent_denied'` or `'gmail_scope_required'`, render `<Alert variant="destructive">` above the existing Card with `auth.login.error.{code}.{title,body}` keys. No client-component conversion. No CTA prop — user clicks the existing "Sign in with Google" button to retry. Researcher to verify the Next.js 16 `searchParams` async-prop signature in case it differs from prior versions.

- **D-B4:** **Onboarding monotonic-forward invariant preserved.** A user at `TEMPLATE_SELECTED` or `COMPLETE` whose Gmail connection later flips to DISCONNECTED (via `GmailAccessGuard`'s `invalid_grant` detection or external Gmail revocation) does NOT regress to `GMAIL_CONNECTED`. Onboarding step stays where it was; the app shows `ReconnectPrompt` based on `GmailConnectionStatus` instead. `OnboardingStep` and `GmailConnectionStatus` remain orthogonal axes (Phase 01.2 invariant preserved).

## Specific Ideas

- **One bundle, one transaction, one place.** The bundled OAuth flow MUST persist user + tenant + GmailConnectionEntity atomically in a single transaction inside the success handler (or its delegated service). Do NOT split into post-login event listeners or background jobs — that re-introduces the half-provisioned-state risk the all-or-nothing policy explicitly avoids.
- **`gmail.settings.basic` is in v1 even though no v1 feature uses it.** Future-proofs Phase 3 rules engine (label/filter management) without forcing users to re-grant later. Bundling now matches inbox-zero's production pattern verbatim.
- **All-or-nothing means user/tenant rows do NOT exist on consent fail.** Even if the OIDC portion succeeds (user has openid+profile+email granted), if `gmail.modify` is missing — no DB write happens. Researcher should confirm Spring Security 7's success handler can short-circuit via `OAuth2AuthorizationException` or similar before the default token-storage step writes the AuthorizedClient. Worst case: store AuthorizedClient (Spring's default), then handler verifies + deletes if scope missing — verify the cleanest path.
- **Reconnect = same registration, signal-only difference.** Do NOT add a second `google` registration variant. The runtime resolver branch is the entire reconnect machinery.
- **`prompt=consent` is OFF for first-time login.** Smooth UX: user sees Google account chooser + scope-list once, signs in, lands in app with template selector. Forcing `prompt=consent` on every login is friction for no benefit (refresh tokens are issued on first grant anyway when `access_type=offline` is set).
- **Five primitives die, no exceptions.** Even `EmptyState` and `LoadingState` deflate. If a third consumer surfaces in a later phase, primitives can re-emerge — but not before. Rule of three is the gate.
- **Polish ≠ brand finalize.** The `frontend-design` skill output is applied within the existing token taxonomy. Logo, palette finalize, font pairings, illustrations all stay Phase 5. Polish goal: surfaces look distinctive and professional, not generic — but not yet brand-locked.
- **`/login` error rendering stays RSC.** Don't `'use client'` just to use `useSearchParams`. Next.js 16's RSC `searchParams` prop covers it; no client-state needed for a static error message.
- **CLAUDE.md Conventions promotion is documentation-only.** Do not refactor any code in 01.5 specifically to enforce the four conventions (the codebase already follows them; promotion just makes them explicit). If the polish pass surfaces a violation, fix it; otherwise no separate enforcement task.
- **Deferred ceremonies live in STATE.md, not CLAUDE.md.** They're phase-bound (Phase 2A, 2C, 6) — STATE.md blockers section is the right home. CLAUDE.md is project invariants only.
- **Privacy invariants from Phase 1 D-E1 still rule the bundled flow.** Login-error logging emits opaque event names (`event=login_consent_denied`) with no email / subject / token contents. Even though no tenant exists yet at error-redirect time, log discipline applies.
- **No new shadcn primitives beyond the `warning` variant edit.** Toast, Sheet, Tabs, DropdownMenu, Popover, Command-Palette stay deferred. The polish pass uses what's already in `components/ui/`.
- **ReconnectPrompt is in the polish list AND the deflation list.** Sequencing: deflation refactor lands first (raw `<Alert variant="warning">`), polish pass lifts visual quality on top. Same plan, two passes within the same change set is fine — or split by surface in one plan if cleaner.
