# Cross-AI Plan Review — Phase 01.5

## Codex Review

## Summary

The plans are detailed and mostly coherent, with strong traceability back to Phase 1.5 decisions. They likely achieve the broad phase goals, but I see two material correctness risks: Plan 01 does not actually guarantee one transaction for user + tenant + Gmail connection, and Plan 03’s React `cache()` design probably will not dedupe reliably because it keys on object identity. Fix those before execution.

## Strengths

- Clear phase slicing: backend OAuth collapse, frontend deflation, `/me` dedupe, polish, docs.
- Good deletion discipline: no deprecated aliases for the old two-leg OAuth flow.
- Strong privacy emphasis: opaque event logs, no token/email/subject logging.
- Good test intent around OAuth resolver behavior, failure redirects, i18n parity, and frontend wrapper deletion.
- Frontend plan correctly keeps `/login` as an RSC and uses closed-enum query-param handling.
- Documentation plan cleanly separates project conventions from deferred phase ceremonies.

## Concerns

- **HIGH: Plan 01 atomicity gap.** `OAuthProvisioningService.findOrCreateGoogleUser(...)` is described as `REQUIRES_NEW`, then Gmail connection upsert happens in a second transaction. That is not “user + tenant + GmailConnectionEntity atomically in one transaction.” If encryption/upsert/user-save fails after provisioning commits, half-provisioned rows remain.

- **HIGH: Plan 01 only checks `gmail.modify`.** Context says all required Gmail scopes must be present. Since `gmail.settings.basic` is bundled, the success handler should probably require both Gmail scopes or explicitly document that only `gmail.modify` is required for v1.

- **HIGH: Plan 03 cache key design is weak.** React `cache()` keys by argument identity, not semantic equality. Multiple RSC callers passing separate `{ headers: { cookie } }` objects will not dedupe. The test even relies on the same object reference, which does not prove the target behavior.

- **MEDIUM: Refresh token null path is missing.** Google may not return a refresh token on repeat auth flows. `client.getRefreshToken().getTokenValue()` can fail after provisioning unless guarded. This should be checked before any DB write or handled for existing connected users.

- **MEDIUM: Plan 02 dependency should include Plan 01.** It removes `SIGNED_IN` UI and mismatch flows while backend Plan 01 owns the corresponding enum and OAuth behavior. Landing Plan 02 before Plan 01 creates an inconsistent app boundary.

- **MEDIUM: frontend-design requirement is weakened in Plan 02.** Context says invoke the skill before authoring/refactoring JSX. Plan 02 says “not required” for Task 1 and “SHOULD” for Task 2. Either make this a hard requirement or explicitly scope it only to Plan 04.

- **MEDIUM: Plan 05 conflicts with current VPS/no-GCP baseline.** The STATE.md blocker text hard-codes `spring-cloud-gcp-secretmanager` and `sm://...`, while project stack says no GCP baseline and secrets come from VPS deployment mechanisms. That should be generalized unless GCP Secret Manager is now a locked future decision.

- **LOW: i18n deletion checks are string-grep fragile.** Nested JSON keys may survive while dotted grep returns 0. Use the existing `i18n:check` plus a small structured assertion if possible.

## Suggestions

- For Plan 01, introduce a single transactional service method for bundled provisioning, or refactor `OAuthProvisioningService` so user, tenant, Gmail connection, and onboarding advancement commit or roll back together.

- Add tests for:
  - missing `gmail.settings.basic`;
  - null refresh token;
  - existing user at `TEMPLATE_SELECTED` or `COMPLETE` does not regress to `GMAIL_CONNECTED`;
  - AuthorizedClient cleanup uses the actual OAuth principal name, not a guessed request principal.

- For Plan 03, normalize the cache key to primitives:
  - `cache(async (cookieHeader: string | undefined) => fetchCurrentUser({ headers: cookieHeader ? { cookie: cookieHeader } : undefined }))`
  - Keep raw `fetchCurrentUser` available for client React Query hooks if `me.ts` is imported client-side.

- Make Plan 02 depend on `01.5-01`, or explicitly state both must merge only as a single wave boundary.

- For UI polish, add Playwright screenshot checks for desktop/mobile after manual walkthrough. Manual review is right, but screenshots catch layout regressions.

- In Plan 05, rewrite Secret Manager blockers as “deployment secret source resolution” unless the project explicitly pivots to GCP Secret Manager.

## Risk Assessment

**Overall risk: MEDIUM-HIGH.** The plans are thorough, but two implementation details threaten core success criteria: backend “atomic provisioning” is currently not atomic, and `/me` dedupe may not dedupe in real RSC call graphs. Once those are corrected, the remaining risk drops to MEDIUM, mostly from OAuth edge cases and UI execution quality.

## 01.5-01-PLAN.md

### 1) Summary
This is a strong backend pivot plan with good decomposition (resolver/failure/success handler, enum migration, dead-code deletion, tests, and Liquibase cleanup). It aligns well with the phase intent, but there is one major design risk: the current task wording may not actually guarantee *single-transaction atomicity* for user + tenant + Gmail connection, which is a core truth for this phase.

### 2) Strengths
- Clear all-or-nothing OAuth intent and explicit error mapping (`consent_denied`, `gmail_scope_required`).
- Good security posture: scope validation, opaque log events, best-effort authorized-client cleanup.
- Excellent cleanup discipline: deletes old 2-leg handlers + tests rather than aliasing.
- Good migration hygiene with idempotent Liquibase 008/009.
- Strong verification gates and grep checks for dead-reference removal.

### 3) Concerns
- **HIGH:** Atomicity gap risk: `findOrCreateGoogleUser(...)` (REQUIRES_NEW) + later Gmail upsert in separate transaction can still create partial state if second step fails.
- **HIGH:** `refreshToken` nullability not handled (`client.getRefreshToken()` can be null in real OAuth flows), possible NPE and inconsistent provisioning behavior.
- **MEDIUM:** `ConnectGmailController` method semantics are inconsistent across docs/tasks (POST in task details vs generic repurpose in context); frontend link/form behavior could mismatch.
- **MEDIUM:** Plan 01 and Plan 02 both in wave 1 with no dependency; frontend can remove `SIGNED_IN` before backend fully migrated.
- **LOW:** Failure handler cleanup relies on extracting principal from request; may fail in some exception paths (cleanup becomes best-effort no-op).

### 4) Suggestions
- Move to a truly atomic service method (single transaction) that provisions user/tenant + Gmail connection together; avoid cross-transaction stitching.
- Add explicit null refresh-token handling and deterministic redirect/error path.
- Lock `/tenant/connect-gmail` contract as either GET or POST in both backend and frontend plan text, then enforce with tests.
- Add `depends_on: [01.5-01]` to plan 02 (or deployment sequencing note) to avoid step mismatch.
- Add one integration test for “Gmail upsert fails after user creation attempt” to prove no partial state.

### 5) Risk Assessment
**Overall risk: MEDIUM-HIGH** due to atomicity and refresh-token edge cases, despite otherwise high plan quality.

## 01.5-03-PLAN.md

### 1) Summary
The `/me` dedupe objective is right, but the proposed `cache()` strategy has practical correctness risks. The tests emphasize same-reference options, which may not match real call behavior. This plan is the weakest of the set in terms of production confidence.

### 2) Strengths
- Good intent: dedupe within request without introducing cross-request staleness.
- Correctly preserves `cache: 'no-store'`.
- Explicitly protects `proxy.ts` invariant.
- Adds dedicated tests for dedupe behavior.

### 3) Concerns
- **HIGH:** `cache()` dedupe may not trigger for real callers if each call builds a fresh options object; tests overfit same-object-reference behavior.
- **MEDIUM:** `getCurrentUser` is used by both server and client paths; `react` `cache()` behavior can be awkward outside intended server render context.
- **MEDIUM:** “No call-site changes required” may be false if you want reliable dedupe.
- **LOW:** Test naming suggests request-level guarantee that implementation may not deliver.

### 4) Suggestions
- Prefer a server-only cached wrapper with stable scalar args, e.g. `getCurrentUserServer(cookieHeader?: string)` using `cache()`, and keep raw function for client/query usage.
- If keeping current API, normalize dedupe key to a string arg rather than object arg.
- Add one integration-style test around `app/layout.tsx` path to validate actual dedupe in the real call graph.

### 5) Risk Assessment
**Overall risk: MEDIUM-HIGH** unless caching contract is tightened.
