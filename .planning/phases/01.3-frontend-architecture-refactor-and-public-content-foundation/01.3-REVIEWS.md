## Codex Review (gpt-5.5 via 9router)

## Summary

The 8-plan sequence is strong in intent and has a good verification mindset, but it is not execution-ready. The biggest risks are not Next 16 fundamentals, which are mostly handled, but local-code mismatches: `Button asChild` does not match the existing Base UI button API, `features/account/api/me.ts` would pull a client-only error module into server/proxy code through `lib/api/client.ts`, and the plan only moves `/me` into feature API modules while ROADMAP #6 says endpoint-specific calls should move out of route pages. I would treat this as **MEDIUM-HIGH risk** until those gaps are fixed.

Docs sanity-checked via Context7 against Next.js, next-mdx-remote, Husky, and lint-staged docs.

## Strengths

- **Plan 01**: Good idea to create Wave 0 architecture tests before refactoring. The tests directly encode success criteria instead of relying only on human review.
- **Plan 02 / 03**: Correctly puts Husky/lint-staged/Prettier and workspace cleanup at the root. This matches the monorepo source-of-truth decision.
- **Plan 03**: Explicitly protects the `proxy.ts` `as unknown as` deviation after `pnpm install`; this is the right risk to verify early.
- **Plan 04**: Consolidating `/me` behind `getCurrentUser({ headers })` is directionally correct and enforces explicit cookie forwarding.
- **Plan 05 / 06**: Correctly accounts for Next 16 async `params` and avoids `<html>/<body>` in route-group layouts.
- **Plan 06**: MDX path traversal is addressed with a slug allow-list before `path.join`; `next-mdx-remote/rsc` usage aligns with current docs.
- **Plan 07**: Updating `EN_SCAN_FILES` is load-bearing and correctly called out rather than left as cleanup.
- **Plan 08**: The final gate covers automated checks plus manual UI/tooling smoke, which is appropriate for this kind of refactor.

## Concerns

- **HIGH — Plan 04 does not satisfy ROADMAP #6 fully.** `01.3-04-PLAN.md:370-373` only creates `/me` and `/me/language` feature APIs/hooks. Existing endpoint calls remain in route pages: `/tenant/status`, `/tenant/disconnect`, `/me/account`, `/onboarding/select-template`, `/onboarding/complete`. That conflicts with success criterion #6: endpoint-specific calls move into feature `api` modules.

- **HIGH — Server/proxy import path may pull client-only code.** `01.3-04-PLAN.md:126` imports `{ api }` from `@/lib/api/client`, but current `lib/api/client.ts` re-exports from `lib/api/errors.ts`, which has `"use client"` and imports next-intl hooks. Then `proxy.ts` and `app/layout.tsx` import `getCurrentUser` (`01.3-04-PLAN.md:424`, `:493`). This can break Next server/proxy bundling even if `tsc` passes.

- **HIGH — Plan 05 uses `Button asChild`, but local `Button` does not support that API.** The existing `apps/web/components/ui/button.tsx` wraps `@base-ui/react/button` and exposes Base UI props, not shadcn Radix-style `asChild`. `01.3-05-PLAN.md` landing code will likely type-fail or render incorrectly.

- **HIGH — Plan 05 moves login "verbatim" into an auth layout that also renders chrome.** Current `app/login/page.tsx` already renders `<main>` and `LanguageSwitcher`. `01.3-05-PLAN.md:151-153` adds another `<main>` and another `LanguageSwitcher` in `(auth)/layout.tsx`, while `:248` says the page is moved verbatim. Result: nested landmarks and duplicate switcher.

- **HIGH — Deleting `app/[locale]` needs runtime proof.** `01.3-05-PLAN.md:298-359` deletes the `[locale]` tree. Context7 next-intl docs still warn that `localePrefix: 'never'` setups may require pages under `[locale]` because middleware rewrites internally. The project context says the mirror tree is dead, but this is precisely where an e2e route smoke should be mandatory before deletion is accepted.

- **MEDIUM — Wave 0 MDX frontmatter test likely never un-skips.** In `01.3-01-PLAN.md:383`, `it.skipIf(!matter)` is evaluated when the test is defined, before `beforeAll` sets `matter`. Since `matter` starts undefined, that test will likely remain skipped forever.

- **MEDIUM — Plan command snippets are Bash-heavy in a PowerShell workspace.** Examples use `rm -rf`, escaped parentheses, `grep`, `cat | head`, and `rmdir` forms across Plans 03, 05, and 08. The environment says `shell=powershell`; these instructions need PowerShell equivalents or an explicit Git Bash requirement.

- **MEDIUM — lint-staged config has overlapping globs.** `01.3-02-PLAN.md:95-105` matches `apps/web/messages/*.json` and also `apps/web/**/*.{md,mdx,json,css}`. lint-staged can run overlapping tasks concurrently, so Prettier and `i18n:check` may race on message files.

- **MEDIUM — Public landing can triple-call `/me`.** Authenticated `/` can hit `/me` in `proxy.ts`, root layout, and landing CTA. Because fetches use `cache: 'no-store'`, request dedupe is unlikely. This is acceptable for scaffolding only if documented, but it is not cheap.

- **LOW — Plan 06 validates slug but not frontmatter consistency at runtime.** Tests validate sample files, but `[slug]/page.tsx` should also reject mismatched `frontmatter.slug` or `frontmatter.locale`.

- **LOW — Plan 08 manual hook tests create real commits.** `01.3-08-PLAN.md:183` and `:190` ask for actual commits with deliberate bad/test edits. That can pollute history unless done on a temp branch with explicit reset cleanup.

## Suggestions

- Split `lib/api/client.ts` into a server-safe API client module and a client-only error hook module, or remove the `errors.ts` re-export from the server import path before Plan 04. Then make `features/account/api/me.ts` import only server-safe code.

- Expand Plan 04 to move current route-page API calls into feature modules:
  - `features/gmail/api/status.ts`, `disconnect.ts`, hooks for status/disconnect.
  - `features/onboarding/api/selectTemplate.ts`, `complete.ts`, hooks for onboarding actions.
  - `features/account/api/deleteAccount.ts`.
  Refactor pages to call feature hooks/functions, not `api.GET/POST/DELETE` directly.

- Replace `Button asChild` usages with the local Base UI-compatible pattern, or use `buttonVariants` on `Link` directly if that is the established local pattern.

- In Plan 05, either make `(auth)/layout.tsx` a minimal wrapper and leave login page chrome alone, or remove `<main>`/`LanguageSwitcher` from the moved login page. Do not ship both.

- Before deleting `app/[locale]`, add an automated route smoke for `/`, `/login`, `/onboarding`, `/settings`, `/docs`, and `/docs/getting-started` under the actual Next dev/build runtime. Structural filesystem tests are not enough here.

- Fix the MDX frontmatter test by importing `gray-matter` inside the test body or using a static `existsSync(node_modules/gray-matter/package.json)` condition before defining `skipIf`.

- Convert all destructive/move/delete examples to PowerShell-safe commands, or explicitly state "run these in Git Bash" at the top of the plans.

- De-overlap lint-staged globs: exclude `apps/web/messages/*.json` from the generic JSON formatter path, or use a JS lint-staged config that serializes message formatting before `i18n:check`.

- Make Plan 08 manual commit tests use a temporary branch and reset instructions, or replace them with `pnpm exec lint-staged` staged-file tests where possible.

## Risk Assessment

**Overall risk: MEDIUM-HIGH.** The architecture direction is sound and the plan covers most Next 16 and security concerns, but several local implementation assumptions are wrong or under-verified. The server/client module boundary around `lib/api/client.ts`, the unsupported `Button asChild` API, incomplete feature API migration, and `[locale]` deletion risk are enough to block execution until revised.

## OpenCode Review (gpt-5.3-codex via GitHub Copilot)

## Summary

Overall, the 8-plan package is strong, unusually explicit, and mostly execution-ready: it maps well to all 7 Phase 1.3 success criteria, preserves key Phase 1.1 invariants, and has good guardrails for Next 16 quirks and the `proxy.ts` cast survival requirement. The biggest risk is **operational sequencing**: enabling strict pre-commit gates early (Plan 02) while knowingly introducing temporary i18n failures in Plans 05–06 can block intermediate commits unless the workflow tolerates non-green checkpoints. There are also a few over-prescriptive and potentially brittle assertions (literal string checks, byte-identical requirements) and minor security/perf hardening gaps around MDX frontmatter validation and docs file I/O strategy.

## Strengths

- **Excellent verification spine (Plan 01 + Plan 08):** creating Wave 0 tests first, then converging to green, gives clear objective closure criteria.
- **Strong invariant protection (Plans 03, 04, 08):** explicit checks for `localePrefix: 'never'`, `proxy.ts` `as unknown as` cast, and scanner coverage reduce regression risk.
- **Good architecture alignment (Plans 04–06):** route groups + feature folders + isomorphic API contract directly implement roadmap criteria #1, #2, #6, #7.
- **Next 16 awareness is explicit (Plans 05, 06):** async `params`, `proxy.ts` naming, and layout constraints are called out repeatedly.
- **Security-conscious docs path (Plan 06):** slug regex + `notFound()` handling + avoiding dangerous MDX overrides is the right baseline.
- **Workspace hygiene addressed concretely (Plan 03):** lockfile/workspace duplication cleanup is clear and test-backed.

## Concerns

- **HIGH — Commit pipeline deadlock risk due to ordering (Plan 02 vs Plans 05–06):**  
  Plan 02 turns on Husky + `i18n:check`, while Plans 05/06 explicitly acknowledge temporary missing translation keys and scanner drift until Plan 07. If commits are expected per plan, pre-commit can block progress.
- **MEDIUM — Overly rigid "literal/byte-identical" acceptance criteria (Plans 04, 05, 08):**  
  Requirements like byte-identical lines or exact regex/literal patterns can reject valid refactors and create false negatives.
- **MEDIUM — MDX frontmatter trust model too weak (Plan 06):**  
  Frontmatter is parsed and cast (`as Frontmatter`) without runtime schema validation; malformed content can cause undefined behavior in listing/rendering.
- **MEDIUM — `process.cwd()` assumption for docs content path (Plan 06):**  
  Using `process.cwd()/content/docs` may be fragile across CI/runtime launch contexts in monorepo deployments.
- **LOW — Potentially noisy lint-staged overlap (Plan 02):**  
  `apps/web/messages/*.json` also matches broader `apps/web/**/*.{md,mdx,json,css}` pattern, causing duplicate Prettier runs.
- **LOW — Scope creep/process overhead (Plans 01 + 08):**  
  Heavy test scaffolding and manual commit experiments are robust but somewhat over-engineered for a pure architecture refactor.
- **LOW — `generate:api` in final verification may create unrelated diff churn (Plan 08):**  
  Can dirty the tree with schema regen even when Phase 1.3 didn't intend API changes.

## Suggestions

- **Reorder or gate hooks to avoid deadlock:**  
  Either (a) move Husky `i18n:check` activation to Plan 07, or (b) keep Husky but make `i18n:check` non-blocking until Plan 07, then enforce.
- **Relax brittle acceptance checks:**  
  Replace "byte-identical/literal string must exist" with behavior-based checks (e.g., compilation + route smoke + import resolution + grep absence/presence where truly needed).
- **Add runtime validation for MDX frontmatter:**  
  Use a small schema (e.g., Zod) for `{title, slug, order, locale}` before use; fail closed to `notFound()` or skip invalid docs.
- **Harden docs path resolution:**  
  Prefer deterministic absolute resolution tied to module location (or a helper) instead of raw `process.cwd()` assumptions.
- **De-duplicate lint-staged globs:**  
  Exclude `messages/*.json` from the broader JSON matcher or narrow patterns to avoid double formatter invocations.
- **Avoid history-noisy manual commit/amend steps in Plan 08:**  
  Replace with a scripted dry-run hook invocation or disposable temporary branch/check.
- **For criterion #6, add one real typed-client usage assertion:**  
  Ensure at least one endpoint function type-checks directly against generated OpenAPI types, not only file presence.

## Risk Assessment

**Overall risk: MEDIUM**

Justification: The plan set is high quality and likely to succeed technically, with strong coverage for roadmap criteria and known Next 16 hazards. The main threat is execution friction from sequencing (early strict pre-commit vs intentionally temporary i18n breakage), plus a few brittle verification choices that can cause unnecessary failures. Address those, and risk drops to LOW.
