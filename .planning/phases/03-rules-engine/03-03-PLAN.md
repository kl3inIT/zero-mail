  <name>Task 1: Rule compiler and result validator</name>
  <read_first>
    - backend/core/src/main/java/com/zeromail/core/llm/service/LlmGateway.java
    - backend/core/src/main/java/com/zeromail/core/llm/model/RuleCompileGatewayResult.java
    - backend/core/src/main/java/com/zeromail/core/rules/model/MatcherNode.java
    - backend/core/src/main/java/com/zeromail/core/rules/model/ActionIntent.java
  </read_first>
  <action>
    Implement command/result records and `RuleCompilerService`.

    Required behavior:
    - Accept tenant id, source text, optional clarification answer, and optional prior compile context.
    - Build a sanitized compiler payload containing schema version, authored source text, language hint, allowed matcher/action ids, and clarification answer if present.
    - Call `LlmGateway.compileRule(CallSite.PREVIEW, compilerPayload)`.
    - Require `RuleCompileGatewayResult.toolName()` to be `rule_compile`.
    - Validate every returned field into typed rules-owned model records.
    - Detect language from source text for D-A2 using a deterministic service-owned heuristic first (`vi` when Vietnamese diacritics/common Vietnamese tokens are present, `en` when English dominates, `unknown` otherwise), then preserve/override with a safe model-provided language only if it is one of `en`, `vi`, `unknown`.
    - If the gateway marks output ambiguous or required slots are missing in a way one answer can resolve, return `RuleCompileResult.requiresClarification(RuleClarificationQuestion question)` with exactly one focused question and do not save.
    - `RuleClarificationQuestion` must be sanitized, max 240 characters, free of raw prompt/tool args, and in the detected source language where possible; unsafe or multi-question clarification payloads are rejected as invalid compile output.
    - Distinguish result states: `compiled`, `clarificationRequired`, and `invalid`. Validation errors are not rendered as clarification prompts.
    - Reject unknown matcher/action ids, unknown schema versions, unsafe actions, malformed or RE2J-unsupported regex, excessive string lengths, empty action list, and semantic nodes where `deferred != true`.

    Logs must be privacy-safe: `event=rule_compile_started tenantId={}` and outcome/reason metadata only. Do not log source text, prompt, completion, tool args, Gmail fields, or labels from user content.

    Addresses review concern: locks ambiguity/clarification semantics and validates the model-provided question instead of delegating UX safety to the LLM.
  </action>

  </verify>
  <acceptance_criteria>
    - Stripe receipt fixture compiles into deterministic matcher(s) plus `archive` and `label`.
    - Unsafe action fixtures (`send`, `forward`, `spam`, webhook, delayed action) are rejected.
    - Ambiguous fixture returns one safe clarification result and creates no row.
    - Malicious, overlong, or multi-question clarification payload is rejected.
    - English and Vietnamese source fixtures produce matching `RuleLanguage` and same-language clarification prompts where possible.
    - Mock gateway result with unknown node leaves no partial persistence.

  <action>
    Implement `RuleManagementService` with service-owned transactions:
    - list ordered rules for tenant.
    - get one rule by tenant and id, returning not found for cross-tenant ids.
    - create from validated compile result, always `enabled=false`, `lastPreviewedEntityVersion=null`, order index appended to tenant's list.
    - update source/compiled matcher/action state, increment Hibernate `version`, set `lastPreviewedEntityVersion=null`, set `lastPreviewedAt=null`, and set `enabled=false` so the edited version cannot remain enabled without a fresh preview.
    - mark template-derived rules customized only when `source_text` or compiled matcher/action state changes due to user edit/recompile. Enable/disable, preview, reorder, and delete do not set `customized=true`.
    - enable only when `lastPreviewedEntityVersion == entityVersion`.
    - disable immediately.
    - delete by tenant/id and normalize remaining order.
    - reorder by full ordered `RuleOrderEntry(ruleId, entityVersion)` list. Validate that the submitted set exactly equals the tenant's current non-deleted rule ids, every id belongs to the tenant, every submitted entity version matches the current row version, and then write contiguous `order_index` values in one transaction. Reject the entire reorder on any mismatch with no partial updates.
    - validate display name/source text as nonblank and bounded. Do not add display-name uniqueness in Phase 3 unless tests prove an existing project convention requires it.

    Use explicit parameter/local names. Do not use abbreviations such as `repo`, `svc`, `ctx`, or `ex`.

    Addresses review concern: locks preview-eligibility reset, customization semantics, and reorder concurrency instead of leaving implementation options open.
  </action>
