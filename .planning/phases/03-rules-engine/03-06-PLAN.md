    Implement `RuleTemplateMaterializationService`:
    - For tenant id, read selected template keys through `OnboardingService.selectedEnabledTemplateKeys(...)`.
    - For each known selected template key, create a disabled `RuleEntity` from the latest active catalog row if no rule with the same tenant/template key exists.
    - Rely on the Plan 01 partial unique index `(tenant_id, template_key) where template_key is not null` for concurrent first-read safety. If a concurrent insert loses the race with a unique constraint violation, retry/reload once inside the service and return the existing materialized rule as skipped, not failed.
    - Append created rules after existing rules in stable order.
    - Preserve `template_key`, `template_version`, and `customized=false`.
    - If a materialized rule was edited/customized, never overwrite it.
    - Unknown/deprecated selected template keys are skipped and included in `RuleTemplateMaterializationResult.skippedTemplates` as key + safe reason enum. Do not log or return user-authored content.
    - Return created/skipped/customized-preserved counts plus `skippedTemplates` for API observability.
    - Log only `event=rules_templates_materialized tenantId={} created={} skipped={} customizedPreserved={} skippedDeprecated={}`.

    Addresses review concern: locks race handling, unknown-key feedback, and template-version pinning.
