<objective>
Move the entire account domain into per-tier sub-packages (`service/` + `persistence/` + `model/`) under `com.zeromail.core.account.*` AND reshape `AccountService` to drop its 3 cross-domain repository injections (per D-D1 + CL-2). The shrunken `AccountService` exposes only `requireCurrentUser`, `updateCurrentUserLanguage`, and a new single-domain `deleteCurrentUser(UUID)` that deletes only the User row.

**Critical interim contract:** the existing `AccountDeletionController` calls `accountService.deleteCurrentTenantAccount(tenantId)`. Plan 06 will replace this with a 4-call orchestration. Between Plan 03 and Plan 06, the controller is wired to a TEMPORARY orchestration that keeps `AccountDeletionE2ETest` green by inlining the 3 not-yet-decomposed deletes (gmail + onboarding + tenant) into the controller as direct repository calls. This is acceptable ONLY because (a) it's a 3-plan transitional state, (b) the controller already lives in `backend/api` which transitively depends on every `core` module, (c) Plan 04 then 05 then 06 progressively replace each direct repo call with the proper domain service, and (d) every plan in this chain ends with `AccountDeletionE2ETest` green.

Purpose: This is the largest plan in Phase 1.2. The account domain holds the most decisions (CL-2 cascading-delete relocation, the AccountService reshape, the OAuthProvisioningService move with its `@Lazy` self-injection idiom, the CurrentUserView/Exception type relocations). Splitting it across two plans would force the AccountDeletionE2ETest to be either skipped or use mocks — both unacceptable per the byte-identical contract.

Output: 9 source files at new paths, 3 new package-info markers, AccountService reshaped with single-domain delete, AccountDeletionController on a transitional bridge, all import-side updates in MeController, two more entity-scan widenings (Application.java + CoreTestApplication.java).
</objective>
