## Summary

Restructuring sang `service/persistence/model/` per-domain layout là sạch và nhất quán: bốn `delete*` methods thực sự là single-domain (chỉ đụng repo của chính domain mình); `AccountDeletionController` orchestrate đúng FK-safe order (children → user → tenant); `@TenantId` filter binding vẫn intact qua `ScopedValueTenantResolver`; modulith `allowedDependencies` được khai báo rõ ràng và ăn khớp với cross-domain imports thực tế (đặc biệt `core.gmail` không có edge tới `account`, đúng D-D4); ArchUnit rules `DomainBoundaryArchTests` được expressed dưới dạng predicate composition nên thực sự fire khi vi phạm tái xuất hiện.

Tuy nhiên có 3 warnings cần cân nhắc:

1. `OnboardingStepEnumPersistenceTest` không round-trip qua Hibernate — chỉ test `enum.name()` thuần Java. Mô tả test claim "real persistence" nhưng coverage thực tế hẹp hơn. Pitfall 5 (column mapping drift từ `EnumType.STRING` → `EnumType.ORDINAL`, hoặc column type changes) sẽ KHÔNG được catch.
2. `UserEntity.advanceTo` dựa vào `ordinal()` để enforce forward-only invariant. Insert một enum constant ở giữa list (ví dụ giữa `SIGNED_IN` và `GMAIL_CONNECTED`) sẽ thay đổi ordinals và silently corrupt invariant cho users đã ở trạng thái cao hơn.
3. `OnboardingService.deleteSelectionsForCurrentTenant` gọi `deleteAll(findByTenantId(...))` — fetch-then-delete-each-row N+1, không phải bulk delete. V1 không phải issue do row count thấp, nhưng hành vi khác `bulk delete` về flush ordering nếu sau này entities thêm cascade.

Info findings là quality-of-life (return type, raw types, defensive null check, redundant filter) — không có security hay correctness gap.

Không có **critical**: không có injection, không có hardcoded secret, không có unsafe deserialization, không có missing tenant filter trên delete path, không có path traversal hay command exec, không có JWT bypass, refresh-token bound với tenantId qua AAD đúng anti-row-swap.

## Warnings

### WR-01: `OnboardingStepEnumPersistenceTest` không round-trip qua Hibernate

**File:** `backend/core/src/test/java/com/zeromail/core/onboarding/OnboardingStepEnumPersistenceTest.java:19-25`

**Issue:** Test class chỉ assert `OnboardingStep.X.name() == "X"` cho 4 constants — đây là tautology của Java enum (Enum#name() luôn trả tên constant) và sẽ pass cho dù `UserEntity#onboardingStep` được map `EnumType.STRING` HAY `EnumType.ORDINAL`. Đoạn Javadoc của test class claim "round-tripping `OnboardingStep` constants through real persistence" và phase context cũng nói "use real persistence (not mocked)", nhưng test KHÔNG load `UserEntity`, KHÔNG dùng `@DataJpaTest` / `EntityManager`, KHÔNG verify column kiểu varchar. Pitfall 5 (T-01.2-E) — ai đó vô tình đổi annotation từ `@Enumerated(EnumType.STRING)` sang `(EnumType.ORDINAL)` — sẽ KHÔNG fail test.

**Fix:** Thêm Spring `@DataJpaTest` (hoặc dùng `@SpringBootTest` đã có) để persist một `UserEntity` với mỗi `OnboardingStep` value, query lại từ DB, verify cả enum value VÀ raw column dạng string thông qua native query:

```java
@DataJpaTest
class OnboardingStepEnumPersistenceTest {
    @Autowired EntityManager em;
    @Autowired UserRepository users;

    @ParameterizedTest
    @EnumSource(OnboardingStep.class)
    void enumPersistsAsString(OnboardingStep step) {
        UUID tenantId = UUID.randomUUID();
        // bind tenant via ScopedValue.where(...).run(...)
        ScopedValue.where(TenantContext.TENANT, tenantId.toString()).run(() -> {
            UserEntity u = new UserEntity(UUID.randomUUID(), tenantId, "sub-" + step, "e@e");
            u.advanceTo(step);
            users.saveAndFlush(u);
            em.clear();
            String raw = (String) em.createNativeQuery(
                    "SELECT onboarding_step FROM users WHERE id = :id")
                    .setParameter("id", u.getId()).getSingleResult();
            assertThat(raw).isEqualTo(step.name());
        });
    }
}
```

Lưu ý: native SQL bị `TenantIsolationArchTests.no_native_sql` rule chặn ngoài `..persistence.lowlevel..`, nên test phải đặt query bridge ở package được allow, hoặc verify qua `JdbcTemplate` (rule chỉ check `EntityManager.createNativeQuery`).

### WR-02: `UserEntity.advanceTo` dùng `ordinal()` — fragile khi reorder enum

**File:** `backend/core/src/main/java/com/zeromail/core/account/persistence/UserEntity.java:62-67`

**Issue:** Forward-only invariant được enforce qua `next.ordinal() < this.onboardingStep.ordinal()`. Nếu sau này thêm một step ở giữa (ví dụ `OnboardingStep { SIGNED_IN, EMAIL_VERIFIED, GMAIL_CONNECTED, TEMPLATE_SELECTED, COMPLETE }`), ordinals của `GMAIL_CONNECTED`, `TEMPLATE_SELECTED`, `COMPLETE` đều shift +1. User đang ở `TEMPLATE_SELECTED` (đã persist `name="TEMPLATE_SELECTED"`, được Hibernate map về enum value mới với ordinal=3, từng là 2) — invariant vẫn correct vì ordinal compare trên cùng JVM enum class, NHƯNG: nếu một dev nghĩ "insert ở giữa nghĩa là 'thêm step trước GMAIL_CONNECTED'" và viết code khác giả định ordinal là stable, sẽ corrupt logic. Pitfall 5 ngầm: ordinal-based logic + `EnumType.STRING` persistence là một gotcha kinh điển.

Bằng chứng đây là rủi ro thực: `OnboardingStepEnumPersistenceTest` chỉ assert `name()`, không assert ordinal. Nếu reorder, persisted strings vẫn round-trip OK (vì `EnumType.STRING`) — nhưng `advanceTo(SIGNED_IN)` từ `EMAIL_VERIFIED` (mới ordinal=1) sẽ giờ là rejected (đúng), tuy nhiên trước reorder `EMAIL_VERIFIED` chưa tồn tại. Edge case real: nếu một step bị insert giữa **TEMPLATE_SELECTED** và **COMPLETE**, user đang ở `COMPLETE` thì `advanceTo(COMPLETE)` (idempotent re-trigger) vẫn OK, nhưng `advanceTo(NEW_STEP)` (ordinal=3) trên user đang `TEMPLATE_SELECTED` (ordinal=2) — pass invariant, advance OK. Tuy nhiên logic của TEMPLATE_SELECTED → NEW_STEP hợp lệ về invariant chưa chắc hợp lệ về domain (skip step?).

**Fix:** Thay ordinal compare bằng allow-list theo state machine, hoặc map mỗi step thành một `int weight` field trên enum:

```java
public enum OnboardingStep {
    SIGNED_IN(0), GMAIL_CONNECTED(10), TEMPLATE_SELECTED(20), COMPLETE(30);
    private final int weight;
    OnboardingStep(int w) { this.weight = w; }
    public int weight() { return weight; }
}

public void advanceTo(OnboardingStep next) {
    if (next.weight() < this.onboardingStep.weight()) {
        throw new IllegalStateException("Onboarding state is forward-only");
    }
    this.onboardingStep = next;
}
```

Weights gap=10 cho phép insert step mới giữa hai step hiện có mà không break invariant cho user đang ở step cao hơn. Đồng thời thêm test parametrize qua `OnboardingStep.values()` cross-product để lock down các transitions hợp lệ.

### WR-03: `OnboardingService.deleteSelectionsForCurrentTenant` không bulk delete

**File:** `backend/core/src/main/java/com/zeromail/core/onboarding/service/OnboardingService.java:56-58`

**Issue:** `onboarding.deleteAll(onboarding.findByTenantId(tenantId))` thực hiện 1 SELECT + N DELETE round-trips (N = số selections của tenant). Spring Data JPA `deleteAll(Iterable<T>)` về bản chất gọi `delete(entity)` lần lượt qua entity manager (không phải bulk DELETE). Hai consequences:

1. **N+1 queries** ở delete path. V1 với một-vài selections per tenant không sao, nhưng noisy trong logs/observability traces khi cascade delete.
2. **Hibernate `@TenantId` filter** đã apply cho `findByTenantId` ngầm (Hibernate sẽ thêm `WHERE tenant_id = ?` từ filter NẾU tenant đang bound), nên parameter `tenantId` truyền vào derived query là redundant với filter — **HOẶC** nếu `TenantContext` không bound khi gọi method (lý thuyết) thì filter dùng `BOOTSTRAP_TENANT` và `findByTenantId(realTenantId)` trả empty → no-op silent. Hiện tại `AccountDeletionController` chạy trong request scope với tenant đã bound, nhưng nếu method này được reuse từ background job không bind tenant, sẽ silently no-op.

**Fix:** Dùng bulk delete query (single statement) và document tenant-binding requirement:

```java
public interface OnboardingSelectionRepository extends JpaRepository<OnboardingSelectionEntity, UUID> {
    List<OnboardingSelectionEntity> findByTenantId(UUID tenantId);

    @Modifying
    @Query("DELETE FROM OnboardingSelectionEntity o WHERE o.tenantId = :tenantId")
    int deleteByTenantId(@Param("tenantId") UUID tenantId);
}

// service:
@Transactional
public void deleteSelectionsForCurrentTenant(UUID tenantId) {
    onboarding.deleteByTenantId(tenantId);
}
```

Nếu giữ shape hiện tại để consistent với `GmailConnectionService.deleteForCurrentTenant` (cũng dùng find-then-delete), document trong Javadoc rằng caller phải đã bind `TenantContext` để `@TenantId` filter active, và rằng N=1 (gmail là 1 row per tenant) nên cost giống nhau.

### IN-04: `OAuthProvisioningService.createTenant` lưu email vào `displayName`

**File:** `backend/core/src/main/java/com/zeromail/core/account/service/OAuthProvisioningService.java:80-86`

**Issue:** `tenantService.createTenant(tenantId, email)` truyền email làm `displayName` → persist plaintext vào `tenants.display_name`. Privacy policy của project (CLAUDE.md): "no long-term storage of raw email **bodies**, prompts, completions, embeddings". Email **địa chỉ** không phải email body, nên technically compliant. Tuy nhiên, `display_name` là human-readable label thường được hiển thị / log; trộn lẫn nó với PII (email) khiến mọi log/trace có dump tenant entity sẽ leak email.
```java
// Either compute a non-PII display name:
String displayName = "User-" + tenantId.toString().substring(0, 8);
tenantService.createTenant(tenantId, displayName);

// Or wrap in Sensitive at the entity level (Plan 04 follow-up):
@Column(name = "display_name", nullable = false)
private Sensitive<String> displayName;
```

Defer này sang Plan 04+ nếu phase này đã verified passed; raise như follow-up.

## Cross-cutting verification (sanity spot-check)

Các kiểm tra này không phải là findings — chỉ ghi lại để minh chứng rằng review đã verify các safety-critical paths.

- **FK ordering của AccountDeletionController**: `onboarding (child) → gmail (child) → user (sibling, FK to tenant) → tenant (parent)`. Đúng FK-safe; nếu tenant có FK cascade `ON DELETE RESTRICT` (chưa thấy migration trong scope) thì user phải xóa trước tenant — order đáp ứng.
- **`@Transactional` ở controller-level**: `AccountDeletionController.deleteAccount()` annotated `@Transactional` (Spring proxy applies vì `@RestController` là proxiable bean). Service methods bên trong đều `@Transactional` default propagation `REQUIRED` → join outer tx → atomic. Failure ở step 3 rollback steps 1-2.
- **`@TenantId` filter binding**: `ScopedValueTenantResolver.resolveCurrentTenantIdentifier()` đọc `TenantContext.TENANT` ScopedValue → fallback `BOOTSTRAP_TENANT (uuid 0,0)` khi unbound. Nghĩa là: nếu `AccountDeletionController` chạy trong request scope với tenant bound thì delete sẽ scope; nếu tenant unbound (bug, không nên happen) thì `findByTenantId(realTenant)` sẽ trả empty (Hibernate filter bind `BOOTSTRAP_TENANT` cho query) và toàn bộ cascade silent no-op. Đó là fail-safe (không cross-tenant delete), nhưng điều quan trọng: sẽ KHÔNG có log signal. Có thể warrant một invariant assert (raise nếu `TenantContext.currentOptional().isEmpty()` trong delete path) — defer.
- **Modulith allowedDependencies**: kiểm tra cross-domain imports vs declared edges:
  - `OnboardingService` (in `core.onboarding`) imports `core.account.service.AccountService` and `core.account.model.CurrentUserNotFoundException`. `onboarding.allowedDependencies = {tenant, account, shared.privacy}` — ✓.
  - `UserEntity` (in `core.account`) imports `core.onboarding.model.OnboardingStep`. `account.allowedDependencies = {tenant, onboarding, shared.privacy}` — ✓.
  - `OAuthProvisioningService` (in `core.account`) imports `core.tenant.TenantContext` and `core.tenant.service.TenantService`. ✓.
  - `core.gmail` imports only `tenant` (via `TenantId` annotation indirect, plus no service-level imports of account/onboarding seen). `gmail.allowedDependencies = {tenant, shared.privacy}` — ✓ (D-D4 explicit no-account-edge).
  - `core.tenant` imports nothing outside JDK/Spring/Hibernate. `tenant.allowedDependencies = {shared.privacy}` — ✓.
- **DomainBoundaryArchTests fire-on-violation**: rule shape là `noClasses().that().resideInAPackage("..core.X..").should().dependOnClassesThat(predicate)`. Predicate composes "name endsWith Repository" AND "resides in another domain's persistence package". Reintroducing e.g. `private final UserRepository users` field inside `core.gmail.service.GmailConnectionService` would cause a class dependency from `..core.gmail..` to `..core.account.persistence..UserRepository` matching predicate → rule fails. ✓ correctly reactive.
- **`javax.*` violations**: chỉ `javax.crypto.*` và `javax.sql.DataSource` — đây là JDK APIs (JCE / JDBC), không phải Jakarta EE — không vi phạm "jakarta.* only" rule (rule áp dụng cho servlet/persistence/validation/annotation, đã được tuân thủ qua `jakarta.persistence.*`, `jakarta.servlet.*`, `jakarta.validation.*`).
- **WebFlux**: không có `import org.springframework.web.reactive.*` ở các file reviewed. ✓
- **Lombok**: không có `import lombok.*`. ✓
- **Hardcoded secrets**: không có. `RefreshTokenCryptoConfig` đọc key từ `${zeromail.crypto.refresh-token-key-base64}` — placeholder phải được resolve từ Secret Manager qua `spring-cloud-gcp-starter-secretmanager`. ✓
- **Privacy / `Sensitive<T>` deny-list**: `UserEntity.email`, `GmailConnectionEntity.googleEmail`, `TenantEntity.displayName(=email)` đều plaintext String. Tuy nhiên `SafetyContractArchTests.sensitive_names_wrapped` chỉ ban field names matching `body|bodyText|prompt|completion|rawContent|refreshToken|accessToken` — `email` không trong deny-list, nên không vi phạm. Khi Plan 04 introduce `refreshToken Sensitive<String>` field, rule sẽ enforce. Hiện tại field tên `refreshTokenEncrypted` (byte[]) intentionally không match regex — code-comment đã ghi lý do.
- **OAuth race-resolution flow**: `findOrCreateGoogleUser` → `findByGoogleSubject` (native, bypass tenant filter) → empty → `tryCreateOrReadAfterRace` → `self.createTenantAndUser` (REQUIRES_NEW) → ON race lose: catch `DataIntegrityViolationException` → re-read via `findByGoogleSubject` → return existing user. Tenant insert rolls back with REQUIRES_NEW commit failure → no orphan tenant. ✓ correctness, but verify Postgres unique constraint `users.google_subject` exists in liquibase changelog (out-of-scope file).
