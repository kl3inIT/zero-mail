## Domain decomposition

### Q1 — Where should `OnboardingSelection` / `OnboardingStep` / `OnboardingService` live?
| Option | Description | Selected |
|---|---|---|
| Own `onboarding` domain | Separate domain `core/onboarding/{service,persistence,model}`. Phase 3's Rules engine reads OnboardingSelection — clean module seam. | ✓ |
| Inside `account` domain | Sub-folder of account or merged. Simpler graph but Phase 3 imports a fatter account contract. | |
| Inside `account`, but `OnboardingStep` enum follows `User` | Compromise: enum in `account/model/`, selections in own `onboarding` domain. | |

**User's choice:** Own `onboarding` domain (Recommended).
**Notes:** Phase 3 cross-domain dependency on OnboardingSelection drove the decision.

### Q2 — Domain owner of the `Tenant` JPA entity?
| Option | Description | Selected |
|---|---|---|

| Fold into `account` | Treat tenants as account-internal (1:1 in v1). Smallest module count; bets on never growing past 1:1. | |

**User's choice:** `tenant` domain owns entity + infra (Recommended).

### Q3 — Name for the Gmail OAuth + connection-state domain?

## Internal package shape

### Q1 — Keep `service/persistence/model` 3-package split or collapse to 2?
| Option | Description | Selected |
|---|---|---|
| Keep 3 packages per ROADMAP goal | `service/` (logic), `persistence/` (JPA), `model/` (enums + view records + domain exceptions). Cross-domain enum import doesn't drag JPA classpath. | ✓ |
| Merge `model` into `persistence` | Simpler but importing enums drags JPA; violates phase goal. | |
| Merge `model` into `service` | Service becomes a kitchen-sink package. | |

**User's choice:** Keep 3 packages per ROADMAP goal (Recommended).
**Notes:** Long discussion clarifying that `model/` holds **domain views** (`CurrentUserView`), **enums**, **domain exceptions** — NOT wire DTOs, which live in `backend/api/dto/`. User initially conflated the two; clarified that wire DTOs and domain views are two distinct layers with two distinct purposes (HTTP contract vs `core` ↔ `api`/`worker` contract).

### Q2 — Add a generic `ResponseGeneral` envelope?
| Option | Description | Selected |
|---|---|---|
| No envelope (Phase 1.1 contract) | Success = raw payload + HTTP status. Error = ApiError (RFC 7807 extended). Modern REST. | ✓ |
| Add `ResponseGeneral` envelope | `{code, message, data}` wrapper on every response. Duplicates HTTP status; breaks Phase 1.1 contract; bloats `openapi-typescript` types. | |

**User's choice:** No envelope — preserve Phase 1.1 contract.

### Q3 — Service tier exposes interface or concrete class?
| Option | Description | Selected |
|---|---|---|
| Concrete class, no interface | Status quo. Spring Boot 4 + virtual threads doesn't need proxy interface; AOP via CGLIB; Mockito mocks concrete. | ✓ |
| Interface in `service/`, impl in `service/impl/` | Allows swap; 4× file count; no real use case in v1. | |
| Interface in `service/`, impl in `service/internal/` (package-private) | Interface public, impl package-private. Defer until justified. | |

**User's choice:** Concrete class only (Recommended).

### Q4 — Entity → View mapping (inside service): where?
| Option | Description | Selected |
|---|---|---|
| Inline in service method | Status quo (`AccountService.requireCurrentUser` style). 5–7 lines next to business logic. | ✓ |
| Static factory on record | `CurrentUserView.from(UserEntity)`. Forces `model` to import `persistence` (wrong tier direction). | |
| Mapper class in `service/` | `AccountMapper.toView(...)`. Over-engineering for 5–10 line mappings in v1. | |

**User's choice:** Inline in service method (Recommended).
**Notes:** User asked why service couldn't return wire DTO directly. Explained: (a) `MeResponse` lives in `backend/api/dto/`; service returning it would create a Gradle module circular dependency (api already depends on core); (b) `backend/worker` (per CLAUDE.md "thin shell" lock) consumes `core` services and must not pull HTTP-shaped DTOs; (c) one view can map to multiple wire DTOs (full / summary / admin shapes); (d) wire DTO renames for i18n/branding shouldn't trigger core rebuild. The two-layer mapping is structurally required, not stylistic.

### Q5 — View → Wire DTO mapping (inside controller): where?
| Option | Description | Selected |
|---|---|---|
| Private static helper in each controller | `MeController` style: `private static MeResponse toResponse(view)`. Refactor `TenantStatusController` to match. | ✓ |
| Static factory on wire DTO record | `MeResponse.from(view)` — wire DTO knows about view. Allowed (api/dto may import core/model). | |
| Mapper class in `backend/api/dto/` | Justified only when mapping needs injected dependencies (i18n bundle, formatter). Not yet. | |

**User's choice:** Private static helper in each controller (Recommended).
**Notes:** Folded a small consistency fix into Phase 1.2 — refactor `TenantStatusController`'s inline mapping to match `MeController`'s helper pattern, since the layout move is already touching that controller's imports.

## Boundary enforcement & migration

### Q1 — Repository cross-domain visibility?
| Option | Description | Selected |
|---|---|---|
| Public + ArchUnit cross-domain ban | Repos `public` (Spring Data needs that for proxy). ArchUnit forbids `core.<A>` importing `core.<B>.*Repository`. Cross-domain reads go through service. | ✓ |
| Package-private repository | Best encapsulation by JLS but requires same-package tests; Spring Data proxy still works but testing friction. | |
| Loose: public repos, only ban entity escape past service | Less rigid; doesn't satisfy ROADMAP success criterion #5. | |

**User's choice:** Public + ArchUnit ban (Recommended).
**Notes:** Concrete consequence flagged: `AccountService` currently injects 4 cross-domain repositories — must be reshaped to call `GmailConnectionService`/`OnboardingService` instead.

### Q2 — Modulith, ArchUnit, or both?
| Option | Description | Selected |
|---|---|---|
| Both — Modulith for graph + ArchUnit for rules | Modulith owns module-graph; ArchUnit owns rule-level invariants (native SQL, ThreadLocal, virtual-thread fan-out, `Sensitive`). | ✓ |
| ArchUnit only | Drops `@ApplicationModule` annotations; no Modulith reporting/visualization. | |
| Modulith only | Drops `SafetyContractArchTests` etc. — unacceptable. | |

**User's choice:** Both (Recommended).

### Q3 — Native SQL allow-list location?
| Option | Description | Selected |
|---|---|---|
| Per-domain `core/<domain>/persistence/lowlevel/` | Each domain owns its native SQL. Regex matcher `..persistence.lowlevel..` in ArchUnit. | ✓ |
| Single `core/shared/persistence/lowlevel/` | Centralized review; violates "shared not for business logic" principle. | |
| Delete allow-list, ban native SQL outright | Phase 4+ may need `SKIP LOCKED` queue polling; preemptive ban → later relaxation → churn. | |

**User's choice:** Per-domain (Recommended).

### Q4 — Migration shape?
| Option | Description | Selected |
|---|---|---|
| Plan-driven, one commit per domain | 5–6 plans (privacy → tenant → account → onboarding → gmail → enforcement/cleanup). Each ends green. Bisect-friendly. Matches Phase 1.1 cadence. | ✓ |
| Big-bang single commit | 50+ files, defeats `git blame` rename tracking, painful bisection. | |
| Deprecated re-export shims | Backwards-compat aliases. Internal monorepo doesn't need them. | |

**User's choice:** Plan-driven, one commit per domain (Recommended).
