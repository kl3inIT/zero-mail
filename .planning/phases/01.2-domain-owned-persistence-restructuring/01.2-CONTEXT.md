# Phase 1.2: Domain-owned persistence restructuring - Context

**Gathered:** 2026-04-26
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 1.2 refactors `backend/core` away from a single global `core.persistence` bucket into domain-owned packages, where each business domain owns its own `service/`, `persistence/`, and `model/` sub-packages. A small `shared/` package is reserved exclusively for stable cross-cutting infrastructure (Phase 1.2 ships only `shared/privacy/` — the `Sensitive` marker contract). Database schema, Liquibase changelog semantics, tenant isolation, log-scrub safety contract, the Phase 1.1 i18n + ApiError additions, and Phase 1 OAuth/refresh-token-encryption behavior must survive the move byte-identical. New module boundaries are enforced both by Spring Modulith (`@ApplicationModule(allowedDependencies = {...})` + `ApplicationModulesTest.verify()`) and by ArchUnit rules (cross-domain repository access, native SQL allow-list, `@Sensitive` marker, virtual-thread fan-out, ThreadLocal ban).

**In scope:**
- Replace `com.zeromail.core.persistence.*` (global bucket) with per-domain `com.zeromail.core.<domain>.{service,persistence,model}` layouts.
- Identify 4 domains: `account`, `onboarding`, `gmail`, `tenant`.
- Move `Sensitive`/`SensitiveJacksonModule`/`SensitiveMarkerScrubFilter` from `core.privacy` to `core.shared.privacy`.
- Move `RefreshTokenCipher`/`RefreshTokenCryptoConfig` from `core.crypto` into `core.gmail.persistence.crypto` (domain-internal, since Gmail is the sole consumer).
- Tenant entity + multi-tenancy infrastructure (`TenantContext`, `TenantPrincipal`, `ScopedValueTenantResolver`, `concurrency/TenantAwareTaskScope`) both stay in `core.tenant`.
- Update Modulith `@ApplicationModule` annotations on every package-info to reflect the new graph (account → {tenant, onboarding, shared.privacy}; onboarding → {tenant, account, shared.privacy}; gmail → {tenant, shared.privacy}; tenant → {shared.privacy}; shared.privacy → {}).
- Update ArchUnit rules: per-domain `..persistence.lowlevel..` allow-list (regex), cross-domain repository import ban, `Sensitive` FQN updated to `com.zeromail.shared.privacy.Sensitive`.
- Update `backend/api/Application.java` `@EntityScan` and `@EnableJpaRepositories` base packages so they discover entities across all new per-domain `persistence/` packages.
- Refactor `TenantStatusController`'s inline view→wire-DTO mapping into a private static helper, matching `MeController`'s `toResponse(...)` style — a small consistency fix folded into Phase 1.2 because the layout move already touches that controller.
- Delete the now-empty `core.persistence` and `core.crypto` packages and their `package-info.java` Modulith annotations.
- One Gradle `git mv`-equivalent commit per domain (5–6 plans), each green before the next starts.

**Out of scope (enforced):**
- Adding any new entity, column, or table (schema is byte-identical).
- Adding any new endpoint, wire DTO, controller, or service method (controllers may only be touched to refactor mapping consistency).
- Introducing Spring Data JDBC for read-side projections (CLAUDE.md mentions it; deferred until a real read-heavy hot path appears).
- Splitting `core` into multiple Gradle modules — internal slicing stays package-based per Phase 1 D-A1.
- Introducing service interfaces in `service/` (concrete `@Service` classes only).
- Introducing a generic `ResponseGeneral`/envelope wire shape — Phase 1.1's RFC 7807 + `ApiError` extension contract is preserved exactly.
- Pre-creating empty domain stubs for Phase 2A/2B/2C/3/4 — each future phase carves its own slot when it lands.
- Promoting `RefreshTokenCipher` to `shared/` speculatively for Phase 2C BYOK — wait until a second real consumer exists.
- Deprecated re-export shims for backwards compatibility — internal monorepo, single big-bang per-domain rename is acceptable.

<decisions>
## Implementation Decisions

### A. Domain decomposition
- **D-A1:** **Four business domains** in `backend/core` after refactor: `account`, `onboarding`, `gmail`, `tenant`. Plus one cross-cutting package: `shared/privacy/`. No empty stubs for future phases — each phase (2A mail, 2B billing, 2C llm, 3 rules, 4 triage) carves its own domain when it lands.
- **D-A2:** **`onboarding` is its own domain**, not folded into `account`. Owns `OnboardingSelectionEntity`, `OnboardingSelectionRepository`, `OnboardingService`, and the `OnboardingStep` enum. Reason: Phase 3's Rules engine (per Phase 1 D-D1) reads `OnboardingSelection` rows on first Rules-page visit — keeping onboarding as a peer domain creates a clean module seam for that future cross-domain dependency rather than fattening `account`'s public surface.
- **D-A3:** **`tenant` domain owns both the `Tenant` JPA entity AND the multi-tenancy infrastructure** (`TenantContext` Scoped Value, `TenantPrincipal`, `ScopedValueTenantResolver`, and `concurrency/TenantAwareTaskScope`). One module = one concern: anything tenant-shaped lives here. `shared/` does not absorb tenant infra. Every other domain has `tenant` in its `allowedDependencies`.
- **D-A4:** **Domain naming = `gmail`**, not `mailbox` or `connection`. Honest about CLAUDE.md's locked v1 scope ("Gmail / Google Workspace only"); matches existing class names (`GmailConnectionEntity`, `gmail_connections` table). Renaming if v2 ever adds IMAP/Outlook is a cheap rename — pretending to be provider-agnostic before a second provider exists is YAGNI.
- **D-A5:** **`OnboardingStep` enum lives in `onboarding/model/`**, even though it is stored as a column on the `users` table. Onboarding domain owns the lifecycle definition; `account/persistence/UserEntity` imports `onboarding.model.OnboardingStep` for column mapping. This adds `onboarding` to `account.allowedDependencies` — explicit, minimal, and honest about which domain semantically owns the enum.

### B. Internal package shape (per domain)
- **D-B1:** **Three sub-packages per domain: `service/` + `persistence/` + `model/`.** Per ROADMAP goal, verbatim. Each holds:
  - `service/` — concrete `@Service` classes (no interfaces — D-B3) and any service-layer support types.
  - `persistence/` — JPA `@Entity` classes, `JpaRepository` interfaces, JPA `AttributeConverter`s, embeddables, `lowlevel/` sub-package for native SQL when needed.
  - `model/` — domain enums (e.g., `OnboardingStep`, `GmailConnectionStatus`), domain view records (e.g., `CurrentUserView`, `TenantConnectionView`), domain exceptions (e.g., `CurrentUserNotFoundException`). **Strictly NOT wire DTOs.**
- **D-B2:** **Wire DTOs (request/response) stay in `backend/api/dto/`.** `MeResponse`, `LanguageUpdateRequest`, `TenantStatusResponse`, `SelectTemplateRequest` — these are HTTP shapes with Jackson + `@Schema` + Bean Validation annotations. They are **not** the same kind of "DTO" as a domain view record:

  | Layer | Lives in | Annotations | Contract |
  |---|---|---|---|
  | Wire DTO | `backend/api/dto/` | Jackson, `@Schema`, `@Valid` | HTTP / OpenAPI client |
  | Domain view (record) | `backend/core/<domain>/model/` | none | `core` ↔ `api` (and `core` ↔ `worker` from Phase 2A) |

  Service must NOT return a wire DTO directly. Doing so would force `backend/core` to depend on `backend/api/dto`, creating a Gradle module circular dependency (since `api` already depends on `core`); and would force `backend/worker` (which CLAUDE.md locks as a thin shell that depends on `core`) to import HTTP-shaped types it does not need.
- **D-B3:** **Service tier exposes concrete `@Service` classes, no interfaces.** Status quo (`AccountService`, `OAuthProvisioningService`, `OnboardingService`, `TenantConnectionService`) preserved. Spring Boot 4 + virtual-thread workload does not benefit from interface proxies; AOP uses CGLIB; Mockito mocks concrete classes fine. Add interfaces only if a real second implementation appears.
- **D-B4:** **Entity → View mapping is INLINE inside service methods.** Status quo of `AccountService.requireCurrentUser` preserved: `return new CurrentUserView(user.getId(), tenantId, user.getEmail(), user.getOnboardingStep().name(), user.getPreferredLanguage());` directly inside the method body. No static factory on the record (would force `model` to import `persistence`, inverting tier dependency). No mapper class (over-engineering for 5–10 line mappings). Extract only when mapping exceeds ~10 lines or has conditional branches.
- **D-B5:** **View → Wire DTO mapping is a private static helper inside each controller.** `MeController` already follows this pattern with `private static MeResponse toResponse(CurrentUserView view)`. **Refactor `TenantStatusController` to match** — replace the inline `new TenantStatusResponse(view.status(), view.googleEmail())` with `private static TenantStatusResponse toResponse(TenantConnectionView view)`. This is a small consistency fix folded into Phase 1.2 because the layout move already touches the controller's imports.
- **D-B6:** **No `ResponseGeneral` / envelope wire wrapper.** Phase 1.1 already locked the contract: success = raw payload + HTTP status code; error = `ApiError` (RFC 7807 ProblemDetail extended with `code`/`params`/`fieldErrors`). Wrapping payloads in `{code: 0, data: {...}}` would duplicate the HTTP status, break the Phase 1.1 contract just shipped, and force every `openapi-typescript`-generated FE type to become `Envelope<T>` (boilerplate × every endpoint). Modern REST best practice (Google API Design, Microsoft REST Guidelines, Stripe, GitHub) avoids envelopes.

### C. `shared/` package boundary
- **D-C1:** **`shared/` is minimal — only `shared/privacy/` exists after Phase 1.2.** Contains the `Sensitive<T>` marker, `SensitiveJacksonModule`, `SensitiveMarkerScrubFilter`. Used by every domain (ArchUnit `SafetyContractArchTests` already references the FQN literally). Update the ArchUnit fixture's `private static final String SENSITIVE = "com.zeromail.core.privacy.Sensitive";` to `"com.zeromail.shared.privacy.Sensitive";`.
- **D-C2:** **`RefreshTokenCipher` does NOT go into `shared/` — it goes into `core.gmail.persistence.crypto/`.** Reason: today the cipher serves a single consumer (`gmail_connections.refresh_token_encrypted`). ROADMAP goal is explicit: `shared` must not become a business-logic dumping ground or a place for "speculative shared" code. Phase 2C BYOK *may* eventually need a second cipher use case, but: (a) Phase 2C may also use request-scoped in-memory key handling that never persists (per CLAUDE.md privacy direction), in which case promotion is unnecessary; (b) lazy promotion when a second real consumer appears is cheaper than speculative shared infrastructure. If/when Phase 2C needs encryption-at-rest for BYOK keys, that phase carves the promotion as part of its work.
- **D-C3:** **Tenant-context infrastructure is NOT split into `shared/tenancy/`** — it stays in `core.tenant`. Splitting would fracture the tenant module across two locations (entity in `tenant/`, runtime infra in `shared/tenancy/`), force them to import each other (the entity reads tenant id from the Scoped Value during `@TenantId` resolution), and complicate the Modulith graph. Tenant is the ground-truth dependency every other domain points at — keeping it as one unified module is simpler.

### D. Boundary enforcement
- **D-D1:** **Repositories stay `public` (Spring Data JPA needs that for proxying), but ArchUnit forbids cross-domain repository imports.** New rule in `TenantIsolationArchTests` (or a new `DomainBoundaryArchTests`): a class in `core.<domainA>` may NOT import any `*Repository` from `core.<domainB>`. Cross-domain reads go through `<domainB>Service` (or a dedicated read view from B's service). Concrete consequence: `AccountService` (currently injects `GmailConnectionRepository`, `OnboardingSelectionRepository`) must be reshaped — the read paths it needs from gmail/onboarding move into `GmailConnectionService` / `OnboardingService` and `AccountService` calls those instead.

  - **Exception:** the `service/` and `persistence/` packages of the same domain may both touch that domain's repositories (intra-domain access stays free).
  - **Note for planner:** Inspect `AccountService` carefully — it currently reaches into 4 repositories across 4 about-to-be-separated domains. Its responsibilities will need to be partitioned (e.g., the gmail-status read path moves into `gmail` domain entirely; `AccountService` retains only User-row reads).
- **D-D2:** **Both Modulith and ArchUnit enforce boundaries — neither alone is sufficient.**
  - **Modulith** owns the high-level module graph: `@ApplicationModule(allowedDependencies = {...})` on each domain's `package-info.java`; CI runs `ApplicationModulesTest.verify()` (already in place from Phase 1).
  - **ArchUnit** owns rule-level invariants: native SQL allow-list, cross-domain repository ban (D-D1), `Sensitive`-marker enforcement, ThreadLocal ban, virtual-thread fan-out via `TenantAwareTaskScope` only. Existing tests (`SafetyContractArchTests`, `TenantIsolationArchTests`) get path/FQN updates, not rule rewrites.
- **D-D3:** **Native-SQL allow-list is per-domain.** Pattern `..core.<domain>.persistence.lowlevel..` (regex `..persistence.lowlevel..`). Each domain creates an empty `lowlevel/` sub-package with a `package-info.java` documenting the convention; no native SQL is written in Phase 1.2 (refactor only). When a future phase needs `SKIP LOCKED` queue polling (likely in Phase 2A's mail-ingestion job table), it adds the class inside *its own domain's* `lowlevel/` — domain-ownership of native SQL.
- **D-D4:** **Modulith allowed-dependency graph** (planner formalizes the exact annotations):
  - `account` → `{tenant, onboarding, shared.privacy}` (account imports `OnboardingStep` enum + may need read-only access to onboarding + tenant entity for joins)
  - `onboarding` → `{tenant, account, shared.privacy}` (onboarding selections are per-tenant, per-user — needs tenant context and User reference)
  - `gmail` → `{tenant, shared.privacy}` (gmail connections are per-tenant; do NOT depend on account directly)
  - `tenant` → `{shared.privacy}`
  - `shared.privacy` → `{}` (leaf)

  Cycles must not appear; if planner discovers an edge that requires a cycle (e.g., `gmail` ↔ `account`), surface as a deviation rather than silently allow.

### E. Migration shape
- **D-E1:** **One commit (one plan) per domain move**, in this order:
  1. **Plan 01.2-01:** Create `shared/privacy/` package, move `core.privacy.*` → `core.shared.privacy.*`, update ArchUnit `SafetyContractArchTests` SENSITIVE FQN, update Modulith `@ApplicationModule` on the new package, delete `core.privacy/package-info.java`. Smallest, lowest-risk move; sets up the import target every later plan needs.
  2. **Plan 01.2-02:** Move `core.persistence.{TenantEntity, TenantRepository}` → `core.tenant.persistence.*`. Update `core.tenant/package-info.java` `allowedDependencies = {shared.privacy}`. Also relocate `lowlevel/` allow-list machinery (per D-D3 — at this point each domain may have its own empty `lowlevel/` package).
  3. **Plan 01.2-03:** Move `core.persistence.{UserEntity, UserRepository}` → `core.account.persistence.*`. Move `core.account.{CurrentUserView, CurrentUserNotFoundException}` → `core.account.model.*`. Update `account/package-info.java` `allowedDependencies = {tenant, onboarding, shared.privacy}`. Refactor `AccountService` to drop cross-domain repository injections (per D-D1) — call `GmailConnectionService`/`OnboardingService` instead (those services become responsible for the read paths).
  4. **Plan 01.2-04:** Move `core.persistence.{OnboardingSelectionEntity, OnboardingSelectionRepository, OnboardingStep}` → `core.onboarding.{persistence,model}.*` (entity+repo in persistence, enum in model). Move `core.account.OnboardingService` → `core.onboarding.service.OnboardingService`. Update `onboarding/package-info.java` `allowedDependencies = {tenant, account, shared.privacy}`.
  5. **Plan 01.2-05:** Move `core.persistence.{GmailConnectionEntity, GmailConnectionRepository, GmailConnectionStatus}` → `core.gmail.{persistence,model}.*`. Move `core.account.{TenantConnectionService, TenantConnectionView}` → `core.gmail.{service,model}.*` (rename to `GmailConnectionService`/`GmailConnectionView` — the current name is a misnomer; this is gmail-domain logic, not tenant-domain). Move `core.crypto.{RefreshTokenCipher, RefreshTokenCryptoConfig}` → `core.gmail.persistence.crypto.*`. Delete `core.crypto` and `core.persistence` packages (now empty). Update `backend/api/Application.java` `@EntityScan`/`@EnableJpaRepositories` to root package `com.zeromail.core` (or explicit list of all 4 `persistence/` packages — planner picks based on Spring Boot 4 + Modulith ergonomics).
  6. **Plan 01.2-06:** Add ArchUnit `DomainBoundaryArchTests` enforcing the cross-domain repository ban (D-D1). Update `TenantIsolationArchTests`'s `..core.persistence.lowlevel..` reference to the regex `..persistence.lowlevel..`. Refactor `TenantStatusController` to follow `MeController`'s `toResponse(view)` private-static-helper pattern (D-B5). Run full test matrix; verify `ApplicationModulesTest.verify()` is green; final cleanup of stale package-info files.

  Each plan: tests stay green, ArchUnit/Modulith pass, schema unchanged, every API contract identical. Bisect-friendly. Per-commit churn is bounded to one domain.
- **D-E2:** **No deprecated re-export shims, no big-bang.** Internal monorepo with no external consumers — no compatibility surface to preserve. Big-bang single-commit move (50+ files at once) defeats `git blame` rename tracking and makes test bisection painful when the inevitable subtle import gets missed.

## Specific Ideas

- **Rename `TenantConnectionService` → `GmailConnectionService`** (and `TenantConnectionView` → `GmailConnectionView`) when moving to `core.gmail.service/` / `core.gmail.model/`. Reason: the current name conflates "tenant" and "gmail connection"; after the domain split, the responsibility is gmail-domain-internal. Planner may revisit if call sites are surprisingly numerous, but the rename should ride along with the move commit.
- **`AccountService` decomposition during Plan 03**: The current `AccountService` injects `OnboardingSelectionRepository`, `GmailConnectionRepository`, `UserRepository`, `TenantRepository` — 4 cross-domain handles. After D-D1, only `UserRepository` (and possibly `TenantRepository` since both are inside `account`/`tenant` domains; planner reviews) remain. The gmail-status read paths and onboarding read paths fold into their respective domain services, which `AccountService` then calls.
- **Empty `lowlevel/` package convention.** Each new domain's `persistence/lowlevel/` folder, when introduced, gets a `package-info.java` documenting: "Allow-listed package for native SQL / raw JDBC.
