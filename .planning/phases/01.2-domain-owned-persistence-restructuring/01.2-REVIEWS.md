# Cross-AI Plan Review: Phase 1.2 - Domain-owned persistence restructuring

## Summary

This is a well-conceived 6-plan refactor with strong supporting artifacts (CONTEXT, RESEARCH, PATTERNS, VALIDATION) and excellent attention to subtle pitfalls (Modulith nested-module naming, logback string-FQN drift, enum persistence semantics, ArchUnit DSL limitations). The bisect-friendly per-domain plan structure is correct. **However, the plans contain a recurring class of dependency-ordering bugs**: each plan's task list specifies the files being relocated but does NOT enumerate the *transitive importers* that will break when their imports' targets disappear. Plans 02 and 03 in particular will fail their own compile-time verify commands if executed literally.

---

## Plan 01.2-01 - Privacy -> core.shared.privacy

### Strengths
- Three-step empirical CL-3 probe with documented fallback chain (A -> B -> C) and explicit STOP/checkpoint condition.
- Logback XML string-FQN update is bundled into the same commit as the Java move (Pitfall 1 closure).
- ArchUnit fixture FQN literal uses the canonical CL-1 form (`core.shared.privacy`, not `shared.privacy`).
- Test files moved alongside source files - package decls + imports both updated.

### Concerns
- **MEDIUM:** Task 1 verify is `:backend:core:compileJava` only. If `backend/api` code imports `Sensitive<T>` directly (e.g., a future ApiError contract or controller field), api compile is not exercised until later. Worth adding `:backend:api:compileJava` to Task 1 verify.
- **MEDIUM:** No explicit grep across `backend/api/`, `apps/web/`, or `backend/worker/` for stale `com.zeromail.core.privacy.` imports inside Task 1/2 - the sweep only appears in `<verification>` (end of plan). If the executor stops after Task 1's success, broken api imports surface late.
- **LOW:** Task 3's CL-3 probe documentation in JavaDoc embeds `<pass|fail>` results into a JavaDoc string - fine, but means future `package-info.java` reads are noisier than necessary.
- **LOW:** The probe modifies and reverts `tenant/package-info.java` repeatedly; if any probe step is interrupted, `tenant/package-info.java` is left in an intermediate state. A `git stash` or explicit "if you abort, restore tenant/package-info to `allowedDependencies = {}`" note would help.

### Suggestions
- Add `:backend:api:compileJava` to Task 1 verify.
- In Task 2 acceptance, add: `grep -rn 'com\.zeromail\.core\.privacy' backend/ apps/ 2>/dev/null` should return zero matches (sweep moved earlier from end-of-plan).

## Plan 01.2-02 - Tenant -> core.tenant.persistence

### Strengths
- Proactive `lowlevel/` package marker per D-D3 (avoids a Plan 06 surprise where the regex needs a target).
- Entity-scan widening to a 2-element array is correctly scoped as transitional (Plan 05 collapses).
- Pitfall 6 / OAuthProvisioningService self-injection acknowledged in the threat model.

### Concerns
- **HIGH - compile break:** `AccountService` and `OAuthProvisioningService` (still at `core.account/` until Plan 03) currently import `com.zeromail.core.persistence.TenantEntity` and `com.zeromail.core.persistence.TenantRepository`. After Task 1 of this plan, those classes no longer exist at the legacy FQN. Task 1's verify command `./gradlew :backend:core:compileJava :backend:api:compileJava` will FAIL. This is the single biggest issue in the plan series.

- **MEDIUM:** Task 2 acceptance includes the sweep `grep -rn 'com\.zeromail\.core\.persistence\.TenantEntity\|...'` returning zero - but the plan never instructed the executor to update the importers, so this assertion is unreachable without out-of-band fixes.

### Suggestions

- List all known transitive importers in `files_modified` so commit hygiene + diff review are meaningful.

## Plan 01.2-05 - Gmail + crypto + entity-scan collapse

### Strengths
- Comprehensive: 11 file relocations + new TenantService + 3 deletions + entity-scan collapse + 4 controller updates + bridge finalization, all sequenced sensibly.
- Pitfall 8 (bean-name autowiring) is checked pre-flight in Task 2 step 1 with a concrete grep command.

- TenantService creation (first occupant of `core.tenant.service/`) is properly motivated and minimal.

### Concerns
- **MEDIUM - package-info deletion ordering:** Task 3 step 4 deletes `core.persistence/package-info.java`. If this `package-info.java` carries `@ApplicationModule(displayName = "Persistence", allowedDependencies = {})`, Modulith may have it as a discovered module up to this point. After deletion, `ApplicationModulesTest.verify()` should still pass (it's not referenced by any other module's `allowedDependencies` after Plan 03). Worth one Modulith verify between steps 1-2 and step 3 just to be sure. If `core.persistence/package-info.java` is kept around just for the JavaDoc but has NO `@ApplicationModule`, no concern.
- **MEDIUM - api compile broken from Task 1 to mid-Task 3:** Task 1 moves gmail entities/crypto; Task 1 verify only runs `:backend:core:compileJava`. `backend/api` references `com.zeromail.core.persistence.GmailConnectionEntity` (in ConnectGmailController, AccountDeletionController, etc.) and breaks immediately. Task 3 step 6-9 fixes this. Between Task 1 and Task 3 step 8, `backend/api` will not compile. Acceptable risk if executor runs all 3 tasks in one session, but the verification gates don't catch the broken interim state.
- **MEDIUM:** `RefreshTokenCryptoConfig` move - does anything reference `com.zeromail.core.crypto.RefreshTokenCryptoConfig` by FQN string in any properties/yaml? Probably not, but worth confirming. The plan claims "env-var lookup strings UNCHANGED" but doesn't verify there's no Spring `@ImportResource` or similar.
- **MEDIUM:** Cipher round-trip is verified (`RefreshTokenCipherTest`) but **the plan does not include a smoke test that decrypts an EXISTING database row** - `GmailConnectionUniquenessTest` only exercises uniqueness, not crypto round-trip against a stored row. If a key rotation or envelope schema bit shifts during the move, only newly-encrypted data round-trips correctly. RESEARCH.md mentions this as Pitfall in T-01.2-F; cipher unit tests cover it for fresh encrypts but not against pre-existing fixture data.
- **LOW:** The plan's grep `! grep -F 'TenantConnectionService\|TenantConnectionView' backend/api/src/main/java/com/zeromail/api/controllers/`*.java has shell-globbing concerns under bash - quotes around the path won't affect the trailing `*.java` correctly. Use `grep -rn` over the directory instead.
- **LOW:** Plan does not check whether `apps/web` or `backend/worker` directly import any of the moved gmail/crypto types via OpenAPI codegen output (probably not since FE goes through OpenAPI, but worth a sanity grep).

### Suggestions
- Add an integration test or one-time verification that an existing encrypted refresh-token row decrypts correctly post-move (could be a small `@Test` reading a fixture seeded by Liquibase).
- Reconsider whether `core.persistence/package-info.java` should be deleted before vs. after the `@EntityScan` collapse - collapse first (so single root scan picks up everything), then delete the empty package marker.
- Use `grep -rn` over directory globs instead of shell-glob `*.java` patterns in acceptance criteria.

## Plan 01.2-06 - ArchUnit boundary + controller cleanup + final check

### Strengths
- DomainBoundaryArchTests uses the 4-explicit-rules shape per Pitfall 4 - pragmatic and correctly identified.
- `..persistence.lowlevel..` regex update is accurate (AspectJ `..` prefix matches all parent packages).
- TenantStatusController `toResponse(view)` extraction is minimal and matches MeController's analog exactly.
- Final canonical AccountDeletionController body is clean - correct FK-safe order, controller-level @Transactional, no transitional cruft.
- Phase gate is appropriately heavyweight (`./gradlew clean check` + 3-way byte-identical sweep).

### Concerns
- **MEDIUM:** The 4 ArchRules in `DomainBoundaryArchTests` use `.dependOnClassesThat().haveNameMatching(".*Repository").and().resideInAnyPackage(...)`. The `.and()` combinator on predicates can have subtle semantics in ArchUnit's fluent DSL - particularly whether `.and()` here means "name matches AND package matches" or chains differently. The pattern is from PATTERNS.md which is authoritative for this codebase's idiom, but the plan should explicitly verify each rule actually fires by doing a one-time intentional violation in a scratch branch before locking. As-is, the rules might be vacuously passing.
- **MEDIUM:** The plan does not include a deliberate "negative test" - e.g., temporarily inject a cross-domain repo into AccountService and confirm DomainBoundaryArchTests fails. Without this, a misconfigured rule would silently permit drift forever. Worth adding a one-time manual probe.
- **LOW:** Final canonical TenantStatusController removes `import org.springframework.transaction.annotation.Transactional` if the original had it - verify the original `currentStatus(...)` was not declared `@Transactional(readOnly = true)`. If it was, the Plan 06 replacement loses transactional read semantics silently.
- **LOW:** Acceptance `! grep -F 'new TenantStatusResponse(view.status(), view.googleEmail())' ... | head -1 | grep -v 'private static'` is a fragile shell pipeline. The intent is "the inline mapping in the handler is gone, only the helper has the constructor call" - better expressed as `grep -c 'new TenantStatusResponse' returns 1`, which the plan also has.
- **LOW:** Final clean check's byte-identical sweep is correct, but the plan does not capture HOW the executor confirms `apps/web/openapi/*.json` exists and what to do if it doesn't (a fresh project may not have it generated yet).

### Suggestions
- Add a one-time manual ArchUnit-fires probe in Task 1: temporarily inject `OnboardingSelectionRepository` into `AccountService`, run `DomainBoundaryArchTests`, confirm it fails, revert.
- Verify TenantStatusController's original method signature/annotations are preserved (especially `@Transactional`).

## Risk Assessment

**Overall Risk: MEDIUM-HIGH**

**Justification:**
- The plan suite is *strategically correct*: the bisect-friendly per-domain progression, the dual Modulith+ArchUnit enforcement, the byte-identical contract, the CL-3 probe with documented fallbacks, and the Wave 0 test additions all reflect senior-level planning.
- The supporting artifacts (CONTEXT, RESEARCH, PATTERNS, VALIDATION) are exceptionally thorough - RESEARCH.md's pitfalls are largely actionable and the plans incorporate them well.
- **The dependency-ordering bug across Plans 02 and 03 is the dominant risk.** It will not produce wrong code (compile-fast catches it), but it will halt execution mid-plan, force the executor to improvise, and create commits whose message ("move tenant entity") doesn't match their actual diff (also touches AccountService, OAuthProvisioningService, tests). This undermines the bisect-friendly goal.
- The cipher round-trip on pre-existing data is a small but real privacy-adjacent gap.
- DomainBoundaryArchTests not being negatively-validated leaves a small chance the rules are vacuously passing.

**To downgrade to MEDIUM or LOW:**
1. Add explicit transitive-importer updates to Plans 02 and 03's `<action>` blocks and `files_modified`.
2. Add a one-time DomainBoundaryArchTests negative probe to Plan 06.
3. Add a fixture-decrypt test to Plan 05 (or note explicitly that no pre-existing encrypted rows exist in dev/test data).
4. Standardize verify commands to include `:backend:api:test --tests "ApplicationModulesTest"` from Plan 02 onward.

## Consensus Summary

### Agreed Strengths

- The plan series is strategically sound: both reviewers agreed the six-plan, per-domain migration is coherent and mostly bisect-friendly.
- Privacy and tenant moves are well isolated, with useful safeguards for Logback string FQNs, entity scanning, and Spring Modulith naming uncertainty.
- The suite leans on the right verification families: compile checks, `ApplicationModulesTest`, targeted domain tests, final `clean check`, and durable ArchUnit enforcement.
- Both reviewers viewed Plan 06's final architecture enforcement as the right end-state shape, while noting that the rule mechanics need proof.

### Agreed Concerns

- **HIGH:** Execution ordering needs tightening before implementation. Claude flagged concrete compile breaks in Plans 02 and 03 because transitive importers are not enumerated; OpenCode also called for mandatory stale-import sweeps and better standalone plan safety.
- **HIGH:** The account deletion order must be canonicalized against real FK constraints. OpenCode highlighted inconsistent `children -> tenant -> user` vs `children -> user -> tenant` guidance; Claude also treated the final delete orchestration as a sensitive area that needs exact preservation.
- **MEDIUM:** The CL-3 working form and Modulith probe need a durable single source of truth. Both reviewers saw drift or interruption risk in temporary `package-info.java` edits and later placeholder substitution.
- **MEDIUM:** Verification should be less partial. Several tasks run only `:backend:core:compileJava`, missing api-side compile failures and Modulith checks that live in `backend/api`.
- **MEDIUM:** Final ArchUnit boundary rules should include a negative/probe validation so they are known to fail on an intentional violation instead of passing vacuously.
- **MEDIUM:** Plan 05 should strengthen crypto/data continuity verification, especially around decrypting an existing encrypted refresh-token row after package moves.

### Divergent Views

- Claude considered transitive importer omissions in Plans 02 and 03 the dominant risk and gave concrete likely broken files (`AccountService`, `OAuthProvisioningService`, `OnboardingService`, `TenantConnectionService`, and tests). OpenCode gave Plan 02 a lower risk rating and focused more on stale import sweeps and smoke gates, so the planner should prioritize Claude's more specific compile-break evidence.
- OpenCode treated delete-order inconsistency as the top cross-plan high issue. Claude did not frame it as the single top issue, but did emphasize preserving canonical deletion/controller behavior and verifying final controller semantics.
- Claude recommended a pre-existing encrypted row decrypt fixture for Plan 05; OpenCode did not call out existing-row crypto continuity specifically, though it agreed Plan 05 is a higher-churn, security-sensitive step.
