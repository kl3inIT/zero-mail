## Decisions Made

- **ArchUnit DSL chaining gotcha discovered + correct pattern locked.** The plan's literal sketch (`.haveNameMatching(...).and().resideInAnyPackage(...)`) does not compile in ArchUnit 1.4.x — `ClassesShouldConjunction` has no zero-arg `.and()`. After confirming via `archunit-1.4.2-sources.jar` inspection (verified `ClassesThat<CONJUNCTION>` returns `CONJUNCTION` from `haveNameMatching` and the `CONJUNCTION` interface only exposes `andShould`/`orShould`), the rule was rewritten to compose `DescribedPredicate<JavaClass>` instances at the predicate level and use the `dependOnClassesThat(DescribedPredicate<? super JavaClass>)` overload. Pattern is now in `DomainBoundaryArchTests`'s class-level JavaDoc for future-domain authors.
- **Threat detected → defect found pattern confirmed.** DomainBoundaryArchTests caught its first real defects on its first execution: `OAuthProvisioningService.tenants` (TenantRepository) and `OnboardingService.users` (UserRepository). Plans 03/04 SUMMARYs claimed to have removed cross-domain repo injections but missed these two. This is exactly the T-01.2-H regression scenario the rule was designed to mitigate — earned its keep immediately.
- **Decomposition shape: extend CL-2 to non-delete writes.** Both fixes follow the same shape Plans 03–05 used for the delete-cascade primitives:
  - **Account → Tenant fix:** new `TenantService.createTenant(UUID tenantId, String displayName)` returns a managed `TenantEntity`. `OAuthProvisioningService` calls it from inside its existing `REQUIRES_NEW` transaction. Spring's `@Transactional` propagation joins (default `REQUIRED`), so atomicity of the tenant + user pair is preserved exactly as before.
  - **Onboarding → Account fix:** new `AccountService.advanceOnboardingStep(UUID tenantId, OnboardingStep next)` runs inside its own `@Transactional`. Throws `CurrentUserNotFoundException` if the user row is absent (semantics preserved). `OnboardingService` no longer needs a managed `UserEntity`; the dirty-tracking flush happens inside `AccountService`'s transaction. The state-machine forward-only invariant in `UserEntity#advanceTo` is unchanged.
- **`account → onboarding` Modulith edge already in place.** `account/package-info.java` declares `allowedDependencies = {tenant, onboarding, shared.privacy}`. Importing `OnboardingStep` into `AccountService` does not require any package-info change. `onboarding/package-info.java` already declares `{tenant, account, shared.privacy}`. Both edges are bidirectional at the module level (which is allowed — Spring Modulith does not forbid bidirectional `allowedDependencies`, only DI-time circular constructors), and Spring DI is satisfied because the dependency graph at runtime is `OnboardingService → AccountService` only (no cycle).
- **AccountDeletionController FK-safe order corrected in JavaDoc.** Plan prose said 'children → tenant → user'; actual code is `onboarding → gmail → user → tenant`. The latter is correct (users.tenant_id → tenants.id requires user-before-tenant; gmail/onboarding both reference tenants.id similarly). Fixed JavaDoc to match reality: 'children (onboarding, gmail) → user → tenant'.
- **Phase 1.2 byte-identical contract verified.** Three sweeps all returned empty diffs: `git diff --stat backend/core/src/main/resources/db/changelog/`, `git diff --stat gradle/libs.versions.toml`, `git diff --stat apps/web/openapi/`. The OpenAPI spec.json byte-identical means the FE OpenAPI codegen produces zero diff.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] ArchUnit DSL `.haveNameMatching(...).and().resideInAnyPackage(...)` does not compile in ArchUnit 1.4.x**
- **Found during:** Task 1 verify gate compile step.
- **Issue:** Plan's literal Java sketch failed `:backend:core:compileTestJava` with "cannot find symbol: method and() — location: interface ClassesShouldConjunction" (4 errors, one per rule). `ClassesThat<CONJUNCTION>.haveNameMatching(String)` returns `CONJUNCTION` (i.e. `ClassesShouldConjunction`), and that interface only exposes `andShould(...)` / `orShould(...)`, not zero-arg `and()`. Confirmed by inspecting `archunit-1.4.2-sources.jar`.
- **Fix:** Rewrote rules to compose predicates at the `DescribedPredicate<JavaClass>` level: defined a `nameEndsWithRepository` static `DescribedPredicate<JavaClass>` field, then used `nameEndsWithRepository.and(JavaClass.Predicates.resideInAnyPackage(...))` and passed through the `dependOnClassesThat(DescribedPredicate<? super JavaClass>)` overload. Compiles cleanly; semantics identical to the plan's intent. Pattern documented in the class-level JavaDoc for future-domain authors.
- **Files modified:** `backend/core/src/test/java/com/zeromail/core/arch/DomainBoundaryArchTests.java`
- **Verification:** `:backend:core:compileTestJava` PASS after fix; ArchUnit suite green.
- **Committed in:** `9529139`

**2. [Rule 1 + Rule 2 - Architectural enforcement bug] Two cross-domain repo injections lingered from Plans 03/04**
- **Found during:** Task 1 first-run of `DomainBoundaryArchTests`.
- **Issue:** Plans 03/04 SUMMARYs claimed AccountService dropped cross-domain repos (Plan 03) and OnboardingService was structured per CL-2 (Plan 04). DomainBoundaryArchTests's first real run revealed two missed violations:
  - **Violation A:** `OAuthProvisioningService` (in `core.account.service`) injected `TenantRepository` (in `core.tenant.persistence`). 3 sites: constructor parameter, field, `tenants.save(...)` call in `createTenantAndUser`.
  - **Violation B:** `OnboardingService` (in `core.onboarding.service`) injected `UserRepository` (in `core.account.persistence`). 4 sites: constructor parameter, field, `users.findFirstByTenantId(...)` calls in both `selectTemplate` and `complete`.
  Both are exactly the T-01.2-H regression the new rule was designed to catch.
- **Fix:** Extended the existing CL-2 service-to-service primitive pattern (already in place for the delete cascade) to non-delete writes:
  - Added `TenantService.createTenant(UUID, String)` — single-domain primitive returning the managed `TenantEntity`. `OAuthProvisioningService.createTenantAndUser` now calls `tenantService.createTenant(tenantId, email)` instead of `tenants.save(new TenantEntity(...))`. `REQUIRES_NEW` propagation on the outer method joins (Spring default `REQUIRED`), so atomicity is preserved.
  - Added `AccountService.advanceOnboardingStep(UUID, OnboardingStep)` — single-domain primitive that throws `CurrentUserNotFoundException` if no user row, then mutates `user.advanceTo(next)` on a managed entity (dirty-tracking flushes on `@Transactional` commit). `OnboardingService.selectTemplate` and `complete` now call `accountService.advanceOnboardingStep(...)` instead of holding a `UserRepository` themselves.
  - `account/package-info.java` already declared `allowedDependencies = {tenant, onboarding, shared.privacy}` (from Plan 04), so importing `OnboardingStep` into `AccountService` required no Modulith change.
- **Files modified:** `backend/core/src/main/java/com/zeromail/core/tenant/service/TenantService.java`, `backend/core/src/main/java/com/zeromail/core/account/service/OAuthProvisioningService.java`, `backend/core/src/main/java/com/zeromail/core/account/service/AccountService.java`, `backend/core/src/main/java/com/zeromail/core/onboarding/service/OnboardingService.java`
- **Verification:** ArchUnit suite green after fix; `OnboardingStateMachineTest`, `MeLanguageIntegrationTest`, `SessionCookieE2ETest`, `AccountDeletionE2ETest`, full clean check all PASS.
- **Committed in:** `9529139` (same commit as Task 1's net-new test, because the must_haves#1 contract requires both: rule must exist AND must pass).
