# Phase 08.1: inbox-zero-style-rule-actions-and-admin-managed-examples-cat - Context

**Gathered:** 2026-05-23
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 08.1 delivers Inbox Zero-style rule examples and expanded rule actions inside the existing Zero Mail rules experience. The user-facing flow stays centered on the current `RuleComposer`: users type or choose an example, convert it to a structured rule, review/edit it, and save it. The phase also makes the examples/action catalog DB-backed and admin-editable, expands the rule action model to include outbound actions, and replaces the current assistant-only Gmail send carve-out with one shared outbound gateway boundary used by both chat and rules.

</domain>

## Requirements (locked via SPEC.md + RACT requirements)

**12 requirements are locked.** The pass/fail requirement source is `.planning/REQUIREMENTS.md` (`RACT-01..12`). The phase scope and safety narrative are captured in `08.1-SPEC.md`.

Downstream agents MUST read both `08.1-SPEC.md` and `.planning/REQUIREMENTS.md` before planning or implementing. The current `08.1-SPEC.md` is a scope/safety spec and does not contain formal numbered `## Requirements`; therefore `RACT-01..12` are the canonical requirement IDs.

**In scope:**

- User rules UI: add Inbox Zero-style persona/example selection to the current `RuleComposer`; keep the existing prompt box, Convert to rule action, and structured review/edit path.
- User rules UI: selected persona examples render below the prompt box where hard-coded suggestions exist today.
- Example catalog: seed personas/examples from the copied Inbox Zero source, with English copied verbatim and Vietnamese translations seeded in DB.
- Example catalog: admin can edit English and Vietnamese text, persona metadata, enabled state, and display order through a minimal admin UI.
- Action catalog: surface `label`, `archive`, `save_draft`, `mark_read`, `star`, `add_to_digest`, `mark_spam`, `send_reply`, `forward_email`, and `send_email`.
- Settings: expose one global `Auto-send rules` setting, default ON. No per-action toggles.
- Runtime: if auto-send is disabled or a send safety gate fails, fallback to saving a Gmail draft instead of sending.
- Architecture: introduce one domain-neutral outbound send gateway used by both chat and rules. Gmail send calls remain inside that gateway boundary only.
- Architecture: fold the `@NamedInterface`/explicit module API-surface todo into planning so the outbound gateway and rules/admin/triage boundaries are not bypassed.

**Out of scope:**

- New wizard/page replacing `RuleComposer` — the existing composer remains the user flow.
- Large admin CMS for examples — no versioning, approval workflow, analytics, bulk import/export, or rich editor in this phase.
- Per-action outbound toggles — user gets one global auto-send rules switch.
- Rule-level acknowledgement checkbox/modal — considered too much friction for the user-first automation direction.
- Arbitrary webhook execution from rules — requires separate allow-list, secret, retry, and leak-review work.
- Permanent delete automation — spam/mark spam is in scope; destructive delete remains out.
- Porting Inbox Zero's TypeScript backend/runtime architecture — Inbox Zero is a product/UX reference only.

<decisions>
## Implementation Decisions

### Rule Creation UX Flow

- **D-01:** Keep the current Zero Mail rule composer. Do not build a new launcher, wizard, or page. The existing prompt box, Convert to rule flow, and Review & edit tab remain the backbone.
- **D-02:** Add `Choose from examples` inside the existing Describe tab. The user selects a persona like Inbox Zero, then examples for that persona render below the prompt box where the current three hard-coded suggestion chips live.
- **D-03:** Clicking an example replaces the full textarea content. It does not append, merge, or ask replace/append.
- **D-04:** The persona set matches Inbox Zero: Founder, Influencer, Realtor, Investor, Assistant, Developer, Designer, Sales, Marketer, Support, Recruiter, Student, Outreach, Other.

### Admin-managed Examples Catalog

- **D-05:** Examples/personas are DB-backed. Hard-coded frontend examples are not sufficient because the requirement is admin-managed without code changes.
- **D-06:** Seed data includes English copied verbatim from Inbox Zero and Vietnamese translations generated/curated during Phase 08.1. The user explicitly wants the Vietnamese seed included, not left blank for later.
- **D-07:** Admin UI is minimal but real: tables/forms for persona key/name/icon/order/enabled and example prompt EN/prompt VI/enabled/order. No heavy CMS features.
- **D-08:** User UI displays content by locale: Vietnamese UI uses `prompt_vi`; English UI uses `prompt_en`. If `prompt_vi` is missing for a future admin-created row, fallback to `prompt_en`.

### Outbound Opt-in UX

- **D-09:** Use one global `Auto-send rules` setting. It defaults ON after Phase 08.1 because the product direction is real automation, not draft-only automation.
- **D-10:** Do not add per-action toggles for reply, forward, and send. The user considered that unnecessary friction.
- **D-11:** Do not require rule-level acknowledgement checkboxes or confirm modals. A global ON setting plus visible rule/action copy is enough from the user perspective.
- **D-12:** Rules with outbound actions should still show clear status/copy such as `Will auto-send` / `Tu dong gui` in the rule review/list surface, but that copy must not block saving.

### Gate Failure Behavior

- **D-13:** If global `Auto-send rules` is OFF or a runtime safety gate fails, the system falls back to saving a Gmail draft. The rule still matches and produces useful output, but it does not send.
- **D-14:** `needs_review` in a separate Zero Mail review inbox is out of scope for this phase because it would require a new review surface.
- **D-15:** Skip-and-audit-only is not acceptable as the default because it makes automation appear to do nothing.

### Send Boundary Enforcement

- **D-16:** Refactor `AssistantSendExecutor` into a domain-neutral shared outbound gateway, e.g. `OutboundSendGateway`. Chat and rules both call the gateway.
- **D-17:** Move/retain `@AllowedSendCallSite` on the gateway boundary, not on an assistant-specific class.
- **D-18:** Replace the current "exactly one assistant send call site" expectation with a stronger package/class boundary rule: direct Gmail send APIs are allowed only inside the shared outbound gateway. Controllers, rule compiler, rule runtime, triage orchestration, admin packages, and worker orchestration must fail architecture tests if they call Gmail send directly.
- **D-19:** Do not create a separate `RuleSendExecutor`. Multiple send executors would weaken the boundary and create inconsistent safety behavior.

### Folded Todos

- **D-20:** Fold todo `2026-05-12-make-backend-core-context-api-surfaces-explicit-with-namedin.md` into this phase. Planning must decide explicit module API surfaces before or while introducing the outbound gateway so rules/chat/admin/triage dependencies do not reach into internal packages. The intent is boundary enforcement, not a broad backend refactor.

### Agent's Discretion

- **D-21:** The agent may choose exact package/class names for the outbound gateway if they are domain-neutral and make ArchUnit boundaries clear.
- **D-22:** The agent may choose the minimal DB schema shape for examples/personas/action descriptors, provided it supports bilingual text, enabled/order fields, and admin editing without code changes.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- `RuleComposer` already has the exact prompt box location for examples. The phase should replace the three hard-coded suggestion chips with persona-filtered DB examples rather than create another entry surface.
- `RulesWorkspace` already owns compile/save state and is the right integration point for example selection feeding the textarea.
- `RuleTemplateGallery` shows a compact template-card/list pattern, but Phase 08.1 examples are persona-driven and should not simply reuse the old template gallery semantics.
- `apps/admin` already has table/dialog/form patterns, query key factories, typed admin API conventions, and shadcn primitives for a minimal admin examples catalog.
- `AssistantSendExecutor` already handles Gmail message build, safety-net recipient check, audit state transitions, and actual `gmail.users().messages().send(...)`; it is the natural extraction point for a shared outbound gateway.

### Established Patterns

- Backend domain packages use `domain/`, `usecases/`, `projection/`, `exception/`, and `persistence/`. The folded `@NamedInterface` todo requires making public API surfaces explicit where this phase crosses modules.
- API DTOs are records under `backend/api/dto/<domain>/`; generated OpenAPI clients must be regenerated, not hand-edited.
- Frontend feature APIs live under `features/<feature>/api`, hooks under `features/<feature>/hooks`, and query keys in `features/<feature>/query-keys.ts`.
- Admin state mutations use append-only audit rows and confirm/reason conventions where destructive. Example catalog changes are not destructive to tenants, but should still be audited.
- Privacy constraints remain: no long-term Gmail-read email bodies, email-content prompts/completions, or embeddings. Draft bodies are allowed only when user-authored/action arguments under the existing carve-out.

### Integration Points

- Rule action expansion touches backend enum/model validation (`RuleActionType`, `ActionIntent`, `ActionIntentJsonValidator`, `RuleCompileResultValidator`), LLM tool schema (`Action`, `AllowListedTools`, tests), frontend manual builder (`rule-structure.ts`), preview/summaries, triage runtime, and audit serialization.
- Outbound action runtime must integrate with sender safety net, Gmail OAuth scope checks, idempotency, rate/daily caps, and audit state transitions before invoking the gateway.
- Example catalog requires Liquibase seed data, admin CRUD endpoints, user read endpoint, admin UI management, and user composer consumption.
- `Auto-send rules` setting likely belongs in user settings now, but Phase 9 may later reorganize settings into tabs. Keep API/data model stable so UI placement can move.

</code_context>
