# Phase 08.1 Research: Inbox Zero-style Rule Actions and Admin-managed Examples Catalog

**Researched:** 2026-05-23  
**Mode:** inline Codex research (`$gsd-plan-phase 8.1 --research --skip-ui`)  
**Status:** Ready for planning

## Executive Findings

Phase 08.1 is a cross-cutting architecture phase, not just a rules UI polish task. It touches:

- persisted rule schema and compiler contracts,
- tenant settings,
- Gmail write execution,
- admin-managed catalog data,
- user rule authoring UI,
- Spring Modulith boundaries,
- privacy and architecture tests.

The lowest-risk implementation is a staged rollout:

1. Reconcile stale docs/requirements first so the executor does not receive contradictory instructions.
2. Add explicit module API surfaces and the domain-neutral outbound gateway boundary before adding new send-capable rule runtime paths.
3. Build the examples/action catalog as DB-backed data with user read APIs and admin CRUD APIs.
4. Wire UI surfaces after APIs/codegen exist.
5. Expand rule action schema and compiler validation.
6. Enable runtime execution only through the gateway, with default-ON global auto-send setting and fallback-to-draft behavior.

## Existing Zero Mail Code Shape

### Rule Composer

`apps/web/features/rules/components/RuleComposer.tsx` already has the correct insertion point:

- Describe tab with the source textarea.
- Three hard-coded example chips (`receipts`, `calendar`, `newsletters`).
- `onSourceTextChange(exampleRule)` already replaces the textarea value.

Implementation should replace these hard-coded chips with persona-filtered DB examples. It should not create a new page or wizard.

### Rule Action Model

Current backend/frontend action support is deliberately narrow:

- `backend/core/.../rules/domain/RuleActionType.java`: `LABEL`, `ARCHIVE`, `SAVE_DRAFT`.
- `backend/core/.../rules/domain/ActionIntent.java`: sealed interface permits only `Label`, `Archive`, `SaveDraft`.
- `backend/core/.../llm/domain/Action.java`: only `label`, `archive`, `save_draft`.
- `apps/web/features/rules/lib/rule-structure.ts`: `MANUAL_ACTION_TYPES = ['label', 'archive', 'save_draft']`.
- `TriageSafetyPolicy`: runtime allow-list rejects every other action.
- `TriageOrchestratorService`: pre-write intent switch handles only the three current action intents.

Implementation impact: action expansion must be done end-to-end. Adding only UI choices or only LLM enum values would create invalid persisted rules or runtime safety rejections.

### Gmail Send Boundary

`AssistantSendExecutor` is the only current Gmail send call site and carries `@AllowedSendCallSite`. `OnlyOneGmailSendCallSiteTest` hard-codes the allowed package to `com.zeromail.core.chat.confirm.send`. This must change.

Implementation direction:

- Extract a shared gateway package, for example `com.zeromail.core.outbound.usecases` plus internal Gmail adapter package.
- Keep actual `gmail.users().messages().send(...)` inside the gateway implementation.
- Move the `@AllowedSendCallSite` marker to the shared gateway implementation.
- Keep chat confirmations using the gateway so Phase 7 behavior is preserved.
- Add ArchUnit tests that fail if rules, triage, controllers, worker, or admin code call Gmail send directly.

### Admin App

`apps/admin` is file-route based. Current authenticated routes are under `apps/admin/src/routes/_authenticated/`, for example:

- `_authenticated/catalog.tsx`
- `_authenticated/master-keys.*.tsx`
- `_authenticated/queue.tsx`
- `_authenticated/spend.tsx`
- `_authenticated/tenants.tsx`

Admin examples/action descriptors should follow the existing feature layout:

- `apps/admin/src/features/rule-catalog/`
- `apps/admin/src/routes/_authenticated/rule-catalog.tsx`

The current admin catalog feature is a useful pattern for TanStack Query hooks, typed API functions, dialogs, tables, and cache invalidation.

## Spring Modulith Boundary Research

Context7 lookup reached quota after the first result, so official Spring docs were used as fallback. Spring Modulith documents that:

- Application modules expose a provided API and hide internal implementation packages.
- `ApplicationModules.of(Application.class).verify()` builds and verifies the module model.
- `@NamedInterface("spi")` can be placed in `package-info.java` for a package that should be exposed.
- `allowedDependencies = "order :: spi"` uses the double-colon named-interface syntax to depend on a specific exported surface.

Source: https://docs.spring.io/spring-modulith/reference/1.4/fundamentals.html

Zero Mail implication:

- Add `package-info.java` named interfaces for the API packages this phase exports (`rules`, `outbound`, `tenant/settings`, admin catalog projections/use cases as needed).
- Restrict package dependencies through `@ApplicationModule(allowedDependencies = {...})` so cross-module calls use `module::api`, not persistence/domain internals.
- Run Spring Modulith verification and regenerate docs after implementation.

## Security and Privacy Notes

- Outbound send bodies for rule actions are draft/action arguments generated for the user-owned automation pathway. They must not include raw Gmail-read bodies and must respect the existing draft-body carve-out.
- Rule evaluation currently uses `semanticEvalContent` built from subject excerpt and metadata only. Do not expand it to raw body/snippet/header content in this phase.
- Admin catalog surfaces are configuration metadata. They must not expose tenant email bodies, prompts, completions, or Gmail-read content.
- Outbound runtime must write append-only audit records with gate/fallback reasons before/around Gmail writes.
- The default-ON global setting increases product usefulness but increases blast radius; this is why the gateway boundary, sender safety net, low-trust guard, caps, idempotency, OAuth scope check, tenant binding, and audit must be tested as a set.

## Planning Recommendation

Use six plans:

1. **08.1-01**: Contract/doc reconciliation + named-interface boundaries + outbound gateway contract.
2. **08.1-02**: DB-backed examples/personas/action descriptor catalog + seed + public/admin APIs.
3. **08.1-03**: Admin UI for bilingual catalog management.
4. **08.1-04**: User rule composer examples, Available Actions panel, and global setting UI.
5. **08.1-05**: Rule action schema/compiler/manual builder expansion.
6. **08.1-06**: Runtime outbound execution, fallback-to-draft, gateway extraction, ArchUnit/privacy/UAT gates.

This order prevents UI from racing ahead of schema/API contracts and prevents runtime sends from being introduced before the architecture boundary is enforceable.
