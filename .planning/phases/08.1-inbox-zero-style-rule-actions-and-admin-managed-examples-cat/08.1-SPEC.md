# Phase 08.1 Spec: Inbox Zero-style Rule Actions and Admin-managed Examples Catalog

## Product Decision

Zero Mail should move from "draft-only automation" to user-controlled inbox automation. From the user's perspective, a rule tool is incomplete if it can categorize mail but cannot send replies, forward mail, or send a new email when the user explicitly asked for that behavior.

This phase allows outbound rule actions only behind explicit settings and runtime safety gates. The goal is not to bypass the existing send restrictions; the goal is to replace the hard ban with a controlled outbound automation boundary that tests can enforce.

## Scope

1. Copy the Inbox Zero-style rule creation flow: `Create rules`, `Choose from examples`, `Add manually`.
2. Seed Zero Mail with the Inbox Zero examples/personas, then make them admin-managed.
3. Add an Available Actions panel and make action availability explicit in the UI.
4. Expand the structured rule action catalog to include:
   - `label`
   - `archive`
   - `save_draft`
   - `mark_read`
   - `star`
   - `add_to_digest`
   - `mark_spam`
   - `send_reply`
   - `forward_email`
   - `send_email`
5. Add one user setting for automated outbound rule actions: `Auto-send rules`.
6. Keep `Auto-send rules` ON by default for new users/tenants.
7. Do not add individual outbound action toggles or per-rule acknowledgement checkboxes/modals.
8. Route all actual Gmail sends through one shared outbound gateway/send executor.

## Safety Gates

Outbound rule actions execute only when all of these pass:

- global `Auto-send rules` setting
- sender safety net
- low-trust/static sender guard
- daily/rate cap
- idempotency key
- tenant isolation
- OAuth scope check
- append-only audit write

If any gate fails or the global setting is OFF, the runtime must downgrade the result to Gmail `save_draft` and record the reason. A separate review inbox surface is out of scope for this phase.

## Non-goals

- Do not port Inbox Zero's TypeScript backend/runtime architecture.
- Do not add arbitrary webhook execution in this phase.
- Do not add destructive delete automation in this phase.
- Do not weaken privacy constraints around Gmail-read email bodies, prompts/completions, or embeddings.

## Architecture Constraint

The old "zero or one Gmail send call site" tests must be replaced with a stricter boundary rule: direct Gmail send calls are allowed only inside the shared outbound gateway/send executor package. Controllers, rule compiler, rule runtime, admin packages, and worker orchestration code must fail architecture tests if they call Gmail send directly.

This preserves the user's requested automation while still preventing bypasses.
