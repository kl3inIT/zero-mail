## Summary

Phase 1.6 is a **frontend-only design infrastructure phase** with zero backend coupling. Most ambiguity has already been removed by SPEC's 9 locked requirements and CONTEXT's 17 implementation decisions. This research closes the remaining library-version-sensitive gaps:

1. **Tailwind 4 `@theme inline` token rebinding works exactly as D-A1 assumes.** Confirmed via Context7: rebinding `--background`, `--foreground`, etc. values inside `:root` and `.dark` blocks reflects in all `bg-background` / `text-foreground` utility classes without rebuild. NEW supplemental tokens (`--accent-soft`) require a `--color-accent-soft: var(--accent-soft)` entry inside `@theme inline` for the `bg-accent-soft` utility to compile.

2. **Be Vietnam Pro `vietnamese` subset is real and necessary.** Confirmed by direct Google Fonts CSS API fetch: subset returns explicit `unicode-range: U+0102-0103, U+0110-0111, ..., U+1EA0-1EF9, U+20AB`, covering the dense Vietnamese precomposed glyph block. Geist Sans `latin-ext` (which the project already loads) covers `U+1EF2-1EFF` only — *not* the full Vietnamese block — so Be Vietnam Pro `vietnamese` is required for correct diacritic rendering on body prose, not optional polish.

3. **Next 16 `cookies()` is async, and `cookieStore.set(name, value, options)` is the correct write path inside a `'use server'` function.** Confirmed by both the local bundled docs (`apps/web/node_modules/next/dist/docs/01-app/03-api-reference/04-functions/cookies.md`) and Context7. The async API is a Next 15 RC change, mature in 16.

4. **WCAG AA contrast: every Teal-palette pair passes for normal-weight body text and large text in both light and dark.** One caveat: `--text-faint` (`#8E8C82` light, `#6B6A63` dark) sits at ~3.2-3.7:1 on `--bg` — passes only for *large text* (≥18pt or ≥14pt bold) and UI components (≥3:1). Use `--text-faint` for captions/timestamps/eyebrows only, never body prose.

**Primary recommendation:** The plan should follow CONTEXT.md decisions verbatim. The only material additions surfaced by research are: (a) explicit `@theme inline` mapping for every supplemental token name; (b) a small Vietnamese-subset weight pruning recommendation (load `[400, 500, 600]` for Be Vietnam Pro; load `[400]` normal+italic for Instrument Serif); (c) a contrast guardrail forbidding `--text-faint` for body prose; (d) explicit Inbox Zero legal-footer copy port (lines 62-90, brand-swapped) plus VI translation drafts; (e) a Visual Sweep checklist schema the verifier can mechanically read.

## Library API Confirmations

### §1 — Tailwind 4 `@theme inline` token rebind semantics [VERIFIED: Context7 `/tailwindlabs/tailwindcss.com`]

**Confirmation 1: Rebinding existing token VALUES in `:root` and `.dark` reflects in all utility classes.** When `--background`, `--foreground`, `--primary`, etc. names stay constant but values change, every Tailwind utility (`bg-background`, `text-primary`, `border-border`, `ring-ring`) automatically resolves through `var(--color-X)` → `var(--X)` and reflects the new value at runtime via CSS cascade. No rebuild needed for value changes; only structural `@theme` changes (adding/removing token names) require a rebuild.

**Confirmation 2: NEW supplemental tokens MUST be exposed via `@theme inline` to generate utilities.** From Context7 official Tailwind v4 docs:

```css
@import "tailwindcss";

:root {
  --acme-canvas-color: oklch(0.967 0.003 264.542);
}

[data-theme="dark"] {
  --acme-canvas-color: oklch(0.21 0.034 264.665);
}

@theme inline {
  --color-canvas: var(--acme-canvas-color);
}
```
*Source: `https://github.com/tailwindlabs/tailwindcss.com/blob/main/src/docs/colors.mdx` — "Reference External CSS Variables in Tailwind @theme inline"*

**Implication for D-A1:** For every NEW supplemental token (`--accent-soft`, `--ink`, `--text-faint`, `--green`, `--green-soft`, `--amber`, `--amber-soft`, `--red`, `--red-soft`, `--blue`, `--blue-soft`, `--violet`, `--violet-soft`), add a matching `--color-{name}: var(--{name})` line inside the existing `@theme inline` block in `globals.css`. Otherwise utilities like `bg-accent-soft`, `text-text-faint`, `bg-green-soft` will not exist and class lookups will fall through to nothing.

**Implication for chrome helpers `--grain-dot`, `--gm-chrome-grad`, `--trust-bg`, `--trust-text`, `--nav-bg`:** These are not solid color tokens — they are gradients, alpha overlays, or specialized backgrounds. For these, use `style={{ background: 'var(--gm-chrome-grad)' }}` (inline style consuming the CSS variable directly) OR add a `--color-trust-bg: var(--trust-bg)` mapping if the token IS a solid color and you want utility-class access. Recommendation: keep the gradient/overlay tokens consumed via `style={{ ... }}` in TopBar/TrustPanel; only solid-color helpers (`--trust-bg`, `--trust-text`, `--nav-bg` if solid) get `@theme inline` entries.

**Confirmation 3: shadcn primitives use `bg-primary text-primary-foreground` etc. directly — they auto-rebrand.** Inspected `apps/web/components/ui/button.tsx` line 11-19: `bg-primary text-primary-foreground`, `bg-secondary text-secondary-foreground`, `bg-destructive/10 text-destructive`, `border-border`, `ring-ring`, etc. — every variant references token-utility classes. Rebinding `--primary` from `oklch(0.205 0 0)` to `#0E5E5A` updates every Button variant with zero source edits. Same logic for `alert.tsx`, `card.tsx`, `dialog.tsx`, `input.tsx`, `separator.tsx`, `skeleton.tsx`, `badge.tsx`. The Phase 1.5 D-C3 `<Alert variant="warning">` reads `--warning` → `--color-warning` → utility class; retuning `--warning` to `#B5731F` (light) / `#D9A064` (dark) automatically warms the warning Alert without touching `alert.tsx`.

**Confirmation 4: `@custom-variant dark (&:is(.dark *))` (already in `globals.css` line 5) is the existing dark-mode selector.** From Context7 official docs the canonical Tailwind v4 form is `@custom-variant dark (&:where(.dark, .dark *));` — a slight variant. The existing project form `(&:is(.dark *))` works for descendants but does NOT match `.dark` itself. **Practical impact: zero**, because the `.dark` class is always applied to `<html>` (root), and every visible element is a descendant — so `.dark *` matches everything that needs dark variants. *Recommendation:* leave `@custom-variant dark` untouched (Phase 1.4 D-C1 baseline). Do NOT change to `&:where(.dark, .dark *)` mid-phase — that's a Phase 1.4 concern not a Phase 1.6 concern.

### §2 — Next.js 16 `next/font/google` Vietnamese subset for Be Vietnam Pro [VERIFIED: Google Fonts CSS API + local Next.js bundled docs]

**Confirmation 1: `next/font/google` `subsets` is an array of strings; subset names come from Google Fonts.** From `apps/web/node_modules/next/dist/docs/01-app/03-api-reference/02-components/font.md`:
> "The font `subsets` defined by an array of string values with the names of each subset you would like to be preloaded. […] You can find a list of all subsets on the Google Fonts page for your font."

**Confirmation 2: Be Vietnam Pro DOES expose a `vietnamese` subset.** Direct fetch of `https://fonts.googleapis.com/css2?family=Be+Vietnam+Pro:wght@400;500;600;700&display=swap` (with browser User-Agent) returns three subsets per weight:
- `/* vietnamese */` — `unicode-range: U+0102-0103, U+0110-0111, U+0128-0129, U+0168-0169, U+01A0-01A1, U+01AF-01B0, U+0300-0301, U+0303-0304, U+0308-0309, U+0323, U+0329, U+1EA0-1EF9, U+20AB`. This is the dense Vietnamese precomposed block (Latin Extended Additional `1EA0-1EF9`) plus the đồng currency sign (`20AB`). **This is the subset the project needs.**
- `/* latin-ext */` — `U+0100-02BA, ..., U+1EF2-1EFF, ...` — covers Latin Extended-A and a partial slice of Vietnamese (`1EF2-1EFF` only).
- `/* latin */` — `U+0000-00FF, ...` — basic Latin only.

**Confirmation 3: Geist Sans `latin-ext` does NOT cover full Vietnamese.** Inspecting Geist's published `latin-ext` unicode-range, it covers `U+1EF2-1EFF` (a 14-glyph slice) but NOT `U+1EA0-1EEF` (the dense precomposed block: ấ, ầ, ẩ, ẫ, ậ, ắ, ằ, ẳ, ẵ, ặ, ẹ, ẻ, ẽ, ế, ề, ể, ễ, ệ, etc.). So the comment in current `apps/web/app/layout.tsx` line 18-20 ("Vietnamese diacritics render via the Latin Extended block, which the 'latin' + 'latin-ext' subsets cover") is **technically wrong for full Vietnamese coverage** — the browser falls back via combining-mark composition or system font. Be Vietnam Pro `vietnamese` subset is required for correct rendering of body Vietnamese prose.

**Confirmation 4: Be Vietnam Pro available weights.** The CSS API serves 100, 200, 300, 400, 500, 600, 700, 800, 900 (regular + italic). For bundle-size discipline, the recommended weight set is `['400', '500', '600']` — covers body, emphasis, and h-level weight without inflating the woff2 payload.

**Confirmation 5: Instrument Serif available subsets/weights.** Direct fetch of `https://fonts.googleapis.com/css2?family=Instrument+Serif:ital@0;1&display=swap` returns `latin` + `latin-ext` only (NO `vietnamese` subset). Single weight `400` available in normal + italic. Instrument Serif is for English display headings only (use `font-serif` utility on hero h1 only); do NOT use it for any Vietnamese text or it will fall back to system serif.

**Recommended `next/font/google` declarations** (planner verifies exact import names — Next/Vercel uses underscore convention `Be_Vietnam_Pro`, `Instrument_Serif`):

```ts
// app/layout.tsx
import { Geist, Geist_Mono, Be_Vietnam_Pro, Instrument_Serif } from 'next/font/google';

const geistSans = Geist({
  variable: '--font-geist-sans',
  subsets: ['latin', 'latin-ext'],  // unchanged
  display: 'swap',
});

const geistMono = Geist_Mono({
  variable: '--font-geist-mono',
  subsets: ['latin'],
  display: 'swap',
});

const beVietnamPro = Be_Vietnam_Pro({
  variable: '--font-be-vietnam-pro',
  subsets: ['vietnamese', 'latin'],   // 'vietnamese' is the critical addition
  weight: ['400', '500', '600'],      // bound bundle size
  display: 'swap',
});

const instrumentSerif = Instrument_Serif({
  variable: '--font-instrument-serif',
  subsets: ['latin'],
  weight: '400',
  style: ['normal', 'italic'],
  display: 'swap',
});
```

**Tailwind 4 mapping** (in `globals.css` `@theme inline`):
```css
--font-sans: var(--font-geist-sans), var(--font-be-vietnam-pro), ui-sans-serif, system-ui, sans-serif;
--font-mono: var(--font-geist-mono), ui-monospace, monospace;
--font-serif: var(--font-instrument-serif), 'Iowan Old Style', Georgia, serif;
```

`<html className="${geistSans.variable} ${geistMono.variable} ${beVietnamPro.variable} ${instrumentSerif.variable} ...">`. Body prose using `font-sans` will hit Geist Sans for Latin glyphs and fall through to Be Vietnam Pro for Vietnamese precomposed glyphs that Geist doesn't cover (browsers do per-glyph fallback when fonts are stacked in the same `font-family`). Hero h1 using `font-serif` hits Instrument Serif for English display headings.

[ASSUMED] The behavior of "browser falls through stacked fonts on a per-glyph basis when the primary font lacks a glyph" is standard CSS3 font-matching behavior and not Next.js-specific. The planner should still test by rendering "Triệt để bảo mật hộp thư" and "ặ ậ ề ể ễ ệ" in dev tools to verify glyph substitution lands on Be Vietnam Pro and not on system fallback.

### §3 — Next.js 16 Server Action cookie write [VERIFIED: bundled docs + Context7]

**Confirmation 1: `cookies()` is async in Next 16.** From `apps/web/node_modules/next/dist/docs/01-app/03-api-reference/04-functions/cookies.md`:
> "`cookies` is an **async** function that allows you to read the HTTP incoming request cookies in Server Components, and read/write outgoing request cookies in Server Functions or Route Handlers."

Version history table line: `v15.0.0-RC | cookies is now an async function. A codemod is available.`

**Confirmation 2: Set inside `'use server'` function.** From the same doc:
```ts
'use server'
import { cookies } from 'next/headers'

export async function create(data) {
  const cookieStore = await cookies()
  cookieStore.set('name', 'lee', { secure: true })
  // or
  cookieStore.set({
    name: 'name',
    value: 'lee',
    httpOnly: true,
    path: '/',
  })
}
```

**Confirmation 3: Available options.** From the docs:

| Option | Type | Description |
|--------|------|-------------|
| `name` | String | Cookie name |
| `value` | String | Cookie value |
| `expires` | Date | Exact expiry date |
| `maxAge` | Number | Lifespan in seconds |
| `domain` | String | Cookie domain |
| `path` | String, default `'/'` | Scope path |
| `secure` | Boolean | HTTPS-only |
| `httpOnly` | Boolean | Restrict to HTTP requests (no JS access) |
| `sameSite` | `Boolean`/`'lax'`/`'strict'`/`'none'` | Cross-site behavior |
| `priority` | `'low'`/`'medium'`/`'high'` | Browser eviction priority |
| `partitioned` | Boolean | CHIPS partitioning |

**D-C1/C3 mapping is fully correct.** The recommended pattern from CONTEXT.md compiles cleanly:

```ts
// apps/web/features/landing/lib/setTheme.ts
'use server';

import { cookies } from 'next/headers';

export async function setTheme(formData: FormData) {
  const raw = formData.get('theme');
  const theme = raw === 'dark' ? 'dark' : 'light';
  const cookieStore = await cookies();
  cookieStore.set('zm-theme', theme, {
    sameSite: 'lax',
    secure: process.env.NODE_ENV === 'production',
    httpOnly: false,
    maxAge: 60 * 60 * 24 * 365,
    path: '/',
  });
}
```

**Confirmation 4: `<form action={...}>` flow with Server Action and `useTransition`.** From Context7:
> "Server Actions are automatically used with `startTransition` when passed to a `<form>` using the `action` prop or to a `<button>` using the `formAction` prop. When invoked, Next.js can return both the updated UI and new data in a single server roundtrip."

> "After you set or delete a cookie in a Server Function, Next.js can return both the updated UI and new data in a single server roundtrip when the function is used as a Server Action."

**Recommended ThemeToggle pattern (Client Component):**

```tsx
// apps/web/features/landing/components/ThemeToggle.tsx
'use client';

import { useTransition } from 'react';
import { setTheme } from '@/features/landing/lib/setTheme';

export function ThemeToggle({ currentTheme }: { currentTheme: 'light' | 'dark' }) {
  const [isPending, startTransition] = useTransition();
  const next = currentTheme === 'dark' ? 'light' : 'dark';
  return (
    <form action={(fd) => startTransition(() => setTheme(fd))}>
      <input type="hidden" name="theme" value={next} />
      <button
        type="submit"
        disabled={isPending}
        aria-label={currentTheme === 'dark' ? 'Switch to light mode' : 'Switch to dark mode'}
        aria-pressed={currentTheme === 'dark'}
        className="..."
      >
        {currentTheme === 'dark' ? <SunIcon /> : <MoonIcon />}
      </button>
    </form>
  );
}
```

Alternative using `useActionState` is also valid but heavier (returns state + formAction + pending). For a single-purpose binary toggle, `useTransition` + plain form action is the lighter pattern.

**Gotcha 1:** A bare `<form action={setTheme}>` (no `startTransition` wrapping) ALSO works — Next auto-wraps via `startTransition`. The wrapper is only needed if you want to drive client-side optimistic UI state alongside the server submit. For a pure cookie-write toggle that re-renders the whole tree on submit, the simpler `<form action={setTheme}>` is fine. **Recommendation:** go with the simpler form unless `frontend-design` skill calls for a pending-state spinner.

**Gotcha 2:** Cookie writes invalidate RSC tree on the next render — Next will return updated UI + new cookie in the same roundtrip. The `<html>` re-renders with `class="dark"` automatically. No client navigation, no `router.refresh()` call needed.

**Gotcha 3:** From the bundled docs: *"HTTP does not allow setting cookies after streaming starts, so you must use `.set` in a Server Function or Route Handler."* — ruling out attempting `cookies().set()` from a Server Component render path. The Server Action pattern is the only correct shape; D-C1 already lands here.

### Anti-Patterns to Avoid

- **DO NOT** introduce a new wrapper primitive like `<StatusAlert>` or `<PageShell>` (Phase 1.5 D-C1 deflated those — do not re-inflate).
- **DO NOT** use raw color names (`text-stone-700`, `bg-amber-50`, `border-blue-300`). Every utility resolves through a token. (Phase 1.4 D-C2 baseline.)
- **DO NOT** use `localStorage` for theme persistence (D-C4 explicit reject).
- **DO NOT** use `prefers-color-scheme` system theme detection in v1 (D-C5 explicit reject; defer to v2).
- **DO NOT** apply `font-serif` to Vietnamese hero headings — Instrument Serif has no Vietnamese subset and will fall back to system serif. Use `font-sans` for Vietnamese and let Be Vietnam Pro handle diacritics.
- **DO NOT** `cookies().set()` from a Server Component render path — Next will throw at runtime. Cookie writes only legal in Server Actions / Route Handlers.
- **DO NOT** create a barrel `apps/web/features/landing/index.ts` re-export (Phase 1.3 D-A5 absolute rule).
- **DO NOT** promote `ZMLogoMark` to `apps/web/components/brand/` until a third consumer outside `features/landing` and `features/auth` exists (D-B3 YAGNI).
- **DO NOT** export `--text-faint` (`#8E8C82` light) for body prose — its 3.22:1 contrast on `--bg` fails AA for body text. Captions/timestamps/eyebrows only.
- **DO NOT** synchronously call `cookies()` (Next 16 requires `await`).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Theme persistence | localStorage + `useEffect` hydration mirror | `zm-theme` cookie + Server Action + RSC read | Hydration mismatch warnings; first-paint flash; doesn't survive cross-tab |
| Dark mode CSS toggle | JavaScript-driven `data-theme="dark"` attribute | Tailwind `dark:` variant + `@custom-variant dark (&:is(.dark *))` (already wired) | Project standard; shadcn primitives auto-resolve |
| Token color application | Inline `style={{ color: '#0E5E5A' }}` | `text-accent` utility class via `--color-accent: var(--accent)` mapping | Token discipline; dark-mode auto-swap; theme switch reflects via cascade |
| Font loading | `<link rel="stylesheet" href="https://fonts.googleapis.com/...">` | `next/font/google` with `variable` + `subsets` | Self-hosting, layout-shift prevention, build-time CSS extraction, no Google network call |
| Pending state on theme submit | Manual `useState({ pending: true })` + `fetch()` | `<form action={setTheme}>` + (optional) `useTransition` | Auto wraps in `startTransition`; revalidates UI in same roundtrip; documented Next pattern |
| i18n parity gate | Manual diff check | Existing `pnpm i18n:check` (`scripts/check-i18n.ts`) | Already shipped; just extend `EN_SCAN_FILES` |
| Lighthouse audit | `lighthouse` npm CLI from scratch | `npx lighthouse https://localhost:3000 --only-categories=performance,accessibility,best-practices --form-factor=mobile` | Standard tool; project may add `pnpm lighthouse:landing` script |
| WCAG contrast verification | Hand calculations every time | Browser DevTools "Inspect → Accessibility → Contrast" + offline ratios in this research | Browser tools surface contrast inline; this research provides the baseline ratios |

**Key insight:** The phase scope is light enough that no new external libraries are warranted. Every requirement composes existing Next 16, Tailwind 4, shadcn, next-intl, and TanStack Query primitives. The risk is *building the wrong thing* (e.g., re-introducing localStorage, hand-rolling a Theme Provider with React Context, hand-rolling a Step Indicator with `useState` instead of reading the server-side enum), not *missing a library*.

## Common Pitfalls

### Pitfall 1: Forgetting `--color-{name}: var(--{name})` for new tokens
**What goes wrong:** Add `--accent-soft: #E6EFEE` to `:root` and `.dark` but forget the `@theme inline` mapping. Tailwind utility `bg-accent-soft` does not exist. Build silent. Class lookup falls through to nothing. Component renders with no background.
**Why it happens:** D-A2 mentions the `@theme inline` mapping but executor may forget when adding the 13 new supplemental tokens.
**How to avoid:** For every NEW token name added in `:root` and `.dark`, add a corresponding `--color-{name}: var(--{name})` line inside `@theme inline`. Verify by writing a test page that renders all 13 with the utility class and visually inspects no fallback.
**Warning signs:** A `bg-accent-soft` div renders transparent in DevTools. Browser computed style: `background-color: rgba(0,0,0,0)`.

### Pitfall 2: Applying `font-serif` to Vietnamese text
**What goes wrong:** Hero h1 uses `font-serif` (Instrument Serif). At locale `vi` the heading text contains Vietnamese diacritics. Instrument Serif has no `vietnamese` subset → browser falls back to system serif → visual inconsistency between EN and VI hero.
**Why it happens:** Cosmetic decision made without locale awareness.
**How to avoid:** Use `font-serif` ONLY for English headings, `font-sans` (Geist + Be Vietnam Pro fallback) for Vietnamese. Either: (a) accept that Vietnamese hero h1 is sans-serif and English hero h1 is serif (locale-conditional class), OR (b) drop Instrument Serif use entirely and pick a different display weight/size in Geist for hero. **Recommendation (a)**: serif tone is a "polish" the EN audience appreciates; VI audience doesn't lose anything if hero is sans (Be Vietnam Pro is a beautiful sans). The `frontend-design` skill picks at execution.
**Warning signs:** Render `vi` locale + DevTools "Computed → font-family" on the hero h1 shows system fallback (Times New Roman, Iowan Old Style) instead of Instrument Serif.

### Pitfall 3: Theme cookie not surviving cross-tab
**What goes wrong:** User toggles theme to dark in tab A; opens tab B; tab B loads in light mode.
**Why it happens:** Cookie not written, or written with `path` other than `/`, or written with mismatched `domain`.
**How to avoid:** D-C3 attributes (`path: '/'`, no `domain`) — cookie is sent with every request to the same origin, both tabs read the same value at SSR time. Verify by toggling in tab A, opening tab B in same browser session.
**Warning signs:** `Application → Cookies → http://localhost:3000` in DevTools shows `zm-theme=dark` but `<html>` in tab B has no `dark` class. Likely the RSC cookie read in `app/layout.tsx` was forgotten (D-C2).

### Pitfall 4: Stale-tree hydration mismatch from theme class
**What goes wrong:** RSC reads `zm-theme=dark` and emits `<html class="dark">`. Client React hydrates and (somehow) calculates a different class. React logs hydration mismatch warning.
**Why it happens:** Mixing localStorage + cookie. If executor adds a "fallback to localStorage" path on the client, the client computes a different class than what the server rendered.
**How to avoid:** D-C4 — NO localStorage anywhere. Cookie is single source of truth. Client never recomputes the `<html>` class — it ONLY trusts the server-rendered value.
**Warning signs:** Browser console: "Warning: Prop `className` did not match. Server: 'geist-sans dark' Client: 'geist-sans'".

### Pitfall 5: Vietnamese diacritic missing in body prose
**What goes wrong:** User views Vietnamese landing. Body prose has correct ASCII Vietnamese ("ban", "bao mat") but precomposed glyphs ("bạn", "bảo mật") render as boxes or fall back to ugly system font.
**Why it happens:** Be Vietnam Pro `subsets` not set to include `'vietnamese'`, OR `--font-be-vietnam-pro` variable not in the `--font-sans` stack, OR `<html>` className does not include `${beVietnamPro.variable}`.
**How to avoid:** Three checks: (a) `next/font/google` Be_Vietnam_Pro call has `subsets: ['vietnamese', 'latin']`; (b) `globals.css` `@theme inline` has `--font-sans: var(--font-geist-sans), var(--font-be-vietnam-pro), …`; (c) root `<html className="...${beVietnamPro.variable}...">`.
**Warning signs:** Render Vietnamese text → DevTools Computed → font-family does not include "Be Vietnam Pro".

### Pitfall 6: Accidentally regressing `reassertServerLocale` flow
**What goes wrong:** Editing `app/layout.tsx` to add cookie read + 2 fonts; accidentally simplifies away the `reassertServerLocale` machinery (Phase 1.5 D-D2 invariant).
**Why it happens:** The current layout is dense with comments and conditional logic; an executor refactoring may eliminate the "complex part" thinking it's optional.
**How to avoid:** Treat `reassertServerLocale` as inviolable. Phase 1.6 ADDS to layout.tsx; never SUBTRACTS from existing flows. Code-review checklist row: "After Phase 1.6 layout edits, `git diff app/layout.tsx` shows only ADDITIONS, no DELETIONS to existing logic."
**Warning signs:** Locale switch behavior breaks in Playwright e2e (Phase 1.5 P05 spec).

### Pitfall 7: TopBar/Footer break the existing "Phase 1.3 light skeleton" header on `(public)/layout.tsx`
**What goes wrong:** `(public)/layout.tsx` already has a header (`<header className="bg-secondary border-b">…`). Replacing it with `<TopBar />` could (a) remove existing keys (`common.nav.docs`, `common.nav.signIn`) that the i18n:check parity guard now requires, (b) break the docs route link, (c) drop `LanguageSwitcher` accidentally.
**Why it happens:** Replacement instead of refactor.
**How to avoid:** TopBar must SUPERSET the existing header capabilities — keep the Sign-in CTA, keep `LanguageSwitcher` integration, optionally re-expose the Docs link (or remove it since landing CTA is "Sign in"). The i18n keys `common.nav.docs` and `common.nav.signIn` either continue to be used (TopBar references them) OR are removed in lockstep with their last consumer (i18n:check parity guard catches this — if a key is removed in vi.json but kept in en.json, the build fails).
**Warning signs:** `pnpm i18n:check` fails with `[parity] vi.json and en.json leaf-key sets differ`.

### Pitfall 8: Stub `/terms` and `/privacy` not under `(public)/` group
**What goes wrong:** Putting `/terms/page.tsx` directly under `app/terms/` — routes outside `(public)/` group don't get the public layout's TopBar/Footer wrapper. Users land on a chrome-less page.
**Why it happens:** Next.js route groups are syntactic; placement matters.
**How to avoid:** `apps/web/app/(public)/terms/page.tsx` and `apps/web/app/(public)/privacy/page.tsx`. The `(public)/layout.tsx` wraps both.
**Warning signs:** `/terms` returns 200 but page renders without TopBar.

### Pitfall 9: `useTransition` inside RSC
**What goes wrong:** Putting `useTransition` import in a Server Component (no `'use client'` directive). Next throws `useTransition only works in client components`.
**Why it happens:** Confusion about which component is the client island.
**How to avoid:** ThemeToggle has `'use client'` at the top. The Server Action `setTheme` (`features/landing/lib/setTheme.ts`) has `'use server'`. TopBar is RSC; it imports ThemeToggle as a client island.
**Warning signs:** Build error "useTransition only works in client components".

## Performance Budget

### Lighthouse ≥ 90 strategy for `/` (mobile + desktop)

**Baseline.** A Next 16 + Tailwind 4 + RSC landing with no client JS islands beyond ThemeToggle (and no images, no third-party scripts) routinely scores 95-100 mobile out of the box. The risks are font loading and Cumulative Layout Shift (CLS).

**Font loading order:**
1. **Preload primary fonts: Geist Sans + Instrument Serif.** Geist is the body default; Instrument Serif is the hero LCP candidate (heading is the largest text on first paint).
2. **Do NOT preload Be Vietnam Pro.** It's the secondary fallback for Vietnamese diacritics. `next/font` automatic preload is fine; explicitly setting `preload: false` is overkill at this bundle size (~20-25KB woff2 for vietnamese subset across 3 weights).
3. **`display: 'swap'` everywhere** to avoid FOIT (flash of invisible text).
4. **`adjustFontFallback` left at default `true`** for `next/font/google` — automatic CLS-reducing fallback metrics.

**Bundle weights estimate (woff2, after subsetting):**
- Geist Sans (latin + latin-ext): ~30-40 KB
- Geist Mono (latin): ~25 KB
- Be Vietnam Pro `vietnamese` + `latin` × 3 weights (400/500/600): ~60-90 KB total
- Instrument Serif (latin) × normal+italic × 1 weight (400): ~25-30 KB
- **Total font payload: ~140-185 KB woff2** — within Lighthouse's friendly threshold for landing pages.

**Recommended weight pruning to stay under 150KB:**
- Be Vietnam Pro: weights `[400, 600]` (drop 500) — unless `frontend-design` skill insists on a 500 medium for body emphasis.
- Instrument Serif: only `weight: '400'`, only `style: ['normal']` initially (italic adds ~12KB; defer until needed).

### LCP candidate: Hero h1 text

The hero h1 is the largest text on first paint. Two scenarios:
- **English hero h1 with `font-serif` (Instrument Serif):** LCP element is a TEXT node. LCP timing depends on font load. Preload Instrument Serif weight 400 normal via `next/font`'s automatic preload. Target: < 2.5s mobile.
- **Vietnamese hero h1 with `font-sans` (Geist Sans + Be Vietnam Pro fallback):** LCP element same text node, font Geist Sans (already preloaded). Target: < 2.5s mobile.

### CLS: Layout shift prevention

- `next/font` automatic fallback metrics adjustment + `display: 'swap'` + `adjustFontFallback: true` = near-zero CLS from font load.
- No images on landing in v1 (per CONTEXT decisions). No CLS from image load.
- ThemeToggle is a fixed-size icon button — no shift on hydration.
- TopBar height is fixed via padding; no shift when fonts swap in.

### Other strategies

- **No third-party JS** on landing (no analytics SDK in v1). Lighthouse "Best Practices" benefits.
- **No client-side router intercepts** — TopBar Sign-in CTA is `<Link href="/login">`, lets Next handle prefetch.
- **Inline SVG for ZMLogoMark** (not external file) — saves 1 HTTP round-trip, file is <500 bytes.
- **No analytics, no Crisp chat, no Datadog browser RUM** in v1. Add only via a future observability phase.

## Critical Landmines

### LM-1: Tailwind 4 `@custom-variant dark (&:is(.dark *))` does not match `<html class="dark">` itself

The existing project form `&:is(.dark *)` matches *descendants of `.dark`*, not `.dark` itself. If any utility is applied directly to `<html>` (rare; usually utilities go on body or wrapper divs), the dark variant won't activate. **Practical impact: zero in this project** — all dark-conditional utilities sit on body or descendant elements. But if `frontend-design` skill puts a `dark:bg-bg` on `<html>`, it will silently fail. *Recommendation: avoid dark-conditional utilities on `<html>` itself.*

### LM-2: shadcn primitive `outline` button variant uses `bg-background` — retunes to paper-warm

Inspecting `button.tsx` line 12-13: `outline: "border-border bg-background hover:bg-muted hover:text-foreground …"`. After token swap, the outline button background is `#FAFAF7` (light) — slightly warmer/cream-ish on a `#FAFAF7` page background, looking borderline invisible. **Mitigation:** outline button border (`--border = #E5E3DA`) provides visible separation. Verify in visual sweep — if outline buttons look ghost-like, the planner can let `frontend-design` skill bump the border weight.

### LM-3: Phase 1.5 P02 STATE.md note line 152 — `<Button>` causes vitest `useRef null-dispatcher` failure

The project uses `Button` from `@base-ui/react/button` (line 1 of `button.tsx`). Per Phase 1.5 P02 deviation, vitest cannot dedupe `react` across `@base-ui/react` transitive boundary; tests using `<Button>` directly fail with `Cannot read properties of null (reading 'useRef')`. The escape pattern is `<a className={cn(buttonVariants({ size: 'lg' }), 'w-full')}>` for any test-rendered surface (e.g., LoginForm, Onboarding). **Implication for Phase 1.6:** TopBar Sign-in CTA (`<Link className={buttonVariants()}>`) and Hero CTA (already `<Link className={buttonVariants()}>` in current code) are already correct. ThemeToggle is a `<button>` element with manual styling — no `<Button>` import. AuthTopBar back-link should be `<Link className={cn(buttonVariants({ variant: 'ghost', size: 'sm' }))}>`, not `<Button asChild><Link>`.

### LM-4: `next-intl` typed-key check rejects unknown namespaces

After Phase 1.5 P07, `next-intl 4.x` strict typed bundle is engaged. Adding new namespaces (`nav.*`, `trust.*`, `how.*`, `feat.*`, `legal.*`, `footer.*`, `onboarding.steps.*`) requires the keys to land in BOTH vi.json and en.json BEFORE the calling component compiles. Otherwise `t('trust.p1.title')` fails the typed-key check. **Mitigation pattern (from Phase 1.3 P05/P07 STATE.md):** keys land FIRST, then components reference them. Or use `t('namespace.key' as never)` cast bypass temporarily during ship sequence.

### LM-5: `pnpm i18n:check` extension forgotten → silent EN-prose leak

The EN-scanner only scans files listed in `EN_SCAN_FILES` (lines 44-72 of `scripts/check-i18n.ts`). New files under `features/landing/components/` MUST be added to that list, otherwise English prose strings won't be flagged and the i18n parity gate becomes a Swiss-cheese check. **Mitigation:** add the file-list extension as Task 0 / Wave 0, not Wave 5.

### LM-6: Stub `/terms` route loaded inside `(public)/` group also gets the TopBar

If `/terms` and `/privacy` live under `(public)/`, the public layout (TopBar + Footer) wraps them — which is fine for landing/docs flow. But on `/login`, a user clicking "Terms" will navigate AWAY from the auth-shell to a public-shell page. Browser back returns to `/login`. **Acceptable UX** — but worth documenting in the visual sweep. *No alternative location is better* — putting `/terms` under `(auth)/` group makes them inaccessible without auth.

### LM-7: First Lighthouse run on `localhost:3000` underestimates Performance

A cold `pnpm dev` server is dev-mode (no production build, no minification, no font preload optimization). Lighthouse against `pnpm dev` typically scores 60-75 — does NOT meet 90. **Verifier MUST run against `pnpm build && pnpm start`** (production build), not `pnpm dev`. Add this to `01.6-VISUAL-SWEEP.md` instructions.

### LM-8: `apps/web/AGENTS.md` directive — read local Next.js docs before writing code

Cited in Phase 1.6 init context: `apps/web/CLAUDE.md` references `@AGENTS.md` which states: *"This is NOT the Next.js you know. APIs, conventions, and file structure may all differ from your training data. Read the relevant guide in `node_modules/next/dist/docs/` before writing any code."* Planner must inject this directive into every executor prompt that touches `apps/web/`. Concretely: before writing the Server Action, executor must read `apps/web/node_modules/next/dist/docs/01-app/03-api-reference/04-functions/cookies.md`. Before writing the font setup, read `apps/web/node_modules/next/dist/docs/01-app/03-api-reference/02-components/font.md`. This is a non-negotiable project rule.

### LM-9: Tailwind 4 `@custom-variant` syntax differs from v3 `darkMode: 'class'`

Project already migrated to `@custom-variant dark (&:is(.dark *))` (Phase 1.4 D-C1). Training data may suggest `darkMode: 'class'` config — that's Tailwind v3, doesn't apply here. No `tailwind.config.js` exists in v4 (config is CSS-driven via `@theme`).

### Q1: Onboarding URL split — 3 separate routes vs single state-driven page?

SPEC REQ-6 says `(protected)/onboarding/{gmail-connect,template-select,complete}` (3 URLs). Reference design has primary "Sign in" + sometimes secondary "Read docs" / "View setup". ### Q3: Instrument Serif application scope

Reference uses Instrument Serif on hero h1 only. Could extend to section h2 titles. **Recommendation: hero h1 only**, English-locale only — Vietnamese hero uses `font-sans` via Be Vietnam Pro fallback. `frontend-design` skill picks size/weight.

### Q4: Be Vietnam Pro weight count

`[400, 500, 600]` (3 weights) vs `[400, 600]` (2 weights). 2 weights saves ~30KB. **Recommendation: `[400, 600]` initially**; add 500 if `frontend-design` skill explicitly requires medium-emphasis text styling that 400/600 can't approximate.

### Q5: HowItWorks step illustrations

Reference has detailed inline mock UIs (Connect with Gmail logo, Rule input with mono cursor, Audit log rows). **Recommendation: port the inline mocks** since they're cleanly contained inline SVG and Tailwind-shapeable. ### Q6: TopBar mobile-only Sign-in CTA visibility

Always visible vs collapsed to icon. **Recommendation: always visible** — it's the only CTA and the page's purpose. Mobile collapse to icon-only adds nothing.

### Q7: Theme toggle ARIA attributes

`aria-label` (recommended) vs `aria-label` + `aria-pressed`. **Recommendation: both** — `aria-label` describes what clicking does, `aria-pressed` exposes the binary state to assistive tech. Pattern in Pattern 3 above includes both.

### Q8: AuthTopBar back-link target on onboarding

Reference shows "← Back to home". On sign-in page, "Back to home" → `/`. On onboarding, "Back to home" is awkward — user already authenticated. **Recommendation: omit back-link on onboarding** (the StepIndicator's completed pills serve as backward nav per D-D5). `frontend-design` skill confirms.

### Q9: Footer position on landing

Reference design footer is sticky-at-bottom. With landing being long-scroll (4 sections), the footer naturally lands at bottom of `<main>`. **Recommendation: not sticky**; footer below content. This matches the Phase 1.3 D-C2 light-skeleton pattern where the existing `(public)/layout.tsx` had no footer.

### Q10: Should the `--grain-dot` overlay apply to landing only or all surfaces?

Reference applies grain to body. **Recommendation: apply to body via `globals.css`** as a subtle overlay (0.018 alpha in light, 0.014 in dark) — it adds paper feel everywhere without visual noise. If `frontend-design` skill reports the grain reads as "noise" on small screens, scope to landing-hero-only via inline `style`. Verify in visual sweep.
