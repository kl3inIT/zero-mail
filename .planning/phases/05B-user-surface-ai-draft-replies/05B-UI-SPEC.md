# Phase 5B — UI Design Contract

> Visual and interaction contract for the Phase 5B authenticated `apps/web` additions: a two-bucket **needs-reply inbox** (To reply / Awaiting reply [+ optional Resolved]) with per-thread draft status and "open in Gmail" links, a **"Draft reply / Regenerate draft"** action surfaced on both the needs-reply rows and the existing `/triage` audit-log rows, and the now-live `/triage` audit list (the `GET /api/triage/audit` endpoint closed in this phase). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope note:** this phase adds to the *authenticated* product surface and inherits the **base token contract** from `app/globals.css` `:root` / `.dark` (teal accent `#0E5E5A`, paper-warm neutrals) — identical to Phase 5A. It does **NOT** opt into the `.zm-proto` / `.zm-auth` clay-accent prototype skin (that skin is public/marketing/auth-only, Phase 1.6). New authenticated UI is built from raw shadcn `base-nova` primitives bound to the existing CSS-variable tokens; **no wrapper components** until the rule-of-three applies (project conventions, 05B-CONTEXT D-18 "no custom wrapper components — reuse the existing `features/triage` `AuditTable`-style table shape; new code under `features/needs-reply/`").
>
> **Hard product constraint reflected in the UI:** review / edit / send of a draft happens **100% in Gmail**. There is no in-app draft preview, no draft body rendered anywhere, no "send" button, no `users.drafts.update`. The needs-reply inbox shows *that a draft exists and its status* and links out to Gmail. Auto-send is impossible by construction (05B-CONTEXT D-19, "Specific Ideas"; DRFT-04).

## Spacing Scale

8-point base scale (12 included as 4×3) — **identical to Phase 5A**. Use Tailwind spacing utilities only; never arbitrary px values for layout gaps.

| Token | Value | Usage |
|-------|-------|-------|
| 2xs | 4px | Icon-to-label gaps, inline chip padding, badge internal padding |
| xs | 8px | Compact element spacing, table cell vertical padding (dense mode), list-item gaps, gap between a row's stacked second-line metadata on mobile |
| sm | 12px | Tab trigger padding, card-list item gaps, gap between draft-status badge and action button |
| md | 16px | Default element spacing, gap between the tab strip and the list, between filter controls |
| lg | 24px | Page section padding, gap between the page heading block and the tab strip, empty-state inner padding |
| xl | 32px | Page content gutters (desktop), gap between major sections |
| 2xl | 48px | Empty-state vertical centering padding, major section breaks |
| 3xl | 64px | Page-level top/bottom rhythm on wide layouts |

Layout spacing scale, restated: **4 / 8 / 12 / 16 / 24 / 32 / 48 / 64**.

**Optical micro-adjustments (not part of the layout scale):** a `2px` (`3xs`) nudge is permitted *only* for badge optical centering, status-dot offsets, and similar hairline insets — **never** for layout gaps, padding, or margins between elements.

**Touch targets:** the per-row action button (`Draft reply` / `Regenerate draft`), the `Mark resolved` (X) control, the "Open in Gmail" link, and the `SidebarTrigger` render with a **minimum 40px hit area** (44px at the 320px breakpoint) even if the visible glyph is smaller — pad the hit area, not the icon. On mobile these controls become icon-only but keep the 44px hit area.

**Exceptions:**
- The needs-reply list and the `/triage` audit `Table` use a **dense row rhythm** (`py-2` / 8px vertical cell padding, ~36–40px row height) at `≥ md` — intended density for a log/queue, consistent with the 5A "evidence locker" table. The card-list renderer below `md` reverts to `lg` (24px) card padding and stacks the row into title → metadata line → status+actions line.
- Tab strip: shadcn `tabs` defaults; do not override trigger height.
- Icon rail (collapsed sidebar) item slot for the new "Needs reply" entry follows the shadcn `sidebar` block defaults (~32–40px square) — do not override; the `TO_REPLY` count badge attaches per the block's badge slot.
- Top-header chrome bar height stays the 5A **56px** — unchanged, this phase adds no chrome.

## Typography

Exactly **4 type sizes** — **identical to Phase 5A**. Geist Sans for everything except Geist Mono for data fields. Tier differentiation (page heading vs. section heading vs. card/row title) is done with **weight and color**, not extra sizes.

| Role | Size | Weight | Line Height | Covers |
|------|------|--------|-------------|--------|
| Label / small | 12px | 500 (medium) | 1.4 | Tab trigger labels, count badges, table column headers, draft-status badge text (`No draft` / `Draft ready` / `Draft sent`), the relative-time label, "classifying…" banner text, nav item label, the muted "Resolved" hint. |
| Body | 14px | 400 (regular) | 1.5 | Default UI text, table cells, the thread subject, the other-party name/email, descriptions, the action button label, empty-state body copy, error-state body copy. (UI-dense product surface — 14px body, not 16px; matches the existing app and shadcn `base-nova` defaults.) |
| Heading | 20px | 600 (semibold) | 1.25 | The `/needs-reply` page heading and the `/triage` page heading; section headings within a page. Card/row titles (the thread subject acts as a "row title") render at the **Body 14px** step with weight 500 — they are *not* a Heading-tier element; the page heading is the only 20px text on these screens. |
| Display | 28px | 600 (semibold) | 1.2 | **Not used on the 5B screens.** Reserved (per 5A) for the largest in-product moments only (credit balance, top-up success amount, onboarding completion) — the needs-reply inbox and audit list have no Display-tier element. |

Type scale, restated: **12 / 14 / 20 / 28** — four sizes, no more. No 16px text anywhere.

Weights are **400 and 600 only** (medium **500** is permitted *solely* for the Label role, nav items, and row-title subjects — treat 500 as a sub-variant of those roles, not a third general weight). No light, no extrabold, no black.

**Mono (`--font-mono`) usage** (data, not body): relative/absolute timestamps in the needs-reply rows and audit rows, the audit-log mono `AI`/automated-action marker (accent-colored, mirrors `.zm-gm-ai` from 5A), any visible thread/message/draft identifier (rare — generally hidden). Mono renders at the **12px Label step** — it is the data-typeface variant of the existing 12px size, **not a fifth size**.

**Serif (`--font-serif`) usage:** none on the 5B screens.

| Role | Token (light → dark) | Usage |
|------|----------------------|-------|
| Dominant (~60%) | `--background` `#FAFAF7` → `#131312`; `SidebarInset` content area | Page background behind the tab strip and the list |
| Secondary (~30%) | `--card` `#FFFFFF` → `#1C1C1A`, `--secondary`/`--muted` `#F1EFE7` → `#232220`, `--sidebar` `#FAFAF7` → `#131312`, the 56px top-header strip | List/table rows on a card surface, the table header row, the tab strip background, the sidebar rail, skeleton row placeholders (`--muted`) |
| Accent (~10%) | `--primary` / `--accent` / `--ring` `#0E5E5A` → `#6FB3A8`; `--accent-soft` `#D6E8E5` → `#1F3A37` for soft fills | See reserved-for list below |
| Destructive | `--destructive` `#B0413E` → `#DA8480`; `--red-soft` for soft fills | The error-state `Alert` (failed to load / failed to generate draft) and its retry affordance only — never decorative, never the `Mark resolved` action (that is a neutral, non-destructive action) |
| Warning (secondary semantic) | `--warning` / `--amber` `#B5731F` → `#D9A064`; `--amber-soft` for soft fills | The "classifying… / recompute in flight" banner; a 409 "a draft is already being generated for this thread" inline notice |
| Success (status only, not a brand color) | `--green` `#2F7D5C` → `#6FB389`; `--green-soft` for soft fills | The `Draft sent` status badge (the user already replied — this thread is effectively done); the empty-state checkmark accent on the "Inbox zero 🎉" To-reply empty state |
| Info | `--blue` `#2C5BA8` → `#8DA8E0`; `--blue-soft` | The `Draft ready` status badge (a Zero-Mail draft is waiting in Gmail) — mirrors the 5A audit-log "draft-saved → blue-soft" mapping |
| Muted / neutral | `--muted` / `--muted-foreground` | The `No draft` status badge, the `Awaiting reply` tab when inactive, the `Resolved` hint, relative-time text |

**Accent reserved for** (explicit — never "all interactive elements"; the per-row `Draft reply` / `Regenerate draft` button is a **neutral default/secondary `Button`**, not an accent button, because there can be many per page — accent stays one-per-screen):
- The active tab underline on the `/needs-reply` `Tabs` and the `/triage` `Tabs` (mirrors `.zm-rules-tab.active` accent underline from 5A).
- The active nav item indicator for the new "Needs reply" sidebar entry (left border / background tint), consistent with all other sidebar items.
- Focus rings (`--ring`) on all focusable controls (tabs, row buttons, the Gmail link, the resolve control).
- The mono `AI`/automated-action marker in the `/triage` audit rows (accent-colored, like `.zm-gm-ai`).
- Inline text links inside body/empty-state copy (e.g. a "learn how drafts work" link to the privacy page), accent-colored, underlined on hover.
- The `TO_REPLY` count badge in the sidebar *may* be accent-tinted (the "inbox-zero progress" emphasis); when it reads `0`, drop the tint or hide the badge entirely (inbox zero = no nag).

If a single page-level primary CTA ever appears on these screens (none is currently planned — the needs-reply inbox has no page-level CTA, only per-row actions), it would be the one accent button; per-row buttons stay neutral regardless.

**Status-color discipline (draft-status badge — exactly three states):**
- `No draft` → neutral `--muted` badge.
- `Draft ready` → `--blue-soft` badge (a Zero-Mail draft exists in Gmail, awaiting the user's review/send).
- `Draft sent` → `--green-soft` badge (the user has replied; the thread is effectively resolved).

The `Mark resolved` action is **neutral**, never destructive-colored — resolving a thread is a benign housekeeping action. The "classifying…" banner is **amber/info-toned**, never red — it is a transient state, not an error.

## Visual Hierarchy — Primary Anchor Per Screen

Each key screen has **one** focal element the layout subordinates everything else to:
- **`/needs-reply`** — the **list of threads under the active tab** is the focal element; the tab strip, the count badges, and the page heading frame it but never compete with it. Within a single row, the **thread subject** is the row's anchor; the other-party name, relative time, draft-status badge, and action button are peripheral metadata around it.
- **`/triage` (now with the live audit list)** — unchanged from 5A: the audit `Table` (desktop) / card list (mobile) is the focal element; the new per-row "Draft reply / Regenerate draft" action is an additional row affordance alongside Undo, not a new focal element.
- **App shell (any route)** — unchanged from 5A: within the chrome, the active nav item + page heading are the anchors; the new "Needs reply" `TO_REPLY` count badge is peripheral status, not focal.

## Key Screens & States

The prototype (`05B-PROTOTYPE.html`) must visualize each of these.

### 1. Needs-reply inbox — populated, "To reply" tab active (desktop ≥ md)
- Page heading (`Needs reply`, 20px/600) + a one-line muted subtitle.
- `Tabs`: `To reply` (active, accent underline) · `Awaiting reply` · *(optional)* `Resolved` — each trigger shows a count badge.
- Dense `Table` (or table-shaped list reusing the `features/triage` `AuditTable` shape): columns ≈ **Subject** (Body 14/500, truncates) · **From / other party** (Body 14/400 muted, the non-self participant) · **Last activity** (mono 12px relative time, e.g. `2h ago`, with absolute on hover via `tooltip`) · **Draft status** (`No draft` muted / `Draft ready` blue-soft / `Draft sent` green-soft badge) · **Actions** (right-aligned: `Draft reply` neutral `Button` when no draft → `Regenerate draft` neutral `Button` when a draft exists; an "Open in Gmail" external-link icon button → `https://mail.google.com/mail/u/0/#all/<threadId>`, opens new tab; a secondary `Mark resolved` X-icon button).

### 2. Needs-reply inbox — "Awaiting reply" tab active
- Same layout; rows are threads where the user is waiting on the other party. Draft-status column is typically `Draft sent` (green-soft) or `No draft`. The `Draft reply` action is generally not shown here (or shown disabled with a tooltip) since the ball is in the other party's court — planner's discretion, but keep the row visually calmer than the To-reply tab.

### 3. Needs-reply inbox — loading
- shadcn `Skeleton` rows (matching the dense row height), 5–8 placeholder rows, with skeleton blocks for subject / from / time / status / actions. Tab strip and heading render immediately (not skeletoned).

### 4. Needs-reply inbox — "classifying… / recompute in flight" banner
- A slim **amber/info-toned** banner above the list: "Updating your needs-reply list…" with a small spinner; the (possibly stale) list still renders beneath it — never blank the list for a background recompute.

### 5. Needs-reply inbox — empty states
- **To reply, empty:** centered empty state — heading "Inbox zero 🎉", body "Nothing needs a reply right now." with a green-soft check accent; vertical padding `2xl`. No CTA (inbox zero should not nag).
- **Awaiting reply, empty:** centered empty state — heading "Nothing awaiting", body "No threads are waiting on the other party."
- *(optional)* **Resolved, empty:** "No resolved threads yet."

### 6. Needs-reply inbox — error state
- shadcn `Alert` variant `destructive`: heading "Couldn't load your needs-reply list", body "Something went wrong fetching your threads. Try again." + a `Try again` button (re-runs the query). Render in place of the list; tabs/heading stay.

### 7. Per-row draft action — generating / regenerating
- When `Draft reply` / `Regenerate draft` is clicked: the button enters a loading state (spinner + disabled, label → "Generating…" / "Regenerating…"). On success: the draft-status badge flips to `Draft ready` (blue-soft) and a `sonner` toast confirms — **"Draft saved in Gmail — review and send it there"** (the toast is the only "confirmation" surface; no in-app draft body). On the per-(tenant,thread) lock being held (HTTP 409): inline amber notice on the row — "A draft is already being generated for this thread." — and re-enable the button after a moment.

### 8. Per-row draft action — failure
- On generation failure (LLM error, Gmail write error): button returns to its prior label; a `sonner` toast (destructive tone) — **"Couldn't generate a draft. Try again in a moment."** — and the row's draft-status badge is unchanged. No raw error text, no stack trace, no draft body.

### 9. `/triage` audit list — now live, with the new row action
- The 5A audit `Table` / card list, now populated by `GET /api/triage/audit` (cursor-paginated; a "Load more" affordance at the list end consumes `nextCursor`). Each `save_draft` row now also shows a **`Draft reply` / `Regenerate draft`** action (alongside the existing `Undo`). Non-`save_draft` rows do not show the draft action. The mono accent `AI` marker stays on automated rows. Filters (`action`, `since`, `until`) from D-13 render as a compact filter bar above the table.

### 10. 320px responsive (all of the above)
- Single-column rows: line 1 = subject (truncates) + draft-status badge; line 2 = other-party name + relative time (muted, 12px); line 3 = action button (icon-only, 44px hit area) + "Open in Gmail" icon + `Mark resolved` icon. Tabs become horizontally scrollable. Empty/error/loading states stack and center. The sidebar collapses to its offcanvas `Sheet`; the "Needs reply" nav item + `TO_REPLY` badge appear inside it.
