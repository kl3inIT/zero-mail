## HIGH-severity Concerns (must-fix before execute)

### HIGH-1: Tool catalog drift — CHAT-05 not delivered (both reviewers, **consensus**)

The 20-Tool Authoritative List in Plan 03 excludes `saveMemory`, `searchMemories`, `addToKnowledgeBase`, `updatePersonalInstructions`. SPEC §CHAT-05 and REQUIREMENTS.md both list these as Phase 7 deliverables. Plan 02 ships the schema (`assistant_memory`, `assistant_knowledge_snippet` tables in changelog 046) but no tools wire to them, so Phase 7 acceptance criterion "saveMemory confirm flow + searchMemories returns saved row" cannot be met.

Codex additionally notes that `readEmail`, `createOrGetLabel`, `manageInbox/mark-read`, `getInboxStats` (CHAT-03 family) appear renamed or dropped — verify each renamed tool still delivers the SPEC behavior.

**Fix paths:**
- **A (preferred):** Restore `saveMemory` (confirm-required), `searchMemories` (read), `addToKnowledgeBase` (confirm-required), `updatePersonalInstructions` (confirm-required). New catalog: 8 read + 7 write-reversible + 5 confirm-required + 3 confirmed-send = 23 tools. Update SPEC's "20 tools" wording to "≥20 tools" or "core 20 + 3 personalization tools" and amend the contract test, preview-body-slot count, and `ChatToolCatalog` boot assertion.
- **B:** Formally defer CHAT-05 to Phase 8 — move the row from Phase 7 → Phase 8 in REQUIREMENTS.md traceability matrix, amend SPEC.md Phase 7 acceptance criteria, and keep the 20-tool catalog. Schema tables remain shipped as unused infrastructure.

Whichever path is chosen, SPEC.md + REQUIREMENTS.md + Plans 03/05/06 + UI-SPEC.md must all be touched in lockstep — no implicit re-scoping.

### HIGH-2: `createRule` confirmation level conflicts with CHAT-06 (Codex HIGH, OpenCode MEDIUM)

CHAT-06 lists `createRule` among risky actions that must render a preview card before persisting (alongside `sendEmail`, `deleteRule`, etc.). The 20-tool catalog categorizes `createRule` as **write-reversible** — generic Confirm/Cancel only, no per-tool preview body. A rule that auto-archives all mail from a domain is arguably more destructive than a single `archiveThread` action.

**Fix:** Upgrade `createRule` (and likely `updateRule`) to **confirm-required**. Add a per-tool body slot with rule preview + destructive-action language. New catalog totals shift (e.g., 7 read + 5 write-reversible + 5 confirm-required + 3 confirmed-send = 20 if path B from HIGH-1; otherwise re-tally). Update Plan 06 preview-body-slot map.

### HIGH-3: Body/privacy policy internal contradiction (Codex)

Plan 02 Task 2.2 bans fields named `body`/`htmlBody`/`textBody` in `chat_message.parts` JSONB. But:
- `sendEmail`/`replyEmail`/`forwardEmail` tool args include `body` (the draft to send).
- Plan 06 replay cards require the draft body after refresh.
- Draft bodies generated by the assistant are LLM completions derived from email context — persisting them may violate the "no LLM completions derived from email content" privacy invariant.

**Decision needed before implementation:**
- Are preview/draft bodies (a) persisted in `chat_message.parts`, (b) held in short-lived Redis only, or (c) replayed as metadata + reload-from-Gmail-on-demand?
- If (a), the body-ban trigger must allow `tool-sendEmail`/`tool-replyEmail`/`tool-forwardEmail` arg bodies but reject `tool-getMessage`/`tool-searchInbox` output bodies. Update trigger regex + ArchUnit + sanitizer accordingly.
- If (b), Plan 06 history sidebar refresh path needs a Redis-fetch fallback for pending drafts.

This is a **Privacy scope policy decision** owned by CLAUDE.md — confirm with user before code lands.

### HIGH-4: `chat_message.updated_at` missing (Codex)

Plan 05 uses CAS on `chat_message.updated_at` for race-safety; `assistant_pending_action.parts_updated_at` depends on it. Plan 02's `chat_message` schema (changelog 042) does not include `updated_at` column.

**Fix:** Either add `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()` + trigger to maintain it in changelog 042, OR move ALL confirmation state/CAS into `assistant_pending_action` and treat `chat_message.parts` as a replay projection only (no CAS source). Codex prefers the second — simpler invariant boundary.

### HIGH-5: Crash-after-Gmail-send-before-audit not solved (Codex HIGH, OpenCode MEDIUM)

Plan 05 Task 5.3 calls Gmail `messages().send()` outside the `@Transactional` boundary (correct, per Pitfall 2). The audit insert + state flip runs in its own `@Transactional` AFTER the send returns. If the process crashes between send-success and audit-commit, the email has been delivered but no audit row exists. Reconciliation cron sees no audit, marks state `FAILED` → UI tells user the action failed → user retries → duplicate email.

Pre-generated `Message-ID` (Pitfall 9) is helpful for deduplication on retry but not sufficient — it only helps if the retry path reaches Gmail; the user may invoke a new `sendEmail` toolcall with a fresh ID after seeing "failed".

**Fix:** Adopt durable pre-send attempt + reconcile-by-Message-ID:
1. Reserve state → INSERT pre-send row into `assistant_action_audit` with state `SEND_IN_FLIGHT` and the pre-generated `Message-ID`.
2. Call Gmail `messages().send()`.
3. On success: UPDATE the same row to state `COMMITTED` + flip `chat_message.parts` state.
4. On crash: reconciliation cron sees `SEND_IN_FLIGHT` rows older than threshold (e.g., 60s) → queries Gmail by Message-ID → if Gmail has it, mark COMMITTED; if not, mark FAILED.

Both reviewers acknowledge this is recoverable infrastructure rather than a structural fix. Code lands in Plan 05; reconciliation logic lands in Plan 04 `AssistantPendingActionReconciler`.

### HIGH-6: Tool execution loop incomplete (Codex)

With `internalToolExecutionEnabled(false)`, the backend must run a loop: model emits tool call → server executes read tool → append sanitized tool result to messages → call model again → repeat until model returns final assistant text. Plans emit tool output to the SSE stream but do not clearly feed the result back into the model for a follow-up generation cycle.

Without this loop, the assistant cannot do "search inbox → summarize results" or any multi-step reasoning. CHAT-01 multi-turn streaming fails as soon as a read tool is invoked.

**Fix:** Plan 04 `ChatOrchestrator.stream()` (Wave 3) must explicitly own the read-tool loop. Architecture sketch:
1. Receive user turn → call model with tool catalog.
2. Stream chunks. If chunk is a read-tool call → execute synchronously → append sanitized output as a `tool_result` message → call model again → continue streaming.
3. If chunk is a confirm-required/confirmed-send tool call → emit preview-card envelope to SSE → return (loop ends; resumes via `/confirm`).
4. If chunk is final assistant text → stream to client → persist to `chat_message.parts` (HIGH-7).

Plan 03's `ChatToolCatalog` already separates read tools from confirm tools; the loop dispatcher belongs in `ChatOrchestrator`. Add an integration test that proves "user asks 'how many unread' → searchInbox runs → final answer streamed".

### HIGH-7: Assistant text response not persisted (Codex)

Plan 04 persists user turns and tool outputs into `chat_message.parts`, but the final assistant text response is not explicitly persisted. Without it:
- CHAT-01 multi-turn context fails after refresh (history is missing assistant's prior answers).
- CHAT-07 history replay shows user turns + tool outputs but no assistant prose.
- `ZeroMailChatMemory` reading from `chat_message.parts` returns incomplete conversation context for follow-up turns.

**Fix:** Plan 04 `ChatOrchestrator` must persist the assistant text response after the SSE stream completes. The persistence happens in a `TransactionTemplate` callback bound to the stream's `onComplete` (not the orchestrator method's `@Transactional` — that has already closed). Add `AssistantTextPart` to the `Part` sealed hierarchy in Plan 02 if not already present. Verify `ChatPartsSchemaV1Test` covers `AssistantTextPart` round-trip.

## MEDIUM-severity Concerns (polish-during-execute or fix-if-cheap)

### MEDIUM-1: `@Transactional` does not cover async streaming callbacks (Codex)

`ChatOrchestrator.stream()` returns a `Disposable`; SSE chunk callbacks run after the method-level transaction closes. Persistence in callbacks (assistant text, tool outputs) must use `TransactionTemplate` or service methods with their own transactional boundaries.

### MEDIUM-2: CI grep gate brittle under GitHub Actions `pipefail` (Codex)

Plan 01 Task 1.9's `grep | wc -l` pipeline can fail with exit code 1 when zero matches are expected (e.g., when count == 0 in Wave 0 baseline). Replace with a small checked-in script (`scripts/ci/count-gmail-send-call-sites.sh`) that returns stable counts even on zero matches.

### MEDIUM-3: Liquibase atomicity claim is inaccurate (Codex)

Plan 02 asserts Liquibase guarantees atomic apply per file. Liquibase does not guarantee one transaction across multiple changeSets within a file. Put `chat_message` table + `chat_message_body_ban` trigger in ONE changeSet (not two changeSets in the same file), OR explicitly handle the partial-apply rollback case.

### MEDIUM-4: Postgres JSONPath examples likely invalid (Codex)

Trigger expressions like `@.type starts with "tool-"` use JSONPath syntax that may not exist in Postgres 17's `jsonb_path_exists`. Validate the actual trigger function against a real Postgres instance in Wave 0 (run the trigger creation + a rejection test before depending on it for ARCH-02).

### MEDIUM-5: CSRF header missing from `useChat` transport (Codex)

`DefaultChatTransport` in Plan 06 issues cookie-authenticated POST to `/api/chat` without a CSRF header. Other typed API calls use `xsrfHeader()`. This can either 403 against the existing CSRF filter or silently weaken CSRF posture. Add the same CSRF header to `DefaultChatTransport`; add a Playwright test proving `/api/chat` and `/confirm` succeed with CSRF parity.

### MEDIUM-6: Spring AI M6 workaround under-proven (Codex)

Plan 03's ARCH-07 tests use synthetic raw-chunk fixtures. The accepted risk from skipping the de-risking prototype (D-12) is offset by these synthetic tests, but a recorded real-M6 chunk fixture or a small `@Tag("llm-eval")` smoke test would harden the workaround. Optional for execution, recommended for confidence.

### MEDIUM-7: Context-window/token-budget not enforced (OpenCode)

AI-SPEC §4b specifies "history truncation at 60% of model context window" and "tool output truncation at 4k tokens." Neither Plan 03 (`ZeroMailChatMemory`) nor Plan 04 (`ChatOrchestrator`) enforces token budgets. Long conversations (>40-50 turns) will silently overflow context. Add a `LlmTokenizer` token counter + `maxHistoryTokens` config; `ZeroMailChatMemory.get()` accepts a token-budget parameter.

### MEDIUM-8: SSE reverse-proxy timeout not configured (OpenCode)

15-second heartbeat keeps backend SSE alive, but nginx (or chosen reverse proxy) default `proxy_read_timeout` of 60s will sever the connection before backend's 30-minute `SseEmitter` timeout. Document `proxy_read_timeout 31m;` (or equivalent) for the `/api/chat` location.

### MEDIUM-9: Orphaned-email gap documentation (OpenCode)

Even after HIGH-5's pre-send-row fix lands, edge crash windows remain (e.g., Gmail accepts but server crashes before any DB update). Document the residual gap in `AssistantSendExecutor` javadoc + `AssistantPendingActionReconciler` log line so future contributors understand the failure model and don't introduce a "Recalled email" feature that can't work server-side (CHAT-FUT-05/CONFIRM-D1 deferred).

## LOW-severity Concerns (cleanup during execution)

### LOW-1: Dead `tool-readEmail` pattern in body-ban trigger (OpenCode)

`chat_message_body_ban` trigger function in changelog 042 references `tool-readEmail`. The 20-Tool Authoritative List renamed this to `tool-getMessage`. The broader `exists(@.body)` check catches the case regardless, but the specific pattern is dead code → maintenance confusion. Fix the trigger pattern to `tool-getMessage`. Also verify `tool-searchInbox` output patterns if search results include body-shaped fields.

### LOW-2: Chat title auto-generation not specified (OpenCode)

`chat.title` column exists (changelog 041) and UI-SPEC shows history sidebar uses first 40 chars of first user message. Plan 04 Task 4.1 creates the `Chat` row but doesn't populate `title` on first turn → empty titles in sidebar. Add `chat.setTitle(userText.substring(0, Math.min(40, userText.length())))` on first-turn creation.

### LOW-3: `@Order` on `PersonalizationSanitizer` stages (OpenCode)

3-stage sanitizer pipeline has implicit ordering. Add `@Order(1)`/`@Order(2)`/`@Order(3)` annotations to lock the order against future stage additions.

### LOW-4: Parallelize Wave 1 test execution (OpenCode)

8 Wave 1 test files each spin up Testcontainers Postgres. Reuse a single container via class-level inheritance to cut suite time. Polish.

### LOW-5: `@PostConstruct` validation for ChatToolCatalog (OpenCode)

Plan 03 recommends boot-time `factory.validate()` but doesn't name the owning bean. Specify `SpringAiStreamingChatModelClient` `@PostConstruct` → call `chatToolCatalog.validate()` → fail boot if size ≠ catalog target.

### LOW-6: Log-line sanitization for Message-ID (OpenCode)

Pre-generated `Message-ID` contains tenant ID (e.g., `<chat-{tenantId}-{uuid}@zero-mail.local>`). Ensure `event=chat_send_committed` log lines exclude the literal Message-ID value (or hash it) to avoid leaking tenant↔email correlation.
