    3. **HIGH-6 read-tool execution loop** — owned by `ChatOrchestrator.executeReadToolLoop(...)`. With Spring AI's `internalToolExecutionEnabled(false)`, the orchestrator (not Spring AI) drives the call/result/call cycle. Pseudocode:
       ```
       List<Message> conversation = new ArrayList<>(initialHistory + userTurn)
       while (true) {
           Disposable subscription = chatLlmGateway.streamChat(
               new ChatStreamRequest(..., conversation, ...),
               new InterceptingSink(sanitizingSink)
           )
           // Wait for the LLM stream to finalize (one full assistant turn) by blocking on a
           // CompletableFuture<TurnOutcome> resolved by the InterceptingSink. NOT blocking the
           // controller's request thread — the wait happens on the TenantAwareReactorScheduler.
           TurnOutcome outcome = turnFuture.get()  // blocks the reactor task, not the HTTP request
           if (outcome.kind() == READ_TOOL_CALL) {
               ChatReadToolHandler handler = readToolHandlerMap.get(outcome.toolName())
               String sanitizedOutputJson = handler.executeJson(outcome.inputJson(), tenantId)  // synchronous
               // Persist tool-output envelope to chat_message.parts
               transactionTemplate.execute(status -> { chatMessageRepository.save(...); return null; })
               // Append tool result as a Message that the model will read on next iteration
               conversation.add(new ToolResultMessage(outcome.toolCallId(), sanitizedOutputJson))
               // Loop — call model again
               continue
           }
           if (outcome.kind() == CONFIRM_REQUIRED || outcome.kind() == CONFIRMED_SEND) {
               // Preview-card envelope was already emitted by the sink during the stream.
               // Persist the pending tool-call to chat_message.parts so replay works.
               transactionTemplate.execute(status -> { chatMessageRepository.save(toolCallEnvelope); return null; })
               // Stream is paused; resumes via POST /api/chat/{id}/confirm (Wave 4).
               streamSink.emitFinish("awaiting-confirmation")
               break
           }
           if (outcome.kind() == FINAL_ASSISTANT_TEXT) {
               // HIGH-7: persist assistant text. CANNOT use @Transactional here — the streaming
               // sink's onComplete callback fires after any method-level @Transactional has closed.
               transactionTemplate.execute(status -> {
                   chatMessageRepository.save(new ChatMessage(..., new ChatMessageParts(
                       List.of(new AssistantTextPart(partId, outcome.assistantText(), Instant.now())),
                       1
                   )))
                   return null
               })
               streamSink.emitFinish("complete")
               break
           }
       }
       ```
       This loop architecture matches the Spring AI M6 `internalToolExecutionEnabled(false)` semantics: the model emits tool calls in the stream; the orchestrator executes them locally; the orchestrator then calls the model again with the tool result appended. Without this loop, the assistant cannot do "search inbox → summarize results" (CHAT-01 multi-turn fails on any read tool).

       Write-reversible / confirm-required / confirmed-send tool calls do NOT execute inline (the loop exits with `CONFIRM_REQUIRED`/`CONFIRMED_SEND` outcome). Wave 4 ships the confirm endpoint that resumes execution after user click — but resume-after-confirm is OUT OF SCOPE for this loop; the loop terminates on confirm pause and Wave 4 starts a fresh stream when the user clicks Send/Cancel.
