## Pre-discussion: Background research synthesized into session

Before formal discussion, the user asked for a deep comparison of JHipster's `AbstractAuditingEntity<T>` and Jmix's `EnumClass<T>` patterns plus naming conventions. Synthesis produced:

- **JHipster pattern** — Single `AbstractAuditingEntity<T>` class with `@MappedSuperclass`, generic `<T>` for ID type, includes 4 audit fields (`createdBy`, `createdDate`, `lastModifiedBy`, `lastModifiedDate`) populated by Spring Data JPA Auditing. Concrete entities declare their own `@Id`.
- **Jmix pattern** — Mandatory `@JmixEntity` + `@Entity`, custom `@JmixGeneratedValue` for UUIDs, `@Version Integer` mandatory for optimistic locking, `EnumClass<T>` interface with `getId()` + `fromId()`, AttributeConverter forbidden for Jmix enums (uses metadata mechanism).
- **Recommendation crystallized** — Adopt principles from both, pull neither dependency. 3-tier hierarchy with `@TenantId` separated into its own tier (multi-tenant invariant enforced at compile time). Lighter `IdentifiedEnum` interface using `@Enumerated(STRING)` with `id() == name()` invariant.

Naming convention agreed: `Abstract<Concept>Entity` (singular, suffix `Entity`); enum class PascalCase no suffix; enum constants UPPER_SNAKE_CASE matching `id()`.

## Area 1: Entity hierarchy shape

### Q1.1 — Topology

| Option | Description | Selected |
|--------|-------------|----------|
| 3-tier (Recommended) | `AbstractEntity` (id+createdAt) → `AbstractAuditableEntity` (+updatedAt+@Version) → `AbstractTenantOwnedEntity` (+@TenantId). TenantEntity extends AbstractEntity. Compiler enforces multi-tenant invariant. | ✓ |
| 2-tier | `AbstractEntity` (id+createdAt+updatedAt+@Version) → `AbstractTenantOwnedEntity` (+tenantId). TenantEntity gets unused fields. | |
| 1-class generic | `AbstractTenantAwareEntity<T>` forces multi-tenant on every entity, including TenantEntity self-reference. | |

**User's choice:** 3-tier (Recommended)
**Notes:** User accepted the recommended preview which showed compile-time enforcement of "tenant-owned entities all extend AbstractTenantOwnedEntity".

### Q1.2 — Audit field naming

| Option | Description | Selected |
|--------|-------------|----------|
| createdAt / updatedAt (Recommended) | Spring Boot modern style. Field Java `createdAt`/`updatedAt`, DB `created_at`/`updated_at`. Annotation name (`@CreatedDate`) does NOT need to match field name. Zero schema migration for TenantEntity. | ✓ |
| createdDate / lastModifiedDate (JHipster) | JHipster convention. Field name 1:1 with annotation. Forces TenantEntity column rename → violates schema-preserve. | |

**User's choice:** createdAt / updatedAt (Recommended)
**Notes:** Aligned with existing TenantEntity column.

### Q1.3 — Schema scope (updatedAt + @Version migration)

| Option | Description | Selected |
|--------|-------------|----------|
| Add Liquibase migration (Recommended) | Phase 1.2.1 IS NOT byte-identical schema. New changeset adds `updated_at` + `version` columns to 3 tenant-owned tables. Backfill `updated_at = created_at`. Update ROADMAP success criteria #6 wording. | ✓ |
| Strict schema-preserve, 2-tier collapse | Honor success criteria #6. Drop AbstractAuditableEntity, only ship 2-tier. Defer audit columns to future phase. | |
| Hybrid: 3-tier defined, defer cols | Declare 3 abstract classes but use `@Transient` for updatedAt + version. RISK: silent persistence drift if `@Transient` swapped to `@Column`. | |

**User's choice:** Add Liquibase migration (Recommended)
**Notes:** Acknowledged that ROADMAP success criteria #6 needs revision from "preserved byte-identical" to "schema additions limited to audit columns".

### Q1.4 — Audit population mechanism (Initial)

| Option | Description | Selected (initial) |
|--------|-------------|----------|
| Hibernate @PreUpdate (Recommended) | Pure Hibernate lifecycle callback. Zero Spring config. Pure Java visibility. | (rejected, see below) |
| Spring Data JPA Auditing | `@EnableJpaAuditing` + `DateTimeProvider` bean. Heavier setup but extension path for `@CreatedBy`/`@LastModifiedBy`. Standard Spring Boot pattern. | (chosen, see below) |
| PostgreSQL DB trigger | `BEFORE UPDATE` trigger sets `NEW.updated_at = NOW()`. Bulletproof against bulk SQL bypass but in-memory test divergence. | |

**Initial response:** User asked for clarification on strengths/weaknesses before choosing.

**Clarification provided:** Detailed comparison of when each option fires/doesn't fire (bulk JPQL caveat applies to Options 1 and 2 equally; Option 3 catches all). Trade-off matrix covering setup cost, future `@CreatedBy` extension, test deterministic Clock injection, indirection magic.

**User's question:** "Nếu không quan trọng vấn đề config phức tạp, Option 2 có phải lựa chọn hợp lý không?"

**Reframed answer:** Yes — Option 2 is architecturally better for Zero Mail's long-term ambition. Reasons:
1. Privacy constraint forbids `createdBy/lastModifiedBy` at row level NOW, but Phase 6 audit log + CASA compliance may need user-action audit later. Option 2's extension path (`AuditorAware<UUID>` bean) is zero-cost to add later.
2. Convention-over-configuration matches Spring Boot ecosystem norms — onboarding devs recognize `@CreatedDate`/`@LastModifiedDate` immediately.
3. `Clock` bean injection at `DateTimeProvider` level is cleaner than per-entity `@PreUpdate` Clock workaround.
4. Entity stays pure data shape (no lifecycle methods).

**User's choice:** Spring Data JPA Auditing (Option 2)
**Notes:** Trade-off accepted: 1 extra config class + `Clock` bean. Caveat documented: bulk JPQL/native SQL still bypass listener (D-A5).

## Area 2: IdentifiedEnum interface contract

### Q2.1 — Interface contract shape (combined sub-questions)

| Option | Description | Selected |
|--------|-------------|----------|
| Minimal (id only) + opt-in OrderedEnum (Recommended) | `IdentifiedEnum` (id + default labelKey) + `OrderedEnum extends IdentifiedEnum` (+ weight). Each enum picks based on whether ordering matters. Idiomatic per-impl `fromId(String)`. | ✓ |
| All-in-one (id + weight + labelKey) | Single interface with `weight()` default = -1 sentinel. Simpler but forces every enum to think about weight. | |
| Generic id type `<T>` | `IdentifiedEnum<T>` to support both String and Integer IDs. No use case in current/near-term scope. | |

**User's choice:** Minimal + OrderedEnum (Recommended)
**Notes:** Implicit further decisions captured: id() returns String (D-B2), labelKey() default = `<ClassSimpleName>.<id>` (D-B3), fromId() per-impl (D-B4), `OnboardingStep implements OrderedEnum` and `GmailConnectionStatus implements IdentifiedEnum` (D-B5).

## Area 3: Enum persistence strategy

### Q3.1 — Storage mechanism

| Option | Description | Selected |
|--------|-------------|----------|
| @Enumerated(STRING) thuần (Recommended) | JPA standard. Since `id() == name()` per D-B2, STRING storage = id storage. Zero boilerplate, zero schema change. Upgrade enum-by-enum to AttributeConverter when first rename need arises. | ✓ |
| AttributeConverter từ đầu | Per-enum Converter class. Decouples Java symbol from DB. ~10 LOC boilerplate per enum for zero immediate benefit. | |

**User's choice:** @Enumerated(STRING) thuần (Recommended)
**Notes:** Migration path documented in `core.shared.lang/package-info.java` (D-C3).
