## Phase Boundary

This phase closes the structural-cleanup gaps that Phase 1.2 intentionally deferred so domain entities, enums, and HTTP DTOs all follow project-wide standards. The work splits into four trục:

1. **`core.shared.persistence.*` abstract entity hierarchy** (3-tier) — DRY the four entity declarations and enforce multi-tenant ownership at the type level.
2. **`core.shared.lang.IdentifiedEnum` + `OrderedEnum` interfaces** — domain enums no longer rely on `name()` for storage or `ordinal()` for ordering.
3. **`backend/api/dto/` group-by-domain reorg** — align HTTP wire DTO layout with the Phase 1.2 domain-owned invariant; full rename `TenantStatusResponse` → `GmailConnectionStatusResponse` (Java class + URL endpoint + OpenAPI tag), with frontend follow-through.
4. **Code-review WR-01/WR-02/WR-03 closure** — fold into the relevant trục (WR-01 → enum persistence test upgrade, WR-02 → `UserEntity.advanceTo` weight-based check, WR-03 → bulk JPQL delete).

The phase does NOT add new product capability and does NOT touch Phase 1.3 frontend architecture refactor (that's a separate phase). Phase 1.3 commits already on the same branch must not be disturbed.

<decisions>
## Implementation Decisions

### A. Entity hierarchy (`core.shared.persistence.*`)

- **D-A1 (Topology):** 3-tier hierarchy — `AbstractEntity` → `AbstractAuditableEntity extends AbstractEntity` → `AbstractTenantOwnedEntity extends AbstractAuditableEntity`. `TenantEntity` extends `AbstractEntity` (NOT tenant-owned — it IS the tenant). The other 3 entities (`UserEntity`, `OnboardingSelectionEntity`, `GmailConnectionEntity`) extend `AbstractTenantOwnedEntity`. Rejected 2-tier (forces TenantEntity to carry unused fields) and 1-class generic (forces every entity to be tenant-aware).

- **D-A2 (Audit field naming):** `createdAt: Instant` and `updatedAt: Instant` (Spring Boot modern style). DB columns `created_at` and `updated_at`. Annotation choice independent of field name (`@CreatedDate` is fine on a field named `createdAt`). Rejected JHipster `createdDate`/`lastModifiedDate` — would force `TenantEntity.created_at` rename.

- **D-A3 (Schema scope):** Phase 1.2.1 IS NOT byte-identical schema. One Liquibase changelog adds `updated_at TIMESTAMP` + `version INTEGER DEFAULT 0` columns to `app_user`, `onboarding_selection`, and `gmail_connection`. Backfill `updated_at = created_at` for existing rows. ROADMAP success criteria #6 must be edited from "Database schema is preserved byte-identical (no Liquibase changes)" to "Database schema additions limited to audit columns (`updated_at`, `version`); no destructive or semantic-changing migrations".

- **D-A4 (Audit population mechanism):** Spring Data JPA Auditing — `@EnableJpaAuditing(dateTimeProviderRef = "appDateTimeProvider")` config class + `Clock` bean (`Clock.systemUTC()` in prod, `Clock.fixed(...)` in tests) + `DateTimeProvider` bean reading from `Clock`. Apply `@EntityListeners(AuditingEntityListener.class)` to `AbstractEntity` so listener fires for both `createdAt` and `updatedAt`. Field annotations `@CreatedDate` on `createdAt` and `@LastModifiedDate` on `updatedAt`. Rejected pure Hibernate `@PreUpdate` (no `Clock` injection point, ugly test config) and DB triggers (in-memory test divergence). NO `@CreatedBy`/`@LastModifiedBy` — privacy constraint forbids identity columns at row level (separate audit log table planned for Phase 6).

- **D-A5 (Caveat — bulk SQL bypass):** `@PreUpdate`/`@LastModifiedDate` lifecycle callbacks DO NOT fire for bulk JPQL `@Modifying @Query`, native SQL via `entityManager.createNativeQuery(...)`, or `JdbcTemplate` updates. Document this in `core.shared.persistence/package-info.java`. If a future bulk update is needed, set `updated_at = NOW()` explicitly in the query, or migrate to a DB trigger for that specific table.

### B. Enum interface (`core.shared.lang.*`)

- **D-B1 (Two-interface design):** `IdentifiedEnum` (base — id + default labelKey) and `OrderedEnum extends IdentifiedEnum` (+ weight). Enum without ordering implements `IdentifiedEnum`; enum with forward-only or priority semantics implements `OrderedEnum`. Rejected "all-in-one with sentinel weight" (forces every enum author to consider weight) and generic `<T>` id type (no Integer use case in current or near-term scope).

- **D-B2 (id type):** `String` only. Rationale: every existing and near-term enum (`OnboardingStep`, `GmailConnectionStatus`, future `LedgerEntryType`, `LLMProvider`, `TriageRulePriority`) has stable string keys. Integer ID would optimize for sort-by-id-in-DB (rare); not worth the generic complexity now. If needed later, can introduce parallel `IdentifiedIntEnum<Integer>` rather than retrofitting generics.

- **D-B3 (labelKey):** Default implementation in `IdentifiedEnum` interface returns `<ClassSimpleName>.<id>` (e.g. `OnboardingStep.GMAIL_CONNECTED`). i18n message bundle key follows this format. Override only when the default is wrong for some reason.

- **D-B4 (fromId pattern):** Per-impl static method `fromId(String)` on each enum class. Idiomatic Java (static methods can't be in interfaces as abstract). 1-liner using `Stream.of(values()).filter(e -> e.id().equals(id)).findFirst().orElseThrow(...)`. Throws `NoSuchElementException` (not `IllegalArgumentException`) on unknown id — fail-loud preference.

- **D-B5 (Enum mapping for current code):** `OnboardingStep` implements `OrderedEnum` (forward-only flow with weights 10/20/30/40). `GmailConnectionStatus` implements `IdentifiedEnum` (states are unordered: PENDING / CONNECTED / REVOKED / ERROR). `UserEntity.advanceTo` uses `current.weight() < next.weight()` instead of `current.ordinal() < next.ordinal()` (closes WR-02).

### C. Enum persistence

- **D-C1 (Storage mechanism):** `@Enumerated(EnumType.STRING)` for all enums implementing `IdentifiedEnum`. Rejected per-enum `AttributeConverter` (10+ LOC boilerplate per enum for zero immediate benefit; can upgrade enum-by-enum when first rename need arises).

- **D-C2 (Invariant):** `id() == name()` — Java symbol literal must equal `id()` constructor argument. Document this rule in `core.shared.lang/package-info.java`. ArchTest enforcement is OUT OF SCOPE for 1.2.1 (would require ArchUnit ability to introspect enum constructor calls — not standard); enforce via `@Enumerated(STRING)` + `id() == name()` documented convention + WR-01 persistence test.

- **D-C3 (Migration path):** When future enum needs to decouple Java symbol from DB (e.g., rename `ACCOUNT_CREATED` → `JUST_REGISTERED` while keeping DB value `"ACCOUNT_CREATED"`), upgrade THAT enum to `AttributeConverter`. Document trigger in `core.shared.lang/package-info.java`. Do not preemptively convert.

- **D-C4 (WR-01 closure):** Replace `OnboardingStepEnumPersistenceTest` (current pure-JVM test) with `OnboardingStepPersistenceTest` `@DataJpaTest` round-trip — persist via Hibernate, then native query verify column type = varchar AND raw value = `"GMAIL_CONNECTED"` (or whatever id). Catches `STRING → ORDINAL` switch.

### D. DTO grouping (`backend/api/dto/`)

- **D-D1 (Layout):** Flat files per domain (`api/dto/<domain>/`). Phase 1.2.1 has 4 DTOs across 3 domains — each domain has 1-2 files, splitting request/response is premature. Document upgrade trigger: ">10 DTOs in single domain → split into `request/` + `response/` sub-folders".

- **D-D2 (Naming convention):** Suffix `*Request` for input DTOs, `*Response` for output DTOs. Already established in current code; carry forward.

- **D-D3 (Error infrastructure scope):** `api/error/*` (`ApiError`, `ErrorCodes`, `FieldErrorDto`, `AllowedParamScalars`) is cross-cutting Phase 1.1 deliverable, NOT domain-specific. Leave in current `api/error/` location; do NOT reorganize into `api/dto/<domain>/`. Document this exception in `api/dto/package-info.java`.

- **D-D4 (Full rename for TenantStatusResponse):** Rename the Java class `TenantStatusResponse` → `GmailConnectionStatusResponse` AND change the URL `/api/v1/tenant/status` → `/api/v1/gmail/connection/status` AND change OpenAPI `@Tag(name = "tenant")` → `@Tag(name = "gmail")`. Project is exploratory pre-launch — clean break preferred over transitional alias. Rejected internal-only rename (preserves D-A4 confusion in API surface) and deprecated-alias path (over-engineering for pre-production app).

- **D-D5 (Frontend follow-through):** Same phase 1.2.1 scope — regenerate `apps/web/lib/api/schema.d.ts` from updated OpenAPI spec, update `apps/web/components/TenantStatus.tsx` (or wherever TenantStatusResponse is consumed) to use new URL + types. The frontend rename is part of this phase's success criteria, not deferred.

### E. Plan structure (Claude's discretion)

- **D-E1:** Plan splitting (number of plans, wave grouping, parallelization) is at planner discretion, but must respect: (1) Liquibase migration is its own atomic plan (DB-changing work isolated); (2) entity hierarchy + audit listener config in same plan as Liquibase migration to avoid `MappingException` between plans; (3) enum interface introduction can ship before applying to concrete enums (1 plan for interface, 1 plan for application + WR-01/WR-02 closure); (4) DTO reorg + URL rename + frontend follow-through can be its own plan.

- **D-E2:** Test gates per plan must include `ApplicationModulesTest`, `MultiTenantLeakIntegrationTest` (FND-05), `AccountDeletionE2ETest`, plus `OnboardingStepPersistenceTest` (new in WR-01 closure) and full `./gradlew :backend:core:check :backend:api:check` at the end of each plan.

### Claude's Discretion

- ArchTest enforcing "every tenant-owned entity extends AbstractTenantOwnedEntity" — interesting but not specified in this phase. Defer unless planner finds a clean ArchUnit pattern (would need to introspect superclass).
- Naming for the abstract-entity test class — pick by convention (`AbstractEntityHierarchyTest` or similar).
- Fields ordering inside abstract classes — Java convention.

## Existing Code Insights

### Reusable Assets

- **Phase 1.2 lock**: `core.shared.privacy.*` already proves `core.shared.<sub>` parent package pattern. New `core.shared.persistence.*` and `core.shared.lang.*` follow the same shape (intra-`shared` siblings, no Modulith edges between them).
- **Phase 1.2 lock**: per-domain `persistence/lowlevel/` markers exist on all 4 domains (D-D3) — abstract entity classes do NOT touch lowlevel; they sit at `core.shared.persistence.*` root.
- **TenantEntity**: already has `@Column(name = "created_at", insertable = false, updatable = false) private Instant createdAt;` — moving to base class is a no-op for schema.
- **3 tenant-owned entities** already have `@TenantId @Column(name = "tenant_id") private UUID tenantId;` — identical shape, perfect candidate for base class.
- **`MultiTenantLeakIntegrationTest`** (Phase 1 FND-05) — re-running this test after entity refactor verifies `@TenantId` discriminator filter still binds when annotation is on a `@MappedSuperclass`.

### Established Patterns

- **`@MappedSuperclass`** with `@EntityListeners(AuditingEntityListener.class)` is the standard Spring Boot 4 + Hibernate 7 pattern for shared audit fields. Verified compatible per Spring docs.
- **`@TenantId`** on a `@MappedSuperclass` field is supported by Hibernate 6.3+ (this project on Hibernate 7.x). The `@Filter` `@TenantId` discriminator binds to whichever field carries the annotation regardless of declaration class.
- **`@Enumerated(STRING)`** is already in use for both `OnboardingStep` and `GmailConnectionStatus` — implementing `IdentifiedEnum` with `id() == name()` requires zero JPA mapping change.

### Integration Points

- **`backend/api/src/main/java/com/zeromail/api/Application.java`** — `@EntityScan("com.zeromail.core")` already collapsed (D-A5 of Phase 1.2). New `core.shared.persistence` mapped superclasses are discovered automatically.
- **`backend/core/src/test/java/com/zeromail/core/support/CoreTestApplication.java`** — same scan root. Test discovery automatic.
- **`JpaAuditingConfig`** as a new `@Configuration` class is auto-loaded by Spring Boot's component scan (in `com.zeromail.api.config` package).
- **Liquibase YAML changelog** — new file `01.2.1-01-add-audit-columns.yaml`, included from `db.changelog-master.yaml` via `includeAll`.
- **OpenAPI generation** — Spring's `springdoc-openapi` regenerates `/v3/api-docs` automatically when `@Tag` annotation changes; frontend `openapi-typescript` regen pulls the new spec.

<specifics>
## Specific Ideas

- The user explicitly compared JHipster's `AbstractAuditingEntity<T>` (single class, generic ID, includes `createdBy`/`lastModifiedBy`) vs Jmix's `EnumClass<T>` (interface-based, explicit `getId()` + `fromId()`) and chose to adapt principles from both rather than pull either dependency. Document this design rationale in `core.shared.persistence/package-info.java` and `core.shared.lang/package-info.java`.

- The user emphasized "lock now = lock for all future Phase 2A/2B/2C/3/4 entities" — this is the strongest guidance. Plans must NOT introduce one-off shortcuts that future phases can't follow.

- Test deterministic time via `Clock` bean injection is the user's preferred pattern — every place currently using `Instant.now()` directly should consider whether to inject `Clock` instead. NOT in scope for 1.2.1 (focused on auditing path only), but flag as a future cleanup if other places use `Instant.now()` directly.

</specifics>
