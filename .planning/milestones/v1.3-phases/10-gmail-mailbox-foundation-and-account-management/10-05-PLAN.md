<objective>
Split the single bundled-Google OAuth flow into three intents (first-login provision / add-mailbox / reconnect-mailbox) using a server-side pending-intent snapshot + attributes + a session shim (D-01/02/03, B+D+E). The resolver reads the `OAuthIntentSnapshot` that Plan 06's `ConnectMailboxController` stored in the session under `ZEROMAIL_OAUTH_PENDING_INTENT`, validates it, stamps `intent`+`targetMailboxId`+`initiatingTenantId` as `OAuth2AuthorizationRequest.attributes(...)`, and clears the pending key (one-shot); the `IntentCarryingAuthorizationRequestRepository` decorator then copies those attributes into the `HttpSession` on `removeAuthorizationRequest` (with the Redis-dirty fresh-`setAttribute` fix) so they survive the callback the framework consumes them on; branch in the success handler (one-shot read). Keep the single bundled Google registration and framework-owned `state` for CSRF.

Purpose: GMA-07/01/04 — connecting another Gmail must never replace the current row. Intent branch AUTHORITY is derived ENTIRELY from the server-side pending snapshot, NOT from any URL param: the resolver reads the snapshot from the session, validates its intent against the closed enum, and reads `initiatingTenantId` from it (stamped server-side by the controller from the authenticated SecurityContext). A tamperable `?intent=`/`?targetMailboxId=` cannot steer the branch or pick the tenant because the resolver never reads request params for branch authority (codex HIGH-A; honors CONTEXT D-01 "intent never rides a tamperable URL param"). An authenticated request with no valid pending snapshot fails closed (management branch unreachable), it does not fall through to first-login provisioning by reading a URL param. The success handler re-checks tenant identity (#9) and one-shot-removes the callback intent at the very TOP before any validation that can short-circuit (codex HIGH-B), and the failure handler clears the intent (#7).
Output: 2 new security classes + resolver/handler/failure-handler/SecurityConfig edits.

NOTE: This plan does NOT add the connect/reconnect trigger endpoints (those are Plan 06's `ConnectMailboxController`, which writes the `ZEROMAIL_OAUTH_PENDING_INTENT` snapshot). It wires the resolver/repository/handler/SecurityConfig so that when an authenticated mailbox-management redirect arrives with a server-side pending snapshot, the flow routes correctly. PENDING-vs-CONNECTED add decision (RESEARCH Open Q2): INSERT a CONNECTED row in the success handler (single write, no orphan PENDING row if the user abandons consent).
</objective>
