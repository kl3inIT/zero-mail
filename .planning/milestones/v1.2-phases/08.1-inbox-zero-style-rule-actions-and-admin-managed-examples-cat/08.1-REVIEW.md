## Critical Issues

### CR-01: Tenant Mismatch Can Still Create Outbound Fallback Drafts

**File:** `backend/core/src/main/java/com/zeromail/core/triage/usecases/TriageOrchestratorService.java:987`
**Issue:** `outboundFallbackReason(...)` checks `AUTO_SEND_DISABLED`, `SENDER_SAFETY_NET`, and `LOW_TRUST_STATIC_FROM` before checking `TenantContext`. `executeGmailPhase(...)` only blocks Gmail writes when the returned reason is `TENANT_CONTEXT_MISMATCH`, so a mismatched tenant context combined with auto-send disabled, protected sender, or low-trust matcher will still call `outboundDraftFallbackPhase(...)` and create a Gmail draft for `dispatchContext.tenantId()`. That violates the required tenant-match gate for outbound rule actions.
**Fix:**
```java
private String outboundFallbackReason(
        TriageDispatchContext dispatchContext, ActionProposal actionProposal) {
    Optional<String> currentTenant = TenantContext.currentOptional();
    if (currentTenant.isEmpty()
            || !currentTenant.get().equals(dispatchContext.tenantId().toString())) {
        return TENANT_CONTEXT_MISMATCH;
    }
    if (!dispatchContext.autoSendRulesEnabled()) {
        return AUTO_SEND_DISABLED;
    }
    if (dispatchContext.senderProtected()) {
        return SENDER_SAFETY_NET;
    }
    if (!allContributingRulesHaveSenderAnchor(dispatchContext, actionProposal)) {
        return LOW_TRUST_STATIC_FROM;
    }
    return null;
}
```
Add cases for tenant mismatch plus each fallback reason and assert neither send nor draft fallback is attempted.

### CR-02: Provider Error Logging Can Persist Raw Gmail-Read Bodies

**File:** `backend/core/src/main/java/com/zeromail/core/chat/llm/springai/SpringAiStreamingChatModelClient.java:109`
**Issue:** Chat read tools intentionally pass raw `getMessage` output, including `bodyText`, to the next model call through `transientToolResponseJsonByCallId`. On stream failure, the warning log appends `serviceExceptionSummary(rootCause)`, and that helper includes `OpenAIServiceException.body().toString()` at lines 250-259. Provider error bodies can echo request/tool-response content, so raw Gmail-read email content can be written to application logs. The debug stack trace at lines 114-117 has the same risk if the exception message embeds the provider body.
**Fix:**
```java
private static String serviceExceptionSummary(Throwable throwable) {
    if (!(throwable instanceof OpenAIServiceException openAIServiceException)) {
        return "";
    }
    return "statusCode="
            + openAIServiceException.statusCode()
            + " code="
            + openAIServiceException.code().orElse("-")
            + " param="
            + openAIServiceException.param().orElse("-")
            + " type="
            + openAIServiceException.type().orElse("-");
}
```
Do not log provider response bodies or unsanitized provider exceptions for chat requests that may include raw Gmail-read tool data.

### CR-03: Raw Read-Tool Bodies Are Reused For More Than One Model Call

**File:** `backend/core/src/main/java/com/zeromail/core/chat/usecases/ChatOrchestrator.java:162`
**Issue:** `transientToolResponseJsonByCallId` is created once for the whole read-tool loop, populated at lines 184-187, and never cleared after the next model call consumes it. `SpringAiStreamingChatModelClient` then substitutes the raw transient response for persisted sanitized output whenever the call id is present. If the assistant calls another read tool before answering, the original raw Gmail body is sent to the provider again on later iterations, not just "the next model call" as required.
**Fix:**
```java
Map<String, String> oneShotToolResponses = Map.copyOf(transientToolResponseJsonByCallId);
transientToolResponseJsonByCallId.clear();
ChatStreamRequest streamRequest = new ChatStreamRequest(
        tenantId.toString(),
        preparedTurn.chatId(),
        modelId,
        personalizationRenderer.render(tenantId.toString()),
        chatToolCatalog,
        history(preparedTurn.chatId()),
        oneShotToolResponses);
```
Keep only the just-executed read tool response for the immediately following model call, then clear it before any subsequent iteration.

### CR-04: Outbound Sends Do Not Preserve Deterministic Message-ID Idempotency

**File:** `backend/core/src/main/java/com/zeromail/core/triage/usecases/OutboundRuleMessageBuilder.java:31`
**Issue:** `SendReply` ignores `tenantId` and `idempotencyKey` entirely when it delegates to `buildReply(...)`. `ForwardEmail` and `SendEmail` try to set a deterministic `Message-ID` at lines 99-102, but `MimeMessage.saveChanges()` is called afterward at line 103; Jakarta Mail's `saveChanges()` unconditionally updates the `Message-ID` header. A retry after Gmail send succeeds but finalization fails therefore emits a fresh message id instead of the deterministic idempotency key, increasing duplicate outbound-send risk.
**Fix:**
```java
mimeMessage.setSubject(requireText(subject, "subject"), StandardCharsets.UTF_8.name());
mimeMessage.setText(requireText(draftBody, "draftBody"), StandardCharsets.UTF_8.name());
mimeMessage.saveChanges();
mimeMessage.setHeader("Message-ID", deterministicMessageId(tenantId, idempotencyKey));
```
Pass the same deterministic id into the reply path as well, setting `Message-ID` after `ReplyMimeBuilder` has called `saveChanges()`. Add a MIME parsing test that asserts the exact `Message-ID` for `send_reply`, `forward_email`, and `send_email`.

## Warnings

### WR-01: Protected Senders Block Safe Non-Outbound Actions

**File:** `backend/core/src/main/java/com/zeromail/core/triage/usecases/TriageOrchestratorService.java:278`
**Issue:** The sender safety net is meant to prevent automatic outbound sends and force outbound fallback drafts. The branch at lines 278-283 rejects every non-outbound action when `senderProtected()` is true, including safe deterministic actions such as `label`, `archive`, `mark_read`, `star`, `add_to_digest`, and `mark_spam`. VIP/protected senders therefore stop receiving normal triage even when no outbound action is involved.
**Fix:** Remove the non-outbound rejection block and keep sender protection inside outbound fallback handling only. Add a regression test with `senderProtected=true` and a `label` or `archive` action that still reaches `gmailWritePhase(...)`.

### WR-02: Persisted Triage Outbound JSON Allows Invalid Recipients

**File:** `backend/core/src/main/java/com/zeromail/core/triage/usecases/TriageActionResultJsonValidator.java:258`
**Issue:** `TriageActionResultJsonValidator.optionalRecipients(...)` only checks that the field is an array of strings and then returns the raw values. `TriageActionArgsCanonicalizer.optionalRecipients(...)` similarly trims and drops blanks but does not enforce the email format or the 10-recipient cap. This is weaker than `ActionIntentJsonValidator` and lets malformed persisted `forward_email` / `send_email` action JSON survive validation until MIME/Gmail execution fails later.
**Fix:** Mirror the rule action validator: trim, reject blanks, enforce `MAX_RECIPIENTS`, and validate with the same email-address pattern in both the JSON validator and canonicalizer. Prefer moving the shared recipient validation into one helper used by `ActionIntent`, `ActionIntentJsonValidator`, `TriageActionResult`, and `TriageActionResultJsonValidator`.
