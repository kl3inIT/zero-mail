# Quick Task 260508-g41: BYOK OpenRouter Preset, Model Selection, Spring AI M5

**Date:** 2026-05-08
**Status:** Complete + follow-up refactor

## Goal

Make BYOK configuration match how users think about provider keys:

- OpenRouter appears as a first-class UI option.
- OpenAI-compatible custom endpoints remain available.
- Anthropic native remains available.
- Users can enter or choose a model id and the tenant BYOK path uses that model.
- Upgrade Spring AI from `2.0.0-M4` to `2.0.0-M5`, applying changelog-driven API fixes.

## Changelog Notes

- Spring AI `2.0.0-M5` was released on 2026-04-27.
- M5 changes ChatClient options merging semantics: request options are treated as deltas; passing a fully built provider options object can replace default options unexpectedly. Prefer passing provider `Builder` instances to `.options(...)`.
- OpenRouter uses the OpenAI-compatible endpoint `https://openrouter.ai/api/v1` and requires a `model` id such as `openai/gpt-4` or `anthropic/...`.
- Anthropic Messages API requires a `model` id such as `claude-sonnet-...`.

## Implementation Steps

1. Add `model` to BYOK backend contracts, entity, persistence, Liquibase migration, current response, and gateway routing.
2. Update BYOK validation/save to require model and probe the selected model where possible without logging key/model output.
3. Update generated OpenAPI/web types after backend changes.
4. Update BYOK frontend with provider presets: OpenRouter, Anthropic, Custom OpenAI-compatible; add model input/datalist.
5. Bump Spring AI to `2.0.0-M5` and change ChatClient `.options(...)` calls to builder-style where required.
6. Update focused unit/e2e tests and run backend/frontend verification.

## Follow-up Refactor: Presets vs Compatible Protocols

User feedback on 2026-05-08 refined the BYOK UX/API shape:

- Model IDs remain free-text with datalist suggestions; do not hard-code a Java enum of models.
- API/UI should use a provider preset (`openrouter`, `openai`, `anthropic`, `openai-compatible`, `anthropic-compatible`) rather than making users reason about the persisted protocol enum.
- Official providers (`OpenRouter`, `OpenAI`, `Anthropic`) resolve to server-owned fixed endpoints and do not show or require endpoint input.
- Compatible providers (`OpenAI compatible`, `Anthropic compatible`) live in a separate UI group and require a user endpoint.
- Backend still persists the runtime protocol (`BYOKProvider`) plus canonical endpoint/model, so gateway routing remains simple.
- Validate should return reason-specific failures for wrong key, rejected endpoint, unreachable endpoint, timeout, and model-not-found cases.
