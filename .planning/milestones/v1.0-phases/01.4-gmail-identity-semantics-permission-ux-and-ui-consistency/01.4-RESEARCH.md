# Phase 1.4: Gmail Identity Semantics, Permission UX, and UI Consistency — Research

**Researched:** 2026-04-27
**Domain:** Spring Security 7 OAuth2 second-leg dispatch + Next.js 16.2 App Router error boundaries + Tailwind 4 design tokens
**Confidence:** HIGH (all critical claims verified via Context7, bundled Next.js docs, or in-repo grep)

## Summary

Phase 1.4 is two-headed: a backend OAuth2 second-leg integrity guard + connection persistence, and a frontend tokens-and-primitives sweep with Next.js 16.2 error boundary baseline. The critical research findings:

1. **Spring Security 7 OAuth2 has only ONE `successHandler` and ONE `failureHandler` per `oauth2Login()` configuration** [VERIFIED: Spring Security 6.5/7.0 reference docs via Context7]. Per-registration dispatch MUST happen *inside* the handler by inspecting `OAuth2AuthenticationToken.getAuthorizedClientRegistrationId()`. The CONTEXT.md phrase "bound to client registration" is conceptual, not configuration — the planner must implement a dispatcher.
2. **Next.js 16.2.0 introduced `unstable_retry` as the new prop on `error.tsx`**, replacing `reset` for the recommended path [VERIFIED: `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/error.md` Version History]. CONTEXT.md D-D2 says "Reset button calling Next's `reset()` prop" — `reset` still exists for cache-only resets, but `unstable_retry` is now the canonical "Try again" affordance because it re-fetches and re-renders. **Planner should use `unstable_retry`.**
3. **Tailwind 4 design tokens layer ALREADY EXISTS in the codebase** — `apps/web/app/globals.css` uses `@theme inline` with the full shadcn token taxonomy (background, foreground, muted, accent, destructive, border, ring, popover, card, sidebar, charts) and `:root` + `.dark` mode CSS custom properties [VERIFIED: read of `apps/web/app/globals.css`]. Phase 1.4's "design-tokens layer" work is therefore **(a) verifying the taxonomy is sufficient (it is)**, **(b) consuming the tokens consistently in JSX**, and **(c) optionally extending with spacing/typography/shadow scales if the sweep reveals gaps**. CONTEXT.md D-C1 over-specifies "new tokens block" — most of it already exists.
4. **`login_hint` pre-fills the email and may suppress the account chooser entirely** if the user is already signed into that Google account in their browser session [VERIFIED: Google OpenID Connect docs]. Combining with `prompt=consent` (already in the resolver) means: chooser may not appear if single-account session, otherwise pre-selects. Do NOT add `prompt=select_account` — would defeat the hint's purpose.
5. **Component scaffolding ALREADY HAS shadcn primitives** at `apps/web/components/ui/{alert,badge,button,card,dialog,input,separator,skeleton}.tsx` [VERIFIED: ls]. The 5 new primitives compose these — no new shadcn installs needed. The existing `<Alert>` (variants `default | destructive`) is the base for `StatusAlert`.

**Primary recommendation:** Implement the backend as a single `OAuth2LoginAuthenticationSuccessHandler` bean that **internally dispatches** by `getAuthorizedClientRegistrationId()` (delegating `google` → existing `OAuthProvisioningService`, `google-gmail` → new identity-check + upsert flow). Mirror the same pattern for failure dispatch. Frontend: extend the existing `globals.css` tokens *only as needed*, build 5 primitives composing existing shadcn, and use `unstable_retry` (not `reset`) in error boundaries.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**A. Same-account guard + Gmail callback persistence**
- D-A1: New `GmailOAuthSuccessHandler` mirrors `GoogleOAuthSuccessHandler`. Within one transactional path: (1) read `OidcUser.subject` of leg 2 + currently-bound user from `SecurityContext`; (2) compare against `currentUser.googleSubject`, throw `GmailIdentityMismatchException` on mismatch (no persistence); (3) on match, encrypt refresh token via `RefreshTokenCipher`, call `GmailConnectionService.upsert(...)`, advance onboarding step `SIGNED_IN → GMAIL_CONNECTED`.
- D-A2: `GmailScopeRequestResolver.customize()` extended to add `login_hint=<currentUser.email>` from `SecurityContextHolder`. Falls through silently if no current user.
- D-A3: New `GmailOAuthFailureHandler` distinguishes `GmailIdentityMismatchException` (POST Google revoke endpoint, redirect `/onboarding?error=gmail_identity_mismatch`) from `error=access_denied` (redirect `/onboarding?error=gmail_consent_denied`). Both error codes added to `ErrorCodes` + vi/en bundles.
- D-A4: `GmailConnectionService.upsert(googleEmail, scopesGranted, refreshTokenEncrypted)` — idempotent upsert; existing methods preserved verbatim. Scopes from `OAuth2AuthorizedClient.getAccessToken().getScopes()`, joined with single space.

### Pattern 1: Single Dispatching Success/Failure Handler

**What:** ONE `AuthenticationSuccessHandler` bean wired to `oauth2Login().successHandler(...)`. Internally it switches on `OAuth2AuthenticationToken.getAuthorizedClientRegistrationId()` and delegates to per-registration handlers.

**When to use:** Always for multi-registration OAuth2 setups in Spring Security 6.x/7.x. The DSL only supports one bean here [VERIFIED via Context7].

**Example:**
```java
// Source: derived from Spring Security 6.5 docs (servlet/oauth2/index.html — accessing registration id)
//         + Spring Security oauth2Login DSL (servlet/oauth2/login/advanced.html)

@Component
public class OAuth2LoginDispatchingSuccessHandler extends SimpleUrlAuthenticationSuccessHandler {
    private final GoogleOAuthSuccessHandler googleHandler;       // existing
    private final GmailOAuthSuccessHandler gmailHandler;         // new

    public OAuth2LoginDispatchingSuccessHandler(
            GoogleOAuthSuccessHandler googleHandler,
            GmailOAuthSuccessHandler gmailHandler) {
        this.googleHandler = googleHandler;
        this.gmailHandler = gmailHandler;
    }

    @Override
    public void onAuthenticationSuccess(HttpServletRequest req, HttpServletResponse res, Authentication auth)
            throws IOException, ServletException {
        if (auth instanceof OAuth2AuthenticationToken token) {
            String regId = token.getAuthorizedClientRegistrationId();
            switch (regId) {
                case "google"       -> googleHandler.onAuthenticationSuccess(req, res, auth);
                case "google-gmail" -> gmailHandler.onAuthenticationSuccess(req, res, auth);
                default -> super.onAuthenticationSuccess(req, res, auth);
            }
        } else {
            super.onAuthenticationSuccess(req, res, auth);
        }
    }
}
```

### Pattern 2: Identity Check Inside Success Handler (atomic, transactional)

**What:** Subject check + encrypt + persist + onboarding-step-advance happen inside ONE `ScopedValue.where(TENANT, tenantId).call(() -> tx.execute(...))` block. Mismatch throws BEFORE any persistence.

**When to use:** Any cross-account-protection flow where a single grant must be either fully consumed or fully rejected (no partial writes).

**Example:**
```java
// Pattern adapted from OAuthProvisioningService.createTenantAndUser
//   (backend/core/src/main/java/com/zeromail/core/account/service/OAuthProvisioningService.java)

@Component
public class GmailOAuthSuccessHandler {
    private final UserRepository users;
    private final GmailConnectionService connections;
    private final RefreshTokenCipher cipher;
    private final OAuth2AuthorizedClientService authorizedClients;
    private final TransactionTemplate tx;
    // ...

    public void onAuthenticationSuccess(HttpServletRequest req, HttpServletResponse res, Authentication auth)
            throws IOException, ServletException {
        OAuth2AuthenticationToken token = (OAuth2AuthenticationToken) auth;
        OidcUser leg2 = (OidcUser) token.getPrincipal();
        // Resolve currently logged-in user (NOT this leg's principal — they may differ).
        UserEntity currentUser = resolveSessionUser(req);   // helper: read from existing session

        if (!leg2.getSubject().equals(currentUser.getGoogleSubject())) {
            throw new GmailIdentityMismatchException();   // -> failure handler
        }

        OAuth2AuthorizedClient client = authorizedClients.loadAuthorizedClient(
                "google-gmail", token.getName());
        String refreshToken = client.getRefreshToken().getTokenValue();
        Set<String> scopes = client.getAccessToken().getScopes();
        String gmailScopes = scopes.stream()
                .filter(s -> s.startsWith("https://www.googleapis.com/auth/gmail."))
                .collect(Collectors.joining(" "));

        UUID tenantId = currentUser.getTenantId();
        ScopedValue.where(TenantContext.TENANT, tenantId.toString())
                .run(() -> tx.executeWithoutResult(s -> {
                    byte[] envelope = cipher.encrypt(
                            refreshToken.getBytes(StandardCharsets.UTF_8),
                            tenantId.toString());
                    connections.upsert(tenantId, leg2.getEmail(), gmailScopes, envelope);
                    currentUser.advanceTo(OnboardingStep.GMAIL_CONNECTED);
                    users.save(currentUser);
                }));

        new SimpleUrlAuthenticationSuccessHandler(webBaseUrl + "/onboarding")
                .onAuthenticationSuccess(req, res, auth);
    }
}
```

### Pattern 3: `login_hint` injection in `OAuth2AuthorizationRequestResolver`

**What:** Add `login_hint=<email>` to `additionalParameters` in the resolver `customize()` method, alongside existing parameters.

**When to use:** When you want the user's Google account chooser to default to a specific email — and possibly skip the chooser entirely if they're already signed in to that account [VERIFIED: Google OIDC docs].

**Example:**
```java
// Extend existing GmailScopeRequestResolver.customize()
private OAuth2AuthorizationRequest customize(OAuth2AuthorizationRequest r) {
    if (r == null) return null;
    Object regId = r.getAttribute("registration_id");
    if (regId == null || !GMAIL_REGISTRATION_ID.equals(regId.toString())) return r;

    var extra = new HashMap<>(r.getAdditionalParameters());
    extra.put("include_granted_scopes", "true");
    extra.put("prompt", "consent");
    extra.put("access_type", "offline");

    // NEW: graceful-degrade login_hint
    Authentication current = SecurityContextHolder.getContext().getAuthentication();
    if (current instanceof OAuth2AuthenticationToken token
            && token.getPrincipal() instanceof OidcUser oidc
            && oidc.getEmail() != null) {
        extra.put("login_hint", oidc.getEmail());
    }
    return OAuth2AuthorizationRequest.from(r).additionalParameters(extra).build();
}
```

### Pattern 4: Next.js 16.2 error boundary with `unstable_retry`

**What:** Client component, takes `{ error, unstable_retry }` props. Use `unstable_retry()` (NOT `reset()`) for the user-facing "Try again" affordance.

**When to use:** Every `error.tsx` and `global-error.tsx` in Next.js 16.2+.

**Example:**
```tsx
// Source: node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/error.md
'use client'; // Error boundaries MUST be Client Components

import { useEffect } from 'react';
import { useTranslations } from 'next-intl';
import { SectionCard } from '@/components/ui/SectionCard';
import { StatusAlert } from '@/components/ui/StatusAlert';
import { Button } from '@/components/ui/button';

export default function Error({
  error,
  unstable_retry,
}: {
  error: Error & { digest?: string };
  unstable_retry: () => void;
}) {
  const t = useTranslations('errors.boundary');
  useEffect(() => {
    if (process.env.NODE_ENV !== 'production') {
      console.error(error);
    }
  }, [error]);

  return (
    <SectionCard heading={t('title')}>
      <StatusAlert variant="error" titleKey="errors.boundary.title" bodyKey="errors.boundary.body" />
      <Button onClick={() => unstable_retry()}>{t('reset')}</Button>
    </SectionCard>
  );
}
```

### Pattern 5: `global-error.tsx` last-resort English-only fallback

**What:** Replaces root layout. Cannot use `next-intl`/`useTranslations` (no provider). Must include own `<html>`/`<body>`. Hard-code minimal English copy.

**Example:**
```tsx
// Source: node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/error.md (Global Error section)
'use client';

export default function GlobalError({
  error,
  unstable_retry,
}: {
  error: Error & { digest?: string };
  unstable_retry: () => void;
}) {
  return (
    <html lang="en">
      <body>
        <h1>Something went wrong</h1>
        <p>Please reload the page. If the problem persists, contact support.</p>
        <button onClick={() => unstable_retry()}>Try again</button>
      </body>
    </html>
  );
}
```

### Pattern 6: Tailwind 4 `@theme inline` token consumption

**What:** Tokens already defined as CSS custom properties in `:root` and `.dark`, surfaced into Tailwind utilities via `@theme inline` mapping. JSX uses `bg-background`, `text-foreground`, `border-border`, `text-muted-foreground`, `bg-destructive` etc.

**When to use:** All JSX in the sweep. Replace `text-stone-700`, `bg-white`, `text-gray-500`, `border-red-200` etc. with token-aware utilities.

**Example:**
```tsx
// BEFORE (current settings/page.tsx line 81):
<Card className="border-red-200 p-6">

// AFTER:
<SectionCard className="border-destructive/30 p-6" heading={t('settings.dangerZone.heading')}>
```

### Anti-Patterns to Avoid

- **Multiple `@Bean SecurityFilterChain` for per-registration handlers** — Spring Security composes them by URL matcher, not by OAuth2 registration. This will not work and will silently shadow the wrong chain.
- **Using `prompt=select_account` together with `login_hint`** — defeats the hint's account-suppression behavior. Use one or the other.
- **Calling `OAuth2AuthorizedClientService.removeAuthorizedClient` BEFORE the failure handler runs** — Spring Security's filter saves the AuthorizedClient before invoking the success handler; if the success handler throws, the AuthorizedClient is still in the store. The failure handler must explicitly call `removeAuthorizedClient` if you want it gone.
- **`reset()` for "Try again" UX in Next.js 16.2+** — `reset` does NOT re-fetch; it just re-renders with stale data. Use `unstable_retry`.
- **Rendering `error.message` or `error.stack` in any `error.tsx`** — Next.js redacts `message` for Server Component errors in production but Client Component errors are forwarded as-is. Treat as untrusted always.
- **Localizing `global-error.tsx`** — `NextIntlClientProvider` is unavailable; calling `useTranslations()` will throw, replacing the error UI with another error.
- **Storing Google's full OAuth scope string in `gmail_connections.scopes_granted`** — `include_granted_scopes=true` returns ALL scopes (openid+profile+email+gmail.modify). Filter to gmail-prefixed scopes only (per CONTEXT.md Specifics).
- **Calling `provisioning.findOrCreateGoogleUser` from `GmailOAuthSuccessHandler`** — leg 2 user MUST already exist (they signed in via leg 1). If not, fail loudly — this is an integrity error, not a provisioning trigger.

## Common Pitfalls

### Pitfall 1: Spring Security DSL accepts only one success/failure handler
**What goes wrong:** Planner writes "wire `GmailOAuthSuccessHandler` per registration `google-gmail`" and developer tries `oauth2Login(o -> o.successHandler(googleHandler).successHandler(gmailHandler))` — the second call overwrites the first.
**Why it happens:** CONTEXT.md uses "bound to client registration X" as conceptual shorthand; Spring Security's DSL doesn't support per-registration dispatch at the chain level [VERIFIED: Context7 Spring Security 6.5 OAuth2 Login DSL docs].
**How to avoid:** Build a single dispatcher (Pattern 1 above). Inspect `OAuth2AuthenticationToken.getAuthorizedClientRegistrationId()` inside the handler.
**Warning signs:** Handler invoked for the wrong registration; mismatch checks running on first-login flow.

### Pitfall 2: Spring Security saves AuthorizedClient BEFORE success handler runs
**What goes wrong:** Identity-mismatch path throws → failure handler redirects → but the `OAuth2AuthorizedClient` for `google-gmail` is already persisted in `OAuth2AuthorizedClientService`. Subsequent code thinking "no client = no grant" is wrong.
**Why it happens:** Order of operations in `OAuth2LoginAuthenticationFilter`: (1) exchange code → (2) save AuthorizedClient → (3) invoke success handler. Throwing in (3) does not roll back (2).
**How to avoid:** In `GmailOAuthFailureHandler`, call `authorizedClientService.removeAuthorizedClient("google-gmail", principalName)` BEFORE the redirect. Then POST Google revoke (best-effort). Document the ordering invariant in the handler.
**Warning signs:** "I rejected the mismatch but the user appears connected." — orphaned AuthorizedClient.

### Pitfall 3: `error.tsx` `reset` vs `unstable_retry` semantic confusion
**What goes wrong:** Developer wires `reset()` to the "Try again" button. User clicks → same error renders again because the underlying data hasn't been re-fetched.
**Why it happens:** CONTEXT.md predates the Next.js 16.2.0 introduction of `unstable_retry` [VERIFIED: bundled `error.md` Version History]. `reset` still exists for cache-only resets.
**How to avoid:** Use `unstable_retry`. Both props are passed; pick the right one for the user-facing CTA.
**Warning signs:** Reload doesn't fix transient failures.

### Pitfall 4: `global-error.tsx` cannot use `next-intl`
**What goes wrong:** Developer adds `useTranslations()` to `global-error.tsx` for consistency with other boundaries. The component throws because `NextIntlClientProvider` lives in the root layout — which `global-error.tsx` replaces.
**Why it happens:** `global-error.tsx` is the fallback for failures in the root layout itself; by definition it cannot rely on root-layout-provided context [VERIFIED: bundled `error.md` Global Error section].
**How to avoid:** Hard-code minimal English copy. Document this as the only English-only fallback.
**Warning signs:** Cascading "An error occurred while loading the error page" loop.

### Pitfall 5: `include_granted_scopes=true` means leg 2's token has ALL scopes
**What goes wrong:** Developer writes `connection.setScopesGranted("https://www.googleapis.com/auth/gmail.modify")` as a hard-coded constant, ignoring what the token actually carries. Future scope changes diverge between code constant and reality.
**Why it happens:** Mental model is "leg 2 added gmail.modify scope" but Google returns the union of all granted scopes.
**How to avoid:** Read `client.getAccessToken().getScopes()`, filter to `gmail.*` prefix, join with single space [per CONTEXT.md Specifics + D-A4]. Never hard-code.
**Warning signs:** Audit log lies about what scopes the user granted.

### Pitfall 6: `ScopedValue.where(...)` not bound before opening JPA tx
**What goes wrong:** `connections.upsert(...)` runs but Hibernate `@TenantId` filter resolves to `null` (or to the wrong tenant from the OAuth callback's "bootstrap" context), corrupting writes.
**Why it happens:** Hibernate captures the current ScopedValue when the JPA session opens, not when entities are written. Per `OAuthProvisioningService` comment: "opening the tx first would capture the bootstrap tenant and reject the user insert."
**How to avoid:** Bind the ScopedValue OUTSIDE the `transactionTemplate.execute(...)` lambda — `ScopedValue.where(TENANT, tenantId).run(() -> tx.execute(...))`, NOT `tx.execute(s -> ScopedValue.where(...).run(...))`.
**Warning signs:** Cross-tenant writes; FND-05 multi-tenant leak test fails.

### Pitfall 7: `login_hint` doesn't force the right account
**What goes wrong:** User has multiple Google accounts in their browser. `login_hint` pre-selects the right one but they can override and pick the wrong one. The mismatch path triggers — which is correct, but a user might think "I told you which account!"
**Why it happens:** `login_hint` is advisory, not authoritative [VERIFIED: Google OIDC docs: "suppresses the account chooser and either pre-fills the email box on the sign-in form, or selects the proper session"]. The user always has final say at the chooser.
**How to avoid:** Document this in the mismatch error message ("This Google account doesn't match the account you signed in with. Please pick the same account."). The subject check is the only authoritative correctness gate.
**Warning signs:** Support tickets asking "why did it reject me?"

### Pitfall 8: Re-running token revoke on every retry
**What goes wrong:** User retries after mismatch → revoke endpoint POSTs again with the same (now invalid) token → 400/401 from Google → noise in logs.
**Why it happens:** Failure handler re-invoked on each new mismatch.
**How to avoid:** Token from the FIRST mismatch is revoked once and discarded. Each NEW mismatch attempt has a NEW token (Google issued a new one for the new code exchange). No retry-on-the-same-token logic needed; just revoke each fresh token once. Log non-2xx responses at WARN, not ERROR.
**Warning signs:** Spam in WARN logs.

### Pitfall 9: Dark-mode token defined under wrong selector
**What goes wrong:** CONTEXT.md D-C2 says `[data-theme="dark"]` but the existing `globals.css` uses `.dark` class selector (per shadcn convention).
**Why it happens:** CONTEXT.md was written from the spec; the existing repo follows shadcn convention.
**How to avoid:** **Match the existing `.dark` selector in `globals.css`** [VERIFIED: read of file]. Do not introduce a `[data-theme="dark"]` selector that no toggle would target. CONTEXT.md should be treated as informative on this detail; existing code wins.
**Warning signs:** Dark-mode tokens defined but never resolve.

### Pitfall 10: `useSearchParams()` in Server Component
**What goes wrong:** Developer adds `useSearchParams()` to the existing `(protected)/onboarding/page.tsx` (which is already `'use client'`) — fine. But if any new error-display logic is hoisted into a Server Component (`onboarding/layout.tsx` say), `useSearchParams()` will fail to compile.
**Why it happens:** `useSearchParams` is a client hook.
**How to avoid:** Keep search-param-reading logic inside the existing `'use client'` page or extract a small client component (`<MismatchAlertHost />`) that the server layout renders.
**Warning signs:** Build error: "useSearchParams only works in Client Components."

### Backend: `GmailConnectionService.upsert(...)` (idempotent)

```java
// Pattern: extends existing GmailConnectionService
//   (backend/core/src/main/java/com/zeromail/core/gmail/service/GmailConnectionService.java)

@Transactional
public void upsert(UUID tenantId, String googleEmail, String scopesGranted, byte[] refreshTokenEncrypted) {
    GmailConnectionEntity row = connections.findByTenantId(tenantId)
            .orElseGet(() -> new GmailConnectionEntity(
                    UUID.randomUUID(), tenantId, googleEmail, GmailConnectionStatus.CONNECTED));
    row.setStatus(GmailConnectionStatus.CONNECTED);
    row.setRefreshTokenEncrypted(refreshTokenEncrypted);
    row.setScopesGranted(scopesGranted);
    row.setConnectedAt(Instant.now());
    row.setDisconnectedAt(null);
    connections.save(row);
}
```

Note: existing entity has no setter for `googleEmail` (only constructor); D-A4 says "defensive — should always equal stored value post-A1 check" so writing it is a no-op for the upsert. If a setter is needed for re-grant scenarios, add `setGoogleEmail(String)` to `GmailConnectionEntity`.

### Backend: Google token revocation client (best-effort)

```java
// Pattern: RestClient wrapper for https://oauth2.googleapis.com/revoke
@Component
public class GoogleTokenRevocationClient {
    private static final Logger log = LoggerFactory.getLogger(GoogleTokenRevocationClient.class);
    private final RestClient client = RestClient.builder()
            .baseUrl("https://oauth2.googleapis.com")
            .build();

    public void revokeQuietly(String token) {
        try {
            client.post()
                  .uri(uriBuilder -> uriBuilder.path("/revoke").queryParam("token", token).build())
                  .header("Content-Type", "application/x-www-form-urlencoded")
                  .retrieve()
                  .toBodilessEntity();
        } catch (RestClientException e) {
            // Best-effort. Never log token contents (privacy contract).
            log.warn("Google token revocation returned non-2xx — leaving stale grant on Google's side");
        }
    }
}
```

## Open Questions (RESOLVED)

> All four questions resolved during /gsd-plan-phase 1.4 (commit `7e7e9ee`). Plan IDs cite the resolution.

1. **RESOLVED — Should the dispatcher handlers be one bean or two (success + failure separately)?**
   - What we know: Both possible; single-bean keeps file count down; two-bean follows Spring's natural separation.
   - What's unclear: Team convention preference.
   - Recommendation: Two beans (`OAuth2LoginDispatchingSuccessHandler` + `OAuth2LoginDispatchingFailureHandler`) — mirrors Spring Security's separation, easier to test independently.
   - **Resolution:** Two beans. Implemented in `01.4-02-PLAN.md` Task 3 (SecurityConfig + dispatcher beans wire success and failure separately).

2. **RESOLVED — Should `GmailIdentityMismatchException` extend `OAuth2AuthenticationException` or be a domain exception?**
   - What we know: Both work. CONTEXT.md leaves it to Discretion.
   - What's unclear: How Spring Security's failure handler discovers/dispatches on the exception type.
   - Recommendation: Extend `OAuth2AuthenticationException` (standard Spring path). The failure handler can check `instanceof GmailIdentityMismatchException` cleanly. Throwing a non-OAuth exception inside the success handler may bypass the failure handler entirely (Spring may treat as unhandled and 500).
   - **Resolution:** Extends `OAuth2AuthenticationException`. Implemented in `01.4-02-PLAN.md` Task 1 (exception class) + Task 2 (handler throws it on subject mismatch).

3. **RESOLVED — Where should the singular `OnboardingState` advance for re-grant happen?**
   - What we know: `advanceTo(GMAIL_CONNECTED)` is forward-only and idempotent if already at `GMAIL_CONNECTED` (weight comparison).
   - What's unclear: Whether re-grant after disconnect should reset `disconnectedAt` (yes per upsert) AND re-advance the step (no-op since `>= GMAIL_CONNECTED`).
   - Recommendation: Always call `advanceTo(GMAIL_CONNECTED)` — no-op if already there, correct if at SIGNED_IN.
   - **Resolution:** Always call `advanceTo(GMAIL_CONNECTED)` after successful upsert. Implemented in `01.4-02-PLAN.md` Task 2 (success handler) — relies on the existing forward-only / weight-comparison semantics.

4. **RESOLVED — Does Phase 1.4 need to add a setter on `GmailConnectionEntity.googleEmail`?**
   - What we know: Existing entity has no setter (only constructor argument). D-A4 says "defensive — should always equal stored value post-A1 check."
   - What's unclear: Re-grant scenarios where the email might legitimately change (it shouldn't post-subject-check, but defense-in-depth).
   - Recommendation: Skip the setter. The subject check guarantees the email is the same. If a future phase needs it, add then.
   - **Resolution:** No setter added. `01.4-03-PLAN.md` Task 1 (`GmailConnectionService.upsert`) reuses the existing constructor-arg path; subject equality is guaranteed by the success handler's identity check.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes | Spring Security 7.0.5 OAuth2Login + Google OIDC subject verification. |
| V3 Session Management | yes | Existing Spring Session + Redis (Phase 1) — preserved. |
| V4 Access Control | yes | Tenant-scoped writes via `ScopedValue` + Hibernate `@TenantId`. |
| V5 Input Validation | yes | OAuth2 callback `error` codes are a fixed enum (`access_denied`, etc.); UI maps `?error=` to a closed set of i18n keys, never echoes raw value. |
| V6 Cryptography | yes | `RefreshTokenCipher` AES-GCM-256 envelope; AAD-bound to tenant; key in GCP Secret Manager. NEVER hand-roll. |
| V7 Errors and Logging | yes | Privacy contract: never log subject/email/token; structured event names + tenant_id only. `error.tsx` never renders `error.message`. |
| V13 API and Web Service | yes | OAuth2 callback endpoint protected by Spring Security filter; revoke endpoint POST is server-to-server. |

### Known Threat Patterns for {Spring Security 7 OAuth2 + Next.js 16 App Router}

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Cross-account grant (user signs in as A, grants Gmail of B) | Spoofing / Tampering | OIDC `subject` claim comparison (D-A1); reject + revoke + redirect with error code. |
| Stale OAuth2AuthorizedClient after rejected grant | Tampering | Failure handler explicitly calls `OAuth2AuthorizedClientService.removeAuthorizedClient`. |
| Refresh-token leakage via logs | Information Disclosure | `@Sensitive` wrapper + Logback scrub filter (Phase 1 D-E1/E2). Token never appears in any `log.X(...)` call. |
| OAuth callback CSRF | Tampering | Spring Security's built-in `state` parameter validation (default behavior, no opt-out). |
| Subject substitution at OIDC userinfo vs ID token | Spoofing | Use `OidcUser.getSubject()` from the verified ID token, NOT `getAttributes().get("sub")` from userinfo. |
| Frontend URL `?error=` value treated as untrusted | Tampering | Map to a CLOSED enum of error codes; unrecognized values render no alert. |
| Error boundary leaking exception body content | Information Disclosure | `error.tsx` NEVER renders `error.message` or `error.stack`. Boundary copy is i18n keys only. |
| `global-error.tsx` exposes app structure on root failure | Information Disclosure | Minimal English-only copy, no stack, no internal IDs. |
| `login_hint` value as XSS vector | XSS | URL-encoded by Spring Security's URI builder; safe by construction. |
| Google revoke endpoint failure leaks token in URL | Information Disclosure | RestClient sends token as query param to Google over HTTPS; never logged on client side. |
