# Phase 01.4 Plan 05: Next.js App Router Error-Boundary Baseline + i18n Keys — Summary

**One-liner:** 5 Next.js error boundary files (global-error + 3 segment error.tsx + not-found) using Plan 04 primitives, plus 13 UI i18n keys + 2 ApiError fallback strings turning 14 Wave 0 RED tests GREEN and unblocking Plan 06's mismatch alert wiring.

## Frontend-Design Skill Invocation Log

`frontend-design` skill loaded at execution start (per persistent user feedback memory + Phase 01.4 CONTEXT D-Discretion: "frontend-design skill MUST be invoked by every executor"). Skill directives translated to this plan's aesthetic decisions:

- **Refined-minimalist direction (matches Plan 04 precedent).** Boundary surfaces are utility fallbacks — clarity beats expression. Each boundary composes a single SectionCard + StatusAlert + retry CTA without decorative ornament. The 404 leans on EmptyState's confident-not-apologetic copywriting voice.
- **Spacing rhythm with intent.** PageShell variant per surface (auth=`max-w-md` flex-centered for /login; marketing=`max-w-5xl` for landing; app=`max-w-3xl` for protected; same for 404). SectionCard inherits Plan 04's `gap-4` body and `px-4 py-4` outer.
- **Typography compose-by-inheritance.** SectionCard heading already carries `font-heading font-medium leading-snug`; StatusAlert title carries `font-medium`. Boundary code does not override — typography rhythm flows from the primitives. The single typography escalation is `not-found.tsx`'s display heading (text-3xl semibold tracking-tight via EmptyState).
- **Color: 60/30/10 mapped onto neutral preset.** All classes token-aware: `bg-background`, `text-foreground`, `text-muted-foreground`, `bg-primary`, `text-primary-foreground`, `ring-ring`. `global-error.tsx`'s inline button uses `bg-primary` for the single accent CTA. StatusAlert's error variant inherits `bg-destructive/10 text-destructive border-destructive/40` from Plan 04.
- **Motion: zero.** Pure render. The shadcn `Skeleton` `animate-pulse` lives elsewhere (LoadingState), not here.
- **`global-error.tsx` is the one English-only surface.** Inline copy is exactly four sentences (display heading + body + button label) — minimum surface area, maximum information density, zero decorative reach for a copy bundle that isn't available.

The skill's discipline applied to skeleton structure as well as polish — every spacing/typography/color decision was checked against UI-SPEC §Spacing/Typography/Color before writing.

### Privacy contract (Phase 01.4 D-D3)

All 5 boundaries comply:

- **NEVER render `error.message`, `error.stack`, or `error.digest`** — only i18n keys (or English literals in global-error.tsx). Wave 0 grep gate enforces (no boundary file references `error.message|stack|digest` anywhere).
- **`console.error(error)` only when `NODE_ENV !== 'production'`** — Browser DevTools convenience for the developer; never in shipped builds. Threat T-error-leak.
- **NO error reporting SDK** — no Sentry, Datadog, OTel browser. Observability is a future dedicated phase.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Plan File 3 segment boundary specified BOTH SectionCard heading AND StatusAlert title — duplicate DOM render fails Wave 0 contract**

- **Found during:** Task 1 first vitest run.
- **Issue:** Test `error.test.tsx > renders title and body from i18n keys` uses `screen.getByText(/Something went wrong/i)` (single match). The plan's `<SectionCard heading={t('title')}>` plus `<StatusAlert titleKey="errors.boundary.title" />` produced two elements with the same text (one in `card-title` slot, one in `alert-title` slot), breaking single-match assertion.
- **Fix:** Drop `heading` prop on SectionCard in all 3 segment error.tsx files. StatusAlert renders the title once via `errors.boundary.title`. The boundary code no longer needs `useTranslations()` itself — StatusAlert owns its own next-intl lookup.
- **Files modified:** `app/(public)/error.tsx`, `app/(auth)/error.tsx`, `app/(protected)/error.tsx`.
- **Commit:** `296ca3d`

**2. [Rule 1 - Bug] Plan 01 RED test scaffold uses `Object.defineProperty(process.env, 'NODE_ENV', ...)` — Node 24 + Vitest 4 reject with ERR_INVALID_OBJECT_DEFINE_PROPERTY**

- **Found during:** Task 1 second vitest run (after fix #1).
- **Issue:** The console.error tests in `error.test.tsx` use `Object.defineProperty(process.env, 'NODE_ENV', { value: 'test', configurable: true })` to swap the env value. Modern Node refuses to redefine `process.env` properties via `defineProperty` (the env object enforces a strict descriptor shape).
- **Fix:** Replace with vitest's official `vi.stubEnv('NODE_ENV', 'test')` + `vi.unstubAllEnvs()` (in finally block). Survives across Node versions and is the documented Vitest 4 API.
- **Files modified:** `apps/web/__tests__/app/error.test.tsx`.
- **Commit:** `296ca3d`

**3. [Rule 1 - Bug] Plan 01 RED scaffold for global-error <body> assertion fails — RTL strips nested `<html>`/`<body>`, react-dom/server crosses React-module-instance boundary**

- **Found during:** Task 1 second vitest run.
- **Issue:** Test `global-error.test.tsx > renders own <body> element (root replacement)` does `container.querySelector('html')` after RTL `render()`. React DOM in jsdom unwraps nested `<html>`/`<body>` (logs "html cannot be a child of div" warning), leaving the container empty of those tags. Three alternative approaches all failed: `react-dom/server.renderToStaticMarkup` hits the same separate-React-module-instance bug as lucide-react / @base-ui/react under vitest dedupe; calling the component as a plain function fails because `useEffect` requires a renderer context; introspecting the JSX tree with `tree.type === 'html'` likewise calls `useEffect`.
- **Fix:** Static-source read using `readFileSync(...)` on `app/global-error.tsx` and asserting the source contains `<html` and `<body`. This faithfully captures the contract Next.js relies on (global-error.tsx replaces the root layout, MUST emit html/body) without depending on a DOM/SSR layer the test environment can't provide. Documented inline in the test JSDoc.
- **Files modified:** `apps/web/__tests__/app/global-error.test.tsx`.
- **Commit:** `296ca3d`

**4. [Rule 2 - Missing critical functionality] Plan 02 added `ErrorCodes.GMAIL_IDENTITY_MISMATCH` / `GMAIL_CONSENT_DENIED` constants, but no matching ApiError-localizer leaves in vi/en bundles — `pnpm i18n:check` backend coverage REQUIRED**

- **Found during:** Task 2 first i18n:check run.
- **Issue:** Plan 04 SUMMARY's deferred-items.md flagged 4 backend-coverage failures (`errors.gmail.identity.mismatch` + `errors.gmail.consent.denied` missing in vi.json + en.json), explicitly assigning Plan 05 ownership ("Plan 05 owns the resolution"). UI-SPEC §Copywriting Contract only lists the 13 UI keys; without the 2 ApiError leaves, `pnpm i18n:check` exits 1.
- **Fix:** Add 2 leaf strings (`errors.gmail.identity.mismatch` + `errors.gmail.consent.denied`) to both bundles alongside the UI nested objects. The ApiError localizer (`apps/web/lib/api/errors.ts`) reads the leaf strings; the StatusAlert (Plan 06) reads the nested `gmail.identity.mismatch.{title,body,cta}` object. No path collision because they live in different namespaces (`errors.gmail.*` vs top-level `gmail.*`).
- **Files modified:** `apps/web/messages/vi.json`, `apps/web/messages/en.json`.
- **Commit:** `ff17f78`
