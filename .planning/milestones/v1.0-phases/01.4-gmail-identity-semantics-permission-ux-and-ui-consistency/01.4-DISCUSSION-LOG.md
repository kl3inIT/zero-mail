## A. Same-account guard + Gmail callback persistence

### A.Q1 — Where to enforce same-account check?

| Option | Description | Selected |
|--------|-------------|----------|
| Custom GmailOAuthSuccessHandler | Mirror GoogleOAuthSuccessHandler bound to registration `google-gmail`. Single class: validate subject → encrypt refresh token → save GmailConnectionEntity. Invariant in one place, transactional, testable. | ✓ |
| @EventListener on Spring authorize event | Listen to authorize-success event; decouples security infra and persistence, but races with redirect and can't reject inline 401 before user lands on /onboarding. | |
| Custom OncePerRequestFilter | Pre-handle filter on /oauth2/callback/gmail. Filter ordering with Spring Security 7's OAuth2 callback flow is brittle. | |

**User's choice:** Custom GmailOAuthSuccessHandler (recommended)
**Notes:** All four sub-decisions in Area A converged on Option 1 — single handler owns full lifecycle.

### A.Q2 — login_hint strategy on leg-2 authorization request?

| Option | Description | Selected |
|--------|-------------|----------|
| Add in GmailScopeRequestResolver | Same place that adds prompt=consent + access_type=offline. Read currentUser.email from SecurityContextHolder; fall through if anonymous. | ✓ |
| Encode email into redirect URL | ConnectGmailController builds redirect URL with ?login_hint=. Breaks resolver pattern; resolver still needs customization, so two customization points. | |
| No login_hint, rely on post-callback subject check | User sees Google account chooser regardless. Safe but worse UX. | |

**User's choice:** Add in GmailScopeRequestResolver (recommended)

### A.Q3 — Mismatch reject behavior?

| Option | Description | Selected |
|--------|-------------|----------|
| Failure handler → redirect /onboarding?error=gmail_identity_mismatch + revoke token | ApiError code `gmail.identity.mismatch`, frontend localizes via `useLocalizedApiError`. POST Google revoke endpoint to drop just-granted token. | ✓ |
| Failure handler → redirect, NO revoke | Simpler. Token sits in Spring's authorized-client store; user can revoke from Google account, but grant lingers until natural expiry. | |
| Save row with status=PENDING_MISMATCH | Over-engineered for v1 single-account; introduces extra state, extra UI, extra confusion. | |

**User's choice:** Failure handler + redirect + revoke (recommended)

### A.Q4 — Persist GmailConnectionEntity path?

| Option | Description | Selected |
|--------|-------------|----------|
| Same GmailOAuthSuccessHandler calls GmailConnectionService.upsert(...) | Refresh token via existing RefreshTokenCipher; idempotent upsert preserves 1-row-per-tenant invariant; scopes from getAccessToken().getScopes() joined by space. | ✓ |
| Async @EventListener from handler | Handler publishes event; async listener persists. Race with redirect; user sees /onboarding before row exists → useTenantStatus reports NOT_CONNECTED. | |
| Rely on JdbcOAuth2AuthorizedClientService default | Spring stores in oauth2_authorized_client table; read at Phase 2A. Misses domain row (status/connectedAt/scopes); violates D-G2 envelope schema (Spring's default isn't AES-GCM v1). | |

**User's choice:** Same handler calls GmailConnectionService.upsert(...) (recommended)

## B. Future workspace/multi-account seam

### B.Q1 — API shape for v1?

| Option | Description | Selected |
|--------|-------------|----------|
| Singular now, list later | Keep GET /gmail/connection/status. v2 introduces parallel GET /gmail/connections additively (OpenAPI version bump). Zero churn now. | ✓ |
| List shape now (array of 1) | Frontend forward-proof but signals multi-account in scope when it isn't; breaks singular controller convention. | |
| Hybrid: keep singular + add list endpoint | Doubles API surface; frontend has to choose. | |

**User's choice:** Singular now, list later (recommended)

### B.Q2 — Add workspace_id column on gmail_connections day-1?

| Option | Description | Selected |
|--------|-------------|----------|
| NO column, tenant_id remains workspace key | Zero schema work, no orphan column, preserves @TenantId discriminator pattern. | ✓ |
| Nullable workspace_id = tenant_id | API can return workspace_id forward-compat, but orphan column violates YAGNI; conflicts with Hibernate @TenantId. | |
| Rename tenant_id → workspace_id | Massive churn touching Phase 1/1.2/1.2.1 invariants; out of scope. | |

**User's choice:** NO column (recommended)

### B.Q3 — tenant → workspace rename strategy?

| Option | Description | Selected |
|--------|-------------|----------|
| KEEP 'tenant' code/schema, alias UI only when v2 | Backend, ArchUnit, Modulith, schema stay 'tenant'. v1 UI text uses "Gmail account" singular. v2 introduces UI-level "Workspace" alias at copy layer; backend untouched. | ✓ |
| Rename backend now (TenantContext → WorkspaceContext) | Touches Phase 1/1.2/1.2.1 invariants — scope creep. | |
| Add typed alias (@Workspace = @TenantId) | Premature abstraction. | |

**User's choice:** Keep code, alias UI later (recommended)

### B.Q4 — /settings 'add another Gmail account' affordance?

| Option | Description | Selected |
|--------|-------------|----------|
| No affordance | Show '1 Gmail account connected: <email>' with reconnect/disconnect only. Simplest, no false promise. | ✓ |
| Disabled-stub button "Add another (coming soon)" | Signals roadmap but commits product timeline; clutter; users will ask "when?". | |
| Single-element list UI ("1 of 1" table row) | Design dry-run for v2 visual pattern; looks weird for single-element. | |

**User's choice:** No affordance (recommended)

## D. Connect-Gmail UX & error-boundary baseline

> User added a new in-scope item mid-discussion: "Add a frontend error-state baseline: route-level and global Next.js error fallbacks backed by reusable UI primitives, without introducing full error reporting or locking final brand styling." Reformulated D to incorporate this as D.Q2 + D.Q3, bundling the original deny-consent / single-account-copy / reconnect questions into D.Q4.

### D.Q1 — Mismatch error rendering location?

| Option | Description | Selected |
|--------|-------------|----------|
| Inline StatusAlert on /onboarding | Read query param via useSearchParams; render alert at top with i18n keys; CTA re-triggers /tenant/connect-gmail; clear param via router.replace. | ✓ |
| Dedicated route /onboarding/error | Separate page + layout; doesn't compose well across multiple error variants. | |
| Toast + redirect to /onboarding | Toast disappears; no Toast primitive (C.Q4 deferred). | |

**User's choice:** Inline StatusAlert (recommended)

### D.Q2 — Scope of the new Next.js error-boundary baseline?

| Option | Description | Selected |
|--------|-------------|----------|
| Full set: global-error + 3 per-group error.tsx + not-found.tsx | 5 small files. global-error for root crashes; per-group for finer recovery; not-found for 404. | ✓ |
| Minimal: only global-error + not-found | Catches root + 404 but no per-group granularity; protected-shell crashes nuke whole app. | |
| Per-group only, no global-error / not-found | Misses root-layout failures and 404s default to Next's branded fallback (token-inconsistent). | |

**User's choice:** Full set (recommended)

### D.Q3 — Error-boundary content discipline?

| Option | Description | Selected |
|--------|-------------|----------|
| i18n-driven copy + Reset + redact details, no reporting | All copy via next-intl keys; Reset button calls reset(); error.message/stack NEVER shown; console.error in dev only; no Sentry/Datadog/OTel. | ✓ |
| Same + render error.message in collapsible Details for dev | Risks production exposure if NODE_ENV check forgotten; privacy contract risk. | |
| Same + add Sentry browser SDK now | Scope creep; observability vendor open per STATE.md blockers. | |

**User's choice:** i18n-driven + Reset + redact, no reporting (recommended)

### D.Q4 — Adjacent UX bundle (deny-consent + single-account copy + reconnect flow)?

| Option | Description | Selected |
|--------|-------------|----------|
| Default bundle | Same failure handler distinguishes access_denied → /onboarding?error=gmail_consent_denied; /settings adds inline footer note "v1 supports one Gmail account, the email you logged in with"; reconnect uses same /tenant/connect-gmail flow with login_hint and subject-check guards. One flow, no special-case branches. | ✓ |
| Bundle but skip /settings copy note | Saves an i18n key but invites confused support tickets. | |
| Discuss each separately | Available if user wanted to dig in. | |
