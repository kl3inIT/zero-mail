# Phase 1.3: Frontend Architecture Refactor and Public Content Foundation - Context

**Gathered:** 2026-04-26
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 1.3 reorganizes `apps/web` from a flat App Router layout into a scalable structure built on (1) route groups `app/(public)`, `app/(auth)`, `app/(protected)`, (2) feature folders that mirror Phase 1.2's backend domains plus a cross-cutting `i18n` slot, (3) an isomorphic typed-API contract that locks how server-fetch (RSC, `proxy.ts`) and client-fetch (TanStack Query) interact with the existing `lib/api/client.ts` singleton, (4) workspace-quality gates (Prettier, Husky, lint-staged) wired at the monorepo root, and (5) public landing + multi-page docs scaffolding using `next-mdx-remote/rsc` over `apps/web/content/docs/*.mdx`. The phase preserves every Phase 1 / 1.1 / 1.2 invariant intact: `localePrefix: 'never'` clean URLs, ApiError contract, log-scrub safety, no body/prompt/completion in logs, the Spring Modulith / ArchUnit boundaries for backend.

**In scope:**
- Refactor `apps/web/app/` into `app/(public)/`, `app/(auth)/`, `app/(protected)/` route groups with per-group `layout.tsx` files; URLs stay clean (`/`, `/login`, `/onboarding`, `/settings`, `/docs`, `/docs/[slug]`).
- Create `apps/web/features/{auth, account, onboarding, gmail, i18n}/` each with `api/`, `components/`, `hooks/` subfolders; deep-import convention (no barrel `index.ts`).
- Move existing flat components to feature owners: `LanguageSwitcher.tsx` → `features/i18n/components/`; `ConnectionHealthBadge.tsx` + `ReconnectPrompt.tsx` → `features/gmail/components/`; `DeleteAccountDialog.tsx` → `features/account/components/`; `TemplateCard.tsx` → `features/onboarding/components/`.
- Drop the dead `app/[locale]/` mirror tree (3 re-export files); next-intl's `localePrefix: 'never'` does not need a dynamic locale segment.
- Consolidate the duplicated `/me` server-fetch (currently in `proxy.ts:reconcileLocaleCookie` + `app/layout.tsx:reassertServerLocale`) into a single isomorphic function at `features/account/api/me.ts` that both call sites import.
- Lock the per-endpoint API shape: one isomorphic function per endpoint (`getX({ fetcher?, signal?, headers? })`) usable from RSC and CSR; CSR hooks live in `features/<name>/hooks/`; per-feature TanStack Query key factory at `features/<name>/api/keys.ts`.
- Extract `(protected)` chrome to `app/(protected)/_components/` (underscore-prefixed → not routed); compose data via feature hooks; LanguageSwitcher imported from `features/i18n/components/` so all 3 group layouts reuse the same component.
- Add Prettier 3 (single root `.prettierrc` + `prettier-plugin-tailwindcss`), Husky 9, lint-staged with Tier B scope at the **monorepo root**; pre-commit runs ESLint + Prettier + `pnpm i18n:check` on staged files.
- Workspace cleanup: delete `apps/web/pnpm-lock.yaml` (duplicate of root); delete `apps/web/pnpm-workspace.yaml` and migrate `ignoredBuiltDependencies: [sharp, unrs-resolver]` to root `pnpm-workspace.yaml`; run a clean `pnpm install` from root and smoke-test `pnpm dev` + `pnpm test`.
- Scaffold public landing at `app/(public)/page.tsx` (Light skeleton — header/main/footer slots with placeholder copy, unstyled-final).
- Scaffold docs at `app/(public)/docs/page.tsx` (index list) + `app/(public)/docs/[slug]/page.tsx` (single doc render) using `next-mdx-remote/rsc` reading from `apps/web/content/docs/*.mdx`; 2-3 sample MDX files with `gray-matter` frontmatter `{ title, slug, order, locale }` to prove the pipeline.

**Out of scope (enforced):**
- Final visual design for landing or docs (typography polish, hero copy, illustrations, marketing CTAs, sidebar/TOC styling). Phase 5 or a dedicated docs-content phase owns the design.
- Auto-generated docs sidebar / TOC / search / breadcrumbs (locked frontmatter shape supports it later — implementation deferred).
- Switching `localePrefix` away from `'never'` (changing to `'as-needed'` for SEO `/vi/docs` vs `/en/docs` would break Phase 1.1 D-B1 contract).
- Adding any new backend endpoint, migration, or wire DTO. Frontend-only refactor.
- Any auth-flow UX changes (login button copy, OAuth scope progression, session lifecycle, CSRF). The `(auth)` group is purely a routing/layout reorg.
- Migrating pre-commit to Tier C (tsc + vitest on staged files) — known anti-pattern; CI owns those checks.
- Promoting Husky/lint-staged into `apps/web/` instead of the root.
- Introducing Fumadocs or any heavyweight docs framework in this phase.
- Pre-creating `features/` slots for Phase 2A/2B/2C/3/4/5 work (mail, billing, llm, rules, triage, drafts, analytics) — each future phase carves its own feature when it lands.
- Backend module changes — Phase 1.2 just landed; no churn allowed across the API contract.

## Implementation Decisions

### A. Feature folder decomposition

- **D-A1:** **Hybrid feature decomposition** — `apps/web/features/{auth, account, onboarding, gmail, i18n}/`. Three folders mirror Phase 1.2 backend domains (`account`, `onboarding`, `gmail`); `auth` carves out the Google OAuth client-side flow that semantically belongs to a separate user-facing concept; `i18n` carves out the Phase 1.1 cross-cutting locale work that does not belong to any backend domain. The backend `tenant` domain is not user-facing on FE — its multi-tenancy infra stays in `lib/` (no frontend feature folder needed). Phase 2A→5 (mail, billing, llm, rules, triage, drafts, analytics) each carve their own feature when they land.
- **D-A2:** **Each `features/<name>/` has exactly three subfolders: `api/`, `components/`, `hooks/`.** `api/` holds isomorphic typed-API functions (D-B1) and the per-feature query key factory (D-B3). `components/` holds feature-internal UI components. `hooks/` holds TanStack Query hooks (`useX`/`useUpdateX`/`useDeleteX`) plus any feature-specific React hooks (e.g., `features/i18n/hooks/useLocaleChange.ts`).
- **D-A3:** **Shared chrome of the `(protected)` route group lives at `app/(protected)/_components/`.** Co-located with the route group; underscore prefix prevents Next from treating it as a route. Examples: `ProtectedHeader.tsx`, `ProtectedSidebar.tsx`, future `GlobalPauseToggle.tsx`. Composes data by calling feature hooks (e.g., `useCurrentUser()` from `features/account/hooks/`). Public and auth groups have leaner per-group chrome inside their own `(public)/_components/` and `(auth)/_components/` if/when needed (Phase 1.3 ships only what landing/login require).
- **D-A4:** **Existing flat `apps/web/components/*.tsx` are moved to their feature owners:**
  - `LanguageSwitcher.tsx` → `features/i18n/components/LanguageSwitcher.tsx`
  - `ConnectionHealthBadge.tsx` → `features/gmail/components/ConnectionHealthBadge.tsx`
  - `ReconnectPrompt.tsx` → `features/gmail/components/ReconnectPrompt.tsx`
  - `DeleteAccountDialog.tsx` → `features/account/components/DeleteAccountDialog.tsx`
  - `TemplateCard.tsx` → `features/onboarding/components/TemplateCard.tsx`
  - `apps/web/components/ui/*` (shadcn primitives) **stay** in `components/ui/` per ROADMAP success criterion #3.
- **D-A5:** **No barrel exports in `features/<name>/`.** Imports use deep paths via the `@/` alias: `import { LanguageSwitcher } from '@/features/i18n/components/LanguageSwitcher'`. Reasons: explicit tree-shaking; refactor-IDE friendly (find-references works on the leaf file, not on a re-export); avoids circular imports as features grow in Phase 2A→5.

### B. API + hooks contract (server vs client)

- **D-B1:** **One isomorphic function per endpoint** in `features/<name>/api/<endpoint>.ts`. Signature shape:
  ```ts
  export async function getCurrentUser(opts?: {
    fetcher?: typeof fetch;     // RSC may pass server fetch with cookie header
    signal?: AbortSignal;
    headers?: HeadersInit;       // RSC passes incoming `Cookie` header here
  }): Promise<CurrentUser> { ... }
  ```
  RSC call sites (e.g., `proxy.ts`, `app/layout.tsx`) pass `{ headers: { cookie } }` explicitly. CSR call sites (TanStack Query hooks) pass `{ signal: queryCtx.signal }` and rely on the default credentialed client. Single source of truth → no type drift between server and client variants.
- **D-B2:** **The base typed client stays at `apps/web/lib/api/client.ts` as a singleton.** Per ROADMAP success criterion #6 verbatim. Each `features/<name>/api/<endpoint>.ts` imports `api` (the openapi-fetch wrapper) from `@/lib/api/client`. No per-feature client factory; no second `server-client.ts` variant. Feature `api/` functions accept the optional `fetcher` to bypass the singleton when RSC needs explicit cookie forwarding.
- **D-B3:** **Per-feature TanStack Query key factory** at `features/<name>/api/keys.ts`:
  ```ts
  export const accountKeys = {
    all: ['account'] as const,
    me: () => [...accountKeys.all, 'me'] as const,
    preferences: () => [...accountKeys.all, 'preferences'] as const,
  };
  ```
  Each feature owns its keys; cross-feature invalidation goes through explicit `queryClient.invalidateQueries({ queryKey: accountKeys.me() })` calls — no implicit string-based magic.
- **D-B4:** **Consolidate the `/me` server-fetch into `features/account/api/me.ts`.** Today `proxy.ts:reconcileLocaleCookie` and `app/layout.tsx:reassertServerLocale` each duplicate the `fetch(${apiBase}/me, { headers: { cookie } })` logic. After Phase 1.3, both call:
  ```ts
  import { getCurrentUser } from '@/features/account/api/me';
  // proxy.ts (response-capable):
  const user = await getCurrentUser({ headers: { cookie: cookieHeader } }).catch(() => null);
  ```
  TanStack Query CSR hook `features/account/hooks/useCurrentUser.ts` calls the same function. Removes the duplication; surfaces a single isomorphic invariant: "/me requires cookie forwarding."
- **D-B5:** **TanStack Query hooks in `features/<name>/hooks/`.** Naming: `useX` for queries, `useUpdateX` / `useDeleteX` for mutations. Hook bodies invoke the corresponding `features/<name>/api/<endpoint>.ts` function. Mutations emit explicit `queryClient.invalidateQueries({ queryKey: <featureKeys>.X() })` after success — no global invalidate.

### C. Route group structure + `[locale]/` cleanup

- **D-C1:** **Drop `app/[locale]/` mirror tree entirely.** The existing 3 re-export files (`app/[locale]/{login,onboarding,settings}/page.tsx`) are dead code under `localePrefix: 'never'` (Phase 1.1 D-B1). After deletion, the single source of truth for routes is the route-group tree.
- **D-C2:** **Three route groups, locked URLs:**

  | Route group | URLs | Purpose |
  |---|---|---|
  | `app/(public)/` | `/`, `/docs`, `/docs/[slug]` | Marketing landing + multi-page docs (no auth required) |
  | `app/(auth)/` | `/login` | Auth-flow surfaces (login today; future password-reset, logout-confirmation) |
  | `app/(protected)/` | `/onboarding`, `/settings` | Authenticated app surfaces |

  `proxy.ts` auth gate keeps redirecting `/onboarding` and `/settings` to `/login` when `ZEROMAIL_SESSION` cookie is absent (PROTECTED list expands as `(protected)/...` grows in Phase 5).
- **D-C3:** **`/` always renders the public landing.** `(public)/page.tsx` shows landing scaffolding for everyone. Authenticated users see the same landing with a CTA pointing to their next step (`/onboarding` if `onboarding_step` is incomplete; future `/dashboard` once Phase 5 ships it). The current `app/page.tsx → redirect('/login')` behavior is removed — landing is the marketing surface and should be shareable by authenticated users. The CTA logic queries the existing `/me` endpoint via `features/account/api/me.ts` (D-B4).
- **D-C4:** **Per-route-group `layout.tsx` files** with a single shared `LanguageSwitcher` import:
  - `app/(public)/layout.tsx` — landing/docs nav (logo, "Docs" link, "Sign in" link, `<LanguageSwitcher>`).
  - `app/(auth)/layout.tsx` — minimal centered-card layout (logo small at top, `<LanguageSwitcher>` compact, no nav). Login card renders inside.
  - `app/(protected)/layout.tsx` — authenticated chrome composing `app/(protected)/_components/ProtectedHeader.tsx` (user menu, `<LanguageSwitcher>`, future `GlobalPauseToggle`, future `ConnectionHealthBadge`).

  All three import `<LanguageSwitcher>` from `features/i18n/components/LanguageSwitcher`. Root `app/layout.tsx` retains the `<html>`/`<body>`/`NextIntlClientProvider`/`QueryProvider` wrapper (the "shell of shells").
- **D-C5:** **OAuth callback redirect target stays unchanged.** Spring Boot owns `/oauth2/authorization/google` and `/auth/gmail/callback`; on success it redirects the browser to `/onboarding`. Frontend has no callback route; the existing `proxy.ts` auth gate sees the new `ZEROMAIL_SESSION` cookie and lets `/onboarding` render. No frontend work needed for OAuth redirect handling in Phase 1.3.

### D. Docs/MDX architecture + landing scaffolding

- **D-D1:** **MDX library = `next-mdx-remote/rsc`.** Lightweight, RSC-native, no design-framework lock-in. Server-side compiles MDX → React tree at request time inside `(public)/docs/[slug]/page.tsx`. Fumadocs and similar full docs frameworks are deferred — they would lock Phase 5 visual decisions and pull in a heavyweight UI layer that Phase 1.3 explicitly defers. Because Next.js 16 has breaking changes (per `apps/web/AGENTS.md`), the planner / executor MUST verify `next-mdx-remote/rsc` compatibility against Next 16.2.4 via Context7 lookup before installation; if incompatible, the fallback is a hand-rolled `compileMDX` wrapper using `@mdx-js/mdx` + `@mdx-js/react` directly.
- **D-D2:** **Content location = `apps/web/content/docs/*.mdx`.** Co-located with the app that renders it; outside `app/` so Next does not treat it as a route. Aligns with ROADMAP success criterion #7's relative path `content/docs/*.mdx`. Deploy artifact ships with the web build automatically. No symlinks, no cross-workspace resolution.
- **D-D3:** **Frontmatter parser = `gray-matter`** with a fixed schema:
  ```yaml
  ---
  title: "Getting Started"
  slug: "getting-started"
  order: 10
  locale: "vi"          # 'vi' | 'en' — matches Phase 1.1 locale allow-list
  ---
  ```
  `(public)/docs/page.tsx` reads the entire `apps/web/content/docs/` folder, parses frontmatter, filters by current locale (from `getLocale()`), sorts by `order`, and lists docs by title. `(public)/docs/[slug]/page.tsx` finds the file matching `params.slug` for the current locale and renders its body via `next-mdx-remote/rsc`. Locale-mismatched MDX file → 404 (so `/docs/billing` rendered while user is in `vi` won't accidentally show the `en` doc).
- **D-D4:** **Scaffolding scope = "Light skeleton".** Concrete deliverable per page:
  - `(public)/page.tsx` — header/main/footer layout slots with placeholder Vietnamese copy ("Zero Mail — AI auto-triage cho Gmail. Trang đang được hoàn thiện."), placeholder English mirror, and a single CTA button "Đăng nhập / Sign in" linking to `/login`. No hero illustration, no marketing sections, no styled-final visuals.
  - `(public)/docs/page.tsx` — index list rendering `<ul>` of docs from frontmatter (title + slug-link); placeholder header.
  - `(public)/docs/[slug]/page.tsx` — single doc render via `next-mdx-remote/rsc`; placeholder header above the article.
  - 2-3 sample MDX files in `apps/web/content/docs/`: `getting-started.{vi,en}.mdx` and `privacy.{vi,en}.mdx` (or similar) — frontmatter populated, body short ("Coming soon" placeholder copy in two languages). The sample files exist purely to prove the pipeline and let Phase 5 designer test their render.
  - i18n keys for landing and docs scaffolding copy added to `messages/{vi,en}.json` per Phase 1.1 D-A2 (namespaced `landing.*` and `docs.*`).
- **D-D5:** **MDX file naming convention to support locale = `<slug>.<locale>.mdx`.** E.g., `getting-started.vi.mdx`, `getting-started.en.mdx`. Listing logic groups by `<slug>` and surfaces only the entry matching the current locale. This avoids stuffing locale into folder paths (`docs/vi/`, `docs/en/`), keeps the frontmatter `slug` field consistent across locales, and aligns with the Phase 1.1 locale-aware-but-not-URL-prefixed model.

### E. Tooling + workspace cleanup

- **D-E1:** **Pre-commit hook scope = Tier B** (ESLint + Prettier + `pnpm i18n:check`). Husky 9 + lint-staged installed at the **monorepo root**. lint-staged config (in root `package.json`):

    "apps/web/**/*.{ts,tsx,js,jsx}": [

  5. **Smoke-test** `pnpm dev` (Next dev server boots), `pnpm test` (vitest suite passes), `pnpm test:e2e` (Playwright switcher smoke from Phase 1.1 P07 still passes), `pnpm i18n:check` (parity script still wires).

### Claude's Discretion

The planner / executor have flexibility within CLAUDE.md and the decisions above on:
- Exact `next-mdx-remote/rsc` version (Context7-verify Next 16.2.4 compat at install time; if not yet compatible, fall back to `@mdx-js/mdx` + `@mdx-js/react` direct usage).
- Husky 9 install command shape (`pnpm dlx husky init` vs scripted) — pick whichever survives a clean `pnpm install`.
- ESLint config form for Phase 1.3 — current `apps/web/eslint.config.mjs` is flat-config; flat-config is required for Next 16 + ESLint 9. Keep flat; do NOT introduce `.eslintrc.*` siblings.
- `tsconfig.json` `paths` aliases — current alias is `@/*` mapping to `apps/web/*`. Add explicit narrower aliases (`@/features/*`, `@/lib/*`, `@/components/*`) only if the executor finds the broad alias causes IDE auto-import noise; default = keep `@/*` alone.
- Whether `app/(protected)/_components/ProtectedHeader.tsx` ships in Phase 1.3 (with placeholder content) or is created lazily once Phase 5 has actual chrome to render — the layout slot must exist either way.
- Sample MDX file slugs (`getting-started`, `privacy`, `troubleshooting` are reasonable defaults; pick the slugs that exercise the pipeline most, not the slugs that pre-design Phase 5 docs IA).
- `lib/locale/` vs keeping locale helpers inline — if any reusable locale code emerges from D-B4 that is NOT account-domain (e.g., a generic `forwardCookieHeader` helper used by future features), extract to `lib/locale/` or `lib/api/server-utils.ts`; otherwise keep co-located in `features/account/api/me.ts`.
- Test file relocation — current tests live at `apps/web/__tests__/{components,e2e,i18n}/`. Plan whether to move feature-specific tests into `features/<name>/__tests__/` (co-location, modern convention) or keep them at the workspace root. Default = move feature-internal unit tests under each `features/<name>/`; keep e2e at `apps/web/__tests__/e2e/` (Playwright config references it explicitly).
- frontend-design skill invocation — executor MUST invoke the `frontend-design` skill before writing landing or docs page UI; this is locked by the user's persistent feedback memory and overrides any executor-level shortcut.

<specifics>
## Specific Ideas

- **`features/<name>/` no-barrel rule is firm.** Even when later phases add many files per feature, do not introduce `index.ts` re-exports. Deep imports via `@/features/<name>/...` keep tree-shaking explicit and refactor-IDE-friendly. If a feature grows large enough to warrant grouping, prefer a deeper subfolder (`features/account/api/me/`, `features/account/api/preferences/`) over a barrel.
- **Isomorphic API functions accept `headers` for explicit cookie forwarding.** RSC `fetch()` does not auto-forward the request's `Cookie` header; the function signature mandates passing it explicitly when called from RSC contexts. This is an invariant the planner must enforce in every feature `api/` function — failure to forward cookies breaks `/me` and any other tenant-scoped endpoint.
- **MDX file naming = `<slug>.<locale>.mdx`** (e.g., `getting-started.vi.mdx`, `getting-started.en.mdx`). Locale is a frontmatter field too, but the filename suffix lets the listing logic do a cheap directory scan grouped by `<slug>`. Avoids stuffing locale into folder paths.
- **`next-mdx-remote/rsc` Next 16 compat is unverified.** The planner / executor MUST run a Context7 lookup against Next 16.2.4 before installing. If incompatible, fall back to `@mdx-js/mdx` + `@mdx-js/react` direct usage with a small custom `compileMDX` wrapper. **Do not silently swap to Fumadocs** — that is a deferred-idea decision, not an executor shortcut.
- **Husky lives at the monorepo root, never in `apps/web/`.** Husky 9+ explicitly recommends repo-root install for monorepos; nested install breaks Git's `.git/hooks` discovery and leaves a bypassed gate. The user has confirmed this anti-pattern memory through Phase 1.1 P07's Playwright placement decision (root vs subdir) — same principle.
- **Workspace cleanup must verify `apps/web/proxy.ts:as unknown as` cast still works.** The cast bridges duplicate-`next` peer-permutations from pnpm hoist (Phase 1.1 P07). After deleting the apps-level lockfile + workspace-yaml and running fresh `pnpm install`, run `tsc --noEmit` and `pnpm test:e2e` to confirm the hoist shape and the cast both still hold. If the cast becomes broken (compile error), the executor must surface this as a deviation, not silently rewrite the file.
- **frontend-design skill is mandatory for landing + docs UI authoring.** Per the user's persistent feedback memory, executors that touch frontend code (specifically the new landing page UI, the docs index list UI, and the per-doc article shell) MUST invoke the `frontend-design` skill before writing the JSX. This is required even though Phase 1.3 explicitly defers final visual design — the skill's discipline applies to skeleton structure, not just polish.
- **The `(public)` landing CTA logic is the only RSC-time I/O on the public surface.** All other public pages (`/docs`, `/docs/[slug]`) read filesystem only, never the API. This keeps unauthenticated cold-cache landings cheap.
- **Landing copy stays in `messages/{vi,en}.json` even though it's "scaffolding".** Hard-coded English / Vietnamese strings on the landing page would violate Phase 1.1 D-D3 (hard-coded EN scanner). The scanner runs on Phase 1 in-scope files; Phase 1.3 must add `(public)/page.tsx` and the landing slot in `(public)/_components/` to the scanner's scope.
