# Phase 01.3: Frontend Architecture Refactor and Public Content Foundation - Research

**Researched:** 2026-04-26
**Domain:** Next.js 16 App Router refactor + frontend tooling at monorepo root + RSC MDX docs scaffold
**Confidence:** HIGH (locked stack already verified in CONTEXT.md; this research focuses on Next 16 specifics, MDX RSC compat, Husky 9 monorepo install, ESLint 9 + Prettier integration, pnpm 10 settings — all confirmed against installed `node_modules/next/dist/docs/` and live npm registry on 2026-04-26)

## Summary

Phase 1.3 is **architecture/tooling, not product**. The stack is fully locked by CLAUDE.md and CONTEXT.md; the open questions are about *how Next 16 actually works in practice* (it differs in non-trivial ways from training data, per `apps/web/AGENTS.md`), whether `next-mdx-remote/rsc` is safe to adopt today, and the exact mechanical shape of Husky 9 + lint-staged + Prettier + ESLint 9 wired at the monorepo root.

The good news: every piece of the tooling stack has a verified, currently-shipping configuration that matches the locked decisions. `next-mdx-remote` v6.0.0 (Feb 2026) has a `./rsc` subpath that compiles MDX inside Server Components, declares only `react: '>=16'` as peer (so React 19.2.4 is fine), and v6 added `blockJS` / `blockDangerousJS` security controls that are valuable for our privacy posture. Husky 9 has dropped the `husky.sh` source line entirely — `.husky/pre-commit` is now plain shell. ESLint 9 + `eslint-config-next` 16.2.4 ships pre-built flat configs (`eslint-config-next/core-web-vitals`, `eslint-config-next/typescript`) which the existing `apps/web/eslint.config.mjs` already consumes correctly. `eslint-config-prettier` 10.1.8 has a dedicated `eslint-config-prettier/flat` import. `prettier-plugin-tailwindcss` 0.7.3 (Apr 2026) supports Tailwind 4 by default (v0.7.0 made v4 the default fallback). `pnpm` 10 accepts `ignoredBuiltDependencies` in **either** root `pnpm-workspace.yaml` **or** root `package.json`'s `pnpm` field — CONTEXT.md picks `pnpm-workspace.yaml`, which matches the documented placement.

The thorny issues identified by research: (1) Next 16 made *all* dynamic API access async — `params`, `searchParams`, `cookies()`, `headers()` are all `Promise<...>` now (Phase 1.3 must use `await params` in every `[slug]` page and `await headers()` in every server component that forwards cookies — the existing `app/layout.tsx` and `proxy.ts` already do this correctly, but the new `(public)/docs/[slug]/page.tsx` must not regress); (2) layouts cannot read pathname/searchParams and won't re-render between sibling routes — so the `(public)`, `(auth)`, `(protected)` layouts can each fetch `/me` once and trust the cache; (3) Next 16 requires a `default.js` for every parallel route slot — Phase 1.3 has no parallel routes, so this is a non-issue but worth noting if Phase 5 introduces them; (4) `next/legacy/image` is removed; (5) `next lint` is removed — `eslint` must be invoked directly (the existing `package.json` already does `"lint": "eslint"`, so this is fine).

**Primary recommendation:** Adopt `next-mdx-remote@6.0.0` via `/rsc` (verified compatible). Install Husky 9 via `pnpm dlx husky init` from repo root with the simplified v9 hook script (no `husky.sh` source). Lint-staged config goes in root `package.json` as a `"lint-staged"` field. Use `eslint-config-prettier/flat` appended last to the existing flat-config array. Keep `prettier-plugin-tailwindcss` as the only Prettier plugin (it must load alongside Tailwind 4 — version `>=0.7.0`). Migrate `ignoredBuiltDependencies` to root `pnpm-workspace.yaml` per CONTEXT.md D-E4.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|--------------|----------------|-----------|
| Public landing render (`/`) | Frontend Server (RSC) | — | Server-rendered, SEO-relevant, calls `/me` once for CTA decision. Browser tier only handles hydration. |
| Docs index render (`/docs`) | Frontend Server (RSC) | — | Reads filesystem (`apps/web/content/docs/*.mdx`) — must run server-side. Pure I/O, no client interactivity. |
| Docs slug render (`/docs/[slug]`) | Frontend Server (RSC) | — | Compiles MDX server-side via `next-mdx-remote/rsc` — `compileMDX` is RSC-only. |
| Login form (`(auth)/login`) | Frontend Server + Browser | API | Form chrome SSR'd; OAuth redirect is server-side; click handler may be client. |
| Onboarding / Settings (`(protected)/*`) | Frontend Server + Browser | API | RSC fetches initial state; TanStack Query owns mutations. |
| Locale negotiation | Proxy (`proxy.ts`) | Frontend Server | proxy.ts owns response cookies (only response-capable boundary in Next 16); root layout owns `<html lang>` read at render time. |
| Auth gate (redirect to `/login`) | Proxy (`proxy.ts`) | — | Cookie inspection at the network boundary, before any layout/page render. |
| Language switcher | Browser (Client Component) | — | Interactive UI; cookie write is optimistic via document.cookie + server reconciliation. |
| `/me` fetch (consolidation target) | Frontend Server (isomorphic function) | Browser (CSR via TanStack Query) | One file (`features/account/api/me.ts`); accepts optional `headers`/`fetcher` so RSC can forward cookies and CSR can use the credentialed singleton. |
| TanStack Query hydration | Frontend Server (prefetch + dehydrate) | Browser (HydrationBoundary) | RSC prefetches; client component receives `dehydrate(queryClient)` and rehydrates. Pattern locked here for Phase 5 to reuse. |
| OpenAPI typed-fetch base client | Browser (singleton) + Frontend Server (per-request) | — | `lib/api/client.ts` singleton for CSR; RSC calls pass an explicit `fetcher` with cookie header to bypass cookie-stripping defaults. |
| ESLint/Prettier/i18n-parity gate | Local dev (Husky pre-commit) | CI | Husky 9 runs at git-commit boundary; CI runs full suite (tsc, vitest, Playwright). |

### Alternatives Considered

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| `next-mdx-remote/rsc` | `@next/mdx` (file-based MDX → page) | `@next/mdx` is the framework-native path documented in `node_modules/next/dist/docs/01-app/02-guides/mdx.md`. It treats `.mdx` files inside `app/` as routable pages. **Rejected** because it forces locale handling into folder structure (`app/docs/[locale]/[slug]/page.mdx` instead of `<slug>.<locale>.mdx`), breaks the deferred-design contract (we'd ship MDX files as routes, not as content), and pulls in Webpack/Turbopack loader plumbing. `next-mdx-remote/rsc` keeps the content outside `app/` (in `apps/web/content/docs/`) and lets us compile per-request with our own slug logic. |
| `next-mdx-remote/rsc` | Hand-rolled `@mdx-js/mdx` + `@mdx-js/react` | Direct usage requires writing a `compileMDX`-equivalent wrapper that parses frontmatter via `vfile-matter`, runs `unified` with remark/rehype plugins, and bridges to React. CONTEXT.md D-D1 lists this as the **fallback** if `next-mdx-remote` is incompatible — **research confirms it is compatible**, so the fallback does not trigger. |
| `gray-matter` | `@stefanprobst/remark-extract-yaml-frontmatter` | gray-matter is the documented frontmatter solution in Next 16's MDX guide (`node_modules/next/dist/docs/01-app/02-guides/mdx.md` lines 622-694) and predates the unified ecosystem's frontmatter solutions. CONTEXT.md D-D3 already locks gray-matter. |
| Husky 9 | simple-git-hooks / lefthook / pre-commit | Husky has the deepest pnpm-monorepo support and the smallest bundle (2 KB gzipped, zero deps). CONTEXT.md D-E1 / D-E2 lock Husky 9. |
| Husky in `apps/web/` | Husky at repo root | Husky **must** be at the same level as `.git` to discover the hooks directory. Subdir installs fail silently. CONTEXT.md D-E2 locks root install. |
| Single root `.prettierrc` | per-package Prettier configs | CONTEXT.md D-E3 explicitly rejects per-package configs. Single root config is simpler and matches single-prettier-version reality. |
| Tier B pre-commit | Tier C (tsc + vitest) | CONTEXT.md D-E1 explicitly rejects Tier C as a known anti-pattern (developers `--no-verify` past slow hooks). |

### Pattern 1: Per-route-group `layout.tsx` with shared LanguageSwitcher

**What:** Each route group (`(public)`, `(auth)`, `(protected)`) has its own `layout.tsx` that wraps the route segment but **does not** redefine `<html>` or `<body>` (those are the root layout's responsibility — having `<html>` in a non-root layout would create a *new* root layout per Next 16 rules and cause full page reloads on navigation between groups).

**When to use:** Always. CONTEXT.md D-C4 locks this.

**Example:**
```tsx
// app/(public)/layout.tsx
// Source: node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/route-groups.md
import { LanguageSwitcher } from '@/features/i18n/components/LanguageSwitcher';
import Link from 'next/link';

export default function PublicLayout({ children }: { children: React.ReactNode }) {
  return (
    <div className="flex min-h-full flex-col">
      <header className="border-b">
        <nav className="mx-auto flex max-w-5xl items-center justify-between px-4 py-3">
          <Link href="/" className="font-semibold">Zero Mail</Link>
          <div className="flex items-center gap-4">
            <Link href="/docs">Docs</Link>
            <Link href="/login">Sign in</Link>
            <LanguageSwitcher />
          </div>
        </nav>
      </header>
      <main className="flex-1">{children}</main>
    </div>
  );
}
```

> **Note:** Because layouts in Next 16 do NOT re-render between sibling routes (they are cached), they cannot read `pathname` or `searchParams`. If you need active-link styling, the `<NavLinks>` portion must be a client component using `usePathname()` (per `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/layout.md` §"Pathname"). `[VERIFIED: layout.md lines 240-289]`

### Pattern 2: Async dynamic-route page with awaited `params` (Next 16 mandatory)

**What:** In Next 16, `params` and `searchParams` are `Promise<...>` always — you must `await` them.

**When to use:** Every `[slug]` page, every layout/page that reads `params`.

**Example:**
```tsx
// app/(public)/docs/[slug]/page.tsx
// Source: node_modules/next/dist/docs/01-app/02-guides/upgrading/version-16.md §"Async Request APIs"
import { notFound } from 'next/navigation';
import { compileMDX } from 'next-mdx-remote/rsc';
import { promises as fs } from 'node:fs';
import path from 'node:path';
import { getLocale } from 'next-intl/server';

interface Frontmatter {
  title: string;
  slug: string;
  order: number;
  locale: 'vi' | 'en';
}

export default async function DocPage({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;
  const locale = await getLocale();
  const filePath = path.join(process.cwd(), 'content', 'docs', `${slug}.${locale}.mdx`);

  let source: string;
  try {
    source = await fs.readFile(filePath, 'utf8');
  } catch {
    notFound();
  }

  const { content, frontmatter } = await compileMDX<Frontmatter>({
    source,
    options: { parseFrontmatter: true },
  });

  return (
    <article className="prose mx-auto max-w-3xl px-4 py-8">
      <h1>{frontmatter.title}</h1>
      {content}
    </article>
  );
}
```

> **Note:** `next-mdx-remote/rsc` v6.0.0 adds `blockJS` / `blockDangerousJS` security knobs that default to `true`. We rely on those defaults — do **not** override them, since untrusted MDX content (even if today the content is repo-owned, future phases may import 3rd-party docs). `[VERIFIED: github.com/hashicorp/next-mdx-remote/releases v6.0.0]`

### Pattern 3: Isomorphic API function (RSC + CSR single source of truth)

**What:** One file per endpoint, one function with optional `fetcher`/`signal`/`headers` for RSC cookie forwarding.

**When to use:** Every endpoint accessed from BOTH server (RSC, proxy.ts) and client (TanStack Query). Mandatory per CONTEXT.md D-B1.

**Example:**
```ts
// features/account/api/me.ts
// Source: CONTEXT.md D-B1 + D-B4
import { api } from '@/lib/api/client';

export interface CurrentUser {
  id: string;
  email: string;
  preferredLanguage: 'vi' | 'en';
  onboardingStep?: string;
}

export interface GetCurrentUserOptions {
  fetcher?: typeof fetch;
  signal?: AbortSignal;
  headers?: HeadersInit;
}

export async function getCurrentUser(opts: GetCurrentUserOptions = {}): Promise<CurrentUser> {
  const { fetcher, signal, headers } = opts;
  if (fetcher || headers) {
    // RSC path — explicit cookie forwarding required (Next 16 fetch() does not auto-forward)
    const apiBase = process.env.NEXT_PUBLIC_API_BASE ?? '';
    const res = await (fetcher ?? fetch)(`${apiBase}/me`, {
      headers,
      cache: 'no-store',
      signal,
    });
    if (!res.ok) throw new Error(`/me failed: ${res.status}`);
    return res.json() as Promise<CurrentUser>;
  }
  // CSR path — credentialed singleton handles cookies automatically
  const { data, error, response } = await api.GET('/me', { signal });
  if (error || !response.ok) throw error ?? new Error(`/me failed: ${response.status}`);
  return data as CurrentUser;
}
```

### Pattern 8: `proxy.ts` consolidating `/me` via the new isomorphic function

```ts
import createIntlMiddleware from 'next-intl/middleware';
import { NextResponse, type NextRequest } from 'next/server';
import { routing } from './i18n/routing';
import { getCurrentUser } from '@/features/account/api/me';   // NEW import

const handleI18n = createIntlMiddleware(routing);
const PROTECTED = ['/onboarding', '/settings'];
const NEXT_LOCALE_COOKIE = 'NEXT_LOCALE';
const COOKIE_MAX_AGE = 60 * 60 * 24 * 365;

async function reconcileLocaleCookie(request: NextRequest, response: NextResponse): Promise<void> {
  if (!request.cookies.get('ZEROMAIL_SESSION')) return;
  const cookieHeader = request.headers.get('cookie');
  if (!cookieHeader) return;
  try {
    const user = await getCurrentUser({ headers: { cookie: cookieHeader } });
    const preferred = user.preferredLanguage;
    if (preferred !== 'vi' && preferred !== 'en') return;
    const current = request.cookies.get(NEXT_LOCALE_COOKIE)?.value;
    if (current === preferred) return;
    response.cookies.set(NEXT_LOCALE_COOKIE, preferred, {
      maxAge: COOKIE_MAX_AGE, sameSite: 'lax', secure: true, path: '/',
    });
  } catch { /* silent */ }
}

export default async function proxy(request: NextRequest): Promise<NextResponse> {
  const intlResponse = handleI18n(request as unknown as Parameters<typeof handleI18n>[0]) as unknown as NextResponse;
  const needsAuth = PROTECTED.some((p) => request.nextUrl.pathname.startsWith(p));
  if (needsAuth) {
    const session = request.cookies.get('ZEROMAIL_SESSION');
    if (!session) return NextResponse.redirect(new URL('/login', request.url));
  }
  await reconcileLocaleCookie(request, intlResponse);
  return intlResponse;
}
```

### Anti-Patterns to Avoid

- **Putting `<html>`/`<body>` in route-group layouts.** This creates *multiple root layouts* per Next 16 (`route-groups.md` §Caveats — "if you use multiple root layouts without a top-level layout.js"). Each navigation between root layouts is a **full page reload** instead of an SPA transition — kills perceived performance. **Keep `<html>`/`<body>` in `app/layout.tsx` only.**
- **Reading `params` synchronously.** Next 16 fully removed sync compatibility (`version-16.md` §Async Request APIs). `const { slug } = params` will throw at runtime; must be `const { slug } = await params`.
- **Reading `cookies()` / `headers()` synchronously.** Same as above — async-only in Next 16. Existing `app/layout.tsx` and `proxy.ts` already do this correctly.
- **Using `fetch()` in RSC without explicit cookie forwarding.** Next 16 RSC `fetch()` does not auto-forward the request's `Cookie` header to same-origin URLs in the way browser fetch does — you must explicitly pass `{ headers: { cookie: cookieHeader } }`. The `getCurrentUser({ headers })` invariant in CONTEXT.md D-B1 enforces this.
- **Using `next/legacy/image`.** Removed in Next 16 (`version-16.md` §next/legacy/image deprecated — well, still importable but flagged removal-in-progress). Use `next/image`. We don't use legacy/image today.
- **Running `next lint`.** Removed in Next 16 (`version-16.md` §`next lint` Command). The existing `package.json` already runs `eslint` directly — no change needed.
- **Configuring Husky inside `apps/web/`.** Husky 9 hooks are wired via Git's `core.hooksPath`, which Husky points at the directory next to `.git`. Sub-directory installs fail silently — the hook file exists but Git never invokes it. **Root only.**
- **Running tsc / vitest in pre-commit (Tier C).** Slow hooks lead to `--no-verify` bypass habit. CONTEXT.md D-E1 locks Tier B (eslint + prettier + i18n parity).
- **Adding a `<head>` to root layout.** Use `generateMetadata()` (already done in `app/layout.tsx` lines 30-37). Direct `<head>` placement bypasses Next 16's metadata streaming + de-dup machinery.
- **Mutating response cookies from a Server Component layout.** `cookies().set(...)` from RSC is silently rejected (per the deviation already documented in `app/layout.tsx` lines 41-46). Cookie writes must live in `proxy.ts`.

## Common Pitfalls

### Pitfall 1: Layouts cannot read pathname or searchParams (Next 16 caching)

**What goes wrong:** Author writes `app/(protected)/layout.tsx` that reads `usePathname()` to highlight active nav — fails because `usePathname` is a client hook (layouts are server components by default, and even if marked `'use client'`, they're cached and won't re-render between sibling routes).
**Why it happens:** Next 16 caches layouts on navigation by design (`layout.md` §"Layouts are cached in the client during navigation").
**How to avoid:** Extract any pathname-aware piece into a small client component with `'use client'` (e.g., `<NavLinks>` per `layout.md` example lines 449-475) and import it into the layout.
**Warning signs:** `usePathname` returns the URL of the *first* visited route in a group, not the current one.
**[VERIFIED: layout.md §Pathname]**

### Pitfall 2: Async Request API regression (Next 16 mandatory)

**What goes wrong:** Phase 1.3 author copies the doc render code from a Next 14/15 tutorial: `const { slug } = params` instead of `const { slug } = await params`.
**Why it happens:** Training data covers Next 14/15 patterns where sync access still worked.
**How to avoid:** Always use the typed signature `params: Promise<{ slug: string }>` and `await params`. Run `pnpm exec next typegen` to regenerate `PageProps<'/...'>` helpers if uncertain. CI's `tsc --noEmit` will catch this if the type is correctly declared.
**Warning signs:** Runtime "params is a Promise, awaiting was expected" error or silent `undefined` for `params.slug`.
**[VERIFIED: version-16.md §"Async Request APIs (Breaking change)"]**

### Pitfall 3: Multiple root layouts triggering full page loads

**What goes wrong:** Phase 1.3 author moves `<html>`/`<body>`/providers from root `app/layout.tsx` into each group layout to "isolate" them — every navigation between `/` (public) and `/login` (auth) becomes a full browser reload, killing client-side state and breaking TanStack Query cache continuity.
**Why it happens:** Multiple root layouts is a documented Next.js feature (`route-groups.md` §Caveats — "Full page load: If you navigate between routes that use different root layouts, it'll trigger a full page reload"); easy to over-apply.
**How to avoid:** Keep ONE root layout at `app/layout.tsx` with `<html>`/`<body>`/providers. Group layouts contain only chrome (header/main/footer), no `<html>`/`<body>`. CONTEXT.md D-C4 already specifies this — research re-confirms.
**Warning signs:** Console flicker, Query cache reset on cross-group nav, browser dev tools "Document" reload entry on every group transition.
**[VERIFIED: route-groups.md §Caveats + layout.md §Root Layout]**

### Pitfall 4: pnpm hoist shape change breaks `as unknown as` cast in `proxy.ts`

**What goes wrong:** After deleting `apps/web/pnpm-lock.yaml` + `apps/web/pnpm-workspace.yaml` and running fresh `pnpm install` from root, pnpm rebuilds the dependency graph. If hoist behavior changed between the two install moments (e.g., due to `@playwright/test` peer-dep registration changing), the duplicate-`next` peer permutation may shift — making the existing `as unknown as` cast either unnecessary (no compile error before, type error after — needs the cast removed) or insufficient (compile error in proxy.ts where there was none before — needs additional brackets).
**Why it happens:** pnpm hoist depends on the exact dependency tree at install time; deleting then re-creating the lockfile non-deterministically can recreate or change the same shape.
**How to avoid:** After workspace cleanup (D-E4) — `tsc --noEmit` from `apps/web/` AND run `pnpm test:e2e` (Phase 1.1 P07 Playwright smoke) before declaring the cleanup successful. If the cast becomes incorrect, document the change as a deviation note (do NOT silently rewrite — Phase 1.1 P07 deviation note is explicitly preserved per D-E5).
**Warning signs:** `tsc --noEmit` succeeds before cleanup but fails after, OR runtime "Type 'NextResponse' is not assignable" on a path that previously worked.
**[VERIFIED: 01.1-CONTEXT.md P07 deviation note + project-level pnpm peerDependencyRules.ignoreMissing config in root package.json]**

### Pitfall 5: lint-staged glob mismatches in monorepo with config at root

**What goes wrong:** Author writes `"**/*.ts"` in root lint-staged config expecting it to scope to apps/web only — instead it matches files in `backend/**`, `buildSrc/**`, etc., causing Prettier/ESLint to fail on Java sources.
**Why it happens:** lint-staged 16 resolves globs relative to the **git repo root**, so `**/*.ts` matches the entire tree.
**How to avoid:** Always prefix globs with the workspace path: `"apps/web/**/*.{ts,tsx,js,jsx}"`. Add `.prettierignore` entries for backend/build artifacts. CONTEXT.md D-E1 specifies the scoped glob already — lock it.
**Warning signs:** Pre-commit stalls or fails on Java/Kotlin/Gradle files.
**[VERIFIED: lint-staged README §Configuration — "If the glob pattern does contain a slash (/), it will match for paths as well"]**

### Pitfall 6: `next-mdx-remote` Turbopack transpilation requirement

**What goes wrong:** With Turbopack now default in Next 16, `next-mdx-remote` may fail to compile on first build because Turbopack's tree-shaking sees ESM/CJS edges in unist/remark deps.
**Why it happens:** Turbopack's Rust-based bundler has stricter ESM expectations than Webpack.
**How to avoid:** Add `transpilePackages: ['next-mdx-remote']` to `next.config.ts`. Per the next-mdx-remote README this is documented as a temporary workaround for an open issue.
**Warning signs:** First `next dev` after install fails with "module not found" or "import vfile-matter" type errors.
**[CITED: hashicorp/next-mdx-remote README §Turbopack — research 2026-04-26]**

### Pitfall 7: Husky 9 hook silent-no-op when shebang is added

**What goes wrong:** Author copies an old Husky 8 tutorial that includes `#!/usr/bin/env sh` + `. "$(dirname -- "$0")/_/husky.sh"` at the top of `.husky/pre-commit`. Husky 9 has DROPPED the husky.sh helper — the source line silently fails to import, and the script may execute partially or skip lint-staged entirely.
**Why it happens:** Husky 9's documented simplification: hooks are just plain shell scripts now.
**How to avoid:** `.husky/pre-commit` is plain shell — single line `pnpm exec lint-staged` and nothing else. No shebang, no source.
**Warning signs:** Pre-commit "succeeds" on bad code; manual `bash .husky/pre-commit` shows error about `husky.sh` not found.
**[VERIFIED: WebSearch + Husky 9 release notes — "the lines #!/usr/bin/env sh and . \"$(dirname -- \"$0\")/_/husky.sh\" are deprecated and should be removed"]**

### Pitfall 8: `prepare` script crashes on CI / Docker fresh install

**What goes wrong:** CI clones the repo, runs `pnpm install`, the `prepare: "husky"` script runs, but `.git/` doesn't exist in the CI shallow checkout — Husky errors and aborts the install.
**Why it happens:** `prepare` runs after `pnpm install` automatically; husky tries to write `.git/hooks/_husky.sh` but there's no .git.
**How to avoid:** Set `HUSKY=0` in the CI env. Alternatively use `"prepare": "husky || true"` so install never fails on hook setup. CONTEXT.md doesn't specify CI behavior; recommend both — `HUSKY=0` in CI and `husky || true` for resilience.
**Warning signs:** CI `pnpm install` step fails with "fatal: not a git repository" type errors.
**[VERIFIED: typicode.github.io/husky/how-to.html — "To avoid installing Git Hooks on CI servers or in Docker, use HUSKY=0"]**

### Pitfall 9: prettier-plugin-tailwindcss 0.6.x incompatible with Tailwind 4

**What goes wrong:** Author installs an older `prettier-plugin-tailwindcss` (e.g., 0.5 or 0.6) — it tries to use the v3 PostCSS API and silently does nothing for Tailwind 4 classes (no error, just no sorting).
**Why it happens:** Plugin v0.7.0 (Oct 2024) added Tailwind 4 default detection.
**How to avoid:** Pin `^0.7.3` (latest as of 2026-04-26).
**Warning signs:** Tailwind classes are not auto-sorted on save / format despite plugin being listed.
**[VERIFIED: github.com/tailwindlabs/prettier-plugin-tailwindcss/releases v0.7.0 release notes]**

### Pitfall 10: Folder rename without `git mv` loses blame history

**What goes wrong:** Author manually creates `app/(auth)/login/page.tsx`, copies content from `app/login/page.tsx`, deletes the original — Git sees this as delete + add, and `git blame` shows the new file as starting at the rename commit, losing all prior authorship.
**Why it happens:** Git rename detection is heuristic — it works ONLY when content similarity is high enough to be detected as a rename in the same commit. Move + edit in separate commits or with significant content change defeats it.
**How to avoid:** Use `git mv apps/web/app/login apps/web/app/\(auth\)/login` (escape parens for shell). Stage the move + any related edits in the same commit. Verify with `git log --follow apps/web/app/(auth)/login/page.tsx`.
**Warning signs:** `git log --follow` on the new file stops at the rename commit instead of showing prior history.

### Applicable ASVS Categories

|---------------|---------|------------------|
| V2 Authentication | yes | Spring Security session cookie owns auth; frontend forwards `Cookie` header on RSC fetch — no JWT, no localStorage tokens. **Preserved**. |

### Known Threat Patterns for Next 16 + RSC + MDX Stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Path traversal via `[slug]` (e.g., `/docs/..%2F..%2Fetc%2Fpasswd`) | Tampering / Information Disclosure | Use `path.join(process.cwd(), 'content', 'docs', `${slug}.${locale}.mdx`)` AND validate `slug` against a regex like `/^[a-z0-9-]+$/`. Reject otherwise via `notFound()`. |
| Locale injection (`/docs/foo` rendered with `locale=../etc`) | Tampering | `getLocale()` is constrained by next-intl's `routing.locales` allow-list (`['vi', 'en']`). Defensive guard already present in `app/layout.tsx` lines 99-102. |
| MDX-injected JSX importing arbitrary modules | Elevation of Privilege | `next-mdx-remote@6.0.0` `blockJS: true` (default) prevents arbitrary `import` and `<script>` tag injection. Don't override the default. |
| MDX-injected component overrides bypassing global components | Tampering | Pass a fixed `components` map to `compileMDX({ components: {...} })`; do not derive from MDX content. |
| `/me` response leak via React Server Component caching | Information Disclosure | RSC fetches use `cache: 'no-store'` (already present in `app/layout.tsx` line 67 and `proxy.ts` line 70). New isomorphic function preserves this. |
| Pre-commit hook bypass (`--no-verify`) leaking unformatted secrets | Tampering | Tier B keeps hook fast (< 5s budget) → reduces bypass incentive. CI runs the same gates as a backstop. |
| Husky `prepare` script execution at install time of attacker-controlled package | Elevation of Privilege | Husky has no postinstall surface; `prepare: "husky"` only runs husky's own binary. The `ignoredBuiltDependencies: [sharp, unrs-resolver]` setting blocks postinstall scripts for those listed packages. |
| Tailwind class injection via MDX `className=` | Tampering | MDX → React tree, then renderer; no string concatenation into a CSS context. Plus Tailwind 4 only emits utilities for classes seen at build time, so an attacker cannot synthesize new utilities at runtime. |
