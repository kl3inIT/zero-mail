## Decisions Made

- **CL-3 working form = `"shared.privacy"`.** Probe A (the dotted-nested literal that CONTEXT D-D4 prescribes) passed `ApplicationModulesTest.verify()` on first run with `tenant → {"shared.privacy"}`. Probes B and C (research-suggested fallbacks) were not needed. This is the single literal Plans 02-05 will use throughout — no per-plan re-discovery, no module-not-found churn.
- **`buildSrc` approved-package update folded into Task 2's commit.** This was not in the original plan but falls under the Pitfall 1 family of silent-failure surfaces: the build-time guard (`sensitiveLogGuard` task wired into `:check`) skips files whose package starts with the configured `approvedPkg`. After moving the privacy classes, leaving `approvedPkg = "com.zeromail.core.privacy"` would (a) no-op the skip for the actual scrubber files and (b) potentially flag legitimate `Sensitive` references inside them. Tracked as deviation R1 below.
- **Fix-up commit `9769dd7` for Task 1.** First Task 1 commit included the renames but not the package-decl edits because the latter applied to the working tree but the renamed paths weren't re-staged before commit. `compileJava` was green at that commit (Gradle compiles working tree, not the index), but the committed source had stale `package com.zeromail.core.privacy;` declarations — which would have broken the next compile. Per execution protocol I created a NEW fix commit rather than amending, so bisect history stays linear and honest.
- **`LogScrubSyntheticTrafficTest` import update bundled into Task 2.** The plan put this test in Task 3 (verify gate). Updating its imports there would have meant `compileTestJava` failed in Task 2's verify step (it couldn't be compiled with stale imports). Bundling the import update into the same commit as the other Pitfall 1 string-FQN updates kept Task 2 self-consistent.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical] `buildSrc/zeromail.sensitive-log-guard.gradle.kts` `approvedPkg` follows the move**
- **Found during:** Task 2 (planning the string-FQN sweep)
- **Issue:** The plan's interface inventory listed only `logback-spring.xml`, `SafetyContractArchTests`, and the two privacy tests as Pitfall 1 surfaces. The `buildSrc` plugin's `approvedPkg = "com.zeromail.core.privacy"` constant is the same shape of silent-failure surface (string-typed FQN reference, not compile-checked, governs whether legitimate `Sensitive` references inside the scrubber classes are flagged or skipped). After the move, leaving `approvedPkg` stale would either (a) no-op the package-prefix skip for the actual scrubber files (so `:check` still passes but the skip semantics drift) or (b) cause spurious violations on any future code that references `Sensitive` inside `core/shared/privacy/`. Either way, the build's safety contract weakens.
- **Fix:** Updated `approvedPkg` constant from `"com.zeromail.core.privacy"` to `"com.zeromail.core.shared.privacy"` and corrected the matching JavaDoc reference at the top of the script.
- **Files modified:** `buildSrc/src/main/kotlin/zeromail.sensitive-log-guard.gradle.kts`
- **Verification:** Bundled into Task 2's commit (`6f43a6f`); subsequent test runs against `:backend:core:test` and `:backend:api:test` continued to pass with no spurious sensitive-log-guard violations.
- **Committed in:** `6f43a6f`

**2. [Rule 1 - Bug] Fix-up commit for stale package declarations in Task 1's renames**
