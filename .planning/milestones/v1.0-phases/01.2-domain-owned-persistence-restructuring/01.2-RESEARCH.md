## Summary

Phase 1.2 is a pure structural refactor: same JPA schema, same Hibernate `@TenantId`-driven discriminator filter, same RFC 7807 + ApiError contract, same `Sensitive<T>` log-scrub guarantee, same controller HTTP shapes. Roughly **40 files** carry the substring `com.zeromail.core.persistence` today (14 source, ~26 docs/tests/configs); the move touches every one. The technical risks cluster in three places:

1. **Spring Modulith nested-module naming under 2.0.7-SNAPSHOT.** `displayName` on `@ApplicationModule` exists [VERIFIED: javadoc] but the **logical name used in `allowedDependencies` for a nested module like `shared.privacy`** is not documented for cross-sibling references. Issue spring-modulith#524 [VERIFIED] explicitly shows that `sharedModules = {"com.app.core.exception"}` throws `IllegalArgumentException: Module com.app.core.exception does not exist!`. CONTEXT D-D4's planned reference `"shared.privacy"` from sibling-module `allowedDependencies` is **likely to fail Modulith verification** unless `shared.privacy` is itself nested under a `shared` module that is annotated separately, OR unless it is referenced as a top-level module via the local-name `"privacy"` (the simple base-package name).
2. **`logback-spring.xml` references `com.zeromail.core.privacy.SensitiveMarkerScrubFilter` as a string FQN** — this is invisible to the Java compiler and ArchUnit. Forgetting to update it during Plan 01 leaves the app running with no scrub filter and only fails when an integration test logs a `Sensitive(...)` literal.
3. **Spring Data JPA repositories MUST remain `public`** for CGLIB/JDK-proxy generation; D-D1's "package-private repos" temptation is correctly avoided in CONTEXT, but downstream agents need this stated.

**Primary recommendation:**
- Use a **single root `@EntityScan(basePackages = "com.zeromail.core")` + `@EnableJpaRepositories(basePackages = "com.zeromail.core")`** in `Application.java` — Spring's `basePackages` recursively scans sub-packages [VERIFIED], so one declaration covers all 4 future per-domain `persistence/` packages plus is forward-compatible for Phase 2A/2B/2C/3/4.
- For Modulith naming, **flatten the cross-cutting package to a top-level module `privacy`** (i.e., `com.zeromail.core.privacy`, NOT `com.zeromail.core.shared.privacy`) so the existing top-level naming convention works without bumping into nested-module fragility — but CONTEXT D-C1 locks `shared/privacy/`. The mitigating recommendation: place an `@ApplicationModule(displayName = "Shared")` on `com.zeromail.core.shared/package-info.java` AND `@ApplicationModule(displayName = "Privacy")` on `com.zeromail.core.shared.privacy/package-info.java`, then test that `allowedDependencies = {"shared.privacy"}` (or the local name `"privacy"`) works empirically against Modulith 2.0.7-SNAPSHOT during Plan 01. Have a documented fallback (use `"privacy"` only) ready.

### Pattern 1: `@ApplicationModule(allowedDependencies = {...})` per domain
**What:** Each domain's `package-info.java` declares its outgoing edges in the modulith graph. Verified at CI by `ApplicationModulesTest.verify()`.
**When to use:** Every package that constitutes a Modulith module.
**Example (verified annotation form):**
```java
// Source: https://docs.spring.io/spring-modulith/docs/current/api/org/springframework/modulith/ApplicationModule.html
@ApplicationModule(
    displayName = "Account",
    allowedDependencies = {"tenant", "onboarding", "privacy"}  // local names — see Pitfall 2
)
package com.zeromail.core.account;

import org.springframework.modulith.ApplicationModule;
```

### Pattern 2: ArchUnit cross-domain repository ban (D-D1)
**What:** New `DomainBoundaryArchTests` rule that fails if any class outside `core.X.*` imports a `*Repository` from `core.Y.*` where X ≠ Y.
**When to use:** Plan 01.2-06.
**Example sketch:**
```java
// Source: ArchUnit user guide — https://www.archunit.org/userguide/html/000_Index.html
@AnalyzeClasses(packages = "com.zeromail", importOptions = ImportOption.DoNotIncludeTests.class)
public class DomainBoundaryArchTests {
    @ArchTest
    static final ArchRule no_cross_domain_repo_imports = noClasses()
        .that().resideInAPackage("..core.(account|onboarding|gmail|tenant)..")
        .should().dependOnClassesThat()
            .haveNameMatching(".*Repository")
            .and().resideInAPackage("..core..")
            .and(not(/* same domain */));
    // Implementation note: ArchUnit's package matcher does NOT support
    // "same domain as caller" predicates directly. The pragmatic shape is FOUR
    // separate rules — one per domain — each banning imports of the other 3 domains'
    // *Repository classes. See Pitfall 4 for the recommended shape.
}
```

### Pattern 3: `@EntityScan` + `@EnableJpaRepositories` single-root recursive scan
**What:** Use `basePackages = "com.zeromail.core"` to scan all sub-packages; Spring recursively descends.
**When to use:** Plan 01.2-05 (`Application.java` line 11–12 update).
**Example (verified syntax):**
```java
// Source: Spring Data JPA EnableJpaRepositories javadoc
//   https://docs.spring.io/spring-data/jpa/docs/current/api/org/springframework/data/jpa/repository/config/EnableJpaRepositories.html
// Source: spring-boot @EntityScan javadoc — basePackages is String[]
@Modulithic(systemName = "zero-mail")
@SpringBootApplication(scanBasePackages = {"com.zeromail.api", "com.zeromail.core"})
@EntityScan(basePackages = "com.zeromail.core")
@EnableJpaRepositories(basePackages = "com.zeromail.core")
public class Application { ... }
```

Recursive descent is implicit and verified by `EnableJpaRepositories` Javadoc note: "Multiple packages or patterns may be specified… Ant-style package patterns supported, e.g. `org.example.**`." Plain `com.zeromail.core` matches all sub-packages [VERIFIED: spring-data javadoc].

**Alternative (rejected as boilerplate):** explicit list `{"com.zeromail.core.account.persistence","com.zeromail.core.onboarding.persistence","com.zeromail.core.gmail.persistence","com.zeromail.core.gmail.persistence.crypto","com.zeromail.core.tenant.persistence"}`. Brittle — every new domain in Phase 2A/2B/2C/3/4 re-edits this list.

### Anti-Patterns to Avoid

- **Package-private `JpaRepository` interfaces.** Spring Data JPA repository proxies (CGLIB or JDK proxy) require visibility for the proxy factory; package-private fails at boot in some Hibernate/Spring combos and silently degrades observability. CONTEXT D-D1 correctly keeps repos `public`. [CITED: Spring Data conventions; widely repeated across Spring docs]
- **`shared/` as a junk drawer.** D-C1 and CONTEXT explicitly forbid this. Only `shared/privacy/` exists in Phase 1.2.
- **Static factory methods on view records (`CurrentUserView.from(UserEntity)`).** Inverts model → persistence dependency. CONTEXT D-B4 + Deferred. Inline mapping in service is the only correct pattern.
- **Modulith `sharedModules = {"shared.privacy"}` with dotted nested name.** Issue spring-modulith#524 [VERIFIED] documents `IllegalArgumentException: Module com.app.core.exception does not exist!` for nested package paths. If `shared.privacy` doesn't resolve, fall back to top-level `com.zeromail.core.privacy` (drop the `shared/` parent) OR use the local name `"privacy"` only.
- **Updating `logback-spring.xml` AFTER Java code compiles.** The `<filter class="...">` string is not compile-checked. Update it inside the same plan-commit that moves `SensitiveMarkerScrubFilter`. Run `LogScrubSyntheticTrafficTest` as proof. [VERIFIED: file inspection of `backend/core/src/main/resources/logback-spring.xml` lines 14, 27]

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Cross-domain dependency enforcement | Custom `pre-commit` hooks scanning imports | Spring Modulith `@ApplicationModule(allowedDependencies)` | Modulith integrates with the JUnit graph + provides cycle detection + does internals-protection automatically. [VERIFIED: docs.spring.io/spring-modulith/reference/verification.html] |
| Package-pattern matching for ArchUnit rules | Regex helpers | ArchUnit's AspectJ-style `..pkg..` patterns | `..persistence.lowlevel..` already used; matches across all 4 domains' lowlevel sub-packages with zero changes. [VERIFIED: archunit.org user guide] |
| Multi-package entity discovery | Manual `entities = {...}` list per Persistence unit | `@EntityScan(basePackages = "com.zeromail.core")` | Single root, recursive scan. Forward-compatible for future domains. [VERIFIED: spring-boot javadoc] |
| Scoped re-binding for virtual-thread fan-out | `Thread.ofVirtual().start(...)` direct calls | Existing `TenantAwareTaskScope` in `core.tenant.concurrency` | Already enforced by ArchUnit `fanout_via_helper` rule. Path stays the same — no change. |

**Key insight:** Every problem this phase touches has an existing project tool (Modulith / ArchUnit / Liquibase / Hibernate `@TenantId` resolver). The phase is structural, not infrastructural — there is nothing to invent.

## Common Pitfalls

### Pitfall 1: `logback-spring.xml` string-FQN reference to `SensitiveMarkerScrubFilter`
**What goes wrong:** Plan 01.2-01 moves `SensitiveMarkerScrubFilter` to its new package, all Java compiles, all unit tests pass. Then a Spring Boot integration test boots the application, Logback initialization tries to instantiate `com.zeromail.core.privacy.SensitiveMarkerScrubFilter` from the XML config, fails with `ClassNotFoundException`, and the application either logs a Logback config error and runs WITH NO SCRUB FILTER, or fails to start (depending on Logback's strictness mode).
**Why it happens:** Logback XML configures appenders by class-name string at boot; the Java compiler does not validate these strings.
**How to avoid:** In Plan 01.2-01, update `logback-spring.xml` lines 14 AND 27 from `com.zeromail.core.privacy.SensitiveMarkerScrubFilter` → `com.zeromail.shared.privacy.SensitiveMarkerScrubFilter` (or whatever final FQN the planner picks per Pitfall 7) IN THE SAME COMMIT as the Java class move. Add a `LogScrubSyntheticTrafficTest` run to that plan's verification.
**Warning signs:** Boot logs contain `Logback configuration error: ClassNotFoundException`. `LogScrubSyntheticTrafficTest` fails with "expected scrub marker; got raw Sensitive(...) string."

### Pitfall 2: Spring Modulith nested-module names in `allowedDependencies` are not documented
**What goes wrong:** CONTEXT D-D4 plans `allowedDependencies = {"shared.privacy"}` (dotted, referring to the nested `com.zeromail.core.shared.privacy` package). Modulith 2.x logical names for nested modules are not formally documented for cross-sibling references; **the closest precedent is issue spring-modulith#524 which shows that `sharedModules = {"com.app.core.exception"}` (a nested package path) throws `IllegalArgumentException: Module com.app.core.exception does not exist!`**.
**Why it happens:** Modulith resolves module names from the simple base-package name by default (e.g., `com.zeromail.core.shared.privacy` → logical name `"privacy"`). Dotted forms only work when `@Modulithic(useFullyQualifiedModuleNames = true)` is set, in which case the form is the **full package** (`com.zeromail.core.shared.privacy`), not a partial dotted form. [CITED: Modulithic javadoc + spring-modulith#524]
**How to avoid:** During Plan 01.2-01 execution, **probe empirically** in this order:
  1. Try `allowedDependencies = {"privacy"}` (local simple name; this is the docs-default).
  2. If Modulith reports module-not-found, add `@ApplicationModule(displayName = "Shared")` to `com.zeromail.core.shared/package-info.java` AND `@ApplicationModule(displayName = "Privacy")` to `com.zeromail.core.shared.privacy/package-info.java` — this makes `privacy` a nested module of `shared`. Then in sibling modules try `allowedDependencies = {"shared :: *"}` (named-interface wildcard reference for nested) per the only documented dotted form.
  3. Final fallback: **drop the `shared/` parent** entirely and place the privacy module at top-level `com.zeromail.core.privacy` (i.e., do NOT move the package in Plan 01.2-01 at all — keep current location). Document the deviation. The user-visible FQN of `Sensitive` does change in this fallback (`com.zeromail.core.privacy.Sensitive`, same as today), but that satisfies CONTEXT D-C1's intent ("`shared/` is minimal — only `shared/privacy/` exists") in spirit if Modulith genuinely cannot reference dotted nested modules.
**Warning signs:** `ApplicationModulesTest.verify()` fails with `Module 'shared.privacy' referenced by 'account' could not be resolved` or similar. The error message format is not documented exactly [CITED: docs.spring.io/spring-modulith/reference/verification.html confirms the verifier exists but does not document message format].

### Pitfall 3: `AccountService` cross-domain repository injection (D-D1) leaves the service unable to perform `deleteCurrentTenantAccount`
**What goes wrong:** Current `AccountService.deleteCurrentTenantAccount(UUID)` injects 4 repos and deletes in a single `@Transactional`: onboarding rows, gmail connection, user, tenant. After D-D1, only `UserRepository` (and possibly `TenantRepository`) can be injected. Naively splitting the cascade into 4 service calls breaks `@Transactional` atomicity (each call may open its own tx).
**Why it happens:** Spring's default `@Transactional` propagation is `REQUIRED` — a new transaction is reused if the caller already has one. So `accountService.delete(tx) → onboardingService.deleteByTenant(tx) → ...` IS atomic IF `accountService.delete` declares `@Transactional`. But injection cycles (account ↔ onboarding) violate D-D4's allowed graph if `OnboardingService` cannot inject `AccountService` AND vice versa.
**How to avoid:** In Plan 01.2-03, refactor the cascade as follows:
  - `OnboardingService.deleteAllForTenant(UUID)` — onboarding owns this op, called by `AccountService`.
  - `GmailConnectionService.deleteForTenant(UUID)` — gmail owns this op.
  - `AccountService.deleteCurrentTenantAccount(UUID)` keeps the outer `@Transactional` and calls onboarding + gmail services then deletes user + tenant via its own (allowed) repos.
  - Verify dep direction: `account → {onboarding, gmail, tenant}` per D-D4. **WAIT — D-D4 lists `account → {tenant, onboarding, shared.privacy}`, NO `gmail`.** This is a real dependency-graph deviation that planner must surface and resolve. Two paths:
    1. Add `gmail` to `account.allowedDependencies` (relaxes the graph).
    2. Move the `deleteCurrentTenantAccount` orchestration to a higher-level service (e.g., a new `core.account.service.AccountDeletionService` in `account` that depends on gmail) — but this still needs `account → gmail`.
    3. Move orchestration UP into `backend/api` (a new `AccountDeletionOrchestrator` in `api/security/` or `api/controllers/`) that calls each domain service — `api` already depends on all of `core`. **This is the cleanest fix.** Today's `AccountDeletionController` already does the calling; just inject the per-domain services there.
**Warning signs:** Modulith `verify()` fails with `Module 'account' depends on 'gmail' which is not in allowedDependencies`.

### Pitfall 4: ArchUnit "same-domain" exclusion is not directly expressible
**What goes wrong:** D-D1 plans a single rule "no class in `core.<X>` imports `*Repository` from `core.<Y>` where X ≠ Y." ArchUnit's fluent DSL has no direct "same-package-as-caller" predicate.
**Why it happens:** ArchUnit's `dependOnClassesThat()` predicate operates on the dependency target, not on a comparison between source and target.
**How to avoid:** Write **four separate rules**, one per domain:
```java
@ArchTest
static final ArchRule account_does_not_import_other_repos = noClasses()
    .that().resideInAPackage("..core.account..")
    .should().dependOnClassesThat()
        .haveNameMatching(".*Repository")
        .and().resideInAnyPackage("..core.onboarding..", "..core.gmail..", "..core.tenant..");

// repeat for onboarding, gmail, tenant
```
This is verbose but explicit and matches the existing fixture style of `TenantIsolationArchTests`. Each new domain in Phase 2A/2B/etc. adds one more rule.
**Warning signs:** A planner trying a single clever rule will struggle and likely under- or over-block. The 4-rule shape is verified by inspection of `TenantIsolationArchTests` (already uses one ArchRule per concern).

### Pitfall 5: `OnboardingStep` referenced via `EnumType.STRING` in `users.onboarding_step` column
**What goes wrong:** Moving `OnboardingStep` from `core.persistence.OnboardingStep` to `core.onboarding.model.OnboardingStep` means `UserEntity` (in `core.account.persistence/`) must import `core.onboarding.model.OnboardingStep`. This requires `account → onboarding` in D-D4. **D-D4 already includes this:** `account → {tenant, onboarding, shared.privacy}`. ✓
**Why it might still go wrong:** The FQN of the class changes. Hibernate's `@Enumerated(EnumType.STRING)` persists `enum.name()`, which is package-independent — values stay `"SIGNED_IN"`, `"GMAIL_CONNECTED"`, `"TEMPLATE_SELECTED"`, `"COMPLETE"`. **No data migration needed.** [VERIFIED: code inspection of `OnboardingStep.java` confirms standard enum]
**How to avoid:** No action — the move is safe by Hibernate's enum-string contract. Add a migration test (Plan 01.2-04) that simply reads existing rows and asserts the enum values deserialize correctly post-rename. Pattern: `LiquibaseMigrationTest` already reads the schema; add a 5-line test that loads a `UserEntity` and asserts `getOnboardingStep() == OnboardingStep.SIGNED_IN`.

### Pitfall 6: `OAuthProvisioningService` self-injection lifecycle change
**What goes wrong:** `OAuthProvisioningService` injects `@Lazy OAuthProvisioningService self` (file inspected: line 42). Spring's self-proxy resolves by bean name `oAuthProvisioningService`. After the package move from `core.account/` to `core.account.service/`, the bean name is unchanged (Spring derives names from class simple-name) — but the proxy creation order may shift if Modulith bootstrap triggers eager init differently.
**How to avoid:** Plan 01.2-03's smoke test must include a successful first-login flow (or at least `AccountDeletionE2ETest` which exercises tenant + user creation). That existing test will catch a broken self-proxy because `createTenantAndUser` is called by `findOrCreateGoogleUser`.

### Pitfall 7: `shared/` subpackage choice creates two valid Java FQN candidates
**What goes wrong:** CONTEXT D-C1 says "move `core.privacy.*` → `core.shared.privacy.*`" but uses the prose-name `"shared.privacy"` for the Modulith dependency target. Two valid Java package roots could exist:
  - `com.zeromail.core.shared.privacy.Sensitive` (CONTEXT's literal direction; nested under `core.shared`)
  - `com.zeromail.shared.privacy.Sensitive` (per the ArchUnit fixture string update CONTEXT D-C1 specifies, which says `"com.zeromail.shared.privacy.Sensitive"` — note this drops the `core.` prefix!)

The CONTEXT contains both forms. The ArchUnit fixture string in D-C1 is the more authoritative because it's a code literal; the prose elsewhere uses `core.shared.privacy.*` as a path. **These are inconsistent.** Planner must pick one.
**How to avoid:** Recommend `com.zeromail.core.shared.privacy.*` (keeping the `core` parent for cohesion with the Modulith package-scan root `com.zeromail.core` and consistency with sibling domains `com.zeromail.core.account/onboarding/gmail/tenant`). This means the ArchUnit fixture literal becomes `"com.zeromail.core.shared.privacy.Sensitive"` (NOT what CONTEXT D-C1 verbatim specifies). **Surface this as a pre-Plan-01 question to the user**; the alternative (move privacy entirely OUT of `core/`) requires `Application.java`'s `scanBasePackages` to include `"com.zeromail.shared"` and creates a second top-level package tree. Recommendation: keep everything under `com.zeromail.core` and treat the CONTEXT D-C1 literal as a typo.
**Warning signs:** ArchUnit test fails with `class com.zeromail.shared.privacy.Sensitive not found`. This will appear immediately in Plan 01.2-01 if the planner copies CONTEXT's literal verbatim.

### Pitfall 8: Renaming `TenantConnectionService` → `GmailConnectionService` breaks bean autowiring by NAME
**What goes wrong:** Spring autowires by type by default, but if any test uses `@Autowired @Qualifier("tenantConnectionService")` or any code uses `applicationContext.getBean("tenantConnectionService", ...)`, the class rename breaks the lookup.
**How to avoid:** Grep for the exact bean name `"tenantConnectionService"` (lowercase first letter, Spring naming convention) before Plan 01.2-05. Verified-empty grep at research time:
```
grep -r 'tenantConnectionService' backend/  →  results expected only in TenantConnectionService.java (defining class) and TenantStatusController constructor binding
```
The current code uses constructor injection only (verified in `TenantStatusController.java`), so type-based wiring works after rename. Safe.
**Warning signs:** `NoSuchBeanDefinitionException: tenantConnectionService` at boot.
