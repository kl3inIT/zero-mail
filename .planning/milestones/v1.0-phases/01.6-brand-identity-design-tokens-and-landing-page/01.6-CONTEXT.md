## Implementation Decisions

### A. Token migration strategy

- **D-A1: Rebind shadcn token names + add reference-style supplemental tokens.** The existing shadcn token names in `apps/web/app/globals.css` (`--background`, `--foreground`, `--card`, `--card-foreground`, `--popover`, `--popover-foreground`, `--primary`, `--primary-foreground`, `--secondary`, `--secondary-foreground`, `--muted`, `--muted-foreground`, `--accent`, `--accent-foreground`, `--destructive`, `--warning`, `--warning-foreground`, `--border`, `--input`, `--ring`, plus `--sidebar*`, `--chart-1..5`) stay — only their *values* are replaced with hex equivalents from the reference design (`zeromail/src/styles.css`). The 8 already-shipped shadcn primitives (`alert.tsx`, `badge.tsx`, `button.tsx`, `card.tsx`, `dialog.tsx`, `input.tsx`, `separator.tsx`, `skeleton.tsx`) auto-inherit the brand without source edits. **NEW reference-style tokens are ADDED alongside** because they have no shadcn equivalent and are needed by the new section components: `--accent-soft`, `--ink`, `--ink-2`, `--text` (alias of `--foreground`), `--text-faint`, `--green`, `--green-soft`, `--amber`, `--amber-soft`, `--red`, `--red-soft`, `--blue`, `--blue-soft`, `--violet`, `--violet-soft`, plus chrome helpers `--grain-dot`, `--gm-chrome-grad`, `--trust-bg`, `--trust-text`, `--nav-bg`. Both light (`:root`) and dark (`.dark`) blocks define matching values per the reference. Phase 1.5's `--warning` / `--warning-foreground` retune to amber-warm hex (`#B5731F` light / `#D9A064` dark) per reference. The `--destructive` retunes to `#B0413E` light / `#DA8480` dark. Reasoning: rebind preserves shadcn's class convention (`bg-background text-foreground` everywhere) while supplemental tokens unlock the section-level "earnest paper" subtle accents that pure opacity utilities can't achieve.

- **D-A2: Hex values, not oklch conversion.** Reference colors stay as hex strings exactly as authored in `zeromail/src/styles.css`. Reasoning: (a) reference is the spec and any oklch conversion drifts perceptual lightness; (b) hex is human-debuggable in DevTools; (c) shadcn supports hex transparently — no compatibility loss. Tailwind 4 `@theme inline` block continues mapping shadcn tokens to color utilities; the new supplemental tokens are exposed via `--color-{name}: var(--{name})` entries so utilities like `bg-accent-soft` / `text-text-faint` work.

- **D-A3: 4-palette swatch picker is NOT exposed.** Reference's `app.jsx` `ACCENT_PALETTES` (Teal/Clay/Ink/Electric) and the `data-accent` attribute writer are dropped. Only the Teal palette ships. v2 multi-palette work (if ever) gets a dedicated phase. CSS variables are NOT scoped to a `[data-accent="..."]` selector — they live directly on `:root` / `.dark`.

- **D-A4: Radii and shadows per reference.** `--radius` retunes from `0.625rem` (shadcn default) to `7px` (reference `--radius`). Add `--radius-sm: 5px`, `--radius-lg: 10px` matching reference. Shadow scale `--shadow-xs` / `--shadow-sm` / `--shadow-md` / `--shadow-lg` per reference values for both light and dark.

- **D-A5: Token-aware classes mandatory (Phase 1.4 D-C2 sweep continues).** No raw color names like `text-stone-700` / `bg-amber-50` / `border-blue-300` anywhere. New section components use only `bg-background` / `text-foreground` / `border-border` / `text-muted-foreground` / `bg-accent` / `bg-accent-soft` / `text-text-faint` / etc. — every utility resolves through a token. The hard-coded `border-amber-500 bg-amber-50` killed in Phase 1.5 D-C3 stays killed.

### B. Component location convention

- **D-B1: Split landing-domain vs auth-domain components.** Landing public surface lives at `apps/web/features/landing/components/`; sign-in chrome lives at `apps/web/features/auth/components/` (extending the existing `features/auth/` from Phase 1.3). Specifically:
  - **`features/landing/components/`**: `TopBar.tsx`, `Footer.tsx`, `ZMLogoMark.tsx`, `Hero.tsx`, `HowItWorks.tsx`, `Features.tsx`, `TrustPillars.tsx`, `ThemeToggle.tsx`, `LangToggle.tsx` (or reuse Phase 1.3 `features/i18n/components/LanguageSwitcher.tsx` if compatible — planner verifies).
  - **`features/auth/components/`**: `AuthTopBar.tsx`, `TrustPanel.tsx`, `LegalFooter.tsx`, `StepIndicator.tsx`.
  - **`features/landing/lib/setTheme.ts`**: Server Action for theme cookie write (utility, NOT a typed-API endpoint — `lib/` not `api/`).
  - Reasoning: clear ownership boundary (landing = public marketing; auth = sign-in chrome); aligns with Phase 1.3 D-A1 hybrid feature decomposition; follows D-A5 deep-import / no-barrel rule.

- **D-B2: Reuse Phase 1.3 `LanguageSwitcher` if its prop API matches.** `apps/web/features/i18n/components/LanguageSwitcher.tsx` (Phase 1.3 D-A4) is the canonical lang toggle. Phase 1.6 re-renders it inside TopBar and AuthTopBar with the brand styling. If it doesn't compose cleanly into the new chrome (e.g., size mismatch), the planner can introduce a small variant prop rather than fork.

- **D-B3: ZMLogoMark is feature-local to `features/landing/`, not promoted to `apps/web/components/brand/`.** Per YAGNI / Phase 1.3 D-A5 deep-import discipline — only one consumer ships in 1.6 (TopBar/AuthTopBar both via `features/landing/`). When/if a third consumer outside landing/auth needs it (e.g., Phase 5 dashboard branded header), promote then. No premature `components/brand/` directory.

- **D-B4: `(public)/_components/` and `(auth)/_components/` route-group chrome directories are NOT introduced.** Phase 1.3 D-A3 reserves these for chrome that uniquely belongs to one route group AND has no domain owner. Landing chrome IS the domain (`features/landing/`); auth chrome IS a domain (`features/auth/`). The route-group `_components/` directory pattern is held in reserve for future shared protected-app chrome (e.g., `(protected)/_components/ProtectedHeader.tsx` per Phase 1.3 D-A3).

- **D-B5: Section components are tree-shakeable, NOT exported via barrel.** Imports from `(public)/page.tsx` use deep paths: `import { Hero } from '@/features/landing/components/Hero'`. No `features/landing/index.ts` re-export file. Aligns with Phase 1.3 D-A5 absolute rule.

### C. Theme cookie implementation

- **D-C1: Server Action + form action pattern.** A `'use server'` function lives at `apps/web/features/landing/lib/setTheme.ts`:
  ```ts
  'use server';
  import { cookies } from 'next/headers';
  export async function setTheme(formData: FormData) {
    const theme = formData.get('theme') === 'dark' ? 'dark' : 'light';
    (await cookies()).set('zm-theme', theme, {
      sameSite: 'lax',
      secure: process.env.NODE_ENV === 'production',
      httpOnly: false,  // client-side may read for instant optimistic toggle if needed
      maxAge: 60 * 60 * 24 * 365,  // 1 year
      path: '/',
    });
  }
  ```
  `ThemeToggle.tsx` (client component) wraps an HTML `<form action={setTheme}>` with a hidden input for the next theme value and uses `useTransition` for pending state.

- **D-C2: First-paint flash prevention via root layout cookie read.** `apps/web/app/layout.tsx` reads `(await cookies()).get('zm-theme')?.value` during RSC render and applies `class="dark"` (or empty) to `<html>` BEFORE first byte ships. No client-side flash. Pattern mirrors Phase 1.5 D-D2 `reassertServerLocale()` flow — read cookie server-side and project into the rendered HTML.

- **D-C3: Cookie attributes locked.** `name='zm-theme'`, `sameSite='lax'`, `secure=true` in production / `false` in dev, `httpOnly=false` (client may read to mirror state in `useState` if a future surface needs it; the cookie is non-sensitive — theme preference is not a secret), `maxAge=31_536_000s` (1 year), `path='/'`. NEVER `__Host-` prefix (path is `/`, secure varies by env, won't pass `__Host-` rules).

- **D-C4: NO localStorage anywhere.** `localStorage.setItem('zm-theme', ...)` and `localStorage.getItem('zm-theme')` are forbidden. Reference design uses localStorage; we deviate to the cookie pattern that aligns with `NEXT_LOCALE` and avoids hydration mismatch warnings.

- **D-C5: Default theme = light when cookie absent.** Aligned with reference (light is the default `:root`); no system preference detection (`prefers-color-scheme`) at v1 — keeps the cookie as the single source of truth and avoids an initial flicker between system-detected and cookie-set values. v2 may layer `prefers-color-scheme` as the cookie-absent fallback.

### D. Onboarding step indicator pattern

- **D-D1: Named-step pills with active accent.** `<StepIndicator currentStep={'GMAIL_CONNECTED' | 'TEMPLATE_SELECTED' | 'COMPLETE'} />` renders 3 inline pills with i18n labels. Visual states:
  - **Active**: `bg-accent text-accent-foreground` (Teal solid, white text)
  - **Completed**: `bg-accent-soft text-accent` with check icon prefix
  - **Future**: `border border-border text-muted-foreground` (outline, muted)
  Pills connected by `<span>→</span>` separators using `text-muted-foreground`. Aligned with reference `auth-onboarding.jsx` named-step pattern.

- **D-D2: Mobile collapse — single active pill + numeric subtitle.** Below 480px viewport, only the active pill renders, accompanied by a small subtitle `text-xs text-muted-foreground`: "Bước 2 trên 3" (vi) / "Step 2 of 3" (en). Avoids overflow / horizontal scroll. Breakpoint: `sm:` (640px) shows full 3-pill row; below `sm` collapses to compact form.

- **D-D3: i18n key namespace = `onboarding.steps.{stepKey}.shortLabel`.** Three keys per locale:
  - `onboarding.steps.gmailConnect.shortLabel` — vi: "Kết nối Gmail" / en: "Connect Gmail"
  - `onboarding.steps.templateSelect.shortLabel` — vi: "Chọn template" / en: "Pick template"
  - `onboarding.steps.complete.shortLabel` — vi: "Hoàn tất" / en: "Done"
  Plus `onboarding.steps.progressLabel` — vi: "Bước {current} trên {total}" / en: "Step {current} of {total}" (for mobile collapse).

- **D-D4: StepIndicator is OWN-state-driven, not URL-driven.** The component takes `currentStep` as a prop derived from `users.onboarding_step` (server-side from `getCurrentUser()`). No URL `?step=` param parsing; no `useSearchParams` read. Reasoning: state machine is the source of truth (Phase 1.5 D-B1 monotonic-forward invariant); URL params would let the UI lie about state.

- **D-D5: Hover/focus on completed pills allows backward navigation.** Completed pills are `<Link>` elements pointing back to their respective onboarding URL (e.g., `/onboarding/gmail-connect` from `template-select`). Active pill is a `<span>` (no link). Future pills are `<span>` muted (no link). Reasoning: matches the monotonic-forward enum (user can revisit completed step UI without enum regression).

- **`--grain-dot` background usage scope** — reference applies a subtle grain dot pattern to body/cards. v1 may opt to apply only to landing hero, or wide-cast everywhere. Planner picks based on visual sweep result.
- **TopBar Sign-in CTA visibility on mobile** — single primary CTA always visible, OR collapse to icon-only with `aria-label`? Recommend always visible (it's the only CTA).
- **Whether `LangToggle` and `ThemeToggle` are 2 separate components or one combined `<HeaderControls>`** — recommend 2 separate components for testability and reuse; combined wrapper is over-abstraction at 2 children.
- **Landing CTA copy when authenticated** — Phase 1.3 D-D4 introduced auth-aware CTA `landing.continueSetupCta`. Phase 1.6 preserves auth-aware behavior; copy refresh in `frontend-design` skill polish.
- **Where to source the Be Vietnam Pro `vietnamese` subset value** — verify via Context7 / Google Fonts API at implementation time; if subset name has changed in 2026 ship cycle, fall back to `latin-ext` which covers Vietnamese diacritics.
- **Placement of theme toggle keyboard shortcut** — none required (per scope). Defer to a future a11y phase.
- **Whether the cookie-read in `app/layout.tsx` is debounced/cached** — single read per RSC render is fine (cookie is request-scoped). No caching needed.
