# Phase 1.6: Brand Identity, Design Tokens, and Landing Page — Specification

**Created:** 2026-04-28
**Ambiguity score:** 0.105 (gate: ≤ 0.20)
**Requirements:** 9 locked

## Goal

`apps/web` adopts the Zero Mail brand identity (Teal accent + Paper-warm neutrals + Earnest trust copy), exposes a demo-ready landing page at `/` with hero + how-it-works + features + trust-pillars sections, and reskins Phase 1.5 sign-in + onboarding surfaces to match the reference visual tone — without changing any backend integration, OAuth flow, or route contract.

## Background

`apps/web` is a Next.js 16 + React 19 + Tailwind 4 + shadcn application that today uses shadcn's stock oklch grayscale token palette (`apps/web/app/globals.css`) and a single Geist Sans + Geist Mono font pairing (`apps/web/app/layout.tsx`). The current public landing (`apps/web/app/(public)/page.tsx`) is a single-column "Plan 04 light skeleton" with one heading, one tagline, and one CTA — explicitly non-marketing, no hero, no how-it-works, no trust pillars. The `(auth)/login` and `(protected)/onboarding/*` surfaces shipped in Phase 1.5 with utilitarian layouts, no brand chrome, no TrustPanel, and no legal footer (Terms / Privacy / Google API Limited Use links).

A reference design lives at `D:/study-materials-summer-2026/EXE202/zeromail/src/` — vanilla React + global CSS, 5,575 lines total. It defines a complete design system (4 accent palettes Teal/Clay/Ink/Electric, warm paper neutrals, semantic colors, 3-font stack with Geist + Be Vietnam Pro + Instrument Serif, shadows, radii) plus landing sections (`sections.jsx` 647 lines), an auth shell (`auth-shell.jsx` 170 lines with TopBar + 2-column TrustPanel), a sign-in screen (`auth-signin.jsx`), a 3-step onboarding flow (`auth-onboarding.jsx` 278 lines), and an i18n VI/EN bundle (`i18n.jsx` 534 lines). The reference is treated as **inspirational-canonical**: palette, typography, layout rhythm, landing section structure, and trust tone are the spec; Next.js/Tailwind 4/shadcn translation is mandatory (no copy-paste of CSS or JSX).

Inbox Zero's production login (`D:/study-materials-summer-2026/EXE202/inbox-zero/apps/web/app/(landing)/login/page.tsx`) shows the CASA / Google OAuth verification compliance baseline: visible Terms of Service link, Privacy Policy link, and Google API Limited Use disclosure beneath the sign-in CTA. Missing these is a launch blocker for Google verification (Phase 6).

This phase exists because Phase 2A's UI gate (PauseBanner, Settings toggle, ReconnectPrompt extension) cannot pass without an established design contract, and because deferring the brand identity decision causes compounding rework on every subsequent frontend phase.

## Boundaries

**In scope:**
- Design tokens (warm-paper neutrals + Teal accent + semantic colors + radii + shadows + chrome helpers) in `apps/web/app/globals.css` for both light and dark modes.
- Typography: Geist Sans + Geist Mono + Be Vietnam Pro (Vietnamese subset) + Instrument Serif via `next/font`, exposed as `--font-sans` / `--font-mono` / `--font-serif`.
- Landing page (`apps/web/app/(public)/page.tsx`) with four sections: Hero, HowItWorks (3 steps), Features, TrustPillars.
- Public layout shell (`apps/web/app/(public)/layout.tsx`) with TopBar (logo + theme + lang + Sign-in CTA) and minimal Footer (copyright + Privacy + Terms).
- `ZMLogoMark` SVG component in `apps/web/features/landing/components/`.
- Sign-in (`(auth)/login`) reskin: 2-column desktop with TrustPanel, single-column mobile, legal footer always visible (Terms / Privacy / Google API Limited Use).
- Onboarding (`(protected)/onboarding/gmail-connect|template-select|complete`) reskin: AuthTopBar with step indicator, single-column cards, no TrustPanel.
- Theme persistence via `zm-theme` cookie (server-readable, no first-paint flash).
- Stub `/terms` and `/privacy` routes with placeholder content (real content deferred to Phase 6).
- i18n VI/EN keys for all new visible strings (`nav.*`, `trust.*`, `how.*`, `feat.*`, `legal.*`, `footer.*`).
- `01.6-VISUAL-SWEEP.md` manual regression checklist proving Phase 1.5 components survive token swap.

**Out of scope:**
- **Auth shell reskin beyond Login + 3 Onboarding steps** — Settings page chrome and any other protected-app surface stay as Phase 1.5 visuals. Reason: scope containment; Settings reskin can ride a future polish phase without blocking landing.
- **Marketing pages (Pricing, FAQ, Blog, full Legal)** — `/terms` and `/privacy` are STUB routes only with placeholder copy. Reason: real legal copy needs counsel review; demo-ready audience does not need pricing.
- **Multi-palette switcher (Clay / Ink / Electric)** — Teal is the only palette in v1; the four-palette swatch picker from `zeromail/src/app.jsx` is dropped. Reason: brand consolidation and reduced surface area.
- **Tweaks panel** (the dev-mode color/density picker from `zeromail/src/tweaks-panel.jsx`) — not ported. Reason: internal tool, not a user-facing feature.
- **Mobile hamburger menu** — TopBar on mobile collapses to logo + Sign-in CTA + compact icon-only theme/lang toggles; no expandable hamburger drawer. Reason: v1 nav has only one CTA; menu is unnecessary.
- **Form-based local-auth login** (the email/password form in `zeromail/src/auth-signin.jsx`) — rejected; Phase 1.5 bundled Google OAuth one-click is preserved. Reason: locked auth model.
- **Animations beyond CSS hover/focus transitions** — no scroll-triggered animations, no Framer Motion entrances, no parallax. Reason: keep landing fast and simple for early testers.
- **Backend changes of any kind** — no Spring controller changes, no DTO renames, no OAuth handler edits, no new endpoints. Reason: phase boundary discipline; design layer only.
- **Visual regression test infrastructure** — no Storybook, no Chromatic, no Percy, no Playwright screenshot snapshots. Reason: manual sweep checklist (`01.6-VISUAL-SWEEP.md`) is the v1 verification mechanism; tooling investment defers to a later observability/quality phase.
- **`localStorage` for theme** — rejected in favor of cookie-based persistence. Reason: server-readable, no first-paint flash, aligns with existing `NEXT_LOCALE` cookie pattern.
- **TrustPanel on Onboarding screens** — onboarding gets step indicator + cards only. Reason: user already granted scope; trust signal redundant at task-completion stage.
- **TrustPanel on mobile sign-in** — mobile Sign-in is single-column form + legal footer only. Reason: viewport too narrow for 2-column without compromising form readability.

## Constraints

- **Performance**: Lighthouse mobile + desktop scores ≥ 90 for Performance, Accessibility, and Best Practices on the landing page (`/`). Verifiable via `pnpm lighthouse:landing` (or equivalent) — actual command name to be confirmed during planning.
- **Accessibility**: All visible text on landing, public layout, sign-in, and onboarding meets WCAG 2.1 AA color contrast (4.5:1 normal text / 3:1 large text) in both light and dark modes. Keyboard navigation reaches every interactive element on TopBar, Hero CTA, and sign-in form.
- **Responsive breakpoints**: Mobile-first design starting at 320px viewport width. Required breakpoints: 320, 480, 768, 1024, 1280. No horizontal scroll at any breakpoint on landing, sign-in, or onboarding.
- **CASA / Google OAuth verification compliance**: Sign-in legal footer always renders Terms link + Privacy link + Google API User Data Policy / Limited Use disclosure paragraph at every viewport (matching Inbox Zero's production pattern). Required for Phase 6 launch verification.
- **Typography subsets**: Be Vietnam Pro must include the `vietnamese` subset for diacritic coverage. Geist Sans `latin-ext` covers Vietnamese diacritics indirectly per Phase 1 layout.tsx; verify before relying on it for body text.
- **No backend coupling**: zero edits to `backend/api`, `backend/core`, `backend/worker`, or any Spring source. Phase 1.6 is pure `apps/web/` changes.
- **Project conventions** (CLAUDE.md): no Lombok (Java side, not relevant here); raw shadcn primitives first (no new wrapper components like `<StatusAlert>` over `<Alert>`); flat folder structure (avoid single-purpose nested parents); deep imports from feature folders (no barrel `index.ts` re-exports).
- **`frontend-design` skill mandatory**: planning and execution agents touching JSX must invoke the Anthropic `frontend-design` skill (per persistent feedback memory) — passed into executor subagent prompts at plan-phase.
