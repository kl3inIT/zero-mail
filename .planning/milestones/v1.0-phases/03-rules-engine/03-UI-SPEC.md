## Product Posture

The Rules page is an authenticated operational tool, not a marketing surface. The UI must feel quiet, dense, inspectable, and safety-forward. Users are trusting the app with a real Gmail inbox, so the interface must make three things visible before enablement:

1. What Zero Mail understood from the natural-language rule.
2. Which recent messages would match and why.
3. That preview made no Gmail changes.

Phase 03 creates, previews, manages, and enables rule definitions only. Do not imply live triage execution, undo, audit history, auto-send, runtime semantic LLM evaluation, or Gmail write execution in this UI.

## Screen Contract

| Surface | Contract |
|---------|----------|
| Route | Protected Rules page under `apps/web/app/(protected)/rules`. |
| Page shell | `main` with `mx-auto w-full max-w-6xl p-6`; mobile uses `px-4 py-4`. Keep it compatible with protected layout `PauseBanner`. |
| Primary layout | Desktop: two-column workspace, left column rule list/template gallery, right column composer and preview. Mobile: single-column order of rule list, composer, preview. |
| Focal point | The rule composer plus preview readiness state is the primary visual anchor. The page should draw the eye first to the natural-language rule input and its current compile/preview state. |
| Rule list | Dense ordered list with enabled state, template/custom badge, last preview state, and reorder controls. No card-inside-card layouts. |
| Composer | Natural-language-first text area, compile status, one inline clarification prompt when needed, compiled matcher/action review, and save state. Users edit source text, not AST JSON. |
| Preview | Impact summary first, then rows of safe message summaries with evidence chips. No full email body, no raw HTML, no raw headers. |
| Template gallery | Starter templates are presented as compact selectable rows/cards with provenance and disabled-by-default status after materialization. |

Visual hierarchy:

1. Page title and Gmail safety note.
2. Composer input and primary CTA.
3. Preview impact summary.
4. Rule list and template gallery.
5. Secondary metadata and provenance.

- Icon-only controls and reorder handles must have at least a 44px touch target on mobile. Treat this as a hit-area size constraint, not a spacing token.

- Preview rows must use fixed grid tracks for sender/domain, subject excerpt, evidence chips, and date on desktop; collapse to stacked metadata on mobile.

## Interaction Contract

### Rule authoring

1. User writes a rule in English or Vietnamese.
2. Primary CTA is `Compile rule` until compile succeeds.
3. If compiler returns ambiguity, show one inline clarification question and block save.
4. Clarification CTA is `Answer clarification`; after answer, recompile.
5. Successful compile shows review-only matcher/action groups and a `Save disabled rule` CTA.
6. Saved rules remain disabled until preview succeeds.

### Preview before enablement

1. Saved disabled rules show `Preview rule` as the primary CTA.
2. Sample size defaults to 25 and offers only 10, 25, 50.
3. Preview summary appears before rows and must include sample size, matched count, proposed action counts, deferred count, and "No Gmail changes were made."
4. Rows show sanitized sender/domain, subject excerpt, date, existing Gmail labels, proposed action chips, and matched matcher-clause chips.
5. `SEMANTIC_INTENT` nodes show deferred semantic-check chips and never count as true/false matches in Phase 03.
6. Enablement CTA `Enable rule` appears only after a successful preview of that rule version.

### Rule management

- Enable/disable is immediate but visually shows pending state.
- Reorder changes use optimistic UI only if the API can rollback on failure; otherwise show pending row locks.
- Edit creates a new rule version and requires preview again before enablement.
- Delete uses a dialog and removes the rule only after explicit confirmation.
- Template-derived rules show `Template` badge and template key/version provenance. Once edited, show `Customized` badge and never imply future template overwrite.

### Privacy and safety states

- Preview never renders raw HTML, full body, raw headers, prompts, completions, or snippets beyond the sanitized subject excerpt returned by the API.
- Body-derived evidence, when required, is represented as sanitized evidence chips such as "body evidence used" without exposing body text.
- Insufficient credits or BYOK/provider errors must explain the next step: top up credits, save a valid BYOK key, or retry after provider recovery.

## Copywriting Contract

Primary user-facing copy must be specific, actionable, and safety-forward. Use i18n keys with English and Vietnamese parity.

| Element | Copy |
|---------|------|
| Page heading | `Rules` |
| Page intro | `Write rules in plain language, preview what would match, then enable only the rules you trust.` |
| Primary CTA before compile | `Compile rule` |
| Primary CTA after compile | `Save disabled rule` |
| Primary CTA before enablement | `Preview rule` |
| Primary CTA after successful preview | `Enable rule` |
| Clarification CTA | `Answer clarification` |
| Template CTA | `Use starter rule` |
| Empty state heading | `No rules yet` |
| Empty state body | `Write your first rule or start from a Gmail template. New rules stay disabled until you preview them.` |
| Preview empty heading | `No preview run yet` |
| Preview empty body | `Run a preview against recent Gmail messages before enabling this rule.` |
| Safe preview notice | `No Gmail changes were made.` |
| Compile error | `Zero Mail could not compile this rule. Edit the wording or answer the clarification, then compile again.` |
| Preview error | `Preview could not finish. Check Gmail connection and credits, then preview the rule again.` |
| Insufficient credits | `Platform credits are depleted. Top up credits or save a valid BYOK key before compiling or previewing rules.` |
| Deferred semantic label | `Deferred semantic check` |
| Conflict warning | `This preview found action conflicts. Review the matched rules before enabling.` |
| Delete dialog title | `Delete this rule?` |
| Delete dialog body | `This removes the rule definition. Gmail will not be changed, but this rule will no longer appear in previews.` |
| Delete confirm CTA | `Delete rule` |
| Delete dismiss CTA | `Keep rule` |

Destructive confirmation:

- `Delete rule`: use a dialog with `Delete rule` as the destructive action and `Keep rule` as the neutral dismiss action.
- Do not use generic primary labels such as `Submit`, `OK`, `Cancel`, or bare `Save`.

Vietnamese copy must preserve the same safety claims:

- `Compile rule`: `Biên dịch quy tắc`
- `Preview rule`: `Chạy thử quy tắc`
- `Enable rule`: `Bật quy tắc`
- `No Gmail changes were made.`: `Không có thay đổi nào được áp dụng lên Gmail.`
- `Delete rule`: `Xóa quy tắc`
- `Keep rule`: `Giữ quy tắc`

## Preview Evidence Contract

| Evidence type | Visual treatment |
|---------------|------------------|
| Sender/domain match | Neutral badge with sender/domain text sanitized by API |
| Subject match | Neutral badge with matcher label; subject excerpt remains in row text |
| Existing Gmail label | Outline badge |
| Proposed label action | Accent badge only when it is the main proposed action; otherwise neutral |
| Archive action | Neutral badge with archive icon |
| Save draft action | Blue/info badge |
| Deferred semantic node | Violet badge plus tooltip: `Phase 03 stores this check, but evaluation is deferred.` |
| Conflict | Warning alert above rows and warning badge on affected row |

Rows must show enough evidence for trust without turning into an in-app mail client. Do not add expandable full-message views in Phase 03.

## Responsive Contract

| Breakpoint | Contract |
|------------|----------|
| Desktop >= 1024px | Two-column workspace; rule list/template gallery left, composer/preview right. Preview table/grid uses stable columns. |
| Tablet 768-1023px | Same page order but single-column composer followed by preview and rule list. Keep sample-size controls inline if they fit. |
| Mobile < 768px | Single-column. Primary CTAs full width only when inside composer/footer areas. Preview rows stack metadata, actions, and evidence chips. |

All buttons and chips must wrap without overlapping. Long rule names, domains, labels, and subjects use `min-w-0`, truncation, or line wrapping according to the component area.

## Accessibility Contract

- Every icon-only command requires an accessible name and tooltip.
- Rule list reordering must have keyboard-accessible up/down alternatives; drag handles alone are not sufficient.
- Clarification, compile, preview, and save results must be announced through an `aria-live="polite"` region.
- Destructive dialogs must trap focus and return focus to the triggering rule row after close.
- Toggle state must use `aria-pressed` or an equivalent accessible switch pattern.
- Color-coded evidence chips must also include text labels; color alone cannot communicate matcher/action state.
