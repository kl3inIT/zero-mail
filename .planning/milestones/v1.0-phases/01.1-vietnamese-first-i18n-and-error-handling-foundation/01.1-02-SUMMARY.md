### Auto-fixed Issues

**1. [Rule 3 — Blocking] Test relocation: AllowedParamScalarsTest module placement**
- **Found during:** Task 1 setup
- **Issue:** Plan 01 placed the Wave 0 stub at `backend/core/src/test/java/com/zeromail/core/i18n/AllowedParamScalarsTest.java`. Plan 02's plan body and PATTERNS.md both place the unit under test (`AllowedParamScalars.java`) under `com.zeromail.api.error`. `backend/core` does not depend on `backend/api` (only the reverse), so a test in `core` cannot import an `api` class.
- **Fix:** Deleted the `core` stub; created the test at `backend/api/src/test/java/com/zeromail/api/error/AllowedParamScalarsTest.java` with all original Wave 0 assertions plus the `filter_preservesIndexCounterEvenForRejected` test the plan body explicitly required and a `filter_handlesNullArray` edge case.
- **Files modified:** deleted `backend/core/src/test/java/com/zeromail/core/i18n/AllowedParamScalarsTest.java`; created `backend/api/src/test/java/com/zeromail/api/error/AllowedParamScalarsTest.java`.
- **Commit:** `b8c95d0`
- **Note:** Plan 02's verify command `./gradlew :backend:core:test --tests "*AllowedParamScalarsTest*"` is now stale — the runnable form is `./gradlew :backend:api:test --tests "*AllowedParamScalarsTest*"`. Updating downstream plans' verify references is left to the orchestrator if needed; the test itself runs under the right module.

**2. [Rule 2 — Auto-add missing critical functionality] OptimisticLockingFailureException handler**
- **Found during:** Task 2 implementation
- **Issue:** Plan 02 `<interfaces>` table maps `OptimisticLockingFailureException` to `CONFLICT` / status 409, but the existing GlobalExceptionHandler only had a generic `IllegalStateException` -> `error.conflict` handler. `OptimisticLockingFailureException` is a `DataAccessException`, not an `IllegalStateException`, so without an explicit handler it would have fallen through to the framework default and lost the dotted-code contract.
- **Fix:** Added `@ExceptionHandler(OptimisticLockingFailureException.class)` emitting `ErrorCodes.CONFLICT`, status 409.
- **Files modified:** `backend/api/src/main/java/com/zeromail/api/config/GlobalExceptionHandler.java`
- **Commit:** `1630ca8`

**3. [Rule 4 — Documented choice, not a question — kept narrow] ConstraintViolationException params is empty Map**
- **Found during:** Task 2 implementation
- **Issue:** `jakarta.validation.ConstraintViolation` does not expose Bean Validation arguments through a public API analogous to `FieldError.getArguments()` (which `MethodArgumentNotValidException` uses). The `MessageInterpolator.Context` carries arguments but is not part of the public `ConstraintViolation` surface.
- **Choice:** Set `params = AllowedParamScalars.filter(new Object[0])` (always empty) for `ConstraintViolation` field errors. The constraint annotation's simple name (e.g., `Pattern`, `NotBlank`, `Size`) is already encoded in the dotted code path; the frontend's ICU MessageFormat lookups for these keys in the `errors.field.*` namespace generally don't depend on additional params anyway. If a future plan needs param-driven validation messages on `@Validated` method parameters, it should switch the binding to `@Valid @RequestBody` (which produces `MethodArgumentNotValidException` and full `getArguments()` semantics).
- **Files modified:** `backend/api/src/main/java/com/zeromail/api/config/GlobalExceptionHandler.java`
- **Commit:** `1630ca8`
