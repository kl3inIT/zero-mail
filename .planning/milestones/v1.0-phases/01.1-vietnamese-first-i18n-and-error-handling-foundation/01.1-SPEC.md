## Goal

Zero Mail defaults every Phase 1 user-facing surface to Vietnamese, lets users switch to English persistently, and exposes API failures as stable machine-readable codes and safe parameters that the frontend localizes.

## Background

Phase 1 has already produced the Spring Boot API surface, typed OpenAPI generation, and the first Next.js screens for login, onboarding, and settings. The current frontend hard-codes English copy in `apps/web/app/login/page.tsx`, `apps/web/app/onboarding/page.tsx`, `apps/web/app/settings/page.tsx`, and related components, while `apps/web/app/layout.tsx` fixes `<html lang="en">`. There is no translation provider, no Vietnamese or English dictionary, no language switcher, and no persisted language preference on `users`.

The backend already has a centralized `GlobalExceptionHandler` that returns RFC 7807 `ProblemDetail` responses with a stable `message` key, but it still sets hard-coded English titles, does not expose a formal `code` + `params` error contract, and the generated OpenAPI schema does not document error responses. The frontend API client currently returns raw `error` values from `openapi-fetch`; route components do not localize API failures.

The local JHipster reference at `D:\study-materials-summer-2026\jhipster` demonstrates useful patterns: separate `en`/`vi` JSON dictionaries, a language menu, Problem Details with message keys and parameters, and field-error localization. This phase keeps the key-based localization and dual-language coverage ideas, adapts them to Next.js 16 / openapi-fetch / shadcn, and rejects `react-jhipster`, Redux locale reducers, Bootstrap menus, and server-rendered localized user-facing errors.

## Requirements

1. **Vietnamese-default frontend strings**: Every Phase 1 user-facing string in `apps/web` is rendered from locale dictionaries, with Vietnamese as the default and English as the secondary locale.
   - Current: Login, onboarding, settings, reconnect, delete-account, template-card, loading, and privacy/safety text are hard-coded in English; `<html lang="en">` is fixed.
   - Target: The Phase 1 UI renders Vietnamese by default, can render equivalent English copy from the same key set, and sets the document language to the active locale.
   - Acceptance: A frontend test or build-time check proves all in-scope UI keys exist in both `vi` and `en`; rendering the app with no saved preference produces `lang="vi"` and Vietnamese copy, while rendering with English selected produces `lang="en"` and English copy.

2. **Persistent language switcher**: A user-facing language switcher lets users choose Vietnamese or English, and the selected language survives reloads and new sessions.
   - Current: No language switcher exists; `UserEntity`, the `users` table, and `/me` response do not carry a language preference.
   - Target: Users can choose exactly `vi` or `en`; unauthenticated screens default to Vietnamese and may remember a browser-local selection, while authenticated sessions persist the selected language per user.
   - Acceptance: In an authenticated flow, switching from Vietnamese to English, refreshing, and signing in again returns the UI in English; switching back to Vietnamese persists the reverse. Unsupported locale values are rejected and do not alter the stored preference.

3. **Stable API error contract**: Every client-visible backend error in the Phase 1 API surface uses a documented machine-readable contract with status, code, safe parameters, and optional field errors.
   - Current: `GlobalExceptionHandler` returns `ProblemDetail` with `message` keys such as `error.badRequest`, but error schemas are not documented in OpenAPI and parameters / field errors are not formalized.
   - Target: Error payloads expose a stable `code` and optional `params` / `fieldErrors` values that the frontend can localize; server-side `title` or `detail` values, if present for RFC 7807 compatibility, are generic diagnostics and are not the user-facing message source.
   - Acceptance: Integration tests trigger authentication, access-denied, validation, bad-request, conflict, and data-integrity failures and assert the response status, `code`, and safe parameter shape; generated OpenAPI includes the reusable error schema for Phase 1 endpoints.

4. **Frontend-localized API failures**: The web client maps API error codes and parameters to active-locale user messages instead of displaying raw server text.
   - Current: `apps/web/lib/api/client.ts` exposes raw `error` values and route components have no common localization path for API failures.
   - Target: API failures shown on login, onboarding, settings, reconnect, disconnect, and delete-account flows are localized in Vietnamese or English based on the active locale.
   - Acceptance: Frontend tests with mocked API failures verify that known error codes display Vietnamese by default, English after switching locale, and a localized generic fallback for unknown codes; tests also prove raw `title`, `detail`, exception names, SQL constraint names, and stack traces are not displayed.

5. **Translation coverage gate**: CI fails when Vietnamese and English dictionaries are missing or drifting for in-scope user-facing keys.
   - Current: No `apps/web` dictionaries or key parity checks exist.
   - Target: Both locales contain the same key set for Phase 1 UI and API error messages, with an automated verification command wired into the existing project scripts or test suite.
   - Acceptance: The verification command passes with complete dictionaries and fails when one locale key is removed or renamed; the command is included in the documented verification path for this phase.

6. **Privacy and safety invariants preserved**: i18n and error handling do not weaken Phase 1 tenant isolation, log scrubbing, or sensitive-data guarantees.
   - Current: Phase 1 has `TenantContext`, ArchUnit safety rules, `Sensitive<T>`, `SensitiveMarkerScrubFilter`, and synthetic traffic tests that prevent body, prompt, completion, refresh-token, and similar sensitive values from leaking to logs.
   - Target: Localized strings, error codes, error parameters, and language-preference flows never contain raw email bodies, prompts, completions, refresh tokens, SQL internals, stack traces, or tenant/user PII beyond already-authorized profile display.
   - Acceptance: Existing Phase 1 ArchUnit and log-scrub tests still pass; a new or extended error-contract test seeds sentinel sensitive values and verifies they do not appear in API error payloads or captured logs.

7. **JHipster pattern decision record**: The implementation context records which local JHipster i18n/error patterns were kept, adapted, and rejected.
   - Current: The roadmap references local JHipster patterns, but no Phase 1.1 context file documents a selection decision.
   - Target: Phase 1.1 `CONTEXT.md` includes a concise "JHipster reference patterns" section with three explicit lists: kept, adapted, rejected.
   - Acceptance: A reviewer can open Phase 1.1 `CONTEXT.md` and see references to the local JHipster files inspected, plus clear rationale for using key-based dictionaries and Problem Detail codes while rejecting JHipster-specific frontend/runtime dependencies.

## Boundaries

**In scope:**
- Locale dictionaries for all Phase 1 web UI strings: login, onboarding, settings, reconnect prompt, connection health, template cards, delete-account confirmation, loading states, and Phase 1 error messages.
- Vietnamese default locale and English secondary locale across `apps/web`.
- A visible language switcher and persisted user language preference for authenticated users.
- Backend data/API support needed to read and update the user's language preference.
- Stable API error code / params / field-error contract for the existing Phase 1 endpoints.
- OpenAPI schema updates so the generated frontend client can type the error contract.
- Frontend error localization for existing Phase 1 API flows.
- Automated checks for translation key parity and safe error payloads.
- Documentation in Phase 1.1 `CONTEXT.md` of JHipster patterns kept, adapted, and rejected.

**Out of scope:**
- Translating future Phase 2+ screens and features - those strings do not exist yet and should be covered when their phases create them.
- Adding languages beyond Vietnamese and English - Phase 1.1 locks only the v1 bilingual baseline.
- Browser-language auto-detection or Accept-Language negotiation - the product default is Vietnamese, with explicit user selection.
- Replacing the frontend stack with `react-jhipster`, Redux locale reducers, Bootstrap menus, or JHipster runtime dependencies - the app is Next.js 16 / TanStack Query / shadcn.
- Server-side construction of localized user-facing error prose - the frontend owns user-visible localization from stable codes.
- Redesigning auth, onboarding, Gmail connection, account deletion, or tenant-isolation business flows - this phase localizes and stabilizes their messaging only.
- Sending localized emails, notifications, or digests - those user surfaces belong to later product phases.
- Storing or exposing raw Gmail content, LLM prompts, LLM completions, embeddings, refresh tokens, SQL internals, stack traces, or unrelated PII - permanently excluded by the project safety posture.

## Constraints

- Supported locales are exactly `vi` and `en`; default locale is `vi`.
- User-facing error text is localized on the frontend from machine-readable codes and safe parameters.
- Error parameters must be allow-listed scalar values such as enum values, translation keys, or resource identifiers that are not raw user content.
- Existing OpenAPI generation via `openapi-typescript` and `openapi-fetch` must continue to work.
- Existing Phase 1 privacy/safety tests remain part of the verification baseline.
- The local JHipster project is a reference only; no direct JHipster frontend/runtime dependency is introduced.

## Acceptance Criteria

- [ ] With no stored preference, the Phase 1 web UI renders Vietnamese copy and document language `vi`.
- [ ] Users can switch between Vietnamese and English from a visible language switcher.
- [ ] Authenticated language preference survives refresh and sign-in across sessions.
- [ ] Unsupported locale values are rejected without changing the stored preference.
- [ ] Every in-scope frontend translation key exists in both Vietnamese and English.
- [ ] The translation coverage check fails when a locale key is missing.
- [ ] Existing Phase 1 API errors return stable `code` values and safe parameter shapes.
- [ ] Generated OpenAPI includes the reusable error schema used by Phase 1 endpoints.
- [ ] Frontend API error displays are localized by active locale and do not show raw server diagnostics.
- [ ] Existing Phase 1 ArchUnit and log-scrub tests still pass after i18n/error changes.
- [ ] Sentinel sensitive values do not appear in localized error payloads or captured logs.
- [ ] Phase 1.1 `CONTEXT.md` documents JHipster patterns kept, adapted, and rejected.
