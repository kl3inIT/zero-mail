### WR-03: tautological me-cache-dedupe regression test
- **Verdict:** `applied`
- **Commit:** `f1f0f57` `fix(01.5): WR-03 add real source-shape regression guard for cache() primitive key`
- **Files modified:** `apps/web/__tests__/features/account/me-cache-dedupe.test.ts`
- **What changed:** Added a new describe block (`WR-03 — getCurrentUserCached primitive-string contract`) that reads `me.ts` source via `node:fs.readFileSync` and asserts the shape:
  - Positive guard: regex `cache\(\s*async\s*\(\s*cookieHeader:\s*string\s*\|\s*undefined\s*\)` MUST match.
  - Negative guards: regex `cache\(\s*async\s*\(\s*opts` and `cache\(\s*async\s*\(\s*\{` MUST NOT match.
- **Why source-shape, not arity:** initial attempt asserted `getCurrentUserCached.length === 1` but React `cache()` normalizes the wrapped function so length is 0 — that assertion failed in vitest. Source-shape regex is the next-best contract guard given that React `cache()` is RSC-context-only and behavioral dedupe cannot be verified outside an RSC render.
- **What stays manual:** Full RSC dedupe (one /me fetch per render despite multiple consumers) is still the deferred manual gate documented in `01.5-03-SUMMARY.md` — no change to that gate.
- **Verification:** `pnpm exec vitest run __tests__/features/account/me-cache-dedupe.test.ts` — 7 tests passed.

## Skipped / Deferred

### WR-06: SecurityConfig @Profile("!test") prevents bundled OAuth filter chain from being exercised in integration tests
- **Verdict:** `skipped` (deferred to a dedicated follow-up plan)
- **File:** `backend/api/src/main/java/com/zeromail/api/security/SecurityConfig.java:13`
- **Reason:** The recommended fix paths (a separate `@Profile("test-security")` SecurityConfig that wires only what tests need, OR removing `@Profile("!test")` and using `@MockBean ClientRegistrationRepository` in the existing tests) require a non-trivial test-infrastructure refactor:
  - Designing a stubbed Google authorization server (or `ClientRegistrationRepository` mock) that the filter chain can resolve at startup.
  - Verifying the existing `BundledGoogleOAuthIntegrationTest` and other test-profile-active integration tests don't regress.
  - Possibly introducing a new `application-test-security.yml` fragment.

  This work exceeds a single-fixer-pass scope per the fix-strategy guidance ("If a fix introduces new compile/lint errors, ROLL BACK that commit and mark the finding `failed`"). Attempting the refactor blindly would risk breaking the `test`-profile integration suite and cascading further fixes.

- **Original issue:** Without the `!test` profile guard removed (or a sibling test-security config), the integration test invokes `handler.onAuthenticationSuccess(...)` directly and never exercises the wired filter chain. End-to-end verification of `OAuth2LoginAuthenticationFilter` → `successHandler` → `failureHandler` (and the `/login?error=...` redirect path) is therefore not covered by automated tests.
- **Recommended next step:** Open a dedicated `01.5-09` (or Phase 02) plan to:
  1. Add a `test-security` profile with a SecurityFilterChain that uses a stubbed `ClientRegistrationRepository` plus the real `successHandler` / `failureHandler` chain.
  2. Add a `MockMvc`-based test that drives `/oauth2/authorization/google` → callback → success-handler-throws → failure-handler-redirect.
  3. Verify the redirect URL matches `/login?error=gmail_scope_required` end-to-end (currently asserted only at the unit-test level for `LoginRedirectAuthenticationFailureHandler`).
