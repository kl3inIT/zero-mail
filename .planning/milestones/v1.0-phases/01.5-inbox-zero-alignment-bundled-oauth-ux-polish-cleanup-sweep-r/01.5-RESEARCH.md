## Executive Summary

1. **Spring Security 7 dynamic `prompt=consent` is solved by a per-request `OAuth2AuthorizationRequest.Builder` customizer that reads a query parameter from the inbound `HttpServletRequest`.** The idiomatic pattern is `DefaultOAuth2AuthorizationRequestResolver.setAuthorizationRequestCustomizer(...)`. The `/tenant/connect-gmail` controller redirects to `/oauth2/authorization/google?reconnect=true`; the resolver inspects that query param via the `HttpServletRequest` reference it already holds and conditionally adds `prompt=consent`. **Recommended over session attributes** (cleaner, stateless, easy to test) **and over distinct registration IDs** (CONTEXT D-A5 says one `google` registration only). [VERIFIED: Context7 spring-projects/spring-security `OAuth2AuthorizationRequestResolver` page]

2. **Atomic provisioning short-circuit** — Spring Security 7's `oauth2Login()` writes the `OAuth2AuthorizedClient` BEFORE invoking the success handler. Cleanest path: success handler reads granted scopes via `OAuth2AuthorizedClient.getAccessToken().getScopes()`, and if `gmail.modify` is missing, throws `OAuth2AuthenticationException` with custom error code → routed to failure handler → which `removeAuthorizedClient(...)` and redirects to `/login?error=gmail_scope_required`. **No half-provisioned DB state ever lands** because the success handler short-circuits BEFORE the `OAuthProvisioningService.findOrCreateGoogleUser(...)` call. The same `OAuth2AuthenticationException` route also catches Google's native `error=access_denied` (full deny) and maps to `/login?error=consent_denied`. [VERIFIED: existing `GmailOAuthSuccessHandler` already follows this exact contract; CONTEXT D-A2 + Spring docs]

3. **Next.js 16.2.4 RSC `searchParams` is a Promise.** Confirmed signature: `searchParams: Promise<{ [key: string]: string | string[] | undefined }>`. The login page stays an `async` Server Component, awaits `searchParams`, switches on `error` → renders `<Alert variant="destructive">` with i18n-keyed title/body above the existing Card. **No `'use client'` conversion, no `useSearchParams()`, no `router.replace()`.** [VERIFIED: `apps/web/node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/page.md` lines 67–120]

4. **React `cache()` for per-request memoization is imported from `'react'`, NOT `next/cache`.** Wrap `getCurrentUser` with `cache(getCurrentUser)`. Per-request scope means the same call within one render pass returns one Promise; the underlying `cache: 'no-store'` fetch still produces a fresh request per render (one fetch per request, deduped within that request). [VERIFIED: `apps/web/node_modules/next/dist/docs/01-app/01-getting-started/06-fetching-data.md` line 548]

5. **shadcn `Alert` `warning` variant is a 4-line cva edit + 2-token Tailwind 4 `@theme inline` addition.** Existing pattern is already proven for `destructive` (which uses `--destructive` exposed via `@theme inline { --color-destructive: var(--destructive); }`). New tokens: `--warning` + `--warning-foreground` declared in `:root` and `.dark`, then bridged by `--color-warning: var(--warning)` and `--color-warning-foreground: var(--warning-foreground)` inside `@theme inline`. cva variant string: `"bg-card text-warning *:data-[slot=alert-description]:text-warning/90"` (mirrors destructive). [VERIFIED: `apps/web/components/ui/alert.tsx` + `apps/web/app/globals.css` direct read]

6. **Liquibase 5.0.2 idempotent cleanup changelogs** use the `delete` and `update` (or `sql`) change types — both are naturally idempotent against an already-clean DB (`DELETE WHERE no_match` is a no-op; `UPDATE WHERE no_match` updates 0 rows). Optional `preConditions` with `sqlCheck onFail: MARK_RAN` can be added but are unnecessary here because the operations are already safe-on-empty. [VERIFIED: Context7 `liquibase/liquibase-docs` preconditions + delete pages]

7. **Inbox-zero scope bundle** is `userinfo.profile + userinfo.email + gmail.modify + gmail.settings.basic` (with optional `contacts` gated by `NEXT_PUBLIC_CONTACTS_ENABLED`). Zero Mail copies the strings verbatim minus contacts; the `userinfo.*` URLs are equivalent to Spring's `openid profile email` shorthand because Google's OIDC discovery maps `openid profile email` to those same URLs server-side. **Spring's standard `openid, profile, email` short scope strings are correct** — do not paste the long `userinfo.*` URLs into `application.yml`. [VERIFIED: `D:/study-materials-summer-2026/EXE202/inbox-zero/apps/web/utils/gmail/scopes.ts` direct read]

**Primary recommendation:** Use the **query-parameter-on-authorization-URL** pattern for the dynamic `prompt=consent` toggle. Single `google` registration, single resolver bean, `/tenant/connect-gmail` controller is a 5-line redirect. Atomic provisioning happens in an extended `GoogleOAuthSuccessHandler` that calls `OAuthProvisioningService.findOrCreateGoogleUser(...)` AND `GmailConnectionService.upsert(...)` AND `userEntity.advanceTo(GMAIL_CONNECTED)` inside a single `ScopedValue.where(TenantContext.TENANT, ...).run(tx.executeWithoutResult(...))`. Scope-missing → throw `OAuth2AuthenticationException("gmail_scope_required")` BEFORE provisioning → failure handler removes the AuthorizedClient and redirects.

## A. Spring Security 7.0.5 Dynamic `prompt=consent` Resolver

### Pattern selection

**Three candidate patterns considered:**

| Pattern | Verdict | Reason |
|---------|---------|--------|
| **Query parameter on authorization URL** (`/oauth2/authorization/google?reconnect=true`) | ✅ **RECOMMENDED** | Stateless. Resolver reads `request.getParameter("reconnect")`. Easy to test (just hit the URL with the param). Survives session loss. Matches the existing controller→redirect→Spring-OAuth-filter flow. |
| **Session attribute** (set by `/tenant/connect-gmail` controller, read by resolver) | ⚠️ Workable but inferior | Requires session round-trip; adds a hidden contract; harder to test. Use only if there's a security reason to NOT expose `reconnect` in the URL — there isn't. |
| **Distinct registration ID** (`google-reconnect` aliasing `google`) | ❌ Rejected | CONTEXT D-A5 forbids it: "Do NOT add a second `google` registration variant. The runtime resolver branch is the entire reconnect machinery." Also doubles `oauth2_authorized_client` rows per user. |

### Idiomatic Spring Security 7 implementation [VERIFIED: Context7]

The current `GmailScopeRequestResolver` uses the older `OAuth2AuthorizationRequest.from(r).additionalParameters(...)` rebuild idiom. The Spring 7 idiomatic path is `DefaultOAuth2AuthorizationRequestResolver.setAuthorizationRequestCustomizer(...)` which receives an `OAuth2AuthorizationRequest.Builder` and an internal reference to the `HttpServletRequest`. **Both styles work in 7.0.5**; the rebuild form is what the current resolver uses, so keep that style for diff-minimization unless the executor wants to migrate to `setAuthorizationRequestCustomizer` for cleaner composition.

**Generalized resolver — final shape (full file replacement, ~40 lines):**

```java
// Source: Adapted from Context7 spring-projects/spring-security `OAuth2AuthorizationRequestResolver`
// docs/modules/ROOT/pages/servlet/oauth2/client/authorization-grants.adoc, plus existing
// GmailScopeRequestResolver.java rebuild-style.
package com.zeromail.api.security;

import java.util.HashMap;
import java.util.Map;
import org.springframework.security.oauth2.client.registration.ClientRegistrationRepository;
import org.springframework.security.oauth2.client.web.DefaultOAuth2AuthorizationRequestResolver;
import org.springframework.security.oauth2.client.web.OAuth2AuthorizationRequestResolver;
import org.springframework.security.oauth2.core.endpoint.OAuth2AuthorizationRequest;
import org.springframework.stereotype.Component;
import jakarta.servlet.http.HttpServletRequest;

@Component
public class GoogleAuthorizationRequestResolver implements OAuth2AuthorizationRequestResolver {

    private static final String GOOGLE_REGISTRATION_ID = "google";
    private static final String RECONNECT_PARAM = "reconnect";

    private final DefaultOAuth2AuthorizationRequestResolver delegate;

    public GoogleAuthorizationRequestResolver(ClientRegistrationRepository repo) {
        this.delegate = new DefaultOAuth2AuthorizationRequestResolver(repo, "/oauth2/authorization");
    }

    @Override public OAuth2AuthorizationRequest resolve(HttpServletRequest req) {
        return customize(delegate.resolve(req), req);
    }

    @Override public OAuth2AuthorizationRequest resolve(HttpServletRequest req, String id) {
        return customize(delegate.resolve(req, id), req);
    }

    private OAuth2AuthorizationRequest customize(OAuth2AuthorizationRequest r, HttpServletRequest req) {
        if (r == null) return null;
        Object regId = r.getAttribute("registration_id");
        if (regId == null || !GOOGLE_REGISTRATION_ID.equals(regId.toString())) return r;
        var extra = new HashMap<>(r.getAdditionalParameters());
        extra.put("access_type", "offline");
        extra.put("include_granted_scopes", "true");
        // D-A5: prompt=consent ONLY when the inbound request carries ?reconnect=true.
        if ("true".equals(req.getParameter(RECONNECT_PARAM))) {
            extra.put("prompt", "consent");
        }
        return OAuth2AuthorizationRequest.from(r).additionalParameters(Map.copyOf(extra)).build();
    }
}
```

## B. Bundled-OAuth Success Handler Atomic Provisioning

### Reference implementation

The existing `GmailOAuthSuccessHandler` already implements the EXACT atomic-tx + ScopedValue pattern needed (filter to `gmail.*` scopes, encrypt refresh token, upsert connection, advance onboarding step). ### Granted-scope verification

```java
// Source: Spring Security OAuth2AuthorizedClient API — getAccessToken().getScopes() returns Set<String>.
OAuth2AuthorizedClient client = authorizedClients.loadAuthorizedClient(
        "google", token.getName());
Set<String> grantedScopes = client.getAccessToken().getScopes();
boolean hasGmailModify = grantedScopes.contains("https://www.googleapis.com/auth/gmail.modify");
if (!hasGmailModify) {
    // Short-circuit BEFORE provisioning. Throwing OAuth2AuthenticationException
    // routes to the failure handler, which removes the AuthorizedClient
    // (Spring already wrote it on token success) and redirects to /login.
    throw new OAuth2AuthenticationException(new OAuth2Error(
            "gmail_scope_required",
            "User did not grant required gmail.modify scope",
            null));
}
```

**Important:** Spring Security 7 writes the `OAuth2AuthorizedClient` BEFORE calling `AuthenticationSuccessHandler.onAuthenticationSuccess(...)`. Therefore the success handler is the right place to read scopes — they are already persisted. If we throw `OAuth2AuthenticationException`, Spring's `OAuth2LoginAuthenticationFilter` routes to the configured `failureHandler`. The failure handler then needs to call `authorizedClients.removeAuthorizedClient("google", principalName)` to drop the orphaned client (mirroring the existing `GmailOAuthFailureHandler` Pitfall 2 logic) and redirect to `/login?error=gmail_scope_required`.

### Failure handler routing — single bean replacement [VERIFIED: existing dispatcher logic]

```java
@Component
public class LoginRedirectAuthenticationFailureHandler extends SimpleUrlAuthenticationFailureHandler {

    private static final Logger log = LoggerFactory.getLogger(...);
    private final OAuth2AuthorizedClientService authorizedClients;
    private final String loginUrl;

    @Override
    public void onAuthenticationFailure(HttpServletRequest req, HttpServletResponse res,
                                         AuthenticationException ex)
            throws IOException, ServletException {
        if (ex instanceof OAuth2AuthenticationException oae) {
            String code = oae.getError().getErrorCode();
            switch (code) {
                case "access_denied" -> {
                    log.info("event=login_consent_denied");
                    redirect(req, res, loginUrl + "?error=consent_denied");
                    return;
                }
                case "gmail_scope_required" -> {
                    // Best-effort cleanup of the half-issued AuthorizedClient.
                    try {
                        authorizedClients.removeAuthorizedClient("google",
                                currentPrincipalName(req));
                    } catch (Exception ignored) { /* best-effort */ }
                    log.info("event=login_gmail_scope_missing");
                    redirect(req, res, loginUrl + "?error=gmail_scope_required");
                    return;
                }
            }
        }
        super.onAuthenticationFailure(req, res, ex);
    }
}
```

### Extended success handler shape

```java
@Component
public class GoogleOAuthSuccessHandler extends SimpleUrlAuthenticationSuccessHandler {

    @Override
    public void onAuthenticationSuccess(HttpServletRequest req, HttpServletResponse res,
                                         Authentication auth) throws IOException, ServletException {
        OAuth2AuthenticationToken token = (OAuth2AuthenticationToken) auth;
        OidcUser oidc = (OidcUser) token.getPrincipal();
        String googleSubject = oidc.getSubject();
        String email = oidc.getEmail();

        // 0. Load the AuthorizedClient (Spring just persisted it).
        OAuth2AuthorizedClient client = authorizedClients.loadAuthorizedClient(
                "google", token.getName());

        // 1. Granted-scope check — short-circuit BEFORE any DB write.
        Set<String> scopes = client.getAccessToken().getScopes();
        if (!scopes.contains("https://www.googleapis.com/auth/gmail.modify")) {
            throw new OAuth2AuthenticationException(new OAuth2Error(
                    "gmail_scope_required",
                    "Required Gmail scope was not granted",
                    null));
        }

        // 2. Provision user + tenant (this binds ScopedValue internally per
        //    OAuthProvisioningService.createTenantAndUser ordering — Pitfall 6).
        UserEntity user = provisioning.findOrCreateGoogleUser(googleSubject, email);

        // 3. Inside a fresh ScopedValue+tx, upsert the GmailConnectionEntity and
        //    advance onboarding step. Mirrors GmailOAuthSuccessHandler steps 3-4.
        UUID tenantId = user.getTenantId();
        UUID userId = user.getId();
        String refreshToken = client.getRefreshToken().getTokenValue();
        String gmailScopes = scopes.stream()
                .filter(s -> s.startsWith("https://www.googleapis.com/auth/gmail."))
                .sorted()
                .collect(Collectors.joining(" "));

        ScopedValue.where(TenantContext.TENANT, tenantId.toString()).run(() ->
            tx.executeWithoutResult(_ -> {
                byte[] envelope = cipher.encrypt(
                        refreshToken.getBytes(StandardCharsets.UTF_8),
                        tenantId.toString());
                connections.upsert(tenantId, email, gmailScopes, envelope);
                UserEntity refreshed = users.findById(userId).orElseThrow();
                refreshed.advanceTo(OnboardingStep.GMAIL_CONNECTED);
                users.save(refreshed);
            }));

        // 4. Privacy-clean event log — opaque event name + tenant UUID only.
        log.info("event=oauth_provisioning_complete tenantId={}", tenantId);

        super.onAuthenticationSuccess(req, res, auth);
    }
}
```

### Privacy contract — preserved

- `event=login_consent_denied` and `event=login_gmail_scope_missing` are opaque event names.
- No `tenantId` is logged on the failure path (no tenant exists yet pre-provisioning).
- Success path logs `event=oauth_provisioning_complete tenantId={uuid}` — UUID only.
- **Never** log email, subject, or token bytes (Phase 1 D-E1).

## D. React `cache()` in Next.js 16 App Router

### Import path [VERIFIED: in-tree docs]

```ts
// Source: apps/web/node_modules/next/dist/docs/01-app/01-getting-started/06-fetching-data.md:548
import { cache } from 'react';
```

**NOT** `from 'next/cache'` (that's `revalidatePath` / `revalidateTag` / `unstable_cache`, a different API surface).

### Per-request memoization semantics

From the official Next.js docs (also visible in `apps/web/node_modules/next/dist/docs/01-app/01-getting-started/06-fetching-data.md`):

> You can share fetched data across both Server and Client Components by combining `React.cache` with context providers.

**Scope guarantees:**

- `cache(fn)` returns a memoized version. Within a **single render pass / request**, repeated calls with the same arguments return the same Promise (deduplicated).
- Across requests, each new render starts fresh.
- The memoization key is `JSON.stringify` of the arguments — wrap argument objects carefully (or wrap with no-arg adapters).

### Interaction with `cache: 'no-store'`

These two layers do not conflict:

- React `cache()` deduplicates calls to `getCurrentUser` **within one request**.
- The underlying `fetch(getApiUrl('/me'), { cache: 'no-store' })` opts out of Next.js's HTTP fetch cache **across requests**.
- Net effect: **one fresh fetch per request, but only one fetch even if N RSC components in that request all call `getCurrentUser()`**.

This is exactly what CONTEXT D-D2 wants.

### Concrete migration

The current `getCurrentUser` (lines 29–43 of `apps/web/features/account/api/me.ts`) takes an `opts` object. React `cache()` keys on argument identity, so:

**Recommended approach (cleanest):**

```ts
// Source: apps/web/node_modules/next/dist/docs/01-app/01-getting-started/06-fetching-data.md:548
import { cache } from 'react';

import { api } from '@/lib/api/client';
import { getApiUrl } from '@/lib/api/base-url';

export interface CurrentUser { /* unchanged */ }

// Internal raw fetcher (unchanged shape).
async function fetchCurrentUser(opts: GetCurrentUserOptions = {}): Promise<CurrentUser> {
  /* existing body */
}

// React-cached wrapper. cache() keys on argument identity, so callers from
// the SAME render pass that pass the SAME `cookieHeader` string converge.
export const getCurrentUser = cache(fetchCurrentUser);
```

**Caveat:** `cache()` argument-key identity is structural for JSON-serializable args. The `fetcher` and `signal` fields of `GetCurrentUserOptions` are NOT serializable (function reference / AbortSignal). For the layout.tsx call site, only `headers: { cookie }` is passed (a plain object), and the `cookie` string is identical across the render pass — so dedupe will work as intended.

If the caller passes an unstable object reference, React's `cache()` behavior is per-reference. For our use case (one cookieHeader string per request, used by `reassertServerLocale` and any future RSC consumer), this works.

### Confidence

**HIGH** — direct in-tree docs verification + standard React 19 API.

## F. Liquibase 5.0.2 Cleanup Changelogs

### Idempotency in YAML [VERIFIED: Context7]

Liquibase's standard `delete` and `update` change types are naturally idempotent against an already-clean DB:
- `DELETE FROM oauth2_authorized_client WHERE client_registration_id='google-gmail'` → 0 rows affected on a clean DB. No error.
- `UPDATE users SET onboarding_step='GMAIL_CONNECTED' WHERE onboarding_step='SIGNED_IN'` → 0 rows affected when the column already lacks `'SIGNED_IN'`. No error.

Since each changeset is gated by Liquibase's `DATABASECHANGELOG` table (Liquibase tracks executed IDs), they only run once anyway. The idempotency property is a backstop for `liquibase clearCheckSums` or manual re-runs — not a per-startup concern.
