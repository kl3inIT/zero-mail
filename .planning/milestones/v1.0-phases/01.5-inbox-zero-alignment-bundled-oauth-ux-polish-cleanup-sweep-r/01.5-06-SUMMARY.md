# Phase 01.5 Plan 06: Race-Loser Atomicity Fix (CR-01) Summary

**Removes second `bundledTx.executeWithoutResult` from race-loser catch block in OAuthProvisioningService — race-loser now reads winner state and returns directly with zero DB writes, restoring the single-transaction guarantee (CR-01)**

## Performance

## Accomplishments

- Eliminated the half-provisioned state risk: the old race-loser catch block opened a second `bundledTx.executeWithoutResult` that, if it failed (cipher error, DB drop), would leave user+tenant rows without a `gmail_connections` envelope — exactly what HIGH-1 was supposed to prevent
- Race-loser path is now a pure read: `users.findByGoogleSubject` + `return new BundledProvisioningResult(winner tenant, winner id, false)` — no write, no second transaction, no way to corrupt state
- Added Javadoc accurately describing the race-loser path and single-tx contract; removed broken `{@link OAuth2AuthenticationException}` link (WR-02 opportunistic fix)
- Added WR-01 dead-code comment on `provisioningTx` + `findOrCreateGoogleUser` for Phase 02 cleanup
- Created `OAuthProvisioningRaceAtomicityTest` with 2 test methods (both passing) on real Postgres 17.6 via Testcontainers

## Decisions Made

- **Drop second bundledTx entirely** rather than guard with `connections.findByTenantId(winnerTenant)` check: the winner's thread already wrote the correct envelope; overwriting with the loser's different refresh token would be a privacy issue (two different tokens, one envelope)
- **W-1 mitigation option 1** (limitation comment in Javadoc): sequential test covers the observable post-fix contract; true concurrent race with DataIntegrityViolationException catch path verified by static grep (0 `bundledTx` calls in catch block)
