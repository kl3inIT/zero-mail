# v1.3 Code Research: Gmail Workspace Foundation

**Date:** 2026-06-07
**Status:** Research complete enough to revise requirements and roadmap
**Scope:** Gmail-only multi-mailbox foundation for one workspace/tenant. Microsoft, Zalo OA, CRM, and full team collaboration stay out of v1.3.

## Why This Research Exists

The first v1.3 requirements draft was useful as product framing, but it was a draft v0 because the codebase shape matters more than the intended feature wording. The main risk is not "can the UI add another Gmail account?" The main risk is that the current backend treats one tenant as having exactly one Gmail connection, and many downstream invariants depend on that assumption.

This research checks two things before planning implementation:

- how Zero Mail currently encodes the single-Gmail assumption;
- how Inbox Zero implements mailbox/account scoping so we can copy the product architecture idea without copying its TypeScript/Next/Prisma implementation style.

## Executive Findings

- Zero Mail is currently tenant-singleton for Gmail: `gmail_connections.tenant_id` is unique, most services call `findByTenantId(...)`, and `GmailApiClientFactory` caches access tokens by `tenantId`.
- Multi-Gmail must start with a mailbox identity migration. Adding an account picker before changing event, projection, audit, and idempotency keys would create cross-account reads/writes.
- Inbox Zero's strongest transferable idea is `EmailAccount` as the product mailbox identity. Rules, actions, executed rules, labels, messages, watch state, and OAuth token lookup all hang off `emailAccountId`; Zero Mail should keep that isolation while putting mailboxes under a shared workspace/tenant business layer.
- Inbox Zero's request model is also useful: every account-scoped API request is guarded by middleware that verifies the active `emailAccountId` belongs to the user before handlers execute. Zero Mail should implement the same concept in Spring for active-mailbox APIs: a mailbox-scoped request guard/context, not ad hoc mailbox params in controllers.
- Inbox Zero's webhook/history flow confirms that watch/history state must live per mailbox and history pointer updates must be monotonic. Zero Mail already has a monotonic tenant pointer; it needs to become mailbox-scoped.
- Business/product decision: v1.3 uses a workspace-shared, mailbox-isolated model. Credits, billing, provider/BYOK, global safety, and templates are workspace-level; inbox, rules, Gmail sync, Gmail actions, outbound execution, and audit provenance are mailbox-level. The primary UX is active mailbox switching, not mixed all-mailbox action context.
- Do not copy Inbox Zero's raw email logging posture. Zero Mail should store connected mailbox email addresses in DB/UI because the product needs them, but logs/telemetry should use tenant id, mailbox id, and optional masked/hash values instead of raw email addresses.

## Inbox Zero Implementation Notes

Local reference repo: `../inbox-zero`.

### Data Model

Relevant file: `../inbox-zero/apps/web/prisma/schema.prisma`.

Inbox Zero separates OAuth identity from product mailbox identity:

- `Account` stores provider OAuth fields and is unique by `[provider, providerAccountId]`.
- `EmailAccount` is the mailbox/product identity: `id`, `email`, `userId`, `accountId`, watch state, sync state, account settings, rules revision, and many product-specific settings.
- `EmailAccount.email` is globally unique and `EmailAccount.accountId` is unique, so one OAuth account maps to one product mailbox.
- `Rule` includes `emailAccountId`; it is unique by `[id, emailAccountId]`, `[name, emailAccountId]`, and `[emailAccountId, systemType]`, with an index on `[emailAccountId, enabled]`.
- `Action` includes `emailAccountId` and relates to `Rule` through `(ruleId, emailAccountId)`, which prevents an action from binding to another mailbox's rule.
- `ExecutedRule` includes `emailAccountId` and indexes by account/message/thread/status.
- `EmailMessage` is unique by `[emailAccountId, threadId, messageId]`.
- Labels, newsletters, groups, categories, feedback, and response-time records are also account-scoped.
- `Organization` and `Member` exist, but team collaboration is a separate layer. `Member.emailAccountId` is unique, which means team membership does not erase the per-mailbox axis.

Transferable idea for Zero Mail: keep `tenantId` as the workspace/business boundary and make every Gmail-derived state hang off a stable mailbox id. The mailbox id can be `gmail_connection_id` rather than a new `email_account_id`, but it must become part of keys and contracts. Workspace settings stay shared; mailbox state stays operationally isolated.

### UI and API Account Context

Relevant files:

- `../inbox-zero/apps/web/providers/EmailAccountProvider.tsx`
- `../inbox-zero/apps/web/components/AccountSwitcher.tsx`
- `../inbox-zero/apps/web/providers/SWRProvider.tsx`
- `../inbox-zero/apps/web/utils/middleware.ts`

Inbox Zero's frontend route segment is `/(app)/[emailAccountId]/...`. The provider resolves the active account from URL params, last-account cookie, or first account. The account switcher rewrites the first URL segment and stores the last account. SWR attaches an email-account header to API requests and resets client cache when the account changes.

The backend route middleware reads `EMAIL_ACCOUNT_HEADER`, verifies the account belongs to the authenticated user, caches account validation, and attaches `{ userId, emailAccountId, email }` to `request.auth`. Route handlers then query by `request.auth.emailAccountId`.

Transferable idea for Zero Mail: add a Spring request-level active-mailbox resolver for mailbox-scoped APIs. It should validate `(tenantId, gmailConnectionId)` before controllers call services. Controllers should not manually trust mailbox ids from path/query/header.

### OAuth Linking and Additional Accounts

Relevant files:

- `../inbox-zero/apps/web/app/api/google/linking/auth-url/route.ts`
- `../inbox-zero/apps/web/app/api/google/linking/callback/route.ts`
- `../inbox-zero/apps/web/utils/oauth/account-linking.ts`

Inbox Zero separates normal login from "link another account". The linking flow uses signed state, Google OAuth with consent, reads the Google profile, then handles cases such as existing provider account, existing email owned by another user, same-user reconnect, orphan cleanup, and new `Account + EmailAccount` creation.

Transferable idea for Zero Mail: v1.3 should separate first Gmail provisioning from "connect additional Gmail" and "reconnect this Gmail". The old `upsert(tenantId, ...)` behavior updates the tenant's single row and would turn "add Gmail" into "replace Gmail".

### Gmail Client and Token Lookup

Relevant files:

- `../inbox-zero/apps/web/utils/email-account-client.ts`
- `../inbox-zero/apps/web/utils/gmail/client.ts`

Inbox Zero token lookup accepts `emailAccountId`, fetches OAuth tokens through the related `Account`, and builds the Gmail client for that account. Refresh-token updates are also saved against `emailAccountId`.

Transferable idea for Zero Mail: `GmailApiClientFactory` must expose mailbox-scoped lookup such as `buildClientForConnectionId(tenantId, gmailConnectionId)` or `buildClientForMailbox(MailboxRef)`. Tenant-only lookup should remain only as a temporary legacy/default adapter with architectural tests preventing use in new mailbox-scoped flows.

### Watch, Webhook, and History Processing

Relevant files:

- `../inbox-zero/apps/web/utils/email/watch-manager.ts`
- `../inbox-zero/apps/web/utils/gmail/watch.ts`
- `../inbox-zero/apps/web/app/api/google/webhook/route.ts`
- `../inbox-zero/apps/web/app/api/google/webhook/process-history.ts`
- `../inbox-zero/apps/web/app/api/google/webhook/process-history-item.ts`
- `../inbox-zero/apps/web/utils/webhook/validate-webhook-account.ts`
- `../inbox-zero/apps/web/utils/gmail/history.ts`

Inbox Zero watch manager iterates eligible `EmailAccount` rows and updates watch fields on the account being processed. The webhook decodes the Pub/Sub payload, looks up the `EmailAccount` by email address, optionally skips on active provider rate-limit, acknowledges quickly, and processes history asynchronously.

The history processor:

- validates the mailbox/account is connected and eligible;
- builds a Gmail client for `emailAccountId`;
- uses `lastSyncedHistoryId` from that email account;
- caps very large history gaps to a bounded window;
- pages through Gmail history for `messageAdded`, `labelAdded`, and `labelRemoved`;
- handles expired history ids by resetting the account's cursor to the webhook history id;
- updates `lastSyncedHistoryId` with a conditional monotonic SQL update so slower processors cannot regress the pointer;
- deduplicates events and processes each message under the same `emailAccountId`.

Transferable ideas for Zero Mail:

- Pub/Sub resolution should return a `TenantMailboxRef`, not just a tenant id.
- `pubsub_delivery`, history pointer, watch renewal, backfill, and ingestion health must be per mailbox.
- History pointer updates should stay monotonic, but keyed by mailbox id.
- Large history gaps and expired cursors should be handled per mailbox, so one stale account does not poison the workspace.

Do not copy directly:

- Inbox Zero's webhook route logs raw email in several places; Zero Mail should not.
- Inbox Zero uses Next `after()` and direct Prisma from the API process. Zero Mail has a separate worker and Postgres-backed queue/outbox path; keep that architecture.

### Rule Matching and Execution

Relevant files:

- `../inbox-zero/apps/web/app/api/user/rules/route.ts`
- `../inbox-zero/apps/web/app/api/user/rules/[id]/route.ts`
- `../inbox-zero/apps/web/utils/ai/choose-rule/match-rules.ts`
- `../inbox-zero/apps/web/utils/ai/choose-rule/run-rules.ts`
- `../inbox-zero/apps/web/utils/ai/choose-rule/execute.ts`
- `../inbox-zero/apps/web/utils/webhook/process-history-item.ts`

Inbox Zero rule APIs always query by `emailAccountId`. Runtime rule execution receives the active `emailAccount`, `provider`, and `rules`. It stores `ExecutedRule` with `emailAccountId`, `threadId`, `messageId`, status, reason, action items, and rule id. Existing execution checks also query by `emailAccountId + threadId + messageId`.

Rule matching mixes deterministic static checks, learned patterns, thread-continuity logic, and AI selection. That matching sophistication is not the v1.3 target. The transferable part is simpler: rules and their executions must be account-scoped so same Gmail ids in two accounts cannot collide.

## Zero Mail Current One-Gmail Assumptions

### Gmail Connection and Client Lookup

Relevant files:

- `backend/core/src/main/resources/db/changelog/changes/003-create-gmail-connections.yaml`
- `backend/core/src/main/java/com/zeromail/core/gmail/persistence/GmailConnectionRepository.java`
- `backend/core/src/main/java/com/zeromail/core/gmail/gateway/GmailApiClientFactory.java`
- `backend/core/src/main/java/com/zeromail/core/gmail/usecases/GmailConnectionService.java`
- `backend/core/src/main/java/com/zeromail/core/account/usecases/OAuthProvisioningService.java`

Current state:

- `gmail_connections` has a unique constraint on `tenant_id`.
- `GmailConnectionRepository.findByTenantId(UUID tenantId)` is the dominant lookup.
- `GmailApiClientFactory.buildClientForTenant(...)` loads the single connection and caches access tokens by `tenantId`.
- `GmailConnectionService` methods are tenant-singleton: current status, disconnect, reconnect clear, watch success/failure, history lost, and mark disconnected all target `tenantId`.
- OAuth success calls `upsert(tenantId, googleEmail, ...)`, so a second Gmail grant would update the existing tenant row rather than create a new mailbox.

Required direction:

- treat each `gmail_connections.id` as the mailbox id;
- remove the active single-row-per-tenant invariant;
- add mailbox-scoped service methods and keep tenant-only methods only as default/legacy adapters during migration;
- key token cache by mailbox id, not tenant id.

### Pub/Sub and History Processing

Relevant files:

- `backend/core/src/main/resources/db/changelog/changes/011-pubsub-delivery-table.yaml`
- `backend/core/src/main/resources/db/changelog/changes/012-mail-message-observed-table.yaml`
- `backend/core/src/main/java/com/zeromail/core/gmail/persistence/lowlevel/PubSubTenantLookupRepository.java`
- `backend/core/src/main/java/com/zeromail/core/gmail/usecases/PubSubIngestionService.java`
- `backend/core/src/main/java/com/zeromail/core/gmail/usecases/GmailDeliveryProcessingService.java`
- `backend/core/src/main/java/com/zeromail/core/gmail/event/MailMessageObserved.java`

Current state:

- Pub/Sub lookup by email returns only `tenant_id`.
- `pubsub_delivery` dedup is `(tenant_id, pubsub_message_id)`.
- `GmailDeliveryProcessingService` loads the Gmail connection by tenant, uses one tenant history pointer, and publishes tenant-only events.
- `mail_message_observed` primary key is `(tenant_id, gmail_message_id)`.
- `MailMessageObserved` carries only tenant id, Gmail message id, thread id, and observed timestamp.

Required direction:

- Pub/Sub lookup must return `(tenantId, gmailConnectionId, googleEmailHash/display metadata if needed)`.
- `pubsub_delivery` should store `gmail_connection_id` and dedup by mailbox where appropriate.
- `mail_message_observed` must include `gmail_connection_id` in primary/idempotency keys.
- `MailMessageObserved` and `MailOutboundObserved` must carry mailbox id.
- Any log emitted by this path should avoid raw email address. Use event name, tenant id, mailbox id, message id only where already allowed by privacy review, and technical status/reason.

### Inbox Projection and Sync State

Relevant files:

- `backend/core/src/main/resources/db/changelog/changes/108-gmail-inbox-projection.yaml`
- `backend/core/src/main/java/com/zeromail/core/inbox/usecases/InboxProjectionWriteService.java`

Current state:

- `gmail_inbox_projection` primary key is `(tenant_id, gmail_message_id)`.
- `gmail_inbox_sync_state` primary key is `tenant_id`.
- `InboxProjectionWriteService` encrypts sender/subject/snippet fields with AAD based on `tenantId + gmailMessageId + field`.

Required direction:

- Projection rows need mailbox id in the primary key and list/thread indexes.
- Sync state must be per mailbox.
- Cursor formats and list APIs need enough mailbox context to disambiguate same Gmail message/thread ids across connected mailboxes.
- Changing encryption AAD to include mailbox id is not a plain Liquibase migration because existing ciphertext was encrypted with the old AAD. Either keep AAD compatible for existing projection fields or add a deliberate app-level re-encryption/versioning plan. This must be decided before implementation.

### Rules, Triage, Outbound, and Audit

Relevant files:

- `backend/core/src/main/resources/db/changelog/changes/021-rules-engine-schema.yaml`
- `backend/core/src/main/resources/db/changelog/changes/025-triage-audit.yaml`
- `backend/core/src/main/java/com/zeromail/core/rules/usecases/RuleManagementService.java`
- `backend/core/src/main/java/com/zeromail/core/rules/persistence/RuleEntity.java`
- `backend/core/src/main/java/com/zeromail/core/triage/usecases/TriageOrchestratorService.java`
- `backend/core/src/main/java/com/zeromail/core/triage/usecases/TriageGmailWriter.java`
- `backend/core/src/main/java/com/zeromail/core/outbound/usecases/GmailOutboundSendGateway.java`

Current state:

- `rules` are tenant-scoped only; runtime loads enabled rules for the entire tenant.
- `TriageDispatchContext` does not carry mailbox id.
- Gmail writes call `TriageGmailWriter` methods with `tenantId` and Gmail ids.
- Outbound sends use `OutboundSendCommand(tenantId, Message)` and `GmailOutboundSendGateway` builds a tenant Gmail client.
- `triage_audit` idempotency is `(tenant_id, gmail_message_id, rule_id, action_type, args_hash)`.

Required direction:

- Rules should be mailbox-owned by default in v1.3: a `gmail_connection_id` ownership column on rules is simpler and safer than an all/selected mailbox scope model.
- Applying the same behavior to another mailbox should be an explicit copy/template action that materializes another mailbox-owned rule, not an implicit all-mailbox runtime rule.
- Runtime triage should evaluate only rules owned by the source mailbox.
- Gmail write operations need an executing mailbox id. For inbound actions, source mailbox and executing mailbox are usually the same; future workflow may allow explicit cross-mailbox send, but v1.3 should fail closed unless explicitly designed.
- Outbound gateway should receive mailbox context and build the client from mailbox id.
- Audit rows need source mailbox id and executing mailbox id, and the idempotency index must include mailbox context.

### UI/API

Relevant files:

- `backend/api/src/main/java/com/zeromail/api/controllers/gmail/GmailInboxController.java`
- `apps/web/features/inbox/api/inbox-api.ts`

Current state:

- Inbox API paths are tenant-only: `/api/gmail/inbox`, `/api/gmail/inbox/{gmailMessageId}`, `/threads/{gmailThreadId}`, `/drafts/{gmailDraftId}`, and read action.
- Frontend inbox API hand-writes DTOs and still carries a TODO to switch to generated OpenAPI types.

Required direction:

- Mailbox-scoped APIs should accept a validated mailbox context. Good options: path segment `/api/gmail/mailboxes/{gmailConnectionId}/inbox`, or a query/header only if a resolver validates it consistently. Path segment is clearer for browser/debugging and generated OpenAPI.
- Active-mailbox views should be the primary UX for inbox, needs-reply, rules, audit, and analytics.
- Any future "all mailboxes" list view should be treated as read-only roll-up with explicit aggregation semantics and cursors that include mailbox id; it must not become an implicit Gmail action context.
- API DTOs should include mailbox metadata/badges where the UI must explain provenance.
- After backend DTO changes, regenerate OpenAPI and switch feature APIs to generated types per project convention.

## Logging and Restricted Scope Note

The user's question was whether logging email addresses is really a restricted-scope issue. The precise answer:

- A raw mailbox email address is not the same as storing Gmail message body or full headers, and it may come from basic profile/OIDC data rather than a Gmail restricted scope.
- However, once the product uses Gmail restricted scopes, Google treats data obtained from Google APIs and data derived from that access under its User Data Policy. The policy requires transparent disclosure, minimum necessary permissions, secure handling, and limited use of data. Google also lists Gmail scopes such as `gmail.modify`, `gmail.readonly`, `gmail.metadata`, and `gmail.compose` as restricted scopes.
- Logs are durable operational storage and often get copied to Loki/Sentry/alerting tools. So Zero Mail's product posture should be stricter than the minimum scope classification: connected mailbox email may be stored in the account/mailbox table and displayed to the authenticated user, but raw email addresses should not be emitted in application logs.

Implementation posture:

- Allowed: `tenantId`, `gmailConnectionId`/mailbox id, operation name, status code, Google error reason, watch expiry, history pointer, counters.
- Allowed when needed: masked email (`a***@domain.com`) or keyed hash for dedupe/debugging.
- Disallowed in logs: raw connected mailbox email, sender/recipient email, subject, snippet, body, raw headers, OAuth token bytes, LLM prompt/completion.
- DB/UI distinction: storing `google_email` in `gmail_connections` is necessary product state; logging it is not.

Sources checked:

- Google Restricted Scope Verification: https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification
- Google Restricted Scopes list: https://support.google.com/cloud/answer/13464325
- Google API Services User Data Policy: https://developers.google.com/terms/api-services-user-data-policy

## Recommended v1.3 Build Order

### Phase 10: Gmail Mailbox Foundation and Account Management

- Introduce mailbox terminology in code: workspace/tenant owns many Gmail mailboxes.
- Migrate existing single Gmail tenants to one primary mailbox using existing `gmail_connections.id` as the stable mailbox id.
- Remove or relax `uq_gmail_connections_tenant_id`; add constraints for active duplicate prevention.
- Add primary/default marker, display purpose/label, and normalized/hash email fields if needed.
- Add workspace-shared vs mailbox-isolated ownership boundary for settings and operational state.
- Add active-mailbox scoped request context/guard for API use.
- Add mailbox-aware Gmail client lookup and token cache while preserving legacy default lookup only as a compatibility adapter.
- Decide encryption AAD migration strategy before touching projection ciphertext.
- Implement connect additional Gmail, reconnect one mailbox, disconnect one mailbox, list connected mailboxes, and set primary/default.
- Split OAuth first-login provisioning from add/reconnect flows.
- Make watch renewal and invalid-grant handling update the specific mailbox row.
- Ensure `users.stop`, token revoke, and local disconnect target only the selected mailbox.

### Phase 11: Mailbox-Scoped Ingestion, Automation, UI, and Verification

- Change Pub/Sub lookup to return tenant + mailbox.
- Store mailbox id on deliveries and observed events.
- Make history cursor, watch history id, inbox sync state, processing jobs, and backfill idempotency mailbox-scoped.
- Change inbox projection keys, list queries, detail/thread lookup, cursors, and mark-read writes to include mailbox id.
- Preserve the no-long-term raw body/prompt/completion/embedding posture.
- Add mailbox-owned rules.
- Update compiler/manual editor contracts to persist owning mailbox id as schema, not as interpreted natural language.
- Filter enabled rule candidates by active/source mailbox.
- Pass source/executing mailbox through triage dispatch, Gmail writer, outbound send gateway, forward/reply assemblers, undo/revert, and audit saga.
- Update audit idempotency and cross-account isolation tests.
- Add connected Gmail accounts/settings UI with display purpose/labels.
- Add persistent active-mailbox switcher and active-mailbox inbox/needs-reply/rules/audit/analytics views.
- Add mailbox-owned rules UI while preserving the existing `When / Then` mental model.
- Regenerate OpenAPI and switch affected frontend feature API code to generated types.
- Verify connect/list/switch/mailbox-owned-rules/send-from/audit flows with Playwright.

## Requirement Adjustments From Research

The current requirements draft is broadly correct, but should be tightened in these areas:

- Add an active-mailbox-scoped request guard/context requirement.
- Clarify workspace-shared vs mailbox-isolated settings/state boundaries.
- Add explicit Gmail client factory/cache mailbox-scoping.
- Add explicit Pub/Sub lookup result shape: tenant + mailbox, not tenant only.
- Add mailbox id to event contracts, processing jobs, backfill, inbox projection, audit idempotency, and outbound command contracts.
- Clarify that storing connected mailbox email in DB/UI is allowed, but raw email address logging is not.
- Clarify that default mailbox fallback is allowed only for legacy/user-facing default surfaces, not for internal write paths where mailbox context is required.
- Clarify that encryption AAD changes require a compatibility or re-encryption plan.

## Verification Focus

Backend tests should prioritize invariants rather than DTO shape:

- Liquibase migration preserves old single-Gmail tenants and creates one primary mailbox.
- Two mailboxes in one tenant can coexist; duplicate Gmail address rules fail closed.
- Gmail client token cache is keyed by mailbox id; one mailbox cannot receive another mailbox's access token.
- Pub/Sub delivery for mailbox A cannot process mailbox B's history or update mailbox B's cursor.
- Same Gmail message id in two mailboxes creates two observed/projection/audit rows.
- Inbox list/detail/thread/read operations require valid mailbox ownership.
- Mailbox-owned rules execute only for their owning/source mailbox.
- Outbound send/reply/forward uses the executing mailbox and audit records both source and executing mailbox.
- ArchUnit forbids tenant-only Gmail client lookup in mailbox-scoped flows.
- Logging tests or review checks ensure raw emails/subjects/bodies/tokens are not emitted.

Frontend/browser verification should cover:

- add account, reconnect, disconnect, set primary;
- active mailbox switcher in inbox, needs-reply, rules, audit, and analytics;
- optional read-only roll-up, if implemented, with clear mailbox badges and no direct Gmail action context;
- rule create/edit under the active mailbox with mailbox-owned persistence;
- send/reply/forward previews showing source and executing mailbox;
- audit rows showing mailbox provenance without exposing raw content.
